# アーキテクチャ — alteroid

この文書は [north_star.md](./north_star.md)（正典）と [PRD.md](./PRD.md)（要件）から導出した設計である。矛盾したら上位文書が勝つ。ここには「どう作るか」だけを書き、要件は書かない。

## 全体像

```
┌─ alteroidd（常駐デーモン）─────────────────────────────┐   ┌───────────────┐
│                                                          │   │ alteroid (CLI) │
│  クローン（Fable / SDK query・組み込みツール0）           │   │ = daemon の    │
│   ├ 道具: manager_start / manager_send / manager_list    │   │ 薄い HTTP      │
│   │       memory_* / journal_* / ask_human               │   │ クライアント    │
│   │       （すべてインプロセス MCP の自作ツール）          │   └───────────────┘
│   ├ 受信箱（イベント駆動ループ）                          │
│   └ 記憶ストア ← **このプロセスだけが接続情報を持つ**       │
│                                                          │
│  スケジューラ / 外部イベント入口 / 承認待ちキュー           │
│  HTTP API（hono）─ chat(SSE)・jobs・承認                  │
│                    日報・日誌・セッションログ（可観測性3層）  │
│  RunnerRegistry ─ 委譲の宛先を決める間接層                 │
└──────┬───────────────────────────────────────────┘
       │ 命令: start / send / answer / stop / resume（HTTP）
       │ 出来事: デーモンが開いたストリームを流れ落ちる（SSE）
       │ **繋ぎに行くのは常にデーモン側。逆向きの経路は無い**
┌──────▼────────────────────────────────────────────┐
│ manager-runner（別プロセス・既定では別コンテナ）             │
│  ・SDK セッションを N 本並行で持つ（人工上限なし）           │
│  ・workspace / MCP 設定 / OAuth トークンを持つ              │
│  ・**記憶ストアへ到達する鍵を持たない**                     │
│  ├ マネージャー（Opus / tools 省略 = preset 全部）× N       │
│  │  └ 作業者（Sonnet / agents 定義, tools 省略 = 全継承）× N │
│  └ 生ログは預けるだけ（永続化はデーモン）                    │
└───────────────────────────────────────────────────┘
```

## プロセスモデル

| 構成要素 | 実体 | モデル | ツール |
|---|---|---|---|
| クローン | デーモン内の長寿命 SDK セッション1本 | `fable` | 組み込み 0（`tools: []`）＋インプロセス MCP の自作ツールのみ |
| マネージャー | **manager-runner の中で** SDK が spawn する子プロセス | `opus` | **`tools` を渡さない**（preset 全部。明示リスト禁止 — AGENTS.md の地雷1） |
| 作業者 | マネージャー配下の `agents` 定義 | `sonnet` | **`tools` フィールドを省略**（親の全ツールを継承） |

- クローンに組み込みツールを与えないのは人間側の写像であり、デグレードではない（north_star「適用範囲」）。この理由付けをマネージャー以下に流用しない
- モデル対応（Fable / Opus / Sonnet）は固定。変更には人間の承認が要る（PRD）
- **マネージャーと作業者は実装物ではない。** どちらも実体は Claude Code そのものであり、alteroid が書くのは配線（起こす・話しかける・クローンへ回す・日誌に落とす）だけである
  - **作業者層の本体は `agents` 定義1個**（`model: 'sonnet'`、`tools` 省略）とマネージャーのシステムプロンプトに書く委譲の指針のみ。作業者用の独自機構（ワーカープール・キュー・独自プロトコル）を作らない。エスカレーションはサブエージェントの結果が親に返る SDK の挙動そのもの
  - この定義を省いて SDK の既定に頼ってはいけない。組み込みサブエージェントは**親のモデルを継承**するため、作業者が Opus で走ってコストが倍になり、固定のモデル対応が SDK の既定値変更で勝手に壊れる床に乗る（2026-08 調査: サブエージェントの既定モデルをセッション全体で指定するオプションは存在せず、`agents` の個別指定が唯一の方法）

## プロセス境界 — なぜ manager-runner を分けるか

**同じ器で走らせている限り、マネージャーは記憶ストアの鍵に届く。** デーモンの環境変数は
`/proc/1/environ` から読めるし、同一 UID なら人格データのファイルも読める。「非対称な
可視性」を掲げながら同居させるのは、鍵を机の上に置いて「見ないでください」と書くのと同じ
である。ツールを削って塞ぐのは禁止されている（north_star 禁止2）ので、**実行環境を分ける**。

| プロセス | 持つもの | 持たないもの |
|---|---|---|
| デーモン（alteroidd） | クローン、記憶ストアの接続情報、日誌・ジョブ・生ログの永続化、承認待ちキュー | 実プロジェクトの workspace、マネージャーの SDK セッション |
| manager-runner | SDK セッション（マネージャー＋作業者）、workspace、MCP 設定、モデル呼び出しの認証 | **記憶ストアの接続情報、人格データ、デーモンへの経路** |
| PostgreSQL | 記憶・日誌・ジョブ・セッションの生ログ | — |

- **runner は判断をしない。** できるのは SDK セッションの start / send / stop / resume と、
  その出来事の返送だけである。許可してよい行為の一覧も、確認の要否の設定も持たない
  （権限境界はクローンが記憶を根拠に決めるもの — PRD「権限境界」）
- **runner は独自のエージェント基盤を持たない。** ワーカープールもキューも作らない。
  作業者は SDK の `agents` 定義1個のままである
- **runner に DB を持たせない。** 生ログ（SessionStore）も日誌も、runner は「預ける」だけで、
  永続化するのはデーモンである。runner に DB 認証情報を置いた瞬間、その中の子プロセスが
  同じ鍵に届く

### runner API — 命令は下り、出来事は上る

| 向き | 経路 |
|---|---|
| デーモン → runner | `POST /managers`（start） / `POST /managers/:id/resume` / `POST /managers/:id/messages` / `POST /managers/:id/answers` / `DELETE /managers/:id` / `GET /managers` / `GET /managers/:id/transcript` / `GET /health`（runner_id を名乗る） |
| runner → デーモン | `GET /events`（SSE）。`session` / `project_key` / `report` / `ask` / `settled` / `tool_use` / `mirror`（生ログ） / `archive` / `closed` |

**接続を張るのは常にデーモン側である。** runner はデーモンの所在も鍵も知らない。逆向きの
コールバック URL を足すと、runner の中の子プロセス（＝マネージャー）がその経路でデーモンの
API へ、つまり記憶へ届くようになる。**この向きを反転させないこと。**

- デーモンが繋いでいない間の出来事は runner 側に溜まる。捨てると、誰も答えられない確認が
  runner に残り、マネージャーが永久に待つ
- デーモンの停止は runner のセッションを止めない。**デーモンの都合で人の仕事を殺さない** —
  再起動後は生きているセッションへ繋ぎ直し、runner ごと落ちていた分だけ resume する

### ローカルでは同一プロセスに落ちる（既知の穴つき）

`alteroid chat` を叩くだけで使える、というローカルの体験に「先に runner を立てる」手順を
足さない。runner の URL が無ければ、デーモンは同じプロセスの runner を使う。**このとき
既知の穴（マネージャーが同じ UID で走る）は残る。** 穴の名前を変えただけの状態なので、
ツール削除で塞がないこと。塞ぐのはコンテナ構成の役目である。

デーモンから見た顔はどちらも同じ（`RunnerClient`）。**デーモンは特定の runner 実装も、
固定 URL も、runner のローカルパスも前提にしない。**

## 同時実行の宛先 — RunnerRegistry

委譲の宛先は `RunnerRegistry`（`list` / `get` / `select`）を通して決める。M4 で登録されるのは
1台（`runner-primary`）で、`select` は常にそれを返す。間接層を最初から置くのは、宛先の決定が
呼び出し側に散らばると M5（複数 runner）で全部書き直しになるからである。

- `select` に**人工的な上限を入れない**。「同時に何本まで」は能力の削除であって配置の判断では
  ない（禁止2）。将来ここで見てよいのは、runner が報告する CPU・メモリ・稼働セッション数と
  いった**実行環境の資源**である
- 走行中のマネージャーの宛先は JobStore に残る（下の対応関係）。`manager_send` は
  `manager_id` から runner を引いて届ける（sticky routing）

## クローンの寿命モデル — 同一性はセッションではなく記憶に宿る

「長寿命セッション」は「不死身のログ」という意味ではない。クローンには寿命の違う3つの層がある。

| 層 | 実体 | 寿命 |
|---|---|---|
| 文脈（コンテキストウィンドウ） | セッションが「頭に載せている」もの | 有限。SDK の自動 compaction で周期的に要約へ潰され、細部は消える |
| トランスクリプト（JSONL） | resume 用の会話の生ログ | ただの再開素材。アーカイブして捨ててよい |
| 記憶（PersonaStore）＋日誌（JournalStore） | 蒸留された価値観・学び／追記専用の記録 | **ここだけが一生モノ** |

- **クローンの同一性は記憶に宿る。** セッションは compaction されても、デーモン再起動で失われても、記憶＋日誌から再構成すれば同じクローンである。セッションの不死身化に工数をかけないこと
- **蒸留は生存条件である。** 大事なことはセッションが忘れる前に記憶へ移す。蒸留を怠ると compaction のたびに人格の一部が消える構造なので、「あると嬉しい機能」として後回しにしない（会話終了時に加え、compaction 前にも蒸留の機会を置く）
- **監査は日誌＋アーカイブで担保する。** PreCompact フックで要約に潰す直前の全文をアーカイブへ落とす。人間が後から追う用途にセッション本体を太らせ続けない

## 同時実行モデル — クローンは複数のマネージャーを使う

人間が Claude Code を複数枚開くのと同じことが、クローンにもできる。

- **委譲はノンブロッキング** — `manager_start(依頼, 作業Dir)` は起動して即 `manager_id` を返す。クローンは完了を待たずに次の判断へ移る
- **受信箱でイベント駆動** — 人間の発言・各マネージャーからの報告や質問・タイマー・外部イベントは、すべてクローンの受信箱に積まれる。クローンは一件ずつ取り出して判断する。これが自律要件（起点4つ）の実装形態でもある
- **会話に戻れる** — `manager_send(manager_id, メッセージ)` で走行中のマネージャーに追加指示や質問への回答を送る。`manager_list()` で一覧と状態を見る
- **数に人工上限を設けない** — 上限はマシンリソースそのもの（＝実行環境の境界）。同時数の設定値やキュー長で絞らない（追加制限禁止）
- **同一リポジトリの衝突も機構で禁じない** — 人間も同じ事故を起こせて、避けているのは判断である。クローンの判断（と記憶）に委ね、git worktree 等の隔離はマネージャーの技量とする

## 配線 — マネージャーから見た「ユーザー」はクローン

マネージャーのセッションで発生する `AskUserQuestion`・許可確認・最終報告を、デーモンがクローンの受信箱へルーティングする。人間 → Claude Code の対話の仕組みが、SDK の機能そのままでクローン → マネージャーに写る。

- クローンは記憶に根拠があれば自分で答え、無ければ `ask_human` で承認待ちキューに積む（PRD「権限境界」の実装点はこの1箇所）
- 承認待ちで止まるのは**その仕事だけ**。他のマネージャーは走り続ける（PRD「自律」）
- 作業者 → マネージャーのエスカレーションは SDK のサブエージェント機構そのもの（結果が親に返る）を使い、独自機構を足さない

エスカレーション・報告・日誌エントリは zod スキーマの型付きメッセージとして `core` に定義する（提供価値2）。

## 非対称な可視性

**下向き（クローン → マネージャー以下）: 同じものが見える**

- マネージャーには人間が使っているのと同じ MCP 設定を渡す（`settingSources` で `.mcp.json` を共有。SDK 公式機能）
- cwd は実プロジェクトの作業ディレクトリ。人間が Claude Code を開く場所と同じ
- クローンはそれをマネージャー越しに見る。人間が PC の画面越しに見るのと同じ写像

**上向き（マネージャー以下 → クローン）: 見えない・書けない**

- 記憶ストアの接続情報（ローカルならパス、クラウドなら DB 認証情報）は**デーモンプロセスだけが持つ**
- マネージャーは manager-runner の中で走る。runner には鍵を配らないので、構造的に触れない
- ツールを絞って実現するのではなく、認証情報の配布範囲と経路（＝実行環境の境界）で守る

クラウド構成では次の3つが同時に成り立って、初めて「到達経路が存在しない」と言える。**env から
消すだけでは足りない**（同じ器なら `/proc/1/environ` で読める）。

1. 別プロセス・別コンテナ（デーモンの環境も人格データも runner から見えない）
2. runner の環境変数にも設定ファイルにも DB 認証情報が無い
3. **runner から DB への経路が無い**（compose ではネットワークを分ける。runner は `db` を名前解決すらできない）

**既知の穴（ローカル）**: 同一プロセスの runner に落とすローカル構成では、マネージャーが Bash で
`~/.alteroid/` を読むことは技術的に可能。SDK のサンドボックス設定は現状ドキュメント未記載
（2026-08 調査）。ローカルはプロセス境界＋監査（PostToolUse フックで全ツール実行を日誌に記録）で
受け、完全な強制はコンテナ構成で成立する。**この穴をツール削除で塞がないこと。**

## 脳は1インスタンス

クローンの生きたインスタンスは常にデーモン内の1本だけ。CLI は core を埋め込まず、デーモンへの薄い HTTP クライアントに徹する（core を CLI にも埋めると chat のたびに脳が分岐する）。CLI と HTTP API はどちらも「脳への接続手段」であり、常駐が自律の前提（PRD）という要件とも一致する。

## ストレージ

core にストアのインターフェースを切り、ドライバを差し替える。

| インターフェース | 中身 | fs ドライバ（ローカル） | pg ドライバ（クラウド） |
|---|---|---|---|
| PersonaStore | 記憶（価値観・学び） | Markdown ファイル群 | PostgreSQL（同じ Markdown 文書をテーブルに） |
| JournalStore | 日誌（追記専用・型付きエントリ: やり取り、判断、エスカレーション、ツール実行、日報） | JSONL | PostgreSQL |
| TranscriptArchive | セッション生ログ（PreCompact 退避分を含む） | JSONL ファイル | PostgreSQL または S3 互換 |
| JobStore | ジョブ・承認待ち・下の対応関係 | JSON | PostgreSQL |

### JobStore が持つ対応関係 — 委譲を復元するための鎖

```
manager_id → runner_id → sdk session_id → workspace locator
```

- **`manager_id → runner_id`**: どの runner で走っているか。`manager_send` の宛先であり、
  デーモンが再起動しても affinity をここから復元する
- **`→ session_id`**: 中断されたセッションの続きへ戻る足がかり（`resume`）
- **`→ projectKey`**: SDK が生ログを預けるときの scope。生ログを後から引き当てる鍵
- **`→ workspace locator`**: どこで作業していたか。**文字列のパスだけにしない**（runner が
  増えれば移送の話になる）

```ts
type WorkspaceLocator =
  | { kind: 'runner-volume'; runnerId: string; path: string }  // M4 の既定
  | { kind: 'shared-volume'; path: string }                    // 共有 FS（M5）
  | { kind: 'git'; repository: string; ref: string; patchId?: string }; // 再構築（M5）
```

M4 で実際に使うのは `runner-volume` だけである。**runner のローカルパス（走行中の
トランスクリプトの置き場など）を台帳に持たないこと** — runner が入れ替わった瞬間に嘘になる。
生ログへは runner の API → アーカイブ → 預かったセッションの生ログ、の順で降りる。

- **fs を先に作る**。記憶が Markdown ファイルであることは「人間がいつでも読んで直せる」（提供価値1）の最短の実装
- SDK セッション自体の永続化は SessionStore アダプタ（SDK 公式）で同じ PostgreSQL に載せる。デーモン再起動時は JobStore の session_id からマネージャーを resume する

## パッケージ構成

```
packages/core        ドメイン全部: クローンループ、委譲（デーモン側）、runner 側の
                     SDK セッション、境界のプロトコル(zod)、ストアIF
packages/storage-fs  ローカル用ドライバ（Markdown / JSONL / JSON）
packages/storage-pg  クラウド用ドライバ（PostgreSQL / drizzle）
apps/daemon          alteroidd = core をホストする常駐プロセス + HTTP API（hono）
apps/runner          alteroid-runner = manager-runner。SDK を隔離して走らせる
apps/cli             alteroid = daemon への薄いクライアント（hono/client で型共有）
```

境界の両側が `core` に居るのは、**プロトコルと型を1か所に置くため**である。実際に動くときは
別プロセス（既定では別コンテナ）で、runner 側のコードはデーモンのストアに触れない
（`Stores` を受け取らない）。

## 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| ランタイム | Node 22 LTS | SDK（要 Node 18+）が子プロセスを spawn する関係で Bun は採らない |
| モノレポ | pnpm workspaces | 標準的。SDK と相性問題なし |
| エージェント基盤 | @anthropic-ai/claude-agent-sdk | 自作しない（AGENTS.md） |
| HTTP | hono | 軽量、SSE 対応、`hono/client` で CLI と型を共有 |
| スキーマ | zod | エスカレーション・プロトコルの型付きメッセージの実体 |
| DB（クラウド段） | PostgreSQL + drizzle | マイグレーション込みで軽量 |
| テスト | vitest | — |
| CLI | commander + SSE ストリーミング | chat は readline ベースで開始。TUI 化は後から可能 |

## 認証

- ローカル: Claude サブスクリプション（OAuth）。人間が `claude` でログイン済みの認証を SDK が使う
- クラウド / コンテナ: `claude setup-token` の長期トークンを `CLAUDE_CODE_OAUTH_TOKEN` としてシークレット注入（公式サポート。2026-08 確認）

## 実装フェーズ

| フェーズ | 内容 |
|---|---|
| M0 | モノレポ雛形 + CI |
| M1 | `init` / `chat` — デーモン内クローン + fs 記憶 + 会話終了時の蒸留。**この時点からデーモン常駐**（chat はデーモンに接続する形。常駐は後から足す機能ではない — PRD） |
| M2 | 委譲 — マネージャー起動（複数並行）、作業者、エスカレーション配線、日誌 |
| M3 | 自律 — スケジューラ、外部イベント、クローンの発意、承認待ちキュー |
| M4 | クラウド — pg ドライバ、SessionStore、**daemon / manager-runner の分離**、Dockerfile + compose（3コンテナ）、setup-token |
| M5 | 複数 manager-runner と水平スケール — runner の登録・生存判定・配置、runner 障害時の再開 |
