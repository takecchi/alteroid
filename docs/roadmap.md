## M5 — 複数 manager-runner と水平スケール

**ゴール**: runner を増やしても、能力もプロトコルも1台構成と同じままでいる。

- [x] runner の登録・heartbeat・生存判定
- [x] 新規マネージャーの runner 配置（CPU・メモリ・稼働セッション等、**実行環境の資源**を材料にする。固定の `maxManagers` のような人工上限は置かない）
- [ ] `manager_id → runner_id` に基づく sticky routing — **機構は実装済みで、足りないのはテストである。** `packages/core/src/manager.ts:1084-1097` の `#runnerOf` が保存済みの `runnerId` を `RunnerRegistry#get` で解決し、`runnerId` が未定義のときだけ先頭の runner へ落ちる（**割り当て先を無視するフォールバックはしない**。見つからなければ `null` を返し、`send` / `abort` / `transcript` / `restore` はどれも別の runner へ回さない）。**それでもチェックを付けていないのは、2台以上を同時に登録した状態で `manager_send` が割り当て先へ届くことを確かめるテストが無いからである**（受け入れ基準2 の字義。実在する `manager.test.ts` の「別の runner のジョブには手を出さない」は 1台しか登録していないので、`get()` が必ず `null` になる経路を通っている。`createRunnerRegistry([...])` を走査した範囲では、2台を同時に生かすテストは1本も無い）。あわせて `Registry#get` は `runnerId` の**線形一致**なので、**同じ `runner_id` を名乗る2台が並ぶと先に見つかった方を返す**（#106 の申し送り。これを片側だけで判定できるようにするのが下の fencing である）
- [ ] 二重実行を止める fencing（貸し出し期限 lease）。**引き取りと移送の可否を判定できるのはこれが揃ってからである** — 「落ちた」は観測の欠落であって停止の証明ではないので、もう動いていないことを片側だけで言える材料が要る
- [ ] runner 障害時の session 再開と workspace 復旧
- [ ] workspace locator の運用選択（runner-volume / 共有 FS / Git 再構築）
- [ ] Railway の複数 Service、AWS ECS/Fargate 等で runner 数を増減できるデプロイ定義
- [ ] 1 runner 構成と能力・プロトコルが同じであることの回帰テスト

**受け入れ基準**:
1. runner を2台以上登録し、複数マネージャーが配置される
2. `manager_send` / 許可確認 / 報告が、常に割り当て先の runner へ届く
3. デーモン再起動後も runner affinity を復元できる
4. 1台の runner 停止時、永続化済み session と workspace から別 runner で継続できる。できない場合は、復旧不能な未永続状態を人間へ明示できる
5. runner 数を増減しても、人工的なセッション数上限や能力削減が入らない
6. 器が入れ替わって新しいコンテナが応え始めたとき、引き取り（`takeOver` → `managers.restore()`）が走る。二重実行を止める仕組み（fencing）が「引き取ってよいか」を判定できることで、生きている器の仕事を奪わずにこれができる
   - 名簿は器の入れ替えと単なる回復を区別できない（生存判定の `ping` は名乗りの中身を読まない）。区別が付かないうちに引き取ると、同じマネージャーが2台で走る
   - 引き取りの契機が「runner が開けたとき」なので、**一度開いた宛先が黙って入れ替わった場合は今も引き取りが走らない**。生存判定（`lost` → `connected` の回復）でその差し込み口だけは生まれているが、判定材料が揃うのは fencing である

**分割**: このフェーズは7つの単位に割れている。`PRn` は単位の名前（PR の題や本文がこの語で参照する）であって、着手順の宣言ではない。並びを決めているのは下の依存であって番号ではない。

- **PR1** 動的な名簿 — runner を後から登録できる / デーモンが runner を待たずに listen する（#36 済）
- **PR2** 生存判定 — heartbeat で黙って死んだ器を拾う（#37 済）
- **PR3** 資源による配置 — cgroup v2 で実行環境の資源を読む（#77 済）
- **PR4** 二重実行の防止 — fencing（貸し出し期限 lease）
- **PR5** 移送 — 別 runner でセッションを引き継ぐ。workspace locator の運用選択を含む
- **PR6** 複数 Service のデプロイ定義
- **PR7** 等価性の回帰テスト

**順序を決めている依存**（手順ではなく、成り立っている事実である。事実が変われば書き換える）:

- **移送は fencing の後でしかできない。** ネットワーク分断のとき、落ちたと見えている runner の中ではセッションが走り続けている。「落ちた」は観測の欠落であって停止の証明ではない。fencing の無いまま移送を入れると、同じセッションが2か所で動き、`gh pr create` のような取り返しのつかない操作が二重に走る。貸し出し期限が要るのは、**もう動いていないことを片側だけで言えるようにする**ためである
- **生存判定が無ければ移送の契機が生まれない。** 黙って死んだ器は接続を閉じないので、誰も「落ちた」と気づけない。ただし気づけることと、もう動いていないことは別である — 生存判定は移送の前提であって、上の1つ目を代替しない。引き取りについて同じことが受け入れ基準6に書いてある
- **動的な名簿は他のどれよりも先にある。** runner が揃うのを待ってから listen するデーモンでは、2台目以降を登録できる瞬間が存在しない
- **workspace locator の運用選択は移送と切り離せない。** workspace がどこにあるかを決めない限り「別 runner で引き継ぐ」の中身が決まらない。runner-volume を選べば引き継ぎは復旧ではなく再構築になり、受け入れ基準4の「復旧不能な未永続状態」の線もそこで動く
- **等価性の回帰テストは比べる対象が揃ってからしか書けない。** 配置と移送が入る前に書いたテストは、1台構成の再確認にしかならない
- **資源による配置は上のどれにも依存しない。** 順序の自由がある唯一の単位であり、制約は下の地雷だけである

**このフェーズの地雷**: 配置の判断（資源を見る）と、能力の制限（何本までと決める）を混同しないこと。前者は実行環境の話であり、後者は禁止2の違反である。

## M7 — provider（Claude 以外のコーディングエージェント）

**ゴール**: 人間が明示的に選んだときだけ、層を動かすエージェントを差し替えられる。**選ばれていないときに何も変わらない。** 要件は [PRD「provider」](./PRD.md#provider-層を動かすエージェントは差し替えられる方針であって既定ではない)、設計は [architecture「全体像」](./architecture.md#全体像)。

- [x] 中立の capability 語彙（`agent-ports.ts`）と `Options` 構築の集約（`claude-provider.ts`）。**provider は Claude だけ・挙動不変**
- [x] SDK へ渡す `Options` を固定する特性試験（`tools` / `maxTurns` を渡さない・クローンには `canUseTool` を繋がない、という「無いこと」の固定を含む）
- [ ] 読み側の中立化 — provider のメッセージを正規化イベントへ写し、畳み込みは**全 provider 共通の1本**にする
- [ ] クローンの道具をインプロセス MCP から stdio MCP サーバへ外出しし、中立の口（1ターンぶんのストリームを開く）を作る
- [ ] 要件を担う能力を欠く provider を既定にできない経路と、**失われているものを日報・クローンの自己認識へ出す**口
- [ ] 台帳の「取れなかった」— 消費を報告しない provider の区間を 0 として積まない
- [ ] 2つ目の provider

**受け入れ基準**:

1. 既定の構成（Claude のみ）で、**既存の振る舞いが1つも落ちない**（[north_star 禁止1](./north_star.md#2つの禁止このプロダクトの憲法) — デグレード禁止）
2. 人間が provider を選んでいない限り、層とモデル帯の対応は Fable / Opus / Sonnet のままである
3. 要件を担う能力を欠く provider を選んだとき、**何が失われるか**が日報とクローンの自己認識に出る
4. 消費を報告しない provider の区間が、台帳で 0 ではなく「取れなかった」として出る
5. provider が持たない能力を、持っているように見せる経路が1つも無い
6. `agent-ports.ts` が SDK を import していない（中立の語彙に Claude の形が漏れていない）

**順序を決めている依存**（手順ではなく、成り立っている事実である。事実が変われば書き換える）:

- **読み側の中立化が無ければ2つ目の provider は載らない。** いまクローンとマネージャーは SDK のメッセージを直接ディスパッチしており、そこへ provider 固有の分岐を足していく形にすると、畳み込みが provider の数だけ分裂する
- **中立の口はクローンの道具の外出しの後でしかできない。** 道具が SDK のインプロセス MCP で生えている限り、中立の request 型に SDK の型が漏れる（architecture「全体像」）
- **「失われているものを出す口」は2つ目の provider より先に要る。** 逆順だと、要件が欠けた provider が入った状態を誰も観測できない期間が生まれる
- **台帳の「取れなかった」も2つ目の provider より先に要る。** 0 が積まれた区間は「その層は安い」と読めるので、後から直しても既に人間へ出した数字は訂正できない
- **`Options` 構築の集約は他のどれにも依存しない。** 順序の自由がある唯一の単位である（済み）

**このフェーズの地雷**: provider を足すことを「能力を増やす」と読んで、既定を動かしたり自動で寄せたりしないこと。**選べることが方針であり、選ばれていないときに何も変わらないことがその方針の内容である。** もう1つ、他 provider を足すときも harness をラップする — agent loop を自作したらこのプロダクトの前提（PRD「提供価値」）が消える。

## フェーズ共通の約束

- フェーズ内の作業は TDD で進め、受け入れ基準は自動テスト化できるものからテストにする（SDK 実呼び出しが要るものは手動確認でよいが、確認結果を PR に書く）
- フェーズ完了 = 受け入れ基準全部 + CI green + 人間の確認。次のフェーズに勝手に進んでよいが、受け入れ基準を満たさないまま「概ね動く」で進まない
- 実装中に要件・設計の矛盾を見つけたら、コードで辻褄を合わせずに手を止めて人間に報告する（バグなのは文書ではなくコード、が原則。ただし文書側が間違っていると思うなら、それを言うのが正しい）
