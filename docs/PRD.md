# PRD — alteroid

## 背景・課題

AIエージェントに仕事を任せる場合、人間がボトルネックになる。全ての判断・レビュー・指示を人間が行う限り、並列度も継続性も人間の可処分時間に制約される。

**これは開発に限った話ではない。** 調査・設計の相談・外部サービスの確認・レビューも同じ構造で、人間が起点である限り人間の可処分時間で止まる。実装はその中で分量が多い一部にすぎない（下記「業務範囲」）。

一方で、判断の大半は「その人の目的・価値観・好みを知っていれば下せる」種類のものである。ならば、人間の価値観をコピーした「クローンAI」に日常判断を委譲し、人間は価値観の伝達と最終承認だけを行えばよい。

## プロダクトの目的

**「人間が PC 上で Claude Code に作業依頼をして物事を進める」— これを人間の代わりにクローン（AI）が行えるようにする**（正典: [north_star.md](./north_star.md)。この PRD の要件はすべてそこから導出される）。

そのために、クローン（最終判断）→ マネージャー（プロジェクト管理）→ 作業者（実作業）という階層型AIエージェント組織を、**ローカル端末やクラウド上でコマンド一発で実行できる**ようにする。

作業者が担うのは実装だけではない（調査・確認・レビューも含む）。

## 提供価値（コア3点）

エージェント実行基盤は自作せず Claude Agent SDK をラップする。alteroid の独自価値は次の3点に絞る。

1. **クローンの永続記憶** — 会話から価値観を蒸留して蓄積。人間がいつでも読んで直せる（信頼の要件）
2. **エスカレーション・プロトコル** — 階層間の型付きメッセージ。判断できないことは上の層へ、結果は圧縮して上へ
3. **役割別モデルルーティング** — クローンは Fable または Opus（既定は Opus。現在は Opus 5.5）、マネージャーは Opus、作業者は Sonnet と、役割ごとにモデルを固定して配置する。判断の質が要る層に上位モデルを置き、量の出る実作業は下の層へ委ねてコストを下げる（対応の詳細は[「層ごとの能力」](#層ごとの能力削るのではなく役割で分ける)）

## 非機能要件: 能力の等価性（デグレード禁止）

alteroid が目指すのは「人間が自分の PC で Claude Code に指示して行っている作業を、クローンが代わりに 24 時間続ける」ことである（[north_star.md](./north_star.md)）。したがって次を要件として置く。

> **能力の等価性** — クローンは、人間が**自分の手と Claude Code の両方で**できることを**すべて**できる。マネージャーは、人間が Claude Code に対してできることを**すべて**できる。作業者は、任された仕事（実装に限らず、調査・確認・レビューを含む）に必要な能力を**すべて**持つ。
> **いずれの層についても**、能力の欠落は仕様ではなく**バグ**として扱う。

> 人間が Claude Code に skill や plugin を入れて使えるなら、クローン・マネージャー・作業者も同じものを使えること。入れたものは器を作り直しても消えないこと。入れられるのはオーナーだけで、取り元は版で固定し、自動では更新しないこと。

**基準は「人間が Claude Code に対してできること」であって、特定の OS でも特定のマシンでもない。** 実行環境は手元の端末（macOS）にもクラウド（Linux）にもなり、どちらも常駐先の一形態にすぎない。したがって「この OS では動く」は要件を満たしたことにならず、逆に「人間の端末と同じ OS を使う」ことも要件ではない。

ここから導かれる規則が2つある。

1. **制限は能力（capability）ではなく方針（policy）として表現する** — 「やらせない」はツールを取り上げることではなく方針の宣言で表す。方針は設定で開けられなければならない。方針を緩めたのに能力が戻らない実装は、この要件に違反している
2. **方針の強制と暴走の抑止は、ツール一覧ではなく実行環境の境界で行う** — サンドボックス・ネットワーク・認証情報の配布範囲。人間の手元の環境が安全なのはツールが少ないからではなく、壊せる範囲がその1台に閉じていて人間が見ているからである。無人運用で置き換えるべきはこの2つであって、**ツールを削ることは置き換えになっていない**（能力が落ちるだけで、残ったツール経由の事故は残る）

### 層ごとの能力（削るのではなく役割で分ける）

対応関係は「**人間 → Claude Code**」が「**クローン → マネージャー**」に写る。人間が Claude Code に指示するのと同じ関係を、クローン（人間の代理）がマネージャーに対して持つ。したがって**等価性の基準はマネージャー（Opus）に置く**。

作業者（Sonnet）は、**マネージャーがコストと文脈のために切り出した実作業の担い手**である。マネージャーだけで全部やると Opus の値段で実作業をすることになるので分けている。**ただし切り出してよいのは、下の層へ預けても成果の質が落ちない仕事だけである。** 作業者の出力の質に責任を持つのはマネージャーであり、Sonnet と Opus で成果が同じだという前提は置かない（線の引き方は下の「何を作業者へ出すか」）。

| 役割 | モデル帯 | 位置づけ | 能力 |
|---|---|---|---|
| クローン | Fable または Opus（既定 Opus） | 人間の代理。最終判断 | **人間が自分の手と Claude Code でできること全部。**（`tools` は preset 一式＋自作ツール）。重い調査と実作業は**方針として**下へ委ねる（長寿命セッションの俯瞰と判断を守るため） |
| マネージャー | Opus | **人間が使う Claude Code に相当** | 人間が Claude Code に対してできること全部。簡単な依頼はここで完結してよい |
| 作業者 | Sonnet | マネージャーが切り出した実作業の担い手 | 実作業に必要な能力は全部。**`tools` は preset 一式**を渡し、明示リストで絞らない（SDK が増やしたツールに自動で追いつくため） |

**「マネージャーは実装しない」は能力の禁止ではなく方針である。** 能力としては実装できる（できなければ「簡単な依頼は Opus だけで完結」が成立しない）。ただし重い実作業を Opus の値段でやるのは無駄なので、**原則として作業者へ委ねる**。これは上の規則1（制限は能力ではなく方針で表す）をこの階層に当てはめたものであり、ツールを取り上げて実現してはいけない。

**「クローンは重い実作業をしない」も能力の禁止ではなく方針である。** クローンは人間そのものの写像であり、**人間には Claude Code のほかに自分の手がある** — 端末を叩き、ファイルを開き、ブラウザで確かめる。その手を取り上げた写像は人間の代替になっていないので、規則1はクローンにも等しく適用される（[north_star.md「適用範囲」](./north_star.md#適用範囲--2つの禁止はどこに効くか)）。

したがってクローンにも**道具は全部渡す**。そのうえで重い調査と実作業を原則としてマネージャーへ委ねるのは、長寿命セッションの俯瞰と判断を守るためであり、これはマネージャーの「実装しない」とまったく同じ扱いである — **方針で表し、道具を取り上げて実現してはいけない。** 「自分で見た方が早い」とクローンが判断した場面で自分で見られること、それ自体が人間の写像に含まれる。

**委譲が原則である理由（俯瞰と判断を守る）は、能力を削る理由には使えない。** クローンの文脈が実作業で埋まると記憶への蒸留が痩せる、という懸念は方針とシステムプロンプトで扱う。道具の有無で扱った瞬間に、それは追加制限になる。

**役割とモデル帯の対応は固定である**（Fable または Opus（既定 Opus） = クローン、Opus = マネージャー、Sonnet = 作業者）。変更には人間の承認が要る。「安いモデルで済ませる」「階層を潰して速くする」方向の最適化は、このプロダクトの前提そのものを壊すので禁止する。

「どこまでが簡単か」の線引きはモデルの判断に委ねる（指針をシステムプロンプトに書く）。**全部を下へ投げることは要件ではない** — 簡単な調査依頼がマネージャーで完結し、作業者が1体も立たないのは正しい動作である。

**何を作業者へ出すかの線は、仕事の種類（コード・デザイン・文章）ではなく「出力の良し悪しを、マネージャーが後から安く確かめられるか」で引く。** 種類で切ると、列挙から漏れた分野が必ず出る。

- **確かめられる仕事は作業者へ出す。** 仕様が決まっていて、合っているかが見れば分かるもの — 方針の決まった実装、情報の収集、資料の下読み、手順の決まった検証、決まったデザインの書き起こし
- **確かめられない仕事はマネージャー自身がやる。** 出力の質そのものが成果で、良し悪しの判定が仕事の中身であるもの — 設計、デザイン、人間や外部へ出す文面、調査からの結論、レビューの合否。作業者に作らせてからマネージャーが直すと、判定と作り直しの両方をマネージャーが払うことになり、費用でも得をしない
- **1つの仕事の中で切ってよい。** 素材やたたき台までを作業者へ出し、判定と仕上げはマネージャーが持つ
- **この線で作業者の仕事を実装に狭めてはいけない。** 調査・確認・レビューの下読みも作業者の仕事である（上の「作業者が担うのは実装だけではない」）

### provider: 層は基本 Claude で動く。他のエージェントは、人間が開けたときだけ作業を頼める相手として入る

**層（クローン・マネージャー・作業者）は、基本 Claude Code で動く**（クローン = Fable または Opus（既定 Opus） / マネージャー = Opus / 作業者 = Sonnet）。等価性の基準もそこに置く（上記「層ごとの能力」）。他のコーディングエージェント（provider。いまは Codex）は、**層そのものを置き換えるのではなく、層が作業を頼める相手（peer）として**入る。人間が自分の PC で Claude Code を使いながら、必要なときだけ別のエージェントに作業を頼むのと同じ形である。

**これは 2026-10-07 のオーナー決定である**（逐語は「alteroidの方針としてClaudeを前提にしましょう。基本的にはClaudeがベースとなって動き、設定次第ではCodexに作業依頼を出せるようになる。にしましょう」）。それ以前は「各層を動かす provider を差し替えられる。選べないことは能力の削除の側にある」としており、層を Codex で動かす口（クローン・マネージャーの provider の設定）があった。**その口はこの決定で撤去した。** 層を Codex で動かすと、承認・記憶への蒸留・3層（サブエージェント）・業務範囲（MCP 連携）など、要件を担う能力が層ごと欠けることは、撤去の前から分かっていた。

**「基本」であって「Claude 以外は使わない」ではない**（オーナーの逐語は「今後対応する可能性もあるので」）。層を他の provider で動かす口は、改めて開けうる。そのため境界（中立の語彙 `agent-ports.ts`）は残し、Claude の形を外へ漏らさない（architecture「全体像」）。開け直すときは、人間の決定でこの節を書き換える。

- **peer を開けるのは人間であり、開ける操作はその provider の設定を済ませることである。** 人間が Codex にログインする（または鍵を置く）ことは、Codex を使えるようにしたということであって、それとは別に「開ける」設定を求めない（2026-10-08 のオーナー決定。逐語は「ユーザーがcodexでログインして使えるようにしたってことはcodexを使えるようにしたってことでしょ？ なので条件？はALTEROID_MANAGER_PEERS=codexではなくcodexの設定が完了しているかどうかじゃない？」）。設定が済んでいなければ閉じていて、閉じていれば呼ぶ道具も見えない。設定を外せば（ログアウト・鍵の削除）閉じる。設定が済んだ時点で開き、そのために器を再起動させない。**どの器で開いているか・閉じているならなぜかは、人間とクローンから見える。** 開いた範囲の中で、呼ぶかどうか・何を頼むかは層のエージェントが判断する（オーナーの逐語は「状況や指示に応じて、(設定済みであれば)codexをmanagerがworkerのように使えるというのが理想」）
- **alteroid 自身が provider を選び直さない。** コストや枠（usage limit）を理由に、自動で peer へ寄せたり層の実体を差し替えたりしない。それは層とモデル帯の対応を実装が勝手に変えることであり、「変更には人間の承認が要る」を迂回する。枠に当たった事実はクローンへ知らせ、どうするかはクローンが記憶に根拠を持って判断する（下記「権限境界」）
- **例外: トークン（認証情報）の切替は、provider の切替ではない。** 人間が登録した認証情報のプールの中で、枠に追い返されたものから次のものへ移ることは、層とモデル帯の対応（クローン = Fable または Opus（既定 Opus） / マネージャー = Opus / 作業者 = Sonnet）を1文字も動かさない。**動かさないことが条件である** — プールの中身と試す順序は人間が登録したものだけで、実装が候補を増やさない。**そして回すのは実装（ロジック）であって、クローンの判断を待たない** — 枠に当たったクローンはターンを回さないので、判断を待つ設計はいちばん要るときにいちばん動かない。何を契機に回すかは**設定で開く**（禁止2の言う方針であり、設定で開けられなければならない）。既定は「無料枠を使い切ったら」— 課金枠を使いたい人がそれを選べることが、この設定が要る理由である。回した事実は日誌とクローンへ必ず出す
- **peer は呼び出した層と同じ構えで作業し、確認はまず呼び出した層が答え、判断できないときだけクローンへ上げる**（2026-10-07 のオーナー決定）。新しい権限は増やさない。peer が実行した操作と、誰が承認したかも日誌に残す（可観測性は層と同じ）
- **provider が持たない能力を、持っているように見せない。** 許可確認を上げられない provider に「それらしい確認」を出すと、人間が承認したのに実際は拒否されているという嘘になる。**持たないことは持たないと出す**
- **取れない消費を 0 として積まない。** コストや使用状況を報告しない provider の区間は、台帳で「取れなかった」として出す。0 を積むとその区間が安いと読める
- **peer に使えるモデルは人間が開ける。** 上のモデル帯は Claude Code の層についての対応である。peer は、人間が設定で開けたモデルの一覧の中から、呼び出した層が名指ししたモデルで走る（「デザインは Codex の◯◯に」のように、頼む側が選ぶ。2026-10-07 のオーナー決定）。一覧の外は断る。指定が無ければその provider の既定のモデルに任せる。**alteroid がモデルを選ばない**

### 業務範囲: 代行するのはコーディングだけではない

人間が Claude Code に頼んでいるのは実装だけではない。調査、設計の相談、外部サービスの確認（Slack を見る・Notion を読む）、レビュー、運用の確認。**これらも等しく代行の対象**である。「実装できること」は要件の一部にすぎない。

- 外部サービスとの接続は **MCP** で行う。人間が使っている連携が、クローンと作業者からも使えること
- 「相談」はクローンとの会話で完結してよい。重い調査は**方針として**マネージャー（Opus）へ委ねてそこで完結させる（能力としてはクローン自身も調べられる。委譲は方針であって能力の欠落ではない。上記「層ごとの能力」）
- 成果物が git 以外の形（調査レポート・要約・提案）になる仕事があり、人間が後から読める場所に残る必要がある

## 要件: 自律（仕事の起点は人間に限らない）

北極星は「クローンが人間に成り代わって**勝手に**物事を進める」ことである（[north_star.md](./north_star.md)）。人間が指示を出した時だけ動くものは、速い自動化ではあっても人間の代替ではない。したがって次を要件として置く。

> **自律** — 仕事の起点は人間に限らない。人間が席にいない間もクローンは動き続け、人間の応答待ちが止めるのは**その仕事だけ**である。

- **起点は4つある** — ①人間の依頼、②時間（定期的な見直し）、③外部イベント（MCP 経由で届く通知・レビュー依頼・失敗した CI、外のサービスが連携の鍵で送るもの（添付を含む）など）、④**クローン自身の発意**（記憶にある目的から次にやることを決める）。④が無いものは自律とは呼ばない
- **継続する依頼は器として持つ** — 「定期的に〜しておいて」は、その場で終わらない依頼である。**記憶に書くだけでは足りない** — 記憶は判断の根拠を置く場所であって時計を持たないので、そこにだけ書いた依頼は「発意のときに思い出せるかどうか」の賭けになり、取りこぼしても誰も気づかない。継続する依頼は起点②として持ち、**時刻が来たら必ずクローンに届く**こと。周期はクローンも人間も後から足せる（クローン自身の道具と、人間の CLI / HTTP API の両方から）
  - **周期の書き方で人間に負けないこと。** 人間が cron でできる指定（曜日・月・間隔）がこの階層でできないなら、それは仕様ではなくバグである（[「能力の等価性」](#非機能要件-能力の等価性デグレード禁止)）。「毎日起こして曜日を見て何もしない」は回避策であって等価ではない — 上位モデルのターンを空焼きする。式は標準の5欄（分 時 日 月 曜日）だけを受け付ける。秒つきの6欄・年つきの7欄は、読めない式として断る — 人間の crontab が持たない「分より細かい周期」を、誤って仕込ませないためである。`every`（N分ごと）は1年（525600分）まで。それより長い周期は cron 式か単発の予定で書く（人間も同じ書き方をするので、能力の欠落ではない）。
  - 何をするか・やらないかの判断は依然としてクローンにある。器が持つのは「いつ起こすか」と「何を頼まれたか」だけで、**やることの一覧ではない**
- **引き受けた仕事は片付くまで器に残す** — 依頼は五月雨に届き、優先度は届いたあとも変わる。**返事をしたことと、片付いたことは別である。** その場で着手しなかった依頼は、受信箱の合図がターンの終了とともに消え、日誌は追記専用で状態を持たないため、**どこからも数え上げられなくなる**。これは上の「記憶に書くだけでは足りない」とまったく同じ構造で、単発の依頼にも等しく起きる
  - 人間の依頼・人間の回答・マネージャーからの一件・外部イベントは、**受け取った時点で**「引き受けたまま終わっていない仕事」として器に載る。（外部イベントは器へ書けたときだけ受け取ったと返し、書けなければ 503 で断る。`POST /chat` の `open` は、器への書き込みの完了までは保証しない。）**クローンが明示的に片付いたと記録するまで消えない**。クローン自身が気づいたこと（人間がメモを取るのに当たる）も同じ器へ載せられる
  - **器が持つのは「何を頼まれたか」と「まだ片付いていないか」だけである。** 順序も優先度も締切も持たない — それは「やることの一覧」の側であり、**何を先にやるかは記憶にある目的と価値観からクローンが毎回決め直す**。器は忘れさせないことだけをする
  - 失敗は**残る側**へ倒す。閉じ忘れは雑音として溜まるが、消えれば依頼そのものが失われる。取り返しがつかないのは後者だけである
- **人間不在で止まらない** — 人間の承認が要る仕事は保留になるが、他の仕事は進む。保留は溜めておき、人間が後から `alteroid chat` と HTTP API でまとめて見られる（どこからが承認待ちかは[「権限境界」](#要件-権限境界クローンが判断する)による）
- **止め方は能力の削除ではない** — 暴走が怖いからターン数や起動回数を削るのは上の規則1に違反する。走り続ける前提を置いた上で、方針と実行環境の境界で抑える

## 要件: 権限境界（クローンが判断する）

「どこまで人間に確認するか」は人によって違う。A は自分の名前で Slack に書かれるのを嫌い、B は許す。**この違いを設定項目や行為の一覧で表現しない。** 人間の価値観をコピーしたクローンが持っているものが、まさにその違いだからである。確認が要る行為を列挙した時点で、クローンは「制限された自動化ジョブ」に戻る（[north_star.md](./north_star.md)）。

> **権限境界** — 何を人間に確認し、何を確認せずに実行するかは、クローンが記憶（価値観）に基づいて判断する。行為の種類による固定の一覧は持たない。

- **判断の基準は「記憶に根拠があるか」** — 根拠があれば実行し、無ければ聞く。取り返しがつかない行為ほど、実行に必要な根拠の確かさが上がる（誤送信は取り消せないが、コードは git で戻せる）
- **既定は自走でも許可制でもない** — 記憶が空のうちは聞くことが多く、価値観が溜まるほど減る。**起動直後に人間の登場が多いのは正しい動作**であり、そこを近道しようと既定値を置くと A と B の違いが潰れる
- **判断は記憶に残り、次の判断の材料になる** — 人間が一度「それはやっていい」「それはやらないで」と言えば、同種の判断は以後そうなる。承認は設定ではなく記憶として持続する
- **人間の制御手段は4つ** — ①記憶を直接読んで書き換える（提供価値1）②日誌を読んで事後に否定する（否定が次の記憶になる）③実行環境の境界（渡す認証情報の範囲）④**継続する依頼を読んで直す**（[「自律」](#要件-自律仕事の起点は人間に限らない)の器。自分が出した「これからずっと」の依頼が見えないのは可観測性の穴になる）。**いずれも行為の一覧ではない** — ④が持つのは「いつ起こすか」と「何を頼んだか」だけで、確認が要る行為の一覧を人間に編集させる形は採らない
- **人間の書き換えは、読んだ版を前提にできる。黙って他の書き手を消さない** — 人間が記憶を開いて直している間にもクローンは同じ記憶へ書く（蒸留・発意・棚卸し）。後勝ちの全文置換では、人間が別の箇所を直しただけで、クローンが蒸留した判断が黙って消える（「判断は記憶に残る」の違反）。`PUT /memory/{slug}` は任意の `ifMatch`（読んだ時の版）を受け、合わなければ**何も書かず 409 でいまの版を返す**。`alteroid memory edit` は読んだ版を持ち回り、衝突したら**人間が書いた内容を捨てずに残して**見比べる手を案内する。前提を付けない HTTP の呼び出しは従来どおり後勝ち。**削除にも同じ線を引く**（Issue #2881。何を消すかを読んで決めたのに、読んでいない内容まで消えてはならない）— `DELETE /memory/{slug}` はクエリ `ifMatch`（読んだ時の版）を受け、合わなければ**何も消さず 409 でいまの版を返す**。`alteroid memory remove` は消す直前に読んだ版を持ち回り（`alteroid memory show` が stderr に出す版を `--if-match <版>` で渡せば、見て決めた内容を前提に消せる）、衝突したら消さずに、いまの版と次の手（`memory show` で確かめて再実行）を案内する。**版は必須。版が無ければ 428 で断り、何も消さず、いまの版（`current`）を返す**（日誌にも積まない）。**クローン側も同じ線を引く** — `memory_write`（全文置換）は、既存の文書には `memory_read` が返した版（`base_version`）を前提に要求し、読んだ後に人間や別のターンが書いていれば**書かずに「その間に変わった」と返して、読み直して判断し直させる**（`memory_frontmatter_set` も同じく版を必須で受ける。`memory_section_move` の切り取りは、読んだ版を前提に書く。`memory_delete`（文書ごと消す）も同じく版を必須で受け、無ければ消さず、合わなければ**消さずに**「その間に変わった」と返す）。追記（`memory_append`）は既存の記述を置き換えないので前提を要らない
- **聞かずに実行した判断は必ず日誌に残る** — 事前承認を既定にしない以上、人間が後から追えて否定できることが[「最終承認」](./north_star.md)の実体になる

## 要件: 自己改善（仕事のやり方を測って直し続ける）

人間は同じ失敗を繰り返さない。同じ種類の仕事を何度もやるうちに、やり方そのものを直していく。**クローンがそれをできないなら、それは仕様ではなくバグである**（[「能力の等価性」](#非機能要件-能力の等価性デグレード禁止)）。

ただし「良くなったか」を測る軸が無いまま改善だけを続けると、改善は**いまの形の周りしか探さない** — 現在の設計を A とすると `A → A' → A''` は進むが、まったく違う設計 B や C へは飛べない。最初に与えられた設計がアンカーになるためである。したがって次を要件として置く（2026-09-16 のオーナー決定）。

> **自己改善** — 仕事の結末は測られ、測った結果が次の仕事のやり方へ反映される。何を良しとするかの基準は**記憶**にあり、設定項目の一覧としては持たない。

**⚠️ 自己評定の仕組みは削除した（2026-10-04 のオーナー決定、#2699）。** クローンが自分の仕事の結末を評定し（`commitment_appraise` 等）、その集計を蒸留・棚卸しへ材料として渡す仕組みを #1055 / #1308 / #1310 で作ったが、使われないままトークンを消費していたため外した。オーナーの依頼（逐語）:「alteroidに自分で自分の作業内容を評価する仕組み作ってもらったと思うんだけど、なんか使ってないし削除お願いします。トークン無駄だし」。**仕事のやり方の器（`practice_*`）は残っている。** 結末を測る仕組みを作り直すなら、改めてオーナーの承認を得ること。

- **最適化の対象は「仕事のやり方」であって記憶ではない** — 記憶はクローンの同一性そのものであり（[architecture.md「クローンの寿命モデル」](./architecture.md)）、分岐させて並行に走らせることは人格の分岐である。分岐できるのは**繰り返し起きる仕事のやり方**（依頼文の型・どこで切り出すか・何を検証に通すか・どの手順書を読ませるか）のほうである
  - **⚠️ [north_star の「仕事の型」](./north_star.md)（＝仕事の**種類**。実装・調査・相談・レビュー）とは別物である。** 狭めてはいけないのがあちら、測って直し続けるのがこちら（同じ種類の仕事を**どう進めるか**）である
  - **やり方はコーディングに限らない** — 定期の調査、外部サービスの確認、返信の下書き、日報。[「業務範囲」](#業務範囲-代行するのはコーディングだけではない)の全域が対象である。**テストが通るかで測れない仕事のほうが多い**ことを前提に置く
- **評価基準の持ち場は記憶である** — 「何を良しとするか」は人によって違い、その違いこそクローンが記憶として持っているものである。これは[「権限境界」](#要件-権限境界クローンが判断する)とまったく同じ構造であり、同じ理由で**評価項目の一覧を設定として持たない**。人間が基準を変えるときに触るのは記憶であって設定ファイルではない
- **やり方の器が持つのは素材であって、実行される定義ではない** — [「自律」](#要件-自律仕事の起点は人間に限らない)の器と同じ線である。器は「こう書いてある」を渡すだけで、従うかどうかはクローンが毎回決める。**従わせた時点で、クローンは「制限された自動化ジョブ」に戻る**（[north_star.md](./north_star.md)）
- **やり方の書き換え・削除も、読んだ版を前提にする**（Issue #2923。記憶の `memory_write` / `memory_delete` と同じ線） — クローンが読んだ後に人間が画面・CLI で同じやり方を直しても、クローンの全文書き直しや削除が黙って消してはならない。`practice_read` は応答の末尾に版（`base_version`）を返し、`practice_write`（全文置換）は**既存のやり方には版を必須**で受け、`practice_remove` も版を**必須**で受ける。無いか合わなければ、**何も書かず（消さず）に「その間に変わった」と返し**、いまの版と読み直す手（`practice_read`）を添える。**新規作成は版なしで通る。**
- **改善の量を能力の上限で抑えない** — 「一度に変える量を制限する」を回数やターン数の上限として実装することは能力の削除である（[north_star.md](./north_star.md) の禁止2）。まとめて変えた回は何が効いたか分かりにくくなるが、それは**観測の側に出す**ことで表す。後から見直して効いたものを特定できる余地も残る
- **候補の並行探索に新しい機構を作らない** — 複数の候補を同時に試すことは、既にある[「同時実行モデル」](./architecture.md)（クローンは複数のマネージャーを使う）で表せる。**安いモデルで候補を大量に回す形は採らない** — 層とモデル帯の対応を実装が勝手に変えることであり、変更には人間の承認が要る（[「層ごとの能力」](#層ごとの能力削るのではなく役割で分ける)）

## 要件: 可観測性（日報・日誌・セッションログ）

人間はほとんどの時間、系を見ていない。それでも任せられるのは「見ようと思えばいつでも全部見える」からである。粒度の違う3層を要件として置く。

| 層 | 中身 | 読まれ方 |
|---|---|---|
| **日報** | 今日何をしたか・何が決まったか・何が保留か、の要約 | 人間が偶に読む。普段の接点はほぼこれだけ |
| **日誌** | クローン⇄マネージャーのやり取り、聞かずに実行した判断、エスカレーション、ツール実行の記録。追記専用 | 何かあったときに掘る |
| **セッションログ** | 各セッションの生のトランスクリプト（compaction で潰される前の全文アーカイブを含む） | 日誌で足りないときの最後の拠り所 |

- 3層すべて `alteroid chat` と HTTP API から読める。日報だけ読んで暮らせるが、掘れば生ログまで一本道で降りられること
- 日報は1日の終わりにクローンがまとめる。これは時間起点のジョブであり、[「自律」](#要件-自律仕事の起点は人間に限らない)の起点②の最初の実例でもある
- 見えることは機能ではなく信頼の要件である。実装の都合でどれかの層が見えなくなったら、それはバグとして扱う
- **添付は、メタデータだけを残し、中身は残さない。** 日誌（`exchange`）と受信箱には、添付の控え（`AttachmentRef`: id・名前・種類・大きさ・sha256）だけを書く。中身は保持期間のあとに消えるが、控えは残るので、後から「添付が在った」ことが追える
  - `conversation_read` と `GET /conversations/:id` で、発言に添付が在ったことが分かる
  - クローンが担い手へ渡した添付も、日誌（`with: 'manager'` の outbound の `exchange`）の控えで追える
  - クローンが人間へ返した添付（`with: 'human'` の outbound の `exchange`）と、担い手から報告に添えて届いた添付（`manager_message`）も、日誌に控えだけが残る

## 要件: インターフェース（CLI・HTTP API・Web UI）

人間が系に触る口は3つある。**どれも同じ HTTP API の上に乗る。**

| 入口 | 位置づけ |
|---|---|
| `alteroid`（CLI） | 端末から。常駐の起動・停止もここ |
| HTTP API | 外部アプリ・自作ツール・ショートカットの口。仕様は `GET /openapi.json` |
| Web UI | 公式に提供する画面。**API の上の実装**であって、独自の経路を持たない |

> **入口の等価性** — ある入口でできることが別の入口でできない状態を作らない。どの入口から入っても、見えるもの（日報・日誌・生ログ）と起こせること（会話・承認・委譲の停止・記憶の書き換え・定期ジョブ・外部イベント）は同じである。

- **Web UI は API の特権的な消費者ではない。** 画面のためだけの経路をデーモンへ足さない。足した時点で「CLI ではできないこと」が生まれ、上の等価性が壊れる
- **画面とデーモンは別のホストに置ける。** 同じ端末に両方置く人もいれば、デーモンを自分のサーバに、画面を静的ホスティングに置く人もいる。配置は運用の都合であって、能力を変える理由にはならない
- 認証は入口ごとに作らない。デーモンに認証を足すなら、それは3つの入口すべてに等しく効く

### 添付（画像・動画・ファイル）

- **人間は3つの入口のどこからでも、発言に画像・動画・ファイルを添えられる**（CLI は `/attach`、Web UI はファイル選択・ドロップ・貼り付け、HTTP API は `POST /attachments` で上げた id を `POST /chat` の `attachments` に渡す）。入口によって添えられる・添えられないが分かれない（上の「入口の等価性」）
- **本文が空で添付だけの発言も送れる。** 添付が無い空の本文は、従来どおり受けない
- **画像（png / jpeg / webp / gif）は、クローンに画像として見える。** 宣言ではなく中身の先頭で確かめる
- **画像の上限を超える画像は、入れる経路で扱いが分かれる。**
  - 人間や連携の鍵が上げるとき（`POST /attachments`）は、画像の上限（1枚の大きさと、幅・高さ 8000 px）を超える画像を受け付けない。寸法が読めない画像は受け付ける
  - クローン（`file_put`）と担い手（出し箱）が入れるときは、上限を超えた画像もファイルとして受け付ける。ただし画像としては見せず、ファイルとして開く案内を付ける
  - 宣言が画像以外で中身が画像のものも、画像としては見えない
- **1ターンに画像として見えるのは、枚数と合計に上限がある。** 超えた分（クローンへは古い発言の画像から、担い手へは1つの指示の後ろの画像から）は、受け付けて保存はするが画像としては見えず、ファイルとして開く案内が付く。上限は環境変数で変えられる（既定は20枚・合計 16 MiB。`ALTEROID_ATTACHMENT_MAX_TURN_IMAGES` / `_MAX_TURN_IMAGE_BYTES`）
- **発言の編集では、元の添付を外せる。** CLI と TUI は `/detach` で外す。CLI の1行の形 `/edit 番号 本文` は元の添付を引き継ぐので、外すには `/edit 番号` の後に `/detach` を使う。どの入口も、元の添付は上げ直さない。会話を移っても、始めた編集の書きかけは落とさない（Web と TUI は書きかけを残し、CLI は編集を続けたままにして、確定すれば始めた会話へ送る）
- 0バイトの添付は、どの入口（Web・CLI・TUI・HTTP API）でも添えられない（0バイトの添付は、ほぼ必ず使い手の間違いであるため）。
- **動画・PDF・ログなど画像以外は、置き場から取り出せる。** クローンは道具 `attachment_fetch` で手元へ取り出し、`Read` で開く
- **クローンは、担い手（マネージャー・作業者）にも添付を渡せる**（`manager_start` / `manager_send` の `attachments`）。人間がクローンに見せたものを担い手に見せられなければ、委譲で能力が落ちる
- **クローンも、人間へファイルを返せる。** 返信（`reply_attach`）と別の会話への投稿（`conversation_post` の `attachments`）に、置き場のファイルを添えられる。クローンの手元のファイルは `file_put` で置き場へ入れる。人間には、人間が添えた添付と同じ形で見え、ダウンロードできる
- **担い手（マネージャー・作業者）も、クローンへファイルを返せる。** 担い手が出し箱（`$ALTEROID_OUTBOX`）に置いたファイルは、報告に添えて届く。受け取れなかったもの（上限を超えた・取り出せなかった）は、理由つきで報告に残る（黙って落とさない）
- **ファイルは置き場に保存して、一覧で見られる。** 一覧は会話ごとではなく1つで、会話・出所（人間・クローン・担い手・連携の鍵）・保存の有無で絞り込む。保存したファイルは期限で消えない。保存しないものは従来どおり保持期間で消える。一覧・保存・取り出し・削除は、3つの入口とクローンの道具から同じようにできる
- **添付は記憶へ自動では写さない。** 中身を覚えておく必要があれば、クローンが自分の言葉で記憶へ書く。資格・鍵を含むファイルは、置き場へ入れず人間へも返さない（方針）。クローンの `file_put` は、資格の置き場（`ALTEROID_CREDENTIAL_DIR` と、`*_FILE` の環境変数が指すファイル）からは読まない（認証情報の配布範囲の境界）
- **上限と保持期間は環境変数で変えられる。** 既定は、1つあたり画像 5 MiB・その他 25 MiB、1発言に10個・合計 50 MiB、保持30日（`ALTEROID_ATTACHMENT_MAX_IMAGE_BYTES` / `_MAX_FILE_BYTES` / `_MAX_PER_MESSAGE` / `_MAX_TOTAL_BYTES` / `_RETENTION_DAYS`）。クライアント（CLI・TUI・Web）の先行検査は、デーモンの上限（`GET /attachments/limits`）に従う。
  - 担い手からの1回の報告にも、1発言と同じ個数・合計の上限が掛かる。1つの上限を超えるファイルは、理由を言って受け取らない
  - **大きいファイルは、外部ストレージ（S3 互換。`ALTEROID_ATTACHMENT_S3_*`）が設定されているときだけ扱える。** 設定されていれば、画像以外の1つの上限は 2 GiB（`ALTEROID_ATTACHMENT_MAX_LARGE_FILE_BYTES`）になり、画像の上限は変わらない。設定が無ければ今までどおり（その他 25 MiB まで）。25 MiB を超えるファイル（大きいファイル）は、1発言の合計（50 MiB）に数えない（個数には数える）。合計の上限はメモリの負荷を抑えるためのもので、大きいファイルはストリームで流れるのでその負荷にならない
  - 大きいファイルを担い手へ下ろすのは、まだできない（#4128 段3）。担い手に添えようとしたときは、黙って落とさず、理由を言って何も送らない
  - 保存したファイルは保持期間の対象外。置き場全体の容量の上限は置かず、使用量（合計と出所ごと）を一覧で見せる（2026-10-08 オーナー決定、#4126）
- **リセット（`alteroid reset` / `POST /reset`）は、添付の中身も消す。** 保存したファイルと `attachment_fetch` の写しを含む（2026-10-08 オーナー決定、#4006）

**非ゴールから外した経緯**: 当初は「UI は API の上に将来誰でも作れる」として非ゴールに置いていた。実際に使ってみて **CLI が読みにくく、作者自身の日常の道具として成立していない**ため、公式の画面を持つことにした。非公式の UI を妨げるものではない（API は変わらず公開されている）。

## ターゲットユーザー

- MVP: 作者自身。**手元の端末に常駐させたままの**個人利用、Claudeサブスクリプション（OAuth認証）前提。常駐は[「自律」](#要件-自律仕事の起点は人間に限らない)の前提であって、後から足す機能ではない
- 将来: 同様の運用をしたい個人開発者。クラウド（VPS / Railway / AWS）は**常駐先の選択肢**であり、ローカル常駐との違いは配置だけである（端末を閉じても走り続ける、認証情報の置き場所が変わる）

## ユーザーストーリー（MVP）

1. `alteroid init` で人格データディレクトリを初期化する
2. `alteroid chat` でクローンと会話する。目的・価値観・好みを自然言語で伝える。会話終了時にクローンが学びを蒸留する
3. 人間が「この機能を作りたい」とクローンに依頼すると、クローンがマネージャーを起こし、マネージャーが作業者に指示を出す
4. 人間が何も言わない間も、クローンは記憶にある目的と届いた外部イベントから次にやることを決め、自分でマネージャーを起こす
5. 作業者が実装し、マネージャーに報告。マネージャーは日誌をまとめてクローンに報告
6. 判断に迷った作業者はマネージャーへ、マネージャーはクローンへエスカレーション。クローンは学びに基づいて判断し、記憶に根拠が無いことだけ人間に確認する
7. 人間は `alteroid chat` または Web UI で日報・日誌・進捗を読み、確認ができる。普段は日報を偶に読むだけでよい
8. 外部アプリ（自作ツール、ショートカット等）から HTTP API 経由でクローンに指示を送り、進捗・日誌・保留中のエスカレーションを取得できる
9. 人間はスクリーンショット・動画・ログなどを発言に添えて渡せる（本文が空でもよい）。クローンはそれを見て、必要なら担い手にも渡す

## スコープ外（非ゴール）

- マルチユーザー / チーム利用 — **利用者ごとにデータを分けない。** 記憶・日誌・会話・実行 API は1つのクローンのものが1組だけ在り、誰が入っても同じものを見る
  - **⚠️ これは「入口を1人に絞る」という意味ではない。** alteroid を使う許可（`alteroid access grant`）は複数のアカウントへ出せる（2026-09-09 のオーナー決定。それ以前は高々1つで、2人目の grant は 409 だった）。同じ人間が私用と仕事用の Google アカウントの両方から入れないことのほうが、実際の使い方に対する欠落だったためである
  - **境界はデータの側に在る。** 「アカウントごとの記憶」「アカウントごとの日誌」「他人の会話は見えない」を作りたくなったら、そこがこの非ゴールを越える線である
