# ADR 0063: `hnsw.iterative_scan` は採らない — 件数は直るが正しさは直らないことを測った

- **状態**: 採用 (2026-09)（**「`hnsw.iterative_scan` を有効にしない」という決定**であり、
  実装の変更は伴わない。docs のみ）

- **文脈**:

  [ADR 0059](./0059-period-in-ann-stage.md) が段1（ANN 検索、`PostgresVectorStore.search`）の
  `WHERE` 句へ `period` の述語を降ろし、式索引 `idx_memories_period_ann_stage`
  （`tenant_id, status, COALESCE(occurred_at, recorded_at)`）を1本足した。これは
  「狭い窓で0件になる」という最悪の形を実際に塞いだ。

  **しかし ADR 0059 は、自分で残余を1つ申告している。**その本文
  （`0059-period-in-ann-stage.md:145-155`）は、押し下げを入れた後でも
  **プランナが式索引ではなく HNSW 経由の近似プランを選ぶ場合があり**、そのとき
  `LIMIT` に届かないままスキャンが終わることを一次実測で記録した。そして
  **この残余を「`hnsw.iterative_scan` の腕（別 ADR）が扱う領域そのものである」と名指しし**、
  同時に「**⚠ ただし本 ADR はこれを『`iterative_scan` を入れるべきだ』とは決めない**」と
  明記して判断を保留した。

  `docs/recall.md:131` と `docs/memory-model.md:341` も、**「フィルタ問題」の対処として
  `hnsw.iterative_scan` + `hnsw.ef_search` の調整を名指ししている**（「mnemora は両方を
  別々に持つ: フィルタ問題は iterative scan で緩和し、スコア問題は over-fetch + 段2の
  再スコアという構造そのもので解く」`docs/recall.md:135`）。また `docs/memory-model.md:575`
  が pgvector `>= 0.8.0` を既に必須としており、**`iterative_scan` は新しい版要件を
  持ち込まない。**

  ⟹ **正典も ADR 0059 も、この腕を「次に試すべき手」として指している。本 ADR は
  その腕を実際に測り、その結果として採らないと決める。**

- **決定**:

  1. **`hnsw.iterative_scan` を有効にしない。** `off`（pgvector の既定）のままとする。
     `relaxed_order` も `strict_order` も採らない。
  2. **実装は1行も変えない。** 本 ADR は測定と決定の記録だけである。
  3. **ADR 0059 の見立ての、外れた側を本 ADR で訂正する**（ADR 0059 の本文は書き換えない
     ——ADR は追記して積む）。
  4. **⭐ ADR 0059 が申告した負債を塞ぐ手は在る、と明記する。ただしその採否は
     本 ADR では決めない。** 厳密（式索引）経路を選ばせれば `recall@40` は **1.000** になり、
     この seed での費用は `relaxed_order` の **約2.5倍**（24ms → 62ms）である。
     **⚠ ただしこの倍率は 100,000行の1点でしか測っておらず、100万件級での伸びは
     まったく測っていない**——**そこが次に測るべき一点である。**下の
     「⭐ 負債を塞ぐ手は在る」節に分けて書く。

- **⭐ 一次実測（すべて本 ADR の作業者が自分で測った値）**:

  **測定台**: この作業環境に **PostgreSQL 17.11 (Debian 17.11-1.pgdg12+2) + pgvector 0.8.6**
  を立てた（CI が使う `pgvector/pgvector:pg17` と同じ版）。**ADR 0059 の測定と直接
  比較できるよう、seed のレシピを 0059 本文から写して揃えた**: 100,000行・256次元・
  `setseed(0.20260908)`・`occurred_at` の20%を NULL。**スキーマは手書きせず
  `packages/postgres` の移行スクリプト（0001/0002/0003）で作り、
  `idx_memories_period_ann_stage` が存在することを確認した。**埋め込み表
  （`memory_embeddings_bench`）だけは手書きし、DDL は `packages/postgres/src/vector-space.ts`
  の `CREATE TABLE` / `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)` を
  書き写した。クエリベクトルは `setseed(0.777)` 由来の1本。`LIMIT 40`
  （`k' = limit 10 × overFetchFactor 4`、`recall-runtime.ts:222-224` と
  `recall.ts:579,582` から読んだ実値）。

  **測ったクエリは段1の実物**——`packages/postgres/src/vector-store.ts:95-103` の骨格を
  そのまま使った（`ORDER BY e.embedding <=> $1` / `LIMIT`、`WHERE` に `tenant_id`・
  `status IN ('active','contested')`・`COALESCE(occurred_at, recorded_at)` の両端包含）。

  **実際に出た分布**（ADR 0059 の seed とは別物なので、0059 の数字とは一致しない）:
  active 69,931 / contested 9,985 / archived 10,020 / forgotten 10,064。
  `occurred_at` NULL 20,026 / 100,000。窓ごとの実在数（厳密 `count(*)`）:
  **0.1% = 92 / 1% = 832 / 10% = 8,089 / 50% = 39,933**。

  **既定のまま変えなかった設定**（`SHOW` した実値）:
  `hnsw.ef_search = 40` / `hnsw.max_scan_tuples = 20000` /
  `hnsw.scan_mem_multiplier = 1` / `random_page_cost = 4` /
  `effective_cache_size = 4GB` / `work_mem = 4MB` / `shared_buffers = 128MB`。

  **`recall@40` の「正解」の作り方**: HNSW を回避させた厳密な上位40件
  （`enable_indexscan = off` / `enable_bitmapscan = off`）を正解集合とし、
  各腕が返した40件のうち何件がその集合に入っていたかを数えた。

  ### 腕 × 窓の表（各セル3回反復。**3回とも完全に同一で、ゆらぎは無かった**）

  | 窓 | 腕 | 返却数 | **recall@40** | 距離順の逆転 | プラン | 時間† |
  |---|---|---:|---:|---:|---|---:|
  | 0.1% | `off` / `relaxed_order` / `strict_order` **3腕とも同一** | 40 | **1.000** | 0 | 式索引 | 1.4–9ms |
  | 1% | **3腕とも同一** | 40 | **1.000** | 0 | 式索引 | 5–15ms |
  | 10% | `off` | **3** | 0.075 | 0 | HNSW | 1.9–3.9ms |
  | 10% | `relaxed_order` | **40** | **0.500** | **12** | HNSW | 18.7–74.9ms |
  | 10% | `strict_order` | **40** | **0.100** | 0 | HNSW | 29–55ms |
  | 50% | `off` | **16** | 0.125 | 0 | HNSW | 1.5–1.8ms |
  | 50% | `relaxed_order` | **40** | **0.350** | **2** | HNSW | 5.9–6.3ms |
  | 50% | `strict_order` | **40** | **0.125** | 0 | HNSW | 8.1–8.5ms |

  † **⚠ 時間は根拠の格を下げて読むこと。**同じサーバで別の測定が同時に走っている下での
  観測であり、**同時実行の影響を受ける。件数と `recall@40` は同時実行の影響を受けないので、
  そちらは信頼できる**（ADR 0059 が同じ理由で速さを根拠に使わなかった姿勢に揃える）。

  ### `EXPLAIN (ANALYZE, BUFFERS)` から読んだプランの実際

  - **0.1% / 1% の窓では `idx_memories_period_ann_stage` が実際に使われる**
    （`Index Scan using idx_memories_period_ann_stage` → `memory_embeddings_bench_pkey`
    への Nested Loop）。0.1% では 92行を索引で取って上位40件へ、1% では 832行を取って
    上位40件へ。**厳密な上位40件と一致する**（`recall@40 = 1.000`）。
    ⟹ **狭い窓は ADR 0059 の索引だけで完全に解けており、`iterative_scan` の出番が無い。**
  - **10% / 50% の窓では HNSW 経由**（`Index Scan using idx_memory_embeddings_bench_hnsw`）。
    HNSW から取り出した行数と、`memories` 側の `Filter`（status + period）を通った行数:

    | 窓 | 腕 | HNSW が取り出した行 | 述語を通って返った行 | Buffers |
    |---|---|---:|---:|---:|
    | 10% | `off` | **40** | **3** | 1,777 |
    | 10% | `relaxed_order` | **551** | **40** | 14,772 |
    | 10% | `strict_order` | **517** | **40** | 20,009 |
    | 50% | `off` | **40** | **16** | — |
    | 50% | `relaxed_order` | **110** | **40** | — |
    | 50% | `strict_order` | **93** | **40** | — |

    ⟹ **`iterative_scan` は確かに「もっと深く掘る」**（40行 → 517〜551行）。
    **そして確かに `LIMIT 40` を埋める。**

- **🔴 いちばん重い結論: `iterative_scan` は件数だけを直し、正しさを直さない**:

  上の表の `recall@40` の列が言っていることは1つである。**`LIMIT` が埋まったことと、
  正しい記憶が返ったことは、別である。**

  10%窓で `relaxed_order` は 40件返すが、そのうち**厳密な上位40件に入っていたのは20件だけ**
  （`recall@40 = 0.500`）。50%窓では 14件だけ（0.350）。**残りは「窓を埋めるために
  拾われた、より遠い候補」である。**

  ### ⚠ `strict_order` は正しさを一切買わない——名前から受ける印象の逆である

  **次にこの ADR を読む人は、名前から「`strict_order` なら厳密で正しい」と読む。
  測った結果はその逆だった。**

  `hnsw.ef_search` を既定の 40 から 800 まで振って、`off` と `strict_order` の
  `recall@40` を並べた（本 ADR の作業者が追加で測った診断。**腕として提案するものではなく、
  上の結果がなぜ起きるかを説明するために測った**）:

  | 窓 | `ef_search` | `off` の返却数 / recall@40 | `strict_order` の返却数 / recall@40 | `relaxed_order` の返却数 / recall@40 |
  |---|---:|---|---|---|
  | 10% | 40 | 3 / **0.075** | 40 / **0.100** | 40 / **0.500** |
  | 10% | 100 | 8 / **0.175** | 40 / **0.175** | 40 / 0.525 |
  | 10% | 200 | 13 / **0.250** | 40 / **0.250** | 40 / 0.525 |
  | 10% | 400 | 29 / **0.425** | 40 / **0.425** | 40 / 0.575 |
  | 10% | 800 | 40 / **0.575** | 40 / **0.575** | 40 / 0.575 |
  | 50% | 100 | 38 / **0.275** | 40 / **0.275** | 40 / 0.325 |
  | 50% | 200 | 40 / **0.425** | 40 / **0.425** | 40 / 0.425 |
  | 50% | 400 | 40 / **0.550** | 40 / **0.550** | 40 / 0.550 |
  | 50% | 800 | 40 / **0.700** | 40 / **0.700** | 40 / 0.700 |

  **`strict_order` の `recall@40` は、`ef_search` のどの水準でも `off` と一致する**
  （唯一の例外は `ef_search=40` の 10%窓で 0.100 対 0.075 ——`off` が3件しか返せず
  分母に届いていないための差であり、`strict_order` が新たに見つけた行は1件だけである）。

  ⟹ **`strict_order` が足しているのは件数だけで、正しさは1件も足していない。**
  腕の比較でも同じことが出ている: `strict_order` が新たに返した37行のうち、
  **`off` の最悪距離を下回るもの（＝より近い候補）は 0 件**だった。
  一方 `relaxed_order` が新たに返した行のうち **8件（10%窓）・16件（50%窓）** が
  `off` の最悪距離を下回っており、**本当に近い候補を拾っている。**

  ⟹ **「順序を守ったまま取りこぼしを直す」という選択肢は、この測定には存在しなかった。**
  正しさを買える腕は `relaxed_order` だけで、それは定義上、距離順を壊す。

- **⭐ 負債を塞ぐ手は在る——厳密（式索引）経路なら `recall@40 = 1.000`、費用は約2.5倍**:

  **本 ADR は `iterative_scan` を採らないと決めるが、「だから残余は塞げない」とは
  言わない。塞ぐ手は在る。**本 ADR の実測から言えることを、正面から書く。

  `recall@40` の正解集合を作るために、**HNSW を回避させた厳密経路を実際に走らせた。**
  その経路は定義上 `recall@40 = 1.000` であり、**`LIMIT 40` も必ず埋まる**
  （窓内の実在数が 8,089 / 39,933 あるため）。⟹ **ADR 0059 が申告した残余
  （`LIMIT` に届かない・真の近傍を取り逃す）は、この経路では両方とも消える。**

  | 窓 | 厳密経路 | `relaxed_order` | `off`（現状） |
  |---|---|---|---|
  | 10% | 40件 / **recall 1.000** / **62ms**† | 40件 / recall 0.500 / 24ms† | **3件** / recall 0.075 / 5ms† |
  | 50% | 40件 / **recall 1.000** / **55ms**† | 40件 / recall 0.350 / 6ms† | **16件** / recall 0.125 / 2ms† |

  † **⚠ 時間は同時実行下の観測であり、根拠の格は低い**（件数と recall は影響を受けない）。

  ⟹ **この1点（100,000行）では、厳密経路は `relaxed_order` の約2.5倍の時間で、
  `recall` を 0.500 → 1.000 にする。**

  **⚠ しかし、この「約2.5倍」を本番の既定を変える根拠にしてはならない。**
  理由を明記する:

  - **測ったのは 100,000行・256次元・単一テナント・同時実行なしの1点だけである。**
    **100万件級（`docs/roadmap.md:249` がオーナー決定として前提とする規模）で
    この倍率がどう動くかは、まったく測っていない。**厳密経路は窓内の行数に比例して
    重くなる形（10%窓なら 8,089行を読む）であり、**規模とともに倍率が広がる可能性が
    あるが、それは推論であって測定ではない。**
  - **⭐ そして倍率が広がるかどうかで結論が変わりうる。**⟹ **次に測るべき一点は
    「2.5倍が規模とともにどう動くか」である。**
  - **プランナに厳密経路を選ばせる方法そのものも、本 ADR では決めていない。**
    分岐点が ≈1.15% と非常に低く、そこでの見積り費用が拮抗している（7935.60 対 7939.68）
    ため、`random_page_cost` 等のコストパラメータに踏み込むか、索引の形に手を入れるかの
    判断が要る。**どちらも測っていない。**

  **⟹ 本 ADR はこの手を「在る」と記録するだけで、採るとも採らないとも決めない。**
  `iterative_scan` の腕と厳密経路の腕を同じ ADR に混ぜると、どちらが効いたのかを
  切り分けられなくなる（ADR 0059 が腕を分けた判断と同じ理由）。**採否はオーナーの判断であり、
  その前に規模を振った測定が要る。**

- **⭐ プランの分岐点を特定した（ADR 0059 が「特定していない」と書いた点）**:

  ADR 0059 は「**プランの分岐点（何%の窓で HNSW 経由に切り替わるか）は特定していない**」と
  書き残した。本 ADR で窓を細かく振って特定した（腕 `off`、この seed・この設定での値）:

  | 窓 | 選ばれたプラン | 見積り top cost |
  |---|---|---:|
  | 1% | `idx_memories_period_ann_stage` | 7374.27 |
  | **1.1%** | **`idx_memories_period_ann_stage`** | **7935.60** |
  | **1.15%** | **HNSW** | **7939.68** |
  | 1.2% | HNSW | 7660.63 |
  | 2% | HNSW | 4931.21 |

  ⟹ **分岐点は 1.1% と 1.15% の間にある。**そこでは**2つのプランの見積り費用が
  ほぼ拮抗している**（7935.60 対 7939.68、差は 0.05%）。
  **⟹ この境界の周辺では、統計のわずかな揺れでプランが裏返りうる。**

  **⚠ この値は本 ADR の seed・行数（100,000行）・既定のコストパラメータ
  （`random_page_cost = 4` / `effective_cache_size = 4GB`）の下での値である。**
  行数やコストパラメータを本番相当に寄せた場合に分岐点が動くかどうかは**測っていない。**

- **🔴 ADR 0059 の見立ては半分外れていた（どちらの半分が外れたかを明示する）**:

  ADR 0059 は残余について「**これは `hnsw.iterative_scan` の腕（別 ADR）が扱う領域
  そのものである**」と書いた。本 ADR の実測に照らすと:

  - **✅ 当たった半分（件数の側）**: `iterative_scan` は確かに `LIMIT` を埋める。
    10%窓で 3件 → 40件、50%窓で 16件 → 40件。**両腕とも、3回とも、例外なく埋まった。**
    ADR 0059 が観測した「`LIMIT 40` に届かないままスキャンが終わる」という症状は、
    この腕で消える。
  - **🔴 外れた半分（正しさの側）**: **残余の正体は「探索が浅い」ことではなく、
    「HNSW がフィルタ下で真の近傍を取り逃す」ことだった。**`iterative_scan` は
    その取り逃しを直さない——`relaxed_order` でも `recall@40` は 0.500 / 0.350 に留まり、
    `ef_search` を20倍（40→800）にしても 0.575 で頭打ちになる。
    **そして `strict_order` に至っては、正しさを一切買わない。**

  ⟹ **「iterative_scan の腕が扱う領域そのもの」という名指しは、症状には当たっていたが
  病気には当たっていなかった。**本 ADR はその訂正を記録する。
  **ADR 0059 の本文は書き換えない**（ADR は追記して積む形である）。

- **⭐⭐ 採否と独立に価値が在る発見: 不正な GUC 値は静かに `off` へ落ちる**:

  **これは `iterative_scan` を採るかどうかと関係なく、記録しておく価値が在る。**

  `hnsw.iterative_scan` に不正な値を渡しても、**`ERROR` にならない。`WARNING` が出て、
  値は黙って `off` のままになる。**本 ADR の作業者が測った実出力:

  ```
  WARNING:  invalid value for parameter "hnsw.iterative_scan": "bogus"
  HINT:  Available values: off, relaxed_order, strict_order.
  → その後の SHOW hnsw.iterative_scan の結果は off
  ```

  ⟹ **タイプミスが「有効にしたつもりで、実際には効いていない」を静かに作る。**
  設定した側は `WARNING` をログで見落とせば、機能が効いていることを疑う理由を持たない。

  **⟹ もし将来この GUC を採用するなら、有効化した直後に `SHOW hnsw.iterative_scan` で
  実値を読み、意図した値になっていることを検査する歯が要る。**設定を書いただけでは、
  それが効いていることの証拠にならない。**この一文は、本 ADR が「採らない」と決めた後も
  残す価値が在る**——次に採ろうとする人が同じ穴を踏まないためである。

  **⚠ 関連して、もう1つ**: この GUC は **`vector.so` がそのバックエンドにロードされるまで
  登録されない**ため、**新規接続でいきなり `SHOW hnsw.iterative_scan` すると
  `ERROR: unrecognized configuration parameter` になる**（本 ADR の作業者が観測した）。
  同一セッションで `LOAD 'vector';` を先に打つか、ベクトル演算子を含むクエリを1本
  投げた後であれば見える。`SET` と startup parameter 経由の設定は未ロードでも通る
  （PostgreSQL のプレースホルダ機構）。**⟹ 「`SHOW` で検査する歯」を書くときは、
  この順序を踏み外すと歯のほうが落ちる。**

- **⭐ 有効化の口は既に在る（採らないと決めても、探し直さないために残す）**:

  段1は `this.db.execute(sql...)`（`vector-store.ts:96-102`）で pool から1文ずつ
  投げており、**セッションを保持していない。**⟹ `SET` を別途打つ形は往復が増え、
  pool がコネクションを張り直すたびに取りこぼす。

  **しかし新しい機構を作る必要は無い。**[ADR 0057](./0057-dedicated-schema-namespace.md) が
  `search_path` を **libpq の startup parameter `options`（`-c search_path=...`）**で
  渡す形を既に採っており（`packages/postgres/src/client.ts:55-66`）、その doc が理由まで
  書いている——「**`options` は接続確立時にサーバへ渡るパラメータなので、pool が新しい
  コネクションを張り直しても自動的に適用される**」。

  本 ADR の作業者が、**同じ口にこの GUC を載せられることを実測した**:

  ```
  PGOPTIONS="-c hnsw.iterative_scan=relaxed_order"
    → LOAD 'vector' 後の SHOW は relaxed_order（vector.so 未ロードの新規接続でも通り、
       ロード後も値が残る）
  PGOPTIONS="-c search_path=public -c hnsw.iterative_scan=strict_order"
    → search_path = public / hnsw.iterative_scan = strict_order（併存する）
  ```

  さらに **`client.ts:61-64` は、呼び出し側が既に `options` を渡していた場合に
  「その値の後ろに空白区切りで追記する」実装になっている**（上書きして黙って捨てない）。
  ⟹ **機構は既に揃っている。将来この判断が覆ったとき、口を探し直す必要は無い。**

- **⚠ 「順序が壊れる」の中身——段1の局所的な保証は壊れるが、下流は壊れない**:

  **`relaxed_order` は距離順を実際に壊す。**本 ADR の作業者が返り値の距離列を
  機械検査した（単調非減少かどうか）:

  | 窓 | 腕 | 逆転したペア数 | 最大の逆転幅 |
  |---|---|---:|---:|
  | 10% | `relaxed_order` | **12** | 0.008969 |
  | 50% | `relaxed_order` | **2** | 0.023837 |
  | 10% / 50% | `off` / `strict_order` | 0 | 0.000000 |

  **それでも `recall-runtime.ts` の下流は壊れない。**根拠3点（すべてコードの現物確認または実測）:

  1. **距離の値そのものは厳密に正しい。**返ってきた40件の `distance` を、別クエリで
     `memory_id` から引き直して突き合わせたところ、**誤差は 0 だった**（`relaxed_order`
     でも）。`SELECT e.embedding <=> $1 AS distance` は `SELECT` リストで毎行 exact に
     評価されており、スキャン方式に影響されない。⟹ **下流は並べ直せる。**
  2. **下流は実際に並べ直している。**`packages/core/src/recall-runtime.ts:347` の
     `scored.sort((a, b) => b.score.total - a.score.total)` が、段1の順序を
     `score.total`（減衰 × 類似度 × タグ × 鮮度）で総入れ替えする。最終提示順を決めるのは
     `recall-runtime.ts:470` の `units.sort((a, b) => b.rankScore - a.rankScore)` で、
     これも `score.total` 由来である。`annHits` の他の使用箇所（`:279` `:284` `:293`
     `:297` `:637` `:642`）は、**件数（`.length`）か集合（`memoryId` のキー）としてしか
     使っていない。**
  3. **`VectorStore` の interface（`packages/core/src/interfaces/vector-store.ts`）は
     「距離昇順で返す」ことを明文で約束していない。**`vector-store.ts:25-27` の
     「`ORDER BY` には距離演算子の結果をそのまま昇順で書く（式にしない）」は、
     **索引を使わせるための SQL の書き方の規約**であって、呼び出し側への順序の保証として
     書かれてはいない。

  **⚠ ただし、細い依存が1つ残る**（本 ADR の作業者が見つけた）:
  **`Array.prototype.sort` は安定なので、`score.total` が完全に同値の候補どうしの
  相対順序は、段1の順序をそのまま引き継ぐ。**実データで浮動小数点が完全一致するのは
  稀だが、フィクスチャでは起こりうる。**⟹ `relaxed_order` を採ると、同値タイの
  並びが非決定的になる。**これは測って確かめたわけではなく、
  `recall-runtime.ts:347` のソートが安定ソートであることから導いた**推論である。**

  ⟹ **本 ADR が `relaxed_order` を採らない理由は、順序ではない。**
  順序は下流の関心事ではないことが確認できた。**採らない理由は、
  `recall@40` が 0.500 / 0.350 に留まり、取りこぼしの本体が直らないことである。**

- **⚠ 適合テストの「順序の歯」は、この現象を測っていない**:

  `packages/testkit/src/vector-store-conformance.ts:141-143` に、明文の順序の歯がある:

  ```
  // 順序の歯: ユークリッドなら B が先になる組であり、A が先に返ることを検査する。
  expect(ids.indexOf(idA)).toBeLessThan(ids.indexOf(idB));
  ```

  本 ADR の作業者は当初これを「`relaxed_order` で赤くなるかもしれない候補」として
  挙げたが、**推測のまま残さず、歯と同じ組（q=`[1,0,0]`, A=`[10,0,0]`, B=`[1,1,0]`、
  HNSW コサイン索引付き）を再現して3腕で測った。**結果は**3腕すべてで
  `A (0.0000000)` → `B (0.2928932)`** で、`enable_seqscan = off` で索引を強制しても
  同じだった。

  **理由は `EXPLAIN` に出ている**: **この歯はデータが2行しか無いので、プランナが
  `Seq Scan` + `Sort` を選ぶ**（実出力: `Seq Scan on tooth (cost=0.00..1.02 rows=2)`）。
  ⟹ **HNSW 索引を一度も通らない。**

  **⚠ だからこの歯は「`relaxed_order` に対して安全である」のではない。
  この歯は、この現象を測っていないのである。**歯が緑であることは、
  `hnsw.iterative_scan` について何も言っていない。**⟹ 将来この GUC を採るなら、
  「2行で緑だったから大丈夫」と読んではいけない。順序を測りたいなら、
  HNSW 索引が実際に選ばれる規模のフィクスチャが要る。**

- **採らなかった案**:

  - **`relaxed_order` を既定オフの任意設定として実装する**: 採らない。
    「使う側が有効にできる口」を足すことは、**その口を有効にすると良くなる、という
    主張を暗に含む。**本 ADR の実測では、有効にしても `recall@40` は 0.500 / 0.350 で、
    厳密な 1.000 には遠い。**「件数だけ埋まって、中身は半分が別物」という状態を
    設定1つで選べるようにすることは、[ADR 0008](./0008-absence-taxonomy.md) の
    「無いを分類して返す」——静かに間違えるより、正直に足りないと言う——という
    この製品の姿勢に反する。**`off` のままなら `ann_unreached` が立つ
    （`recall-runtime.ts:644`）が、件数だけ埋めると**その omission すら立たなくなる。**
    ⟹ **`iterative_scan` は「静かに落ちる」を「静かに間違える」へ変える。**
  - **`strict_order` を採る（順序が壊れないので安全に見える）**: 採らない。
    上の `ef_search` 診断の通り、**`recall@40` が全水準で `off` と一致する。**
    順序が壊れないのは、正しさを何も足していないからである。
    **`LIMIT` を遠い候補で水増しするだけであり、`ann_unreached` を黙らせる分、
    現状より悪い。**
  - **`hnsw.ef_search` を上げる**: 本 ADR では決めない。**測りはした**（上の診断表）
    ——10%窓で `ef_search = 800` にすると `off` のままでも 40件返り、`recall@40` は
    0.575 になる。**`iterative_scan` を使わずに件数が埋まり、順序も壊れない**という
    点で `relaxed_order` より筋が良い。**しかし 0.575 は厳密の 1.000 に遠く、
    かつ時間は 5ms → 25ms に伸びる（この時間は同時実行下の観測であり格は低い）。**
    ⟹ **これは本 ADR が切り出した腕ではない。**別の判断として残す（下の「これが
    覆るとしたら」参照）。
  - **本 ADR を書かず、測定結果だけを報告して終える**: 却下。
    **ADR 0059 が「iterative_scan の腕が扱う領域そのもの」と名指しした見立てが
    半分外れていたことは、次にこの残余へ手を伸ばす人が最初に知るべき事実である。**
    記録しなければ、同じ腕がもう一度立てられる。

- **これが覆るとしたら / 残余は誰が塞ぐのか**:

  **⚠ まず、残っている穴の位置を正確にしておく。**本 ADR の実測では、
  **狭い窓（0.1% / 1%）に穴は無い**——ADR 0059 の式索引が使われ、`recall@40 = 1.000` で
  厳密な上位40件が返る。**残余は広い窓（分岐点 ≈1.15% より広い側）にある**、
  すなわち**プランナが HNSW 経由を選ぶ領域**である。

  **本 ADR の測定から言えること**（測っていないことは測っていないと書く）:

  1. **`hnsw.ef_search` を上げる。** ⟹ **測った。**10%窓で 800 まで上げると
     `iterative_scan` 無しで 40件埋まり、`recall@40 = 0.575`。50%窓で 0.700。
     **引き換えるもの**: 時間が 5ms → 25ms（10%窓、格の低い観測）。そして
     **0.575 / 0.700 は厳密ではない。**さらに `ef_search` はクエリ単位ではなく
     セッション/接続単位の設定なので、**狭い窓のクエリにも同じ値が掛かる**
     （狭い窓は既に 1.000 なので害は無いはずだが、**そこは測っていない**）。
  2. **プランナに厳密（式索引）経路を選ばせる。** ⟹ **上の「⭐ 負債を塞ぐ手は在る」節に
     分けて書いた。**要点だけ再掲する——**正解集合を作るために実際に
     走らせた経路であり、`recall@40 = 1.000` は定義上保証される。**
     **引き換えるもの**: この seed・100,000行で、厳密経路は **62ms（10%窓）/ 55ms（50%窓）**
     に対し、`off` は 5ms、`relaxed_order` は 24ms だった（すべて格の低い時間観測）。
     ⟹ **この規模では、厳密は `relaxed_order` の約2.5倍の時間で `recall` が 2倍になる。**
     **⚠ ただし分岐点が 1.15% と非常に低い**（見積り費用が 7935.60 対 7939.68 で拮抗）
     ため、プランナの選択を動かすには `random_page_cost` などのコストパラメータか、
     索引の作り方に踏み込む判断が要る。**そこは測っていない。**
     **⚠ そして 100万件級（`docs/roadmap.md:249` がオーナー決定として前提とする規模）で
     厳密経路の時間がどう伸びるかは、まったく測っていない。**本 ADR の実測は
     100,000行の1点のみである。
  3. **段1の `LIMIT`（`k'`）を上げる。** ⟹ **直接は測っていない。**ただし
     `ef_search` の診断が示唆することがある——HNSW 経路で返る件数を決めているのは
     探索の深さであり、`LIMIT` を上げても pgvector は `ef_search` の範囲でしか
     候補を持たない。**`ef_search` を上げずに `LIMIT` だけ上げても効かない可能性が高いが、
     これは推論であって測定ではない。**
  4. **ADR 0059 の索引をもっと選択的にする**: ⟹ **測っていない。**本 ADR は
     索引の形に手を付けていない。

  **⟹ 本 ADR の結論として、「いま知られている手では塞げない」とは書かない。
  手は在る（上の 1. と 2.）。ただし本 ADR はどれも採らない**——`iterative_scan` の腕を
  測ることが本 ADR の範囲であり、**`ef_search` と厳密経路は別の腕である。
  同じ ADR に混ぜると、どちらが効いたのか切り分けられなくなる**（ADR 0059 が
  腕を分けた判断と同じ理由）。**どれを次に立てるかはオーナーの判断である。**

  **本 ADR の決定が覆る引き金**:

  - **1,536次元・100万件級で測り直したとき**、`relaxed_order` の `recall@40` が
    本 ADR の 0.500 / 0.350 と大きく違う値を示したら、この決定を見直す。
    **本 ADR の実測は 256次元・100,000行・クエリベクトル1本の1点のみである。**
  - **埋め込みが時間軸と相関する現実のデータで測ったとき。** 本 ADR の seed の埋め込みは
    **時間軸と一切相関しない一様乱数**であり、しかも距離が極端に密集している
    （全100,000行で min 0.1736 / max 0.3355 / 平均 0.2462 / 標準偏差 **0.0177**）。
    10%窓の厳密な上位40件は 0.1869–0.2001 の範囲で、**平均から1標準偏差以内の薄い層**である。
    ⟹ **この条件下では「上位40件」がほぼ任意であり、`recall@40` は厳しすぎる物差しで
    ありうる。**`relaxed_order` が返した 0.192–0.206 と厳密の 0.187–0.200 は、
    距離としてはほとんど差が無い。**相関のある埋め込みでは `recall@40` の低さが
    実害に直結しないかもしれないし、逆かもしれない。測っていない。**
  - **プランの分岐点（≈1.15%）が本番のコストパラメータで大きく動くと分かったら。**
    分岐点が十分に広い窓へ移れば、そもそも HNSW 経路に落ちる場面が減り、
    残余そのものが小さくなる。

- **確かめていないこと（まとめ）**:

  - **1,536次元は未測定。** 実運用で使う OpenAI 埋め込みの次元数であり、
    埋め込みテーブルの行幅が違う——プラン選択・費用が変わりうる。
  - **100万件級は未測定。** `docs/roadmap.md:249` がオーナー決定として前提とする規模の
    1桁下（100,000行）でしか測っていない。**これは ADR 0059 と同じ限界である。**
  - **クエリベクトルは1本のみ**（`setseed(0.777)`）。**ADR 0059 と同じ制約が残っている。**
  - **同時実行下では未測定。** そして**時間の値は、同じサーバで別の測定が同時に
    走っている下での観測**なので、速さの根拠には使えない。
  - **`random_page_cost` / `effective_cache_size` を本番相当に寄せた場合に、
    分岐点や 10%窓の選択が変わるかは見ていない。**
  - **`hnsw.max_scan_tuples`（20000）と `hnsw.scan_mem_multiplier`（1）は既定のまま
    変えていない。** iterative scan はこの2つで打ち切られるため、**これらを上げたときに
    `recall@40` が改善するかは測っていない。**
  - **`ef_search` を上げたとき、狭い窓（式索引経路）に害が無いことは測っていない。**
  - **段1の `LIMIT`（`k'`）を上げる案は測っていない**（上の 3. は推論である）。
  - **埋め込みテーブルだけは手書きした**（`memory_embeddings_bench`）。本番では
    `registerEmbeddingSpace()` がテーブル名を決めて作る。DDL は `vector-space.ts` から
    書き写した。
