# ADR 0067: 予行フラグの fail-open を安全側へ反転する — そして `--dry-run` は信頼発行元の設定を検証できないと実測した

- **状態**: 採用 (2026-09)

- **⚠ この ADR が決めたこと・決めていないこと（先に書く）**:

  | | |
  |---|---|
  | **決めた（A）** | `workflow_dispatch` の `dry_run` 判定を安全側へ反転する。「安全（`"true"`）と明示されたときだけ予行」ではなく「**危険（`"false"`）と明示されたときだけ本番**」にする。それ以外（`"true"` / 空 / 未定義 / 想定外の値）はすべて予行へ倒し、**想定外だったことを `::warning::` で名指しする**。`release` 契機は本番のまま変えない |
  | **決めた（B）** | 「本番と同じ経路を、副作用だけ止めて走らせる」形の予行（`--dry-run`）は、**副作用の直前で判定される条件**（認証・認可・信頼関係、存在検査、サーバ側の検証全般）を**構造的に検出できない**と明記する。信頼発行元（Trusted Publisher）の未設定は、この形の実測でそれを裏付けた具体例である |
  | **一緒に入れた** | (A) の実装。判定を `scripts/publish-dry-run.mjs` の純関数 `decideDryRun()` へ切り出し、CLI 入口を `scripts/decide-publish-dry-run.mjs` に置き、`scripts/__tests__/publish-dry-run.test.mjs`（純関数を直接呼ぶ）と `scripts/__tests__/decide-publish-dry-run.test.mjs`（CLI を子プロセスで起動して `$GITHUB_OUTPUT` と `::warning::` を見る）に歯を17本置いた。**この ADR と同じ PR に入っている。**⚠ ただしこの ADR の草稿は実装と**並走**して書かれており（決定の記録と実装が別々に進んだ）、ファイル名を確定させたのは統合の時点である |
  | **決めていない** | 予行に「段1（信頼発行元の設定）の検算」という意味を持たせる新しい仕組みを追加すること。この ADR では追加しない（下の「採らなかった案」）。段1 の検算は、ADR 0066 がすでに設計していた「最初の本番 publish が黙って壊れず落ちる」という後退路に、事実上委ねたままにする |

- **文脈**:

  [ADR 0066](./0066-start-publishing-with-oidc.md) は publish を「段0（手元からの初回）→
  段1（npmjs.com で信頼発行元を設定）→ 段2（`workflow_dispatch` の予行を通す）→
  段3（GitHub Release で本番）」という順で設計した。段1 について、0066 はこう書いている
  （0066 の現物から逐語で引いた）:

  > **⚠ npm は保存時に設定を検証しない**（npm の文書に明記）。repo 名や workflow 名を
  > 間違えても保存でき、**publish を打った瞬間に初めてエラーになる。**⟹ 段2 の予行を必ず通すこと。

  そして「引き受けた負債」節はこう書いて、空欄のまま残していた（同じく逐語）:

  > 段2 の予行（`--dry-run`）でどこまで検出できるかも**確かめていない。**

  この ADR は、その空欄をこの器で実測して埋めた結果と、実測の過程で見つけた別の欠陥（A）を
  1本にまとめて記録する。

- **(A) 予行フラグの fail-open**

  `.github/workflows/publish.yml`（この器で確認。170〜174行、逐語）:

  ```bash
  DRY=""
  if [ "${{ github.event_name }}" = "workflow_dispatch" ] && [ "${{ inputs.dry_run }}" = "true" ]; then
    DRY="--dry-run"
    echo "予行（--dry-run）です。registry へは何も上がりません。"
  fi
  ```

  `dry_run` が文字列 `"true"` と**一致しないどんな値でも** `DRY` は空になり、下の
  `npm publish` は `--dry-run` を持たずに実行される——**つまり本番の publish になる。**
  workflow 定義側は `type: boolean` / `default: true` で UI の既定をチェック済みにしているが、
  それは「UI の初期状態がチェック済みである」だけであり、**機構がこの分岐を予行側へ
  強制しているわけではない。**`"True"` / `"1"` / 空文字列 / 未定義 / API 経由で別の文字列を
  渡した場合は、いずれも黙って本番へ落ちる。

  **⭐ なぜ今これが重いか（この器で実測）**:

  | 確認したこと | 結果 |
  |---|---|
  | `npm view @mnemora/{core,testkit,postgres,openai} versions`（この器で実行） | **4パッケージとも `["0.1.0"]` のみ** |
  | `packages/*/package.json` の `version`（この器で `grep` して確認） | **4パッケージとも `0.1.1`** |
  | main のどの commit で 0.1.1 になったか（`git log` で確認） | `e988f0363fd8a99919ca7319b250aaaa26bae17f`
  （「4パッケージを 0.1.1 へ上げる — npm 上の 0.1.0 に届いていない3件を出す (#77)」） |

  `workflow_dispatch` 経路は `packages/core/package.json` の版をそのまま使う
  （`publish.yml` の「Release の tag から版と dist-tag を決める」段。`release` イベントでなければ
  `require('./packages/core/package.json').version` を読む）。⟹ **いま `workflow_dispatch` を
  誤って本番側へ倒すと、registry に無い `0.1.1` へ実際に publish されうる。**

  これまでは「E403 `cannot publish over the previously published versions`」という**冪等分岐**が
  押し間違いの実害を吸収していた（同じ版を上げようとしても、既に上がっていれば弾かれて
  緑のまま終わる）。**しかし版がずれた今、その分岐は本番判定の誤りを吸収しない。**
  0.1.1 は registry に無いので、fail-open した本番 publish はそのまま通ってしまいうる
  （下の(B)の対照 run が示すとおり、通るかどうかは信頼発行元の設定状態にも依存するが、
  それに依拠して安全と見なすべきではない——設定が直った瞬間に、この穴は無条件で開く）。

  npm の `unpublish` は実質不可逆である。**押し間違いが取り返しのつかない公開になる経路は、
  機構で塞ぐべきである。**

- **(B) 🔴 予行は、信頼発行元の設定を検算していない**

  **⚠ 出所の書き分け**: 以下の run 2本の**conclusion とステップ単位の成否**は、
  この ADR を書いた作業者自身が `gh run view <run-id> --repo takecchi/mnemora --json jobs`
  で独立に確認した。**信頼発行元（Trusted Publisher）が run 34262743432 の時点で
  未設定だったという状態そのものは、依頼者（このタスクを切り出したクローン）の申告であり、
  この作業者は npmjs.com の設定画面を見ていない。**この区別を保ったまま記録する。

  | | run `34262743432`（予行） | run `34254090760`（本番、対照） |
  |---|---|---|
  | 引き金 | `workflow_dispatch`、`dry_run=true` | `release`（`v0.1.1`） |
  | 開始 | 2026-09-08 18:23:26 UTC | 2026-09-08 16:56:23 UTC |
  | `conclusion`（この作業者が確認） | **`success`** | **`failure`** |
  | `npm publish（依存の向きの順に、tarball を上げる）`段（この作業者が確認） | **`success`**（4パッケージとも `+ @mnemora/<name>@0.1.1` で「publish した」表示） | **`failure`**（`@mnemora/core@0.1.1` で停止） |
  | そのときの信頼発行元の状態 | 🔴 **未設定**（**依頼者の申告**。オーナーへ依頼中で返事待ちとのこと） | 同左（申告の対象は run 34262743432 側であり、この作業者は本番 run 時点の設定状態を別途確認していない） |

  **⭐ 本番 run のログをこの作業者が直接読んだ**（`gh run view --job <id> --log`）。
  実際に出ていたエラーは:

  ```
  npm error code E403
  npm error 403 403 Forbidden - PUT https://registry.npmjs.org/@mnemora%2fcore - OIDC permission denied for this action
  ```

  **これは実際に npm から返ってきたエラー文面であり、この作業者がこの器で確認した。**
  ただし「`OIDC permission denied` の原因が信頼発行元の未設定である」という**因果の特定**は
  npmjs.com の設定画面を見た依頼者の申告に基づくものであり、この作業者は
  「未設定だから 403 になった」を npm 側の設定表示から直接確認していない
  （リポジトリ名・workflow ファイル名の食い違いなど、設定は在るが誤っている場合でも
  同じ `OIDC permission denied` が返る可能性を、この作業者は排除できていない）。

  🔑 **これでも十分に核心を突いている**: 予行の `npm publish --dry-run` は、
  本番と**まったく同じコマンド**（`--access public --provenance --tag <tag> --dry-run`、
  同じ OIDC トークン取得経路）を通りながら、**全ステップ success で終わった。**
  同じ commit・同じ workflow・同じ認証経路の本番 run は、その**同じ publish 段**で
  落ちている。⟹ **予行と本番のあいだで唯一違うのは `--dry-run` の有無であり、
  信頼発行元の状態に起因する失敗を、予行は再現していない。**

  ADR 0066 が段2 に期待していた役目（「段1 を保存時に検証しない npm の代わりに、
  publish を実際に打つ前に間違いを見つける」）は、**この種類の間違いに対しては
  機能していない。**

- **⭐ (B) の一般化 — この ADR の芯**

  **「本番と同じ経路を、副作用だけ止めて走らせる」形の検査は、副作用の直前で判定される
  条件を検出できない。**

  - 認証・認可（トークン / OIDC の信頼関係 / 権限）
  - 存在検査（宛先が実在するか、既に在るか）
  - サーバ側の検証全般

  これらは**サーバへ実際に要求を投げて初めて判定される。**`--dry-run` はその要求を
  （少なくとも書き込みを伴う形では）投げないので、**構造的に**見えない。npm の
  `--dry-run` は「梱包・認証トークンの取得・payload の組み立てまでは行うが、実際の
  `PUT`（書き込み）は行わない」という設計であり、今回の実測はその設計どおりの結果である
  ——**npm の `--dry-run` が壊れているのではなく、この種の検算に使うと構造的に届かない
  範囲がある、ということである。**

  ⟹ **`--dry-run` が緑であることは「梱包と手元の配線が正しい」以上のことを
  言っていない。**サーバ側の権限・存在・検証の状態については、緑からも赤からも
  何も読み取れない。

  ⟹ **この形の検査を「本番前の検算」として設計に組み込むときは、何が検算されないかを
  先に書き出すこと。**ADR 0066 は「段2 の予行を必ず通すこと」と書いたが、
  「通ったら何が確認されたことになるのか」を書いていなかった——その欠落が、
  この ADR が埋めた空欄そのものである。

  **⭐ 追記（2026-09-08、[PR #80](https://github.com/takecchi/mnemora/pull/80)）: 同じ形が、検査の側でも起きていた。**

  上の一般化は「本番と同じ経路を、副作用だけ止めて走らせる検査」＝**予行**について書いたもので
  ある。⟹ **だが下の「引き受けた負債」の1つ目は、まったく同じ形が*歯*で起きていたことを
  記録している**——この ADR が置いた2本の歯はどちらも `publish.yml` を1バイトも読まないので、
  workflow から呼び出しを消して元のインライン `if` に戻す変異を、**全門が緑のまま通した**（実測）。

  ⟹ 🔑 **したがって (B) は、もう一段抽象化できる:**

  > **検査の入口が本番の入口とずれている限り、そのずれの分だけ検出できない。**

  | | 本番の入口 | 検査の入口 | ずれ ⟹ 見えないもの |
  |---|---|---|---|
  | **(B) 予行** | `npm publish`（サーバへ `PUT` を送る） | `npm publish --dry-run`（`PUT` を送らない） | 認証・認可・存在検査・サーバ側の検証 |
  | **負債1（歯）** | `publish.yml` の step が CLI を打つ | 歯が純関数／CLI を直接呼ぶ | **workflow の配線そのもの** |

  ⟹ **どちらも「本番と同じはず」の経路を検査しているつもりで、入口が1段ずれていた。**

  ⟹ ⭐ **判定を純関数へ切り出しても、呼び出し側がその関数を呼んでいることは自動的には
  保証されない。**皮（workflow）と芯（純関数）の間の配線には、**皮を入力に取る歯**を
  別に1本置く必要がある。

- **決定**:

  **1. `publish.yml` の `dry_run` 判定を、次の4つの振る舞いへ固定する。**
  （実装は同じ PR に入っている。上の表を見よ。）

  | # | 入力 | 振る舞い |
  |---|---|---|
  | ① | `workflow_dispatch` かつ `dry_run` が `"true"` | 予行（`--dry-run`） |
  | ② | `workflow_dispatch` かつ `dry_run` が `"false"` | 本番 |
  | ③ | `workflow_dispatch` かつ `dry_run` がそれ以外（空・未定義・想定外の文字列） | **予行へ倒す。かつ `::warning::` で「想定外の値を受け取った」ことを名指しする** |
  | ④ | `release` | 本番（変更なし） |

  **③がこの決定の芯である**——①と②だけなら、fail-open している現行コードでも
  `"true"`/`"false"` を正しく渡すかぎり同じ結果になり、直したことにならない。
  **「想定外の入力は安全側へ倒れる」ことと「安全側へ倒れたことが見える」ことの両方を
  固定する。**静かに安全側へ倒れるのは、静かに危険側へ倒れるのと同じくらい追いにくい
  ——`::warning::` を欠くと、③が発火し続けていることに誰も気づかないまま、
  「なぜか毎回予行になる」という別の形の不透明さを生む。

  **2. `--dry-run` が検算しない範囲を、`publish.yml` と ADR に明記する。**
  少なくとも「認証・認可（信頼発行元を含む OIDC の関係）」「存在検査」「サーバ側の検証全般」
  の3種を、**予行が緑でも保証しない**ものとして書き残す。

  **3. 段1（信頼発行元の設定）を検算する新しい仕組みは、この ADR では追加しない。**
  理由は下の「採らなかった案」。

- **採らなかった案**:

  | 案 | 採否 | 理由（この作業者の判断） |
  |---|---|---|
  | **予行の中で信頼発行元の設定を、npm の別の手段（API 等）で問い合わせる** | 却下（今回は） | **npm にこの用途で使える公開 API が在るかどうかを、この作業者は確かめていない。**在ったとしても、それは「実際に publish が通るかどうか」の代理指標にしかならず、**代理を検査する経路がもう一段増える**——今回の欠陥自体が「本番と別の経路を検査していた」ことに起因するものではなく「本番と同じ経路のはずが、副作用の手前で止めていた」ことに起因するので、さらに別の代理経路を足すと同じ種類の乖離リスクを増やしかねない。**確かめていない**という状態のまま採否を決めているので、将来この選択肢を再検討する余地は残す |
  | **捨て版（例: `0.0.0-check.N`）を本番 publish して検算する** | 却下 | registry を実際に汚し、**取り消せない**（npm の `unpublish` は実質不可逆、というこの ADR の前提そのものに反する）。検算の代償が、検算対象のリスクと同じ大きさになる案は採らない |
  | **段2 を諦め、段1 の検算を「最初の本番 publish が落ちること」に委ねる** | **事実上、現状維持として採用** | ADR 0066 はすでに「（provenance が）通らなかった場合、workflow は最初の本番 tag で落ちる」「黙って壊れるのではなく落ちる形にはしてある」と書いている。今回の対照 run（`34254090760` が `E403 OIDC permission denied` で落ちた）は、まさにその設計どおりに機能した実例である。**この ADR は、この後退路を置き換える新しい仕組みを提案しない**——ただし、この後退路は「本番 publish を実際に1回打って、失敗するかどうかで確認する」という形をしており、**予行が代替できないことを確認しただけで、後退路自体の費用（本番経路を1回実行する必要があること）は変わっていない。**これは残る負債として下に書く |

- **引き受けた負債**:

  - 🔴 **歯は判定関数と CLI を見ているが、`publish.yml` がその CLI を呼んでいることは
    見ていない。**⟹ **`publish.yml` から「予行か本番かを決める」step を丸ごと消しても、
    歯は1本も赤くならない**——`DRY_RUN` が空になり、`[ "${DRY_RUN}" = "true" ]` が偽になって
    本番へ倒れる。**つまり直す前と同じ fail-open へ、歯を1本も赤くせずに戻せる。**
    この ADR が固定したのは**判定の論理**であって、**workflow の配線**ではない。
    塞ぐなら `publish.yml` を YAML として読み、step の存在と `env:` の受け渡しを検査する
    歯を足すことになるが、**この回では入れていない**——workflow の構造を歯で固定し始めると
    「どこまで固定するか」を別に決める必要があり、それはこの回の範囲を超える。
    ⚠ **これは「(A) を直したことで新しく生まれた負債」である。**直す前は判定が
    `publish.yml` の中に直接書かれており、切り出せる先が無い代わりに、
    **配線が外れるという壊れ方も無かった。**

    ✅ **この負債は塞がった（2026-09-08、[PR #80](https://github.com/takecchi/mnemora/pull/80)）。**
    `scripts/__tests__/publish-yml-dry-run-wiring.test.mjs`（43本）が `publish.yml` を入力に取り、
    ①判定の段を yml から取り出し ②そのステップが `env:` で渡している名前を **yml から読み取り**
    （`EVENT_NAME` / `DRY_RUN_INPUT` を歯に書き写さない——書き写すと、名前が変わったときに
    歯のほうが古いまま緑になる）③yml に書いてある通りのコマンドと env 名で本物のスクリプトを
    起動し、`decideDryRun()` と**同じ入力集合**（event_name 4種 × dry_run 9種 = 36通り）を流して
    **答えが一致する**ことを見て ④判定の答えが `npm publish` の段まで届いていること
    （`steps.<id>.outputs.dry_run` という出力名と、それを受けて `--dry-run` を立てる shell 分岐）を、
    **yml から取り出した shell を実際に `bash` で走らせて**確かめる。
    ⭐ **そして、この負債の実在は肯定的に証明された。**上に書いた「step を丸ごと消しても歯は
    1本も赤くならない」を、**この歯が無い木**（`0670091` を別ディレクトリへ clone）で実際に
    撃ったところ、**6門すべて exit 0・落ちた歯は0本**（`typecheck` / `lint` / `format:check` /
    `test` / `build` / `pack:check`。ルートの vitest は `Test Files 7 passed` / `Tests 104 passed`）。
    新しい歯は変異3種すべてで赤くなった——呼び出しを消してインライン `if` へ戻す（41 failed）/
    `EVENT_NAME:` → `EVENT:`（10 failed）/ `id: dry-run` → `id: dryrun`（2 failed）。
    **`TypeError` は0件で、すべて名指しのアサーションである**（最初の実装では判定の段が消えたときに
    素の `TypeError` が出ていたので、名指しのアサーションに置き換えた）。
    ⚠ **残る弱さは歯自身が名乗っている**——YAML を構造として解析せず文字列で見ているので、
    書き方の変更に弱い。⟹ **壊れたときは「配線が変わった」か「書き方が変わった」かを見て、
    配線が変わっていないなら取り出し方のほうを直すこと（歯を消さないこと）。**
  - **決定1（①〜④）と実装が一致していることは、この ADR を書いた作業者が
    実装を読んで確認したものではない**（草稿は実装と並走して書かれ、統合の時点で
    突き合わせた）。⟹ **コードレビューとしての精査は、この PR のレビューで行う。**
  - **段1（信頼発行元の設定）の検算は、依然として「最初の本番経路を実際に1回走らせて、
    落ちるか通るかを見る」以外の手段が無い。**この ADR はそれを代替する仕組みを追加していない
    （採らなかった案）。⟹ 信頼発行元の設定を直したあと、**それが正しく効いたことを
    確認する唯一の方法は、実際に本番 publish（Release 経由）を1回打つことである**
    ——そしてそれは4パッケージ全部に対して不可逆の書き込みを試みる、ということでもある。
  - **npm の `--dry-run` がどこまで実要求を送るか（トークン取得のみで止まるのか、
    別のエンドポイントへの読み取り要求は送るのか等）を、npm の実装レベルで確かめていない。**
    この ADR の一般化は「送っていないなら検出しない」という論理的な帰結と、
    今回1本の対照 run から観測した実測に基づくものであり、**npm の `--dry-run` の
    内部実装を読んだ上での結論ではない。**
  - **「想定外の値」が実際に発生しうる経路（誰が・どう `workflow_dispatch` を叩けば
    `dry_run` に `"true"`/`"false"` 以外の値が入るか）を、この ADR では列挙していない。**
    GitHub Actions の REST API 経由の呼び出しがどこまで型を強制するかは確認していない。
  - **(A) の fail-open が実際に踏まれた形跡（過去に想定外の値で本番へ落ちた実行）が
    あるかどうかは調べていない。**この ADR は将来の事故を防ぐために書いており、
    過去の事故の有無は本 ADR の対象外である。

- **これが覆るとしたら**:

  - **npm が `--dry-run` の意味を拡張し、信頼関係（Trusted Publisher）の検証まで
    実際にサーバへ問い合わせるようになったとき。**そのときは(B)の一般化のうち
    「認証・認可」の項目が外れ、段2 が段1 の検算として機能するようになる。
  - **npm がこの用途で使える公開 API（信頼発行元の設定を読み取り専用で確認できるもの）を
    提供し、それをこの作業者もしくは別の作業者が確認したとき。**「採らなかった案」の
    1番目を再検討できる。
  - **4パッケージの版が揃って `0.1.1` が正しく registry に上がり、次のずれが
    生じるまでの間。**その間は「registry の版と main の版がずれている」という
    今回の緊急性の前提（冪等分岐が効かない窓）は一時的に閉じるが、**fail-open 自体は
    版のずれと無関係に存在する欠陥なので、この ADR の決定1 の必要性は変わらない。**
  - **オーナーが「本番経路を1回実際に走らせて段1 を確認する」という残る負債の解消を
    別途決めたとき**（たとえば専用の使い捨て組織・パッケージ名での確認など）。
    この ADR ではその設計を提案していない。
