# ADR 0083: 既定 `TokenCounter` を文字種で重み付けする — 「4文字 ≒ 1トークン」は日本語で予算を静かに超えさせる

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-10

**⚠ 各主張の出所を分ける。**「私が実行して確かめた」と「読んだだけ」と「人から受け取った前提」を
混ぜない（[AGENTS.md](../../AGENTS.md)）。

---

## 文脈

### 現物（**私が読んだ。`main` の `d2ec8cf`**）

```ts
export const heuristicTokenCounter: TokenCounter = {
  count(text: string): { tokens: number; counter: "heuristic" } {
    const tokens = Math.ceil(text.length / 4);
    return { tokens, counter: "heuristic" };
  },
};
```

そして `RecallBudget.maxMemoryTokens` / `promptBudgetTokens` は、**このカウンタの値で判定される**
（`packages/core/src/recall-runtime.ts` の `effectiveTokenBudget` → 段4 の `fits()` → `unitTokens`）。

⟹ **カウンタが少なく数えれば、予算はその分だけ緩む。**

### 何が既に決まっていて、何が決まっていないか（**全81件の ADR と docs を当たった**）

決まっている（[docs/architecture.md](../architecture.md) §5.9・[docs/recall.md](../recall.md) §6）:

> 既定実装は文字数ベースの推定（`counter: 'heuristic'`）。（…）**推定値を実測値の顔で返してはならない**

**決まっていない**: **「4文字 ≒ 1トークン」という係数そのもの**。この式は
`heuristic-token-counter.ts` のコードと docstring にしか無く、**ADR で採択された記録は無い。**
[ADR 0073](./0073-digest-band-bounded-without-taxonomy.md) が
「トークン概算 = ceil(chars / 4)（heuristicTokenCounter の実装そのまま）」と書いているのは、
**既存の実装を所与として引用しているだけ**であって、式を検討・採択した記録ではない。

⟹ **本 ADR は原則を変えない。既存の器（文字数ベース・`counter: 'heuristic'`）の中で、
係数だけを実測に合わせる。**

### 報告（**受け取った前提**。出所は Issue #108、報告者は `the-phage-dev`）

社内 Slack AI エージェントへの導入検討中の外部報告。**mnemora にとって初めての外部からの
実利用フィードバックである。**主張は「日本語（CJK）は 1文字あたり 0.6〜1トークン程度なので、
4文字≒1トークンでは実際の 2.5〜4倍ほど少なく見積もる」「導入先では CJK 0.7 / 字、
非 CJK 0.28 / 字 を使っている」。

⚠ **この 0.7 / 0.28 は報告者が自分の用途で使っている値であり、mnemora にとって正しい保証は無い。
本 ADR はこの数字を採らない。**自分で測った（下記）。

### なぜ重いか

[docs/north-star.md](../north-star.md) の物差しは「**使う側が、会話ログを全部プロンプトへ
積むのをやめられたか**」である。予算が守られないなら、その物差しの根が抜ける。
そして**このリポジトリの主たる利用場面は日本語である**（`examples/chat` の会話コーパス
`src/scenario.ts` は全文日本語、docs も全文日本語）。**既定が、主たる利用場面で外れていた。**

## 実測2: なぜ 0.9 / 0.25 か（**私が決めた。根拠は私が計算した**）

### 非 CJK = 0.25（**据え置き**）

**壊れていない側を動かさない。**実測1のとおり `en` の合計比は 1.128 で、**過小評価していない**
（予算に対して安全側に 13% 振れている）。全121件の最小二乗回帰が出す最適値は 0.269 だが、
**0.25 に据え置くと純 ASCII のテキストは従来と1トークンも変わらない**——
互換性が無料で手に入る。差は 121件全体の合計比で 0.991 対 1.02 程度であり、
**この差のために互換性を捨てる理由が無い。**

### CJK = 0.9

**3つの独立な根拠が同じ値を指した。**

1. **回帰**: 121件全件の最小二乗（`o200k_base`、切片なし）は `a = 0.8885, b = 0.2690`（R² = 0.990）。
   **小数第1位に丸めて 0.9。**（`cl100k_base` では `a = 1.2099` になる。下の「対象トークナイザ」参照。）
2. **全体の一致**: `b = 0.25` に固定して `a` を振ったとき、**121件全体の合計比が最も 1.00 に近いのが 0.9**。

   | `a` | 0.70 | 0.80 | 0.85 | **0.90** | 0.95 | 1.00 |
   |---|---|---|---|---|---|---|
   | 全121件の合計比 | 0.88 | 0.94 | 0.96 | **0.991** | 1.02 | 1.04 |
   | `ja` の合計比 | 0.92 | 1.06 | 1.12 | **1.182** | 1.24 | 1.30 |
   | `ja` の1件ごとの最悪の過小評価 | −21.4% | −12.5% | −7.1% | **0%** | 0% | 0% |

3. **過小評価をしない下限**: `a = 0.9` は、**`ja` 16件のうち1件も過小評価しない最小の候補**である。
   予算の話では**過小評価と過大評価は等価ではない**——過小評価は「守ると言った予算を守らない」
   （＝約束が破れる）であり、過大評価は「使えたはずの枠を使い切らない」（＝品質の損）である。
   [docs/north-star.md](../north-star.md) は「⚠ トークンを削ったこと自体は成果ではない」と
   書いているので過大評価も無料ではないが、**破れる約束のほうが重い。**
   だから中央値（0.77）ではなく、分布の上側を覆う値を採った。

### 代償（**測った**）

**日本語の合計を 18% 過大評価する。**とくに短い定型句で大きい:

| サンプル | 実測 (o200k) | 推定 | 誤差 |
|---|---|---|---|
| `了解です、ありがとう。` | 5 | 10 | **+100%** |
| `はい、大丈夫です。` | 5 | 9 | +80% |
| `今日はいい天気ですね。` | 6 | 10 | +67% |

**理由**: よく使われる日本語の定型句は `o200k_base` で1語まるごと1トークンに載る。
**文字数ベースの推定は、この「よく出る語ほど効率が良い」という性質を原理的に表現できない。**
これは係数の選び方の問題ではなく、**文字数ベースであることの限界**である。

⚠ **中国語では 0.9 はぎりぎり足りているだけである**（合計比 1.017、下限 1.00 に対して余裕 1.7%）。
コーパスの中身が少し変われば反転しうる。**歯のコメントにもそう書いた。**

|---|---|---|
| `th` タイ語 | 0.564 | **過小評価のまま** |

| `ru` キリル文字 | 0.864 | **過小評価のまま** |

## 決定

1. **既定 `TokenCounter` を、コードポイントを CJK / 非 CJK に分けて重み付けする式に変える。**
   **CJK = 0.9 トークン/コードポイント、非 CJK = 0.25 トークン/コードポイント**（従来の 1/4 据え置き）。
   `Math.ceil` は維持する（予算に対して切り上げは安全側）。

2. **`counter: 'heuristic'` を返す契約は変えない。**
   精度が上がっても**これは依然として推定であり、実測値の顔をしてはならない**
   （[docs/architecture.md](../architecture.md) §5.9・[docs/recall.md](../recall.md) §6）。
   ⚠ **精度が上がったことで「もう `exact` と名乗ってよい」と読まれるのが、この変更のいちばん危ない副作用である。**

3. **係数は 20分率の整数比（18/20・5/20）で書く。**`0.9 * n` のような浮動小数の乗算を避ける
   ——丸め差が環境によって出力を変える余地を、整数演算で断つ。

4. **文字数は「コードポイント」で数える**（`for...of`）。`String.length` の UTF-16 コード単位ではない。
   サロゲートペア（CJK統合漢字拡張B、絵文字）を2文字と数える理由が無い。
   ⚠ **この結果、非 BMP の文字を含むテキストは非 CJK であっても従来と値が変わる。**
   従来と完全に一致するのは「非 CJK かつ BMP 内の文字だけ」のテキストである（純 ASCII を含む）。

5. **CJK の範囲表は手で書き写した固定表とする**（19区間、各行にブロック名）。Unicode の
   ブロック改定には追随しない。**ハングルを CJK に含める**（`ko` の実測 1.057 は許容範囲に入る）。

6. **依存を増やさない。**`js-tiktoken` は本体の依存にも devDependency にも足さない
   （[docs/autonomy.md](../autonomy.md) §3「依存の追加方針の変更」はオーナー専権）。
   実測は**記録（fixture）として持ち込み**、再生成手順を `scripts/record-token-count-reference.mjs`
   に置く。⚠ **このスクリプトはどの門にも入っていない。**手で `js-tiktoken` を入れないと走らない。

7. **対象トークナイザは `o200k_base`（gpt-4o / gpt-4o-mini 系）とする。**
   旧世代の `cl100k_base` に対しては日本語で約12%過小評価する（合計比 0.878）。
   ⚠ **これは残る欠落である。**`cl100k_base` に合わせるなら `a ≈ 1.21` が要るが、
   そうすると `o200k_base` の利用者に対して日本語を 35% 過大評価することになる。
   **どちらかしか選べない。**現行世代を採った。
   **Anthropic のトークナイザに対しては測っていない**（`packages/anthropic` が在るので、
   これを書かないと嘘になる）。

8. **トークン予算の経路に歯を置く。**調査で分かったこと: **`maxMemoryTokens` /
   `promptBudgetTokens` を実際に行使するテストは、変更前のリポジトリ全体で0本だった**
   （既存の予算の歯は全部 `maxMemoryChars`）。**Issue #108 が壊れると言っている当の経路に、
   歯が無かった。**

## 歯が何を守っているか

`packages/core/src/__tests__/heuristic-token-counter.test.ts`（9本）と
`recall-pipeline.test.ts`（2本）。**許容範囲は私が決めた。理由は各歯のコメントに書いた。**

| 歯 | 何を測るか | 帯 | 実測 |
|---|---|---|---|
| 契約 | 常に `counter: 'heuristic'` | — | — |
| 空文字 | 0 トークン | — | — |
| 互換性 | 非CJK（`en` 全件）は従来どおり `ceil(len/4)` | 完全一致 | 一致 |
| 方向 | 同じ文字数なら日本語が英語の3倍以上 | ≥3倍 | 3.6倍 |
| コードポイント | SIP の漢字4文字が4トークン（UTF-16 単位なら2になる） | =4 | 4 |
| **全体の一致** | 121件の合計比 | **0.95〜1.10** | **0.991** |
| **過小評価しない** | `ja`/`zh`/`ko` の合計比 | **1.00〜1.35** | ja 1.182 / zh 1.017 / ko 1.057 |
| 1件ごと | `ja` 全16件で 推定 ≥ 実測 | 0件の違反 | 0件 |
| 断り書き | `th` は依然 1.00 未満 | <1.00 | 0.564 |
| 記録 | 旧式の `ja` 合計比 | <0.40 | 0.353 |

**帯の決め方**:
- **0.95〜1.10（全体）**: 下限は「合計で 5% を超えて予算を割り込まない」、
  上限は「その代償として 10% を超えて枠を捨てない」。**予算は合計に効くので、合計で縛る。**
- **1.00〜1.35（`ja`/`zh`/`ko`）**: 下限 1.00 は **Issue #108 の要求そのもの**
  （日本語主体の用途で予算を割り込まない）。上限 1.35 は実測2の代償を上から縛る。
- ⚠ **「断り書き」の歯（`th` < 1.00）は欠陥を固定する歯ではない。**
  JSDoc が「タイ語は過小評価する」と書いていることが**実態と一致していること**を測る歯である。
  タイ語が直ったらこの歯は赤くなる——**そのときは実装ではなく JSDoc を直せ、という合図。**
- ⚠ **「記録」の歯（旧式 < 0.40）は実装を一切参照しない。**実装をどう壊しても赤くならない。
  **回帰検知の歯ではなく、「直す前は何が起きていたか」を数値で残すためだけの歯である。**
  歯のコメントにもそう書いた。

## この PR が*しない*こと

- 🔴 **`usage.share` が 1 を超えうる穴は直さない**（下の「引き受ける負債」を見よ）。
- **`RecallUsage` に `budgetExceeded` を足さない**（Issue #108 の案3）。型を触るので影響範囲が広い。
  **まず既定を実態へ寄せるほうが効く。**必要なら別 ADR。
- **タイ語・アラビア語・キリル文字を直さない。**3つ目のバケットが要る（下記）。
- **`examples/chat/README.md` の `compare` の実測表を測り直していない。**
  あの表の「tokens(概算)」列は旧カウンタの値であり、**この変更で必ず動く**。
  ⚠ **しかしこの器には Postgres が無く（`compare` は DB を要する）、測り直せなかった。**
  README には**測り直していないことを明記した**。chars 列と比率列（北極星の主測定）は影響を受けない。
- **[ADR 0073](./0073-digest-band-bounded-without-taxonomy.md) を書き換えない。**
  同 ADR の「トークン概算 = ceil(chars / 4)」は**当時の記録**である。
  ⚠ ただし目次帯の上限は**文字数**で決まっており（`char_budget`）、トークンは見積もりの
  記述にしか出てこないので、**実装の挙動は変わらない**（現物を読んで確認した）。

## 検討して採らなかった案

- **報告者の案1（JSDoc / README に注記するだけ）。** **却下**（ただし**注記は入れた**）。
  既定が外れたままなら、注記を読まなかった利用者は静かに予算を超え続ける。
  **注記は「直したこと」の代わりにはならないが、「直しきれなかった範囲」の説明としては要る。**
  ⟹ **案2 を採り、案1 は案2 の一部として実施した。**
- **報告者の案3（`usage` に `budgetExceeded` を足す）。** **却下（今回は）。**
  「予算判定が推定に基づく」ことの露出として筋は良いが、`RecallUsage` の型を触るので影響範囲が広い。
  ⚠ **そして、いま `budgetExceeded` を足すと `false` を返す**——推定が予算内だと言っているのだから。
  **推定が外れていること自体は、その真偽値では検知できない。**先に既定を実態へ寄せるのが順序である。
- **報告者の係数（CJK 0.7 / 非CJK 0.28）をそのまま使う。** **却下。**
  自分で測ったら 0.7 は `ja` の合計比 0.92（**まだ 8% 過小評価**）、
  1件ごとの最悪で **−21.4%** だった。**他人の用途で当たっている値が、こちらで当たっている保証は無い。**
- **`a` に中央値（`ja` の 0.77）を採る。** **却下。**中央値を採ると**定義上、半分のサンプルが
  過小評価される。**予算の話で「半分は約束を破る」は選べない。
- **`a = 1.0`（切りの良い数字）。** **却下。**日本語の合計比が 1.30 になる——
  **枠の 23% を使わずに捨てることになる。**回帰（0.8885）からも遠い。
- **`a = 0.8`。** **却下。**`ja` の1件ごとの最悪の過小評価が **−12.5%**、`zh` は **−33%** 残る。
  合計比も 0.94 で、全体として過小評価側に寄る。
- **🔴 モデルB: 「ASCII / 非 ASCII」で分ける（CJK 判定表を持たない）。** **却下。実測で落とした。**
  CJK を含むクラスではモデルA とほぼ同等の精度が出る（非ASCII ≈ CJK だから）。
  **しかしキリル文字・タイ語・アラビア語を「非 ASCII」として CJK と同じ重みに昇格させるため、
  o200k で +70%〜+180% の過大評価になる**（`a=1.0` 付近で最大 +218%）。
  モデルA の同クラスの誤差は −19%〜−57% である。
  ⟹ **CJK 判定表を書く複雑さは、この3スクリプトに対して数字の上で正当化された。**
  ⚠ **ただしモデルA がこの3つを正しく扱っているわけではない。英語と同じ重みに落として
  誤差を小さく見せているだけである。**
- **3つ目のバケット（キリル・タイ・アラビア用）を足す。** **却下（今回は）。**
  実測は `ru`/`th`/`ar` が各5件しかなく、**すべて自作文である。**
  **5件の自作文から係数を出して「実測に基づく」と名乗るのは、この ADR がやめようとしていることそのもの。**
  ⟹ **測ってから足す。測っていないなら足さない。**
- **`tiktoken` / `js-tiktoken` を（dev でも）依存に足して、CI で対照を計算する。** **却下。**
  [docs/autonomy.md](../autonomy.md) §3 が「依存の追加方針の変更」をオーナー専権と明記している。
  ⚠ **そして依存を増やさないことは、この既定カウンタが存在する理由そのものである**
  （`packages/core` は zod 以外の実行時依存を持たない。`dependency-boundary.test.ts` が機械的に検査）。
  ⟹ **記録（fixture）＋再生成スクリプト**という形にした。カセット
  （[ADR 0051](./0051-recorded-provider-cassette.md)）と同じ扱いである。
- **`cl100k_base` に合わせる（`a ≈ 1.21`）。** **却下**（決定7）。
  現行世代（`o200k_base`）の利用者に対して日本語を 35% 過大評価する。
- **`String.length`（UTF-16 コード単位）のまま数える。** **却下**（決定4）。
  サロゲートペアを2文字と数える理由が無い。**ただし従来との完全一致は失われる**（決定4 の⚠）。

## 引き受ける負債・覆えていない範囲

- 🔴 **`usage.share` が 1 を超えうる穴は、この PR では直していない**（**再現を確認した**）。
  段4 の**強制**は `sum(count(digest_i))`（1件ずつ数えて足す）だが、`usage.share` の**分子**は
  `count(digests.join("\n"))`（連結を1回数える）である。**各 digest の重みがちょうど整数になると
  逆転する。**実際に再現した: 非 CJK 20文字の digest 2件（各5トークン）に
  `maxMemoryTokens: 10` を渡すと、強制側は `5+5=10 ≤ 10` で両方残すが、分子は改行込み41文字で
  `ceil(41/4) = 11` になり、**`usage.share = 1.1`** が返る。
  `RecallUsageSchema` の `.max(1)` と `RecallUsage.share` の JSDoc（「この値は 1 を超えない」）が破れる。
  `recall()` の出力は zod で検証されていない（`recall-runtime.ts:201` が検証するのはクエリだけ）ので
  **例外にはならず、値が静かに壊れる。**
  ⚠ **これは本 ADR の変更が作った穴ではない。**旧式 `ceil(len/4)` でも算術的に同じ逆転が起きる
  （**式が同一であることから確実だが、`main` をチェックアウトして走らせる形の確認はしていない**）。
  **どちらの数え方を正とするかは別の判断**なので、ここでは直さずに提起する。
- **`cl100k_base` に対しては日本語を約12%過小評価したままである**（決定7）。
- **タイ語 0.564 / アラビア語 0.813 / キリル文字 0.864 は過小評価のままである**（実測3）。
- **絵文字を含むテキストは 0.987**（ほぼ合っているが、絵文字そのものは非 CJK 扱いで
  0.25/字 で数えている——合っているのは**日本語部分の過大評価が絵文字の過小評価を
  打ち消しているから**であって、絵文字が正しく数えられているからではない）。
- ⚠ **コーパスの `en`/`zh`/`ko`/`ru`/`th`/`ar`/`emoji_ja` は全部自作文である。**
  実運用の分布をどれだけ代表しているかは**確かめていない。**
  ⟹ **`zh`/`ko` の合計比（1.017 / 1.057）は、この自作コーパス限定の数字である。**
- **短い定型句の過大評価（最大 +100%）は残る**（実測2）。文字数ベースであることの限界。
- **`examples/chat` の `compare` の実測表は測り直していない**（Postgres が無い器で作業した）。
- **`packages/anthropic` のトークナイザに対しては測っていない。**

## これが覆るとしたら

- **`o200k_base` が旧世代になったとき。** 係数は世代に紐付いている。次世代のトークナイザで
  日本語の圧縮率が変われば、0.9 は外れる。**フィクスチャを録り直して回帰を引き直せば済むようにしてある**
  （`scripts/record-token-count-reference.mjs`）。
- **`counter: 'exact'` の実装が同梱されたとき。** 「依存を増やさない」が覆れば、
  `tiktoken` を使う `TokenCounter` を別パッケージ（`@mnemora/tiktoken` 等）で出せる。
  そのとき既定をどちらにするかは**製品の判断**であり、[docs/roadmap.md](../roadmap.md) §5 行きである。
- **CJK 以外の非ラテン文字の利用者から実利用の報告が来たとき。**
  そのときは**3つ目のバケット**を、**その利用者の実物で測ってから**足す。
- **`usage.share` の穴を塞ぐと決めたとき。**「強制と計測で数え方が違う」ことを
  どちらに寄せるかが決まると、`unitTokens` か `usage` のどちらかが動く。
