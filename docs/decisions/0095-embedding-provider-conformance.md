# ADR 0095: `EmbeddingProvider` の適合テストを新設する — 順序の検査は決定性を前提にしているので、決定性を「宣言させる」

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-10

**⚠ 各主張の出所を分ける。**「【実測】」と書いたものは**この作業でこの器から実行して取った**もの。
「【実測・委】」は**委譲先の作業者が測り、書き手が受け取った**もの。

**この ADR は [Issue #116](https://github.com/takecchi/mnemora/issues/116) を塞ぐ。**
#116 は [ADR 0072](./0072-anthropic-llm-provider.md) の負債1 と
[ADR 0085](./0085-local-embedding-provider.md) の負債4 が指していた同じ穴である。

---

## 問い

`EmbeddingProvider` の実装が満たすべき契約を、**実装を問わず同じ歯で**検査できるか。
できるなら、**何を要求してよく、何を要求してはいけないか。**

---

## 文脈

### 無かったもの

`packages/testkit` の適合テストは **Store 系5種だけ**で、provider 向けは 1 本も無い。
一方 `EmbeddingProvider` の実装は**実質4つ**ある——
`@mnemora/openai` / `@mnemora/local-embedding` /
testkit の `DeterministicEmbeddingProvider` / `RecordedEmbeddingProvider`。
**それらが同じ契約を満たすことを検査する歯は、どこにも無かった。**

### ADR 0072 が却下した理由は、埋め込みには当たらない

ADR 0072 は provider 向けの適合テスト新設を却下し、負債1 として残した。
その理由は「**LLM は非決定的なので、同じ出力を要求できない**」である。

⟹ **埋め込みについては、その理由がそのままでは当たらない。**
`DeterministicEmbeddingProvider` も `RecordedEmbeddingProvider` も決定的であり、
`@mnemora/local-embedding` はプロセス内の ONNX 推論で、
[ADR 0090](./0090-embedding-input-token-limit.md) の live テストが
**同じ入力に対してビット単位で一致するベクトル**を前提に境界を測れている。

⚠ **ただし「決定的な実装が在る」は「契約として決定性を要求してよい」と同じではない。**
そこが本 ADR の芯である（下記）。

### 🔴 芯: 順序の検査は、決定性を前提にしている

「**返る順序が入力順に対応する**」は、`embed(ctx, texts)` の契約の要である
（対応がずれると、呼び出し側で memory とベクトルが 1 つずれて結び付く。
`@mnemora/local-embedding` の `embed()` のコメントが、まさにこの壊れ方を名指ししている）。

**ところが、それを実装非依存に検査する方法は「同じ入力を並べ替えて、結果も並べ替わるか」しかない。**
⟹ **同じ入力に毎回違うベクトルを返してよい実装に対しては、この検査は意味を持たない。**

**⟹ 順序と決定性は切り離せない。**適合テストは、この事実を隠してはならない。

---

## 決定

### 決定1: `describeEmbeddingProviderConformance(options)` を新設する

`packages/testkit/src/embedding-provider-conformance.ts`。
Store 系の `describe*Conformance` と同じ形（`describe` を1つ生やす関数）にする。

**無条件に走る歯（7本）** ——`packages/core/src/interfaces/embedding-provider.ts` の契約と、
壊れ方が説明できるものだけ:

| # | 何を固定するか |
|---|---|
| 1 | `space.provider` / `space.model` が空でない文字列、`space.dimensions` が**正の整数** |
| 2 | `space` が `embed()` の**前後で変わらない**（3欄とも）——「1インスタンス = 1 space」 |
| 3 | `embed(ctx, [])` が `[]` を返す |
| 4 | `embed(ctx, [a,b,c])` が**ちょうど3件**返す |
| 5 | 各ベクトルの長さが `space.dimensions` と**一致する**——「次元を動的に変えない」 |
| 6 | 各成分が**有限の数**（`NaN` / `Infinity` を含まない） |
| 7 | 1件渡すと1件返る |

**`deterministic: true` のときだけ走る歯（2本）**: 同じ入力の再現性と、順序の対応。

### 決定2: 🔴 `deterministic` は**省略できない宣言**にする（`?` を付けない）

**なぜ必須か。**任意にすると、`LocalEmbeddingProvider` の
`maxInputTokens` で踏んだのと同じ形になる（ADR 0090 決定2）——
**「この実装は決定的でない」と「宣言し忘れた」が、同じ `undefined` に潰れる。**
⟹ **区別できない 2 種を 1 つにしない。**型で宣言を強制する。

### 決定3: `false` のとき、歯は**消さずに `it.skip` で名前を残す**

**テスト名が消えると、「そもそも歯が無い」のか「走って通った」のかがログから区別できない。**
これは `packages/local-embedding` の live テストが
`describe.skip` や `if (!live) return` を採らなかったのと同じ理由である。

⟹ **「測っていない」ことを、テスト名で名乗らせる。**

### 決定4: `texts` を**呼び出し側に注入させる**（suite が文字列を決め打ちしない）

`RecordedEmbeddingProvider` は**記録に無い入力で例外を投げる**（ADR 0051）。
⟹ **何を埋め込ませてよいかは、カセットを持っている側にしか決められない。**
suite が固定の文字列を持つと、その 1 実装に当てられなくなる。

### 決定5: ⛔ **バッチ不変性は検査しない**

`embed([a,b])` が `embed([a])` と `embed([b])` の連結に一致するか——**測らない。**

**理由**: 本物の埋め込みモデルは**バッチを padding して処理する。**
`@mnemora/local-embedding` の transformers.js 経路は
`this.tokenizer(texts, { padding: true, … })` で呼ばれており
（ADR 0090 §1.4）、**バッチの中身によってテンソルの形が変わる。**
⟹ **成立するとは限らず、この作業では測っていない。**
**⛔ 測っていないものを契約にしない。**（§6 の「これが覆るとしたら」に置いた。）

### 決定6: ⛔ 実 adapter 2つには、この PR では当てない

`@mnemora/openai` と `@mnemora/local-embedding` に当てるのは**別の作業**にする。

**理由は設計ではなく進行である**——本 ADR の作業と並行して
`@mnemora/local-embedding` は ADR 0090 の PR が触っており、
`@mnemora/openai` は別の作業の範囲に在る。**同じファイルを2本の PR が触ると衝突する。**

⟹ **本 PR が当てたのは testkit 自身が持つ 2 実装だけである。**
⚠ **これは「4つ全部が契約を満たすことを確かめた」ではない。**§5 の負債1。

## 検討した選択肢

### 3.1 決定性を**無条件に**要求する

**却下。**`@mnemora/openai` の `OpenAIEmbeddingProvider` を**実 API に対して**走らせたとき、
ビット単位の再現性が保証されているという根拠を、この作業では持っていない。
⟹ **無条件に要求すると、適合テストが「実装が守れない契約」を主張することになる。**
契約が嘘になるくらいなら、**宣言させて、宣言に応じて測る範囲を変える。**

### 3.2 `deterministic` を任意（`deterministic?: boolean`）にする

**却下。**決定2 の通り、「決定的でない」と「宣言し忘れた」が潰れる。
**⟹ 忘れた実装は、黙って歯を 2 本失う。**

### 3.3 Store 系の適合テストと同じ形をそのまま持ってくる

**却下。**Store 系は「同じ DB に対する同じ操作」を測るので、実装の別が振る舞いを変えない。
provider は**「実 API を叩くもの」と「叩かないもの」が混在**しており、
**適合テストの適用範囲そのものを設計しないと持ってこられない。**
ADR 0072 が却下したのは、まさにこの設計をしていなかったからである。

### 3.4 「ゼロベクトルを返さない」を歯にする

**却下。**[ADR 0040](./0040-zero-vector-never-returned.md) は
**ゼロベクトルが絡む候補が `recall()` の結果に出ない**ことを決めているが、
**それは recall 側の契約であって、provider に「ゼロベクトルを返すな」を課すものではない。**
⟹ **他所の ADR の結論を、別の層の契約として言い換えない。**
代わりに置いたのは**「成分が有限の数である」**（歯6）——
`NaN` が混ざったベクトルは、どの層でも意味を持たないので、provider の契約として説明できる。

### 3.5 `embed()` に渡せる入力長の上限を歯にする

**却下。**上限は**実装ごとに違う**（ADR 0090: `local` は 8192 トークン、
`@mnemora/openai` は別の値）。⟹ **適合テストが持てる形の契約ではない。**

## 5. 結果（この決定が招くもの）

**良い面**
- **`EmbeddingProvider` の契約が、初めて実装非依存の歯になった。**
  新しい adapter は `describeEmbeddingProviderConformance` を呼ぶだけで 9 本を当てられる。
- **「決定的でないので測っていない」が、テスト名としてログに残る。**
- **順序と決定性が切り離せないという事実が、型（必須の `deterministic`）とコメントの両方に載った。**

**引き受けた負債**

1. 🔴 **当てたのは 4 実装のうち 2 つだけである。**
   `@mnemora/openai` と `@mnemora/local-embedding` には**まだ当てていない**（決定6）。
   ⟹ **「4つが同じ契約を満たす」ことは、まだ確かめられていない。**
   ⚠ **この suite がその 2 つに対して緑になるかどうかも分からない。**
2. **バッチ不変性は測っていない**（決定5）。**本物のモデルでは成立しない可能性がある。**
3. **決定性の宣言は自己申告である。**`deterministic: true` と宣言しておいて
   実際は決定的でない実装を、この suite は見破れない（歯8 が偶然通ることはありうる）。
4. **`LLMProvider` の適合テストは今も無い**（ADR 0072 の負債1 のうち、埋め込み側だけを返済した）。
   ⚠ **そちらは「LLM は非決定的」という却下理由が今も生きている。**

---

## 6. これが覆るとしたら

- **バッチ不変性を実測したとき。**成立するなら歯を1本足せる。
  成立しないなら、**それは `packages/local-embedding` の側に名前を付けるべき事実**になる。
- **実 API の `@mnemora/openai` が決定的でないことを実測したとき。**
  3.1 の判断が「却下」から「実測に基づく却下」に変わる。
- **`EmbeddingProvider` の契約（`packages/core`）が変わったとき。**
  たとえば ADR 0090 負債1 の提起（`LocalEmbeddingPipeline` の必須 interface 化）が
  provider の契約側に及んだ場合、歯を足すことになる。
- **決定6 の「進行上の理由」が消えたとき**（走行中の PR が着地したとき）。
  ⟹ **負債1 を返す作業が、そのまま次の一手である。**

---

## 7. 確かめていないこと

- **`@mnemora/openai` / `@mnemora/local-embedding` にこの suite を当てていない。**
  緑になるかは**分からない**（負債1）。
- **バッチ不変性を測っていない**（決定5 / 負債2）。
- **実 API の埋め込みが決定的かを測っていない**（3.1 の根拠は「保証を持っていない」であり、
  「非決定的だと実測した」ではない）。
- **【実測・委】`RecordedEmbeddingProvider` に当てるためのカセットは、テストの中で
  `CassetteRecorder` を使って組み立てている**（`examples/chat` のカセットは読んでも触ってもいない）。
  ⚠ その過程で `CassetteRecorder.toCassette()` が
  **embedding 節と llm 節の両方に1件以上を要求する**ことが分かり、
  この suite が使わない LLM の記録を1件だけ足している。
  **このガード自体が妥当かは、本 ADR では問い直していない**（ADR 0051 の既存の不変条件である）。
