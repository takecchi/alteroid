# ADR 0097: `usage.share` は 1 を超えうる — `.max(1)` は保証ではなく、守られていない宣言だった

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-10

**⚠ 各主張の出所を分ける**（[ADR 0094](./0094-identifier-probes-local-embedding.md) /
[ADR 0088](./0088-retrieval-quality-measured-in-ci.md) の体裁を踏む）。

- **【実測】** — この ADR の書き手が、この器で自分の手で走らせた。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【受】** — 委譲元（マネージャー）から報告として受け取り、自分では再導出していない。

## 文脈

**【受】マネージャーが別の作業者に「段0」を走らせ、`main`（`faa25c6`）で次を確認したという
報告を受け取った**（この ADR の書き手は「段0」自体は走らせていない）:

> `recall()` の `usage.share` が `1.1` を返す条件が実在する。非CJK20字の digest 2件に
> `maxMemoryTokens: 10` ⟹ 段4 の強制（`unitTokens`、digest ごとに ceil）は `5+5=10 ≤ 10`
> で両方残すが、`share` の分子（`memoryTokens` = `digests.join("\n")` を1回 count）は
> `ceil(41*5/20) = 11` ⟹ `11/10 = 1.1`。

**【実測】この ADR の書き手は、上記を自分で再現した。** `packages/core/src/recall-runtime.ts`
を読むと（§「段4」「usage」節）:

- 段4の強制（`fits`）は `unitTokens`（digest ごとに `tokenCounter.count()` を呼び、件数ぶん
  `Math.ceil` する）の合計で判定する。
- `usage.share` の分子（`memoryTokens`）は `finalMemories.map(m => m.digest).join("\n")` を
  **1回だけ** `count()` する。

この2つは別の式であり、加法的に一致しない——改行区切り文字の分だけ後者が前者を上回ることが
あり、そのとき段4は「予算内」と判定して両方残すのに、実際に返した量を測り直すと超えている。
`packages/core/src/__tests__/recall-pipeline.test.ts`（本 PR で share の実値まで固定した）が
この再現を歯にしている。

**【現物】`RecallUsageSchema.share` は `z.number().nonnegative().max(1).optional()` だった。**
また `RecallUsage.share` の JSDoc は逐語:

> ⚠ 分子は `memories` tier だけであり、目次帯を含まない。したがってこの値は 1 を超えない
> （段4の切り詰めが予算を守ることを保証しているため）。

**【現物】この理由づけは偽である。** 段4の切り詰めが保証するのは「強制側（`unitTokens` の
合計）が予算を守ること」であって、「`share` の分子（連結して測った量）が予算を守ること」では
ない。上の再現がその反例である。

**【現物】`recall()` の出力は zod で検証されていない。** `recall-runtime.ts` が `.parse()` を
呼んでいるのは入力の `RecallQuerySchema` だけであり（該当行1箇所のみ）、出力側の
`RecallUsageSchema` / `RecallResultSchema` を `.parse()` している箇所はテスト
（`recall.test.ts`）以外に無い。⟹ `share: 1.1` は例外にならず、静かに呼び出し側へ出る
（`.max(1)` は実行時には何も検査していない——検査経路自体が無いため）。

**【現物】この負債は [ADR 0083](./0083-cjk-aware-heuristic-token-counter.md) の
「引き受ける負債」に既に文書化されている**（逐語）:

> 🔴 `usage.share` が 1 を超えうる穴は、この PR では直していない（再現を確認した）。
> （…）どちらの数え方を正とするかは別の判断なので、ここでは直さずに提起する。

**【現物】`recall-runtime.ts` の `budgetExceeded` 周辺のコメント（PR #125 由来）は、
「連結側（`memoryTokens`）を正とする」と明文で決めている**（逐語）:

> 呼び出し側が実際にプロンプトへ積むのは「連結された1本」であり、`unitTokens` の合計は
> その連結後の量を表さない。

⟹ **分子（連結して測る）は正しい。触るべきは `.max(1)` と JSDoc のほうである。**

---

## 決定

1. **`RecallUsageSchema.share` から `.max(1)` を外す。** `z.number().nonnegative().optional()`
   にする（`nonnegative()` は残す——負の値は依然として不正である）。
2. **`RecallUsage.share` の JSDoc を書き換える。** 「目次帯を分子から外したことで 248% 問題は
   直った」という記述は残す（それ自体は有効な修正だった）。**ただし「だから 1 を超えない」は
   偽なので削り、「1 を超えうる。超えたときは `budgetExceeded` が `true` になる」に置き換え、
   なぜ超えるのか（強制側と計測側で数え方が違う）を明記する。**
3. **`docs/recall.md` の同じ主張（§6、旧417行目付近の型コメント・旧456〜461行目付近の表と
   結論）を同様に書き換える。** 同ファイル内には元々、`usage.budgetExceeded` の節
   （旧484〜505行目付近）に「強制と計測で数え方が違う」ことを正しく説明した記述が**既に
   同居していた**——矛盾していたのは§6前半のほうだった。両方を突き合わせて整合させた。
4. **段4の強制（`fits`/`unitTokens`）は変えない。** ふるまいの変更はこの ADR の範囲外。
5. **`share` の分子・分母の式は変えない。** 連結して測ること自体は正しい
   （PR #125 の決定を維持する）。
6. **既存の歯 `share: 2.483 は弾く` を書き換える。** 前提が崩れた以上、この歯は
   「実装が正しく動いている証拠」ではなく「実在する正しい値を誤って拒否する仕様」を
   固定していた。`.max(1)` を外した意図に合わせて、**`2.483` を受け付けることを歯にし直し**、
   `nonnegative` 側（負値を弾く）だけを引き継いだ。「黙って消す」のではなく、なぜ意味を
   変えたかをテストのコメントと本 ADR に書いた。

## 歯（変異試験込み）

`packages/core/src/__tests__/recall-pipeline.test.ts`
（`describe("recall() — usage.budgetExceeded（Issue #108「案3」）")`）に3本足した:

1. **歯1（主）**: 非CJK20字の digest 2件・`maxMemoryTokens: 10` で、`usage.share` が
   `1.1`（`toBeCloseTo(1.1, 10)` かつ `toBeGreaterThan(1)`）であることと、
   `usage.budgetExceeded` が `true` であることを**同じ実行結果に対して**両方測る。
2. **歯2（対照・⭐ 赤くなってはいけない変異）**: 歯1 と**同じ2件の digest**を使い、
   `maxMemoryTokens` だけを `11`（＝連結して測った量そのもの）に変える。`share` は
   `1`（境界ちょうど）、`budgetExceeded` は `false`。**歯1 だけでは「`budgetExceeded` を
   常に `true` と主張しているだけ」の歯でも緑になる**——この歯が、同じ入力・同じ digest
   で `false` になる経路を実際に踏むことで、歯1 の `true` が「本当に超えたときだけ true」
   であることを保証する。
3. **歯3（境界の実測）**: 同じ2件の digest を固定し、`maxMemoryTokens` を `10 / 11 / 12` と
   動かす `it.each`。期待値（`1.1` / `1` / `11/12`）は実装を読んで書き写した値ではなく、
   `heuristicTokenCounter` を直接呼んで独立に導いた値である（歯のコード内の前提 `expect` を
   参照）。

**変異試験（実際に走らせた。【実測】）:**

- 変異前に `cp packages/core/src/recall-runtime.ts /tmp/mutation-backup/recall-runtime.ts.orig`
  で退避コピーを取った（`git checkout` は使わない——`docs/autonomy.md` §4 の実績のある穴）。
- 変異: `budgetExceeded: charsExceeded || memoryTokensExceeded || promptTokensExceeded` から
  `memoryTokensExceeded` を落とす。
- 結果: `pnpm --filter` 相当（`packages/core` で `vitest run`）で
  **63 tests 中 3 failed**——歯1、境界の実測（`maxMemoryTokens=10` の行）、および
  既存の「chars 予算とトークン予算を両方申告しても…」の歯が赤くなった。
  **⭐ 歯2（対照）と境界の実測の `11`/`12` の行は緑のままだった**——対照が対照として機能した
  証拠である。
- 退避コピーから戻し（`cp /tmp/mutation-backup/recall-runtime.ts.orig packages/core/src/recall-runtime.ts`）、
  `git diff` が空であることを確認。再実行で **118 tests 全緑**に戻った。

## 境界の実測（歯3。オーナー名指しの要求）

**固定した入力**: 非CJK20字の digest 2件（各 `heuristicTokenCounter` で5トークン、
連結すると改行込み41文字で `ceil(41/4) = 11` トークン）。

| `maxMemoryTokens` | 強制側（`unitTokens` 合計） | `share` の分子（連結） | `share` | `budgetExceeded` |
| ---: | ---: | ---: | ---: | :--- |
| 10 | 10（両方残る） | 11 | **1.1**（>1） | `true` |
| 11 | 10（両方残る） | 11 | **1**（境界ちょうど） | `false` |
| 12 | 10（両方残る） | 11 | **0.9167…**（<1） | `false` |

**境界は `maxMemoryTokens = 11`（＝連結して測った量そのもの）に在る。** この digest2件の
組み合わせでは、強制側が「両方残す」と判定する上限（`unitTokens` 合計 `10`）と、
`share` が「予算内」と判定する上限（連結して測った `11`）が**1トークンだけずれる**——
このずれの大きさは「連結の区切り文字（`\n`）1個ぶんの重み」に一致する
（非CJK 1文字 = `ceil(5/20) = 1` トークン）。**digest の件数が増えるほど、
連結で増える改行文字の数も増えるため、このずれは一般には1トークンより大きくなりうる**
（複数件・複数の区切り文字が同時に丸めの向きを動かしうるため——ここでは2件の場合だけを
実測しており、3件以上の一般式は確かめていない）。

## 採らなかった案

- **(却下) `share` の分子を強制側（`sum(count(digest_i))`）へ寄せる。** `unitTokens` の合計は
  改行区切りのぶん**構造的に過小**であり、呼び出し側が実際にプロンプトへ積む量（連結された
  1本）を表さない。⟹ **報告値を過小にするのは予算超過を*隠す*方向であり、目次帯混入で
  248% を誤報していたのと逆方向に、こんどは「超えているのに超えていないと言う」誤りを作る。**
  加えて、`share` と `budgetExceeded` が同じ戻り値の中で別の数え方をすることになり、
  それ自体が新しい不整合を生む。**PR #125 が明文で決めた「連結側（実際に積む量）が正」を
  巻き戻すことになるため、却下する。**
- **(却下) 段4の強制を連結側へ寄せる。** 数え方は1本に統一されるが、**切り落とし件数が
  変わる＝ふるまいの変更**である。どの digest が残り、どれが `budget_dropped` になるかが
  変わりうる——これは値の意味を正す話ではなく、機能の挙動を変える話であり、
  別 ADR・別 PR の主題である（`docs/autonomy.md`「ついでに直さない」）。
- **(却下) 既存の歯 `share: 2.483 は弾く` をそのまま黙って削除する。** `docs/autonomy.md` §2
  も本 PR の依頼も「黙って消さない」ことを要求している。**意味を反転させ、なぜ反転させたかを
  歯のコメントとこの ADR に残した**（上記「歯」節の3を見よ）。
- **(却下・別案として提起) `RecallUsageSchema` / `RecallResultSchema` を `recall()` の出力に
  対して `.parse()` する。** 筋は良いが、`recall()` が例外を投げるようになるという
  **ふるまいの変更**であり、この PR には混ぜない。代わりに Issue として起票した
  （[Issue #131](https://github.com/takecchi/mnemora/issues/131) — 実装は別 PR）。

## 引き受けた負債

1. **「強制と計測で数え方が違う」という穴そのものは、この ADR では直していない。**
   ADR 0083 が「どちらの数え方を正とするかは別の判断」として意図的に見送った範囲であり、
   本 ADR が回収したのは**その穴自体ではなく**、「`share` は 1 を超えない」という
   `RecallUsageSchema` / JSDoc の**誤った保証の宣言**のほうである。
   **強制側と計測側をどちらかに統一するかどうかは、依然として別の判断として残る。**
2. **`recall()` の出力は依然として zod で検証されていない（fail-open）。** この ADR は
   「`.max(1)` を外す」ことでこの経路の実害（静かな検査失敗ではなく、そもそも検査されて
   いない）を減らす方向ではあるが、**根本（出力を検証する経路が無いこと）は直していない**
   ——[Issue #131](https://github.com/takecchi/mnemora/issues/131) として起票済み。
3. **3件以上の digest でのずれの一般式は確かめていない。** 上の「境界の実測」で2件の場合の
   ずれ（1トークン）だけを実測した。件数が増えたときにずれがどう振る舞うかは、
   本 ADR の範囲では測っていない。
4. **`.max(1)` を外したことで、`share` の値そのものが実態からどれだけ外れているか
   （ヒューリスティックなカウンタの誤差）を検知する手段は無いままである。**
   これは ADR 0083 が `budgetExceeded` について既に引き受けている負債と同種であり、
   新たに増えた負債ではない。

## これが覆るとしたら

- **強制側と計測側の数え方をどちらかに統一すると決めたとき。** そのとき `share` は
  常に 1 以下に戻るか（強制側を連結側に寄せる場合）、`budgetExceeded` の意味が変わるか
  （分子を強制側に寄せる場合）のどちらかになる——上の「採らなかった案」で却下した2案が、
  そのときは再検討の対象になる。
- **`recall()` の出力を zod で検証する経路が実装されたとき（Issue #131）。**
  そのとき `share` に `.max(1)` のような上限を付け直す設計変更は、**例外という形で
  呼び出し側に影響する**ため、値の意味そのものとは独立に再度検討する必要がある。
- **digest 3件以上でのずれの一般式が実測されたとき。** 境界の表は2件の場合に限った実測
  であり、一般式が分かれば境界表はそちらに置き換わる。
