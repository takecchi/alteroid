- **状態**: 採用 (2026-09)
- **日付**: 2026-09-09

**🔴 採用したのは決定であって、実装はまだ入っていない。**この ADR の時点で
`packages/*` の差分は空である。**「採用」と書いてあることを「もう動いている」と
読まないこと** —— [ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §6 が
「**スキーマに在ることと、作られていることは別である**」と書いたのと同じ罠が、
ADR の状態欄にも在る。実装は別 PR で入れ、そのとき本 ADR に着地を追記する。

**⚠ 各主張の出所を分ける。**この文書では次の3つを混ぜない
（[AGENTS.md](../../AGENTS.md)「確かめていないことは『確かめていない』と書く」の適用）。

PostgreSQL 17.11 + pgvector 0.8.6。**実 API は1回も叩いていない。**
**コードは1行も変えていない。**

## 1. 測ったこと 【現物】— `ann_truncated` ≡「スコープが k' 以上ある」

発火条件は、これだけである（`packages/core/src/recall-runtime.ts:283-286`、逐語）:

```ts
// over-fetch の打ち切り（docs/recall.md §3「正直に書くべき限界」）: LIMIT に達したなら
// その先に何件あるかは原理的に数えられない。
if (candidateGenerationExecuted && annHits.length >= kPrime && kPrime > 0) {
  omitted.push({ kind: "ann_truncated", countKind: "unknown" });
}
```

`kPrime` は（`recall-runtime.ts:222-224`、逐語）:

```ts
const limit = validatedQuery.limit ?? DEFAULT_RECALL_LIMIT;
const overFetchFactor = validatedQuery.overFetchFactor ?? DEFAULT_OVER_FETCH_FACTOR;
const kPrime = Math.max(1, Math.round(limit * overFetchFactor));
```

**⟹ `kPrime` はスコープの件数を一切見ない。**既定では 75件でも100万件でも 40 である。
**⟹ スコープに k' 件以上あれば、必ず鳴る。**

**⟹ `ann_truncated` は「スコープが k' 以上ある」という命題と同値であり、
何かを失ったかどうかを一切言っていない。**

### 1.1 実測 【実測】— 7/7 で鳴り、実損は 0/7

`examples/chat` の `retrieval` ベンチ（arm C、カセット再生、スコープ 75件、k'=40）:

- **7 probe すべての `omitted` に `ann_truncated` が出た。**
- **同じ7 probe の gold の順位は 1 / 1 / 2 / 6 / 1 / 1 / 2** —— **全部 k' の内側**。

**⟹ 偽陽性率は、いま在る唯一の測定で 7/7 である。**

### 1.2 ⚠ 依頼の言い方を1つ直す

本件は当初「**75件中 35件が一度もスコアされていない（47%）**」として持ち込まれた
（[ADR 0068](./0068-the-bench-must-not-lie-about-what-it-measured.md) §(e)）。
**その数字は正しいが、危険の在り処をずらしている。**

**ANN は距離順に上位 k' を取るので、切られる35件は「最も似ていない35件」である。**
**⟹ 切られること自体は欠陥ではなく、ANN がやるべき仕事そのものである。**

**⟹ 正しい問いは「何件切られたか」ではなく、
「切られた側に、本来 top-k に入るべきものが居たか」である。**

## 2. 測ったこと 【現物】— 読み手は0件。そして書かれた一手は 100% 発火する

`.omitted` を読んでいる箇所を全部見た。**`ann_truncated` を読んで振る舞いを変えるコードは
1箇所も無い。**

| 場所 | 何をしているか |
| --- | --- |
| `packages/core/src/recall-runtime.ts:285` | **書き手**（読み手ではない） |
| `examples/chat/src/compare.ts:172-173` | **文字列化して表に出すだけ**（網羅 switch の1分岐。分岐しない） |
| `packages/postgres/src/bench/scale-bench.ts:1496` | **ログ文を組み立てるだけ**（`assert` ではない） |

`omitted` を読んで**分岐する**唯一の呼び出し側は `examples/chat/src/backfill.ts:67` だが、
見ているのは `filtered` / `period` であって `ann_truncated` ではない 【現物】。

そして `docs/recall.md:236` は、この札の「次の一手」をこう書いている（逐語）:

> | `ann_truncated` | 「見えていない領域があるかもしれない」という不確実性そのものが一手になる——**例えば厳密検索へのフォールバックを選べる。** |

**🔴 いまこの一手を実装すると、100% の確率で発火する**（§1 の通り、スコープが k' 以上なら
必ず鳴るため）。**⟹ ANN 索引を一度も使わないのと同じになる。**

**⟹ これは「読まれない観測口」より一段悪い。「読んでも次の一手が決まらない観測口」である。**
`omitted` に載っている他の札（`below_threshold` なら閾値を緩める、`not_indexed` なら
埋め込みジョブの遅延を疑う、等）はどれも一手が決まる。
**`ann_truncated` だけが、鳴っても何も決まらない。**

## 3. 🔴 k'=40 の安全性は、「5項のうち4項が定数」に完全に依存している

[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) が測った通り、
`total = similarity × decay × tagMatch × freshness × strength` の4項は、このベンチでは定数である。

**⟹ `total` の順位 = `similarity` の順位。**
**⟹ similarity 上位 k' 件の中に、total 上位 k 件が必ず入る（自明に）。**
**⟹ いま実損が 0/7 なのは、over-fetch 係数 4 が良い値だからではなく、
スコアが similarity 1項しか見ていないからである。**

### 3.1 【実測】窓の余裕 — 窓の外が top-10 に入るのに必要な倍率

カセットの実ベクトルから、`sim@10 / sim@41` を計算した（スコープ 75件、k'=40）:

| probe | color | pet | **exercise** | diet | family | language | travel |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 必要な倍率 | 1.485 | 1.473 | **1.330** | 1.892 | 1.824 | 1.958 | 1.622 |

### 3.2 🔴 `occurredAt` を入れると、この余裕は割れる 【計算】

`freshness` の起点は `occurredAt ?? recordedAt` であり、
[ADR 0036](./0036-clamp-freshness-at-one.md) の clamp で上限は 1.0。
半減期（既定 720時間 = 30日）だけ過去の出来事なら 0.5。

**⟹ `freshness` 単独で 2.0 倍の開きが出る。**

**⟹ 2.0 > 1.958 —— 7 probe すべてで、窓の外の候補が top-10 に入りうる。**

**🔑 これは、`hit@1` を直すために誰もが挙げる手
（抽出スキーマに時刻の欄を入れて `occurredAt` を実データから埋める。
ADR 0033 の負債 §4 / [ADR 0058](./0058-measure-the-time-term-in-a-separate-arm.md) の
「これが覆るとしたら」の筆頭）が、そのまま k'=40 の安全余裕を割ることを意味する。**

### 3.3 ⛔ だから、これは `occurredAt` を入れる前に立てる門である

**ADR 0068 は「測定器を先に固める」という理由で `occurredAt` を後回しにした。
本 ADR は、その順序を維持したまま、理由を差し替える。**

- **旧: 測定器を先に固める。**
- **🔴 新: `ann_truncated` が「損したかもしれない」を言えるようになるまで、
  `occurredAt` を入れてはいけない —— 入れた瞬間に k'=40 の安全余裕が割れ、
  しかも割れたことに気づく口が無いから。**

**⟹ 次に誰かが `occurredAt` を入れようとしたら、本節が門である。**
`hit@1` と `ann_truncated` は別件ではなく、**同じ1つの問題の裏表**である。
**別々の PR で順に直すと、後の PR が前の PR を静かに壊す。**

## 4. 【実測】規模を振ると、余裕は単調に薄くなる

カセットは74発話ぶんしか無いため（§9）、部分集合で N を振った。
各 N で60回サンプルした中央値、gold/distractor 14件は常に含める。

| N | 見られる割合（k'=40） | 必要な倍率（7 probe の最小） |
| --- | --- | --- |
| 45 | 89% | **2.329** |
| 50 | 80% | 1.919 |
| 55 | 73% | 1.693 |
| 60 | 67% | 1.583 |
| 65 | 62% | 1.454 |
| 70 | 57% | 1.387 |
| 75 | 53% | **1.330** |

**7 probe すべてで単調減少である。**

**⟹ `freshness` の 2.0 倍を下回る交差は、N = 50〜55 の間で既に起きている。**
**⟹ 75件は「まだ安全な小ささ」ではなく、既に危険側である。**
**⟹ 100万件を測るまでもなく、方向は確定している。**

## 5. 検討した案 — **案A を採る**（実装はこの ADR には入っていない）

**直す対象は1つ: `ann_truncated` が情報を持っていないこと。**

### 案A: 札を「鳴る/鳴らない」から「安全余裕」へ変える（**✅ 採用**）

**判定式**:

```
R = total_k / ( sim_k' × M_max )

  total_k = 返した最後（k 位）の total            … 既に手元に在る
  sim_k'  = ANN が返した最後（k' 位）の similarity … 既に手元に在る
  M_max   = 非 similarity 項の積の上界
```

**R ≥ 1 なら、窓の外の候補は原理的に top-k へ入れない ⟹ 鳴らさない。**

**健全性の根拠**: ANN は距離順に返すので、窓の外の候補 c は必ず `sim_c ≤ sim_k'`。
その total は `sim_c × M_c ≤ sim_k' × M_max`。これが `total_k` 以下なら、
c は k 位を抜けない。**⟹ 41位以降を取りに行かずに、上界だけで判定できる。**

**⚠ 当初「41位の similarity は捨てているので後から計算できない」と疑ったが、
40位が手元に在れば上界としては足りる。**厳密な X ではなく**保守側の上界**を使う。

**`M_max` は計算できるか** 【現物】:

| 項 | 上界 | 出所 |
| --- | --- | --- |
| `freshness` | **1.0** | `MAX_FRESHNESS`（ADR 0036 の clamp）。**式の副作用ではなく、選んだ結果として 1** |
| `decay` | **1.0**（⚠ 前提付き。§6 参照） | `0.5 ** (elapsed / halfLife)` は `elapsed ≥ 0` で 1 以下。**clamp は無い** |
| `tagMatch` | **1 + 0.1 × クエリタグ数** | `computeTagMatch`。**クエリ側だけで決まる** |
| `strength` | **🔴 上界が無い** | 型は `number`、DB は `real`。後述 |

**⟹ 4項のうち3項は、既に解析的な上界を持っている。足りないのは `strength` だけに見える。**
**⚠ この読みは §6 で一部訂正する** —— `decay` の 1.0 も「保証」ではなく「前提」だった。

**【実測】この式が今日どう振る舞うか**（スコープ 75件、k'=40、`M_max = 1`）:

| probe | color | pet | exercise | diet | family | language | travel | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| R（いま） | 1.455 | 1.447 | **1.291** | 1.881 | 1.823 | 1.913 | 1.551 | **7/7 で鳴らない** |
| R（`occurredAt` 後、`freshness ∈ [0.5,1]`） | 0.727 | 0.723 | **0.645** | 0.941 | 0.912 | 0.957 | 0.776 | **7/7 で鳴る** |

**⟹ いまの世界では沈黙し（実損 0/7 と一致）、`occurredAt` が入った瞬間に鳴る。**
**⟹ §3.3 の門が、文書ではなく実行時の札として立つ。**

**費用**: 追加のクエリは0。`annHits` の最後の要素と、既に計算済みの `total_k` を使うだけ。

**採用にあたって決めた3点は §6〜§8 に置いた**（`strength` の上界の出し方 / この判定が既定戦略に
固有であること / 厳密探索を前提とすること）。

### 案B: 札を2つに割る

`ann_truncated`（いまの意味＝窓が埋まった）を残し、
`ann_truncated_unsafe`（損失が起こりえた）を足す。
[ADR 0027](./0027-split-superseded-forgotten-omission.md) が
`superseded` / `forgotten` を割ったのと同じ形。

- **利点**: 既存の意味を壊さない。npm に出ている `0.1.1` の利用者が居ても互換。
- **欠点**: **情報を持たない札が残る。**「鳴っても何も決まらない札」が1つ増えたまま。
  `docs/recall.md:236` の一手は、依然としてどちらに紐づくのか曖昧。

### 案C: 発火条件だけ変える（型は1文字も変えない）

`ann_truncated` を「損失が起こりえたときだけ」鳴らす。`Omission` の型は変えない。

- **利点**: 差分が最小。`countKind: 'unknown'` の意味（何件かは分からない）も保たれる。
- **欠点**: **意味の破壊的変更である。**「窓が埋まった」を読んでいた利用者が居れば壊れる
  （**リポジトリ内には0件**だが、`@mnemora/core` は npm に出ている）。
  そして**安全余裕の値そのものは外に出ないので、呼び出し側は「どれくらい危ないか」を知れない。**

### 案D: `sim_k'` を札に載せるだけ（判定は呼び出し側にさせる）

- **利点**: core が判定を持たない。最小の追加。
- **🔴 欠点**: **呼び出し側が `M_max` を計算するには、スコアリング戦略の内部を知る必要がある。**
  ⟹ 内部が漏れる。そして**呼び出し側が計算を間違えても誰も気づかない。**
  ADR 0008 の「呼び出し側の次の一手が変わるか」に照らすと、
  **一手が決まらない情報を渡しているだけになりかねない。**

### 案E: 何もせず、文書を直す ⛔（対照として置く）

`docs/recall.md:236` の「厳密検索へのフォールバックを選べる」を、
「この札は 100% 鳴るので一手にならない」と書き直す。

**⟹ 採らない。**これは**正典が付けた条件を満たしていないことを、
満たしていると認めるだけ**である。`docs/north-star.md` の条件のほうを変えるなら、
それはオーナーの判断であり、実装の都合で正典を書き換えないという AGENTS.md の規律に触れる。

### 採らない方向（既に測って捨ててある）

- **`hnsw.iterative_scan` / `relaxed_order`** ⛔ ——
  [ADR 0063](./0063-hnsw-iterative-scan-not-adopted.md)（「**件数は直るが正しさは直らない**」）と
  [ADR 0064](./0064-exact-path-cost-vs-scale.md)（30万件で `recall@40` が 0.325 / 0.200 まで悪化）。
- **`overFetchFactor` の既定値を上げる** ⛔ —— **札を直すことの代わりにならない。**
  口は既に開いており（`RecallQuery.overFetchFactor` は呼び出しごとに上書きできる 【現物】）、
  値を大きくしても「損したかどうかを言えない」性質は1ミリも変わらない。

## 6. 採用にあたって決めた3点 — (1) `strength` の上界は「常に 1」を根拠にしない。**戦略に宣言させる**

**⛔ 「`strength` は常に 1 だから上界は 1」を根拠にはしない。**

確かに `buildNewMemoryFromCandidate` は無条件に `strength: 1` を書き、
[ADR 0041](./0041-reinforce-does-not-change-strength.md) は「`reinforce` は `strength` を
動かさない」と決めており、**`strength` に 1 以外を書く箇所はリポジトリに0件である** 【現物】。

**⚠ しかしそれは型の保証ではなく、現在の実装の性質である。**
**⟹ 「設定が在る」を「機構が動いている」と読み、「記述が在る」を「保証が在る」と読む** ——
これはこのリポジトリが繰り返し踏んできた形（[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §6・
[ADR 0067](./0067-dry-run-fail-open-and-does-not-verify-trusted-publisher.md)・
[ADR 0068](./0068-the-bench-must-not-lie-about-what-it-measured.md)）であり、
**その罠を、罠を直すための実装の中に作り込まない。**

### 決定: **`ScoringStrategy` が「自分の項の上界」を宣言する口を持つ**

- 既定戦略は `strength ≤ 1` を**宣言する** ⟹ **現在の実装の性質を、型として書き出す。**
- **宣言しない戦略では「判定不能」**。⟹ **沈黙（安全だと判定した）と判定不能を、別の顔で返す**
  （[ADR 0008](./0008-absence-taxonomy.md) の「無いには種類がある」を、判定そのものにも適用する）。

**⟹ これで「`strength` は常に 1」を根拠として使いながら、それが宣言＝検査できる対象になる。**

### ⚠ 宣言の形は `number` ではない — 項によって依存先が違う 【現物】

上界を作ろうとして、4項が同じ顔をしていないことが分かった。

| 項 | 上界 | **保証か、前提か** | 根拠 |
| --- | --- | --- | --- |
| `freshness` | 1.0 | **🟢 保証** | `Math.min(MAX_FRESHNESS, ...)` が式の中に在る（[ADR 0036](./0036-clamp-freshness-at-one.md)） |
| `tagMatch` | `1 + 0.1 × クエリタグ数` | **🟢 保証** | `computeTagMatch` の形そのもの。**クエリ側だけで決まる** |
| `decay` | 1.0 | **🔴 前提** | **clamp が無い。** 後述 |
| `strength` | 1.0 | **🔴 前提** | 型は `number`、DB は `real`。書き込み側の性質でしかない |

**⟹ 宣言は「クエリを受け取って上界と前提を返す」形になる。**単なる定数では足りない ——
`tagMatch` はクエリタグ数に依存し、`decay`/`strength` は**前提を伴う**からである。

### 🔴 `decay` に上界が無いことは、この ADR を書く途中で見つけた 【現物】

`packages/core/src/strategies/scoring.ts:56-61`（逐語）:

> **⚠ 上限を掛けるのは `freshness` だけで、`decay` には掛けない。**
> `decay` の起点は `lastReinforcedAt ?? recordedAt` であり、どちらも「mnemora が知った時刻」
> 系である。（…）**戦略の側で頭打ちにし、減衰関数そのものは変えない。**

**⟹ `decay = 0.5 ** (elapsed / halfLife)` が 1 以下であることは、
`now ≥ (lastReinforcedAt ?? recordedAt)` を前提にしている。**
起点が未来なら `decay > 1` になる（`freshness` が clamp を必要としたのと同じ理由で、
[ADR 0036](./0036-clamp-freshness-at-one.md) は `freshness` にだけ clamp を掛けた）。

**⚠ この ADR は `decay` に clamp を掛けることを決めていない。**それは振る舞いの変更であり、
ADR 0036 が `decay` を意図的に対象外にした判断に触れる。**ここでは「前提である」と名乗らせるだけにする。**

## 7. (2) ⛔ この判定は「既定戦略に固有」である — 注入口はこの決定では作らない

**🔴 文書と実装が食い違っている** 【現物】。`packages/core/src/strategies/scoring.ts:10-11`（逐語）:

> 以下の実装はその制約の範囲で選んだ Phase 1 の既定であり、**`ScoringStrategy` を差し替えれば
> 別の式を使える。**

**しかし `RuntimeDeps`（`packages/core/src/runtime.ts:64`）に `scoringStrategy` の欄は無く、
`recall-runtime.ts:334` は `defaultScoringStrategy` を直接 import して呼んでいる。**
**⟹ 差し替える口は存在しない。**「やると決めたのに守られていない」記述である。

**⛔ 注入口は、この決定では作らない。**消費者が居ないものをこの決定に抱き合わせない
（[ADR 0024](./0024-remove-exact-counts-option.md) の「実装の無い予約を残さない」と同じ線）。
**オーナーの台帳へ回した。**

**⟹ 代わりに、本 ADR は明示する: この安全余裕の判定は*既定戦略に固有*である。**
`ScoringStrategy` を差し替える口は現状 `RuntimeDeps` に無く、`scoring.ts:10-11` の記述は
実装に追いついていない。**⭐ ただし §5.1 の「戦略が上界を宣言する」形にしておけば、
注入口が後から入ったときに自然に繋がる** —— 宣言を持たない戦略は「判定不能」に落ちるだけで、
黙って誤った上界を使うことにはならない。

## 8. (3) ⚠ この上界の健全性は「厳密探索」を前提とする

案A の健全性は「窓の外の候補は必ず `sim ≤ sim_k'`」に依っている。**これは ANN が
距離順に返すことの帰結であり、実装の偶然ではない** —— が、**`sim_k'` は「索引が返した
k' 番目」であって「真の k' 番目」ではない。**

**⟹ 近似索引（HNSW）が scope の他の場所へ行ってしまい、真の上位を取りこぼしていた場合、
上界は破れる。**そのズレは本 ADR が扱う事象ではなく、
[ADR 0025](./0025-ann-underfill-is-not-reported-in-omitted.md) /
[ADR 0026](./0026-ann-unreached-omission.md) の `ann_unreached` が別に扱う。

**⛔ 塞げていない範囲を、塞いだことにしない。**

### 🔴 前提のうち、歯にできるものとできないもの

**オーナーの基準:「『厳密探索を前提とする』と書くだけで、その前提を歯にできないなら、そう名乗らせること」。**

| 前提 | 歯にできるか | 見込み |
| --- | --- | --- |
| `strength ≤ 1` | **🟢 できる見込み** | `strength` に 1 以外を書く経路がソースに無いことを機械的に検査する。前例が在る（`packages/core/src/__tests__/dependency-boundary.test.ts` は `package.json` を読んで依存境界を機械的に担保している）【現物】 |
| `decay ≤ 1`（起点が未来でない） | **🟡 部分的** | 単体の歯なら書けるが、**「未来の `recordedAt` が入り込む経路が無い」ことは検査できない**（クロックのずれ・外部からの投入） |
| `sim_k'` が真の k' 番目 | **🔴 できない** | **これは近似索引の定義そのものである。**歯にできない ⟹ **そう名乗らせる**（判定に「厳密探索前提」と書く） |

**⟹ 3つの前提のうち、歯にできるのは1つだけである。**残る2つは、
**判定の結果そのものに「この前提の上に立っている」と書かせる**
（沈黙・判定不能・発火の3値では足りず、沈黙にも根拠の強さの差が在る）。
**⚠ その3値以上の表現をどう持たせるかは、実装 PR の設計に委ねる。ここでは決めていない。**

## 9. ⚠ 確かめていないこと

- **§3.2・§4 は算術である。**「窓の外が入りうる」ことしか言っていない。
  **「実際に入って `hit@1` が落ちた」は測っていない。**`occurredAt` が入った世界では
  一度も走らせていない。
- **N > 75 は測っていない。**45→75 の単調減少から方向を言っているだけで、
  100万件での値は言えない。
- **HNSW の近似誤差を分離していない。**§3.1・§4・§5 の計算は**厳密なコサイン順位**であり、
  pgvector の HNSW が実際に返す40件とは一致しない可能性がある
  （そのズレは [ADR 0025](./0025-ann-underfill-is-not-reported-in-omitted.md) /
  [ADR 0026](./0026-ann-unreached-omission.md) の `ann_unreached` の領域）。
- **`decay ≤ 1` と `strength ≤ 1` は前提であって、検査していない**（§6）。
  前者は「起点の時刻が未来でない」こと、後者は「`strength` に 1 以外を書く経路が無い」ことに依る。
  **どちらもこの ADR の時点では歯になっていない。**
- **案A を実装していないので、実際の `recall()` でこの判定が期待通り鳴る/沈黙することは
  確かめていない。**§5 の R の値は、カセットのベクトルから担当者が計算したものである。
- **`packages/postgres/src/bench/scale-bench.ts` は走らせていない。**
  1万〜100万件で規模を振れるベンチだが（`pnpm --filter @mnemora/postgres run bench:scale`）、
  Part 4 は `ann_truncated` が**出たかどうかを印字するだけ**で、失った中身は測っていない 【現物】。
- **`retrieval` ベンチで規模を振ることはできない** 【現物】——
  `haystackSize` は `runRetrievalQualityArm` の引数に在るが `cli.ts` は渡しておらず、
  カセットは74発話ぶんしか無いので増やせば `RecordedProvider` が例外を投げる
  （黙って倒れない設計）。振るにはカセットの録り直し（実 API。ADR 0019 の実測で
  `retrieval` は約 $0.0045）か CLI の新設が要る。

## 10. これが覆るとしたら

- **`strength` を 1 以外にする経路が入ったら。**既定戦略の宣言（`strength ≤ 1`）が偽になる。
  **⟹ そのとき宣言を直し忘れると、判定は「安全だ」と嘘をつく。**宣言を歯で縛る理由がここに在る（§8）。
- **`decay` に clamp が入ったら。**§6 の「前提」が「保証」に変わり、宣言が1つ強くなる。
- **`ScoringStrategy` に実際の注入口が入ったら。**案A は戦略側から上界を貰う形になる。
- **`freshness` の clamp（ADR 0036）が外れたら。**`M_max` の上界そのものが消える。
- **埋め込みモデルを替えたら。**§3.1・§4 の数字は `text-embedding-3-small`(256次元) に固有である。
- **`hit@1` を諦めて `hit@10` だけを物差しにすると決めたら。**窓の外が top-**10** に入るかどうかは、
  そもそも `hit@10` には影響しない（gold は既に返っている）。**⟹ この ADR の重みは物差し次第で変わる。**
