# ADR 0094: 識別子・固有名詞の probe を、鍵もカセットも要らないローカル埋め込みで測る — ゴールデンセットを増やす道を1本開ける

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-10

**⚠ 各主張の出所を分ける**（[ADR 0088](./0088-retrieval-quality-measured-in-ci.md) /
[ADR 0085](./0085-local-embedding-provider.md) の体裁を踏む）。

- **【実測】** — 本物の PostgreSQL に対して**この ADR の書き手が自分の手で**走らせた。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【受】** — 報告として受け取り、再導出していない。
  ⚠ **委譲文で渡された数字は、書き手にとってはすべて【受】である。**
  この ADR で【実測】と書いてあるものは、書き手が引き直した分だけである。

## 文脈

**Issue #109**（外部の採用検討者 `the-phage-dev`。#106 / #108 と同じ報告者）の
「提案する形」は3項目である。逐語:【現物】

> 1. **固定した小さなゴールデンセット**（数十件程度の記憶と問い、期待される上位）を repo に置き、
>    `hit@1` / `hit@10` / MRR を出す。
> 2. それを**実 embedding で、週次などの頻度**（毎 PR でなくてよい）で走らせ、結果を数字として残す。
>    API キーが必要なので `schedule` + secret のあるジョブに限定する形が現実的だと思います。
> 3. **前回値との差分が閾値を超えたら落とす**、あるいは落とさずともログに出す。
>    閾値の設定自体が難しいので、まずは「値が残る」だけでも十分価値があります。

**[ADR 0088](./0088-retrieval-quality-measured-in-ci.md) が塞いだのは項目2と3である。**
項目1は**明示的に閉じなかった。**逐語:【現物】

> - **ゴールデンセットをどう増やすか。**Issue #109 の項目1（数十件）は**この ADR では塞がらない。**

そして ADR 0088 は「⛔ この ADR が閉じないもの」で、**次に何が先に要るか**まで書いていた。逐語:【現物】

> **そして項目1は、カセットのままでは構造的に閉じている**（文脈 §2）。
> probe を1件足すと鍵が変わり、記録に無い入力は例外になる。
> **⟹ 順序は「実 API で録り直せる手段」または「入力が固定されない埋め込み provider」が先である。**

**⟹ この ADR は、その順序の後者に従っている。**
[ADR 0085](./0085-local-embedding-provider.md) が足した `@mnemora/local-embedding`
（外部サービスへ繋がないプロセス内 ONNX 推論）は、**入力が固定されない埋め込み provider**
そのものである——鍵もカセットも要らないので、probe を1件でも100件でも足せる。

### なぜ「識別子」から増やしたか

**【現物】既存の probe 7件（`examples/chat/src/probe-set.ts`）はすべて日本語の query であり、
ASCII の識別子・固有名詞を含む query は0件だった。**
Issue #106（[ADR 0084](./0084-lexical-recall-channel.md) の出発点）が名指しした用途
——人名・チャンネル名・社内システム名・案件コード・チケット番号——を、
**既存ベンチは1件も測っていなかった。**
⟹ 「数十件へ増やす」の第一歩を、**測っていない領域**に置いた。

## 決めたこと

1. **`identifier-probes` サブコマンドを足す**（`examples/chat`）。
   擬似LLM（`DeterministicLLMProvider`）＋ **ローカル埋め込み**
   （`local`/`ruri-v3-30m/sym`/256次元）で、**3群を別々に**集計する。
2. **既存には1文字も触らない**（後述 §3）。別ファイル・別 arm・別基準値ファイルにする。
3. **CI に1ジョブ足す**。⛔ **門にしない**（後述 §7）が、
   **基準値との差分は Job Summary に出す**（後述 §8）。
4. **「重みを取得できなかった」と「測ったが値が悪かった」を型で区別する**
   （`status: "measured" | "weights_unavailable"`）。

## 1. 【実測】測った条件と値

**本物の PostgreSQL 17.11 + pgvector 0.8.6**（ローカルにソースから立てたもの、
127.0.0.1:5544。**本番ではない**）。

```
env -u OPENAI_API_KEY DATABASE_URL=... MNEMORA_IDENTIFIER_PROBE_JSON=<path> \
  pnpm --filter @mnemora/example-chat run identifier-probes
```

🔴 **数字には必ず「arm・`(provider, model, dimensions)`・haystack 条件」の3つを添える。**
⚠⚠ **256次元は両方の空間で同じである。⟹ 次元数では区別できない。**
`local`/`ruri-v3-30m/sym`/**256次元** と `openai`/`text-embedding-3-small`/**256次元**は
**別の空間**であり、同じ MRR の値でも意味が違う。

| 群 | probe | `(provider, model, dimensions)` | llm | haystack | MRR | hit@1 | hit@10 | 出所 |
|---|---|---|---|---|---|---|---|---|
| 既存 arm **B** | 日本語意味 7件 | `(openai, text-embedding-3-small, 256)` 記録再生 | deterministic | 疎 | 0.714 | 4/7 | **6/7** | 【実測】`retrieval` を走らせ `retrieval-baseline.json` と一致 |
| 既存 arm **C** | 日本語意味 7件 | `(openai, text-embedding-3-small, 256)` 記録再生 | recorded | 疎 | 0.738 | 4/7 | **7/7** | 【実測】同上 |
| 新 `japanese` | **同じ**日本語意味 7件 | **`(local, ruri-v3-30m/sym, 256)`** | deterministic | 疎 | **0.810** | **5/7** | 7/7 | 【実測】 |
| 新 `identifiersSparse` | ASCII 識別子 12件 | **`(local, ruri-v3-30m/sym, 256)`** | deterministic | 疎 | **1.000** | **12/12** | 12/12 | 【実測】 |
| 新 `identifiersDense` | 同じ識別子 12件 | **`(local, ruri-v3-30m/sym, 256)`** | deterministic | **密** | **1.000** | **12/12** | 12/12 | 【実測】 |

⚠⚠ **合成しないこと。**この repo では「条件を落とした数字」が実際に**3度**壊れており
（[ADR 0068](./0068-the-bench-must-not-lie-about-what-it-measured.md) 冒頭・
[ADR 0081](./0081-similarity-is-the-only-term-that-ranks.md) §3.2 が記録している）、
逐語で警告を繰り返す: **`MRR 0.714` は arm B の値であり、その arm の `hit@10` は 6/7 である。
`hit@10 = 7/7` は arm C（MRR 0.738）。**⛔ **`MRR 0.714 / hit@10 7/7` という arm は存在しない。**

## 2. なぜ (あ) ローカル埋め込みで新しい probe を測る、を採ったか

**採らなかった2案:**

- ⛔ **(い) カセットを録り直して既存の `recorded` 経路で測る。**
  カセットの鍵は入力文字列の SHA-256 であり（`packages/testkit/src/__fixtures__/cassette.ts`）、
  **probe を1件足すと鍵が変わって例外になる**【現物】——録り直しには `OPENAI_API_KEY` が要る。
  **その鍵をオーナー代理も委譲元も持っていない**【受】。
  ⟹ **probe が1件も増えず、Issue #109 の項目1が閉じない。**
- ⛔ **(う) 埋め込みを使わず、語彙チャンネル（ADR 0084）だけで識別子を測る。**
  **この判断をした時点で、`LexicalStore` と `recall` の候補生成は別の作業
  （PR #124 / ADR 0092「語彙チャンネルのクエリ語彙を OR で結び、`lexicalMatch` を
  被覆率にする」）で書き換わっている最中だった。**
  ⟹ **動いている的に物差しを当てても、出た数字が何を意味するか言えない。**
  ⚠ **【現物】その PR は、この作業の途中で `main` に入った**
  （`origin/main` が `2790176` へ進み、`0092-lexical-or-coverage.md` が `main` に在る）
  ——⟹ **いまは「動いている最中」ではない。**
  それでもこの ADR は (あ) のままである: **語彙チャンネルで識別子を測るのは、
  この PR で足した probe 集合の上で別途できることであり**（probe 集合は
  `recall` の呼び方に依存しない）、⟹ **順序の判断**として (あ) を先に置いた。
  ⚠ これは「語彙チャンネルを測らない」という決定ではない。
  ⭐ むしろ**この PR が足した12 probe が、その測定の土台になる**
  ——⟹ 「これが覆るとしたら」の第4項を見ること。

## 3. 🔴 既存に触っていないこと、と その理由

**⛔ 1文字も変えていないもの**【現物：`git diff` で確認】:

- `examples/chat/src/probe-set.ts`（既存 probe 7件と既定 haystack）
- `examples/chat/retrieval-baseline.json`
- 既存 arm A / B / C（`retrieval-quality.ts` の arm 構成）
- `scripts/retrieval-quality-summary*.mjs` と `retrieval-quality` ジョブ

**⟹ 新しいファイル・新しい arm・新しい基準値ファイルにした**
（`time-term-probe-set.ts` が既存 probe 集合に触らず別ファイルを足した先例に倣う）。

**理由を逐語で:**
**arm ごとに probe 母数が違う数字が1つのファイルに同居する形は、
`MRR 0.714 / hit@10 7/7` のような「存在しない arm の合成」を*増やす*方向である。**
この誤りは実際に3度起きており、ADR 0068 が一本まるごと費やして塞ごうとし、
ADR 0081 §3.2 が再発を記録している。
⟹ **7件の母数と12件の母数を同じ表・同じ基準値ファイルに混ぜない。**

**【実測】既存 arm が動いていないことは、推論ではなく実行で確かめた**
——同じ commit で `retrieval` を走らせ、`retrieval-baseline.json` の `arms` と
**完全一致**した（3 arm すべての `llmMode`/`embeddingMode`/MRR 3種/hit@1/hit@10/probe件数）。

## 4. ⭐ ローカル埋め込み vs OpenAI 埋め込みの比較 — これは副産物ではない

**この比較は、この製品が必要としている比較そのものである**（オーナー代理の指示）。【受】

`@mnemora/local-embedding` の README は「確かめていないこと」の第1項で、
**この比較を名指しで欠落として挙げていた。**逐語:【現物】

> - **`@mnemora/openai` と比べて想起の質がどうなるか**は、このパッケージの作業では測っていない。
>   上の「日本語」は**モデルカードの主張であって、この repo のゴールデンセットでの実測ではない。**

**⟹ `japanese` 群がこの空白を埋める。**
既存 arm B（`(openai, text-embedding-3-small, 256)` の記録再生・llm=deterministic・疎 haystack）と
新 `japanese` 群（`(local, ruri-v3-30m/sym, 256)`・llm=deterministic・疎 haystack）は、
**probe が同一の7件で、LLM 層も同一（`DeterministicLLMProvider`）——差は埋め込みだけである。**

| | arm B `(openai, text-embedding-3-small, 256)` | 新 `japanese` `(local, ruri-v3-30m/sym, 256)` |
|---|---|---|
| MRR | 0.714 | **0.810** |
| hit@1 | 4/7 | **5/7** |
| hit@10 | 6/7 | 7/7 |

⚠ **標本7件。⛔ ここから優劣を一般に主張しない**
（[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §3
「🔴 ⚠ 標本は probe 7件である。ここから失敗率も成功率も主張しない」）。
**順位が1つ動くだけで hit@1 は 5/7 から 4/7 になる。**
⟹ 言えるのは「**この7件・この2空間・この haystack では、ローカル側が下回らなかった**」までである。
⛔ **「ローカル埋め込みのほうが良い」と外に書かない。**

## 5. 🔴🔴 #106 の失敗を再現できなかったこと — ⛔ これを勝ちに見せない

**識別子12件は、疎・密の両条件で hit@1 = 12/12 だった。**【実測】

**⟹ このベンチは、#106 が報告した失敗を1件も再現していない。**

⛔ **「だから #106 は問題ではない」とは書かない。**書けるのはここまでである:

> **この埋め込み（`(local, ruri-v3-30m/sym, 256)`）・この probe 集合（12件）・
> この haystack（疎60件 / 密60件）では、報告された失敗は再現しなかった。**

⚠ **そして `(openai, text-embedding-3-small, 256)` ではこの12 probe を測れない**
——カセットにこの12 probe の記録が無く、`RecordedEmbeddingProvider.embed` は例外を投げる【現物】。
⟹ ⛔ **「OpenAI の埋め込みなら失敗する」とも「しない」とも言えない。**

⚠ 併せて: ADR 0084 §9 も **「報告者の主張（同形式の別 ID に埋もれる）は実埋め込みでは
単純な形で再現しなかった」**と記録している【現物】——**再現しなかったという観測は2本目である。**
それでも #106 は**閉じない**。再現しないのは「この条件では」であって、
報告者の環境（実データ・別の埋め込み・別の密度）を否定しない。

## 6. 密な haystack の設計を、値を見る前に1度だけ固定した

⛔ **欲しい数字が出るまで的を動かしていない。**

- `identifiersSparse`（既定 haystack、識別子0件）を**先に**測った ⟹ 全12 probe が hit@1。
- **その結果を見た後**、#106 の逐語「同じ形式の別の識別子が近傍に来て、欲しいものが埋もれます」を
  表す第3の条件（`identifiersDense`。probe と同じ書式ファミリーの識別子を計60件含む haystack）を
  **1度だけ設計し、1度だけ測った。**
- **値を見てから haystack や probe を作り直していない**
  （`identifier-probe-set.ts` の `DENSE_IDENTIFIER_FAMILIES` のコメントに、この経緯を残してある）。
- ⛔ **`sparse` を `dense` に差し替えていない。**両方とも出す
  ——「疎条件では #106 を表していなかった」という**発見そのものを消さない。**

## 7. ⛔ 門にしない理由、と ⚠ 「なぜ*今は*門にしないか」

ADR 0088 §2.1 が **「標本7件では閾値の門は偽陽性を出す」**として明示的に採らなかった案である。
この ADR の probe は 7件・12件・12件であり、**同じ理由がそのまま当たる。**

⚠ **「なぜ*今は*門にしないか」を1行残す**（そうしないと、次に読む人が
「CI に載っているのに門にしないのは怠慢だ」と読む）:

> **probe を増やした後に、その母数で偽陽性が出ないかを実測してから、別途決める。**
> 門を置く条件は「標本が増えたこと」ではなく「**増えた母数で偽陽性率に上限を置けると測れたこと**」である。

⛔ **偽陽性率を上限で抑えられない門は、いずれ無視されるか無効化される。それは門が無いより悪い**
（ADR 0088 §2.1 の逐語）。

**⚠ ただし1つだけ、意図して赤くする経路がある**——**モデル重みを取得できなかったとき**、
`identifier-probes` の段自体は非0で終わる（`process.exitCode = 1`）。
**これは「想起の質の門」ではない。「測れなかったことを緑にしない」という別の線である。**

## 8. ⭐ 要約スクリプトが基準値を読んでいなかった — ADR 0088 §3 が名指しした形の再発だった

**正直に書く。この PR は、レビューの時点で ADR 0088 §3 の失敗形を再現していた。**

【現物】`scripts/identifier-probe-summary.mjs` と `-lib.mjs` は
`examples/chat/identifier-probe-baseline.json` を**読んでいなかった。**
doc コメントはその理由に「⛔ 門にしない」を挙げていた。

🔴 **それは取り違えである。「⛔ 門にしない」と「⛔ 基準値と比べない」は別のことである。**
ADR 0088 §3 は**両方を同時にやっている**——基準値と diff を取って Job Summary に出し、
**かつ**相違では落とさない。そして §3 は、この repo の先例（`ci.yml` の `compare` ステップ）を
挙げて逐語でこう書いていた:【現物】

> **⟹ 約束したのは「表を生ログに出すこと」であり、表の中身に対する assertion は1つも無い。**
> …**⟹ 気づくかどうかは、人間が生ログを開くかどうかに委ねられている。**
> **⛔ この ADR は同じ形を繰り返さない。**

**基準値ファイルはコミットされているのに、誰もそれと比べない。
⟹ 値が動いても誰も気づかず、誰も基準値を更新せず、
⟹ 新しい値が PR の diff に現れる輪が閉じない。**——**これが、その繰り返しだった。**

**⟹ 直した形は ADR 0088 §3 の3点そのままである:**

1. `--baseline <path>` を足し、CI ジョブで `examples/chat/identifier-probe-baseline.json` を渡す。
2. **一致していれば1行で黙り、違うときだけ展開する**（⭐ §3-3「常に同じ量を出す観測口は読まれない」）。
3. ⛔ **相違では落とさない（`exit 0`）。**非0になるのは**入力そのものが壊れているとき**だけ
   （JSON が読めない・`status` が未知・`measured` なのに必須項目が無い・基準値が壊れている）。

**🔴 そして比べる項目は数字だけではない。**
`embeddingSpace`（`provider`/`model`/`dimensions`）・`haystackKind`・`label` も比べる。
⛔ 数字だけを比べると、**空間や haystack 条件が変わったのに数字が同じ**場合を
「一致」と出してしまう——256次元は両方の空間で同じなのだから、これは実際に起こりうる。

**🔴 `status: "weights_unavailable"` のときは、比較を1つも出さない。**
オーナー代理の逐語:【受】

> **私が怖いのはジョブが落ちることではありません。
> 『HF から取れなかった』が『想起の質が下がった』に見えることです。**

⟹ ⛔ **「測れなかった」を「基準値と違う」に化けさせない。**
`--baseline` を渡していても、`weights_unavailable` の要約には比較節が1つも出ない。

### 8.1 ⚠【実測】そのレビューで、もう1つ食い違いが出た — `label` が条件を落としていた

**基準値ファイルに記録された `japanese` 群の `label` と、
bench が実際に出す `armLabel` が一致していなかった。**【実測】

```
実測（bench が出した）: identifier-probes/japanese(llm=deterministic, embedding=local/ruri-v3-30m/sym/256次元)
基準値（コミット済み）: identifier-probes/japanese(llm=deterministic, embedding=local/ruri-v3-30m/sym/256次元, haystack=sparse)
```

⚠ **渡された「基準値は実測と一致している」という前提は、**
**基準値ファイル自身の `provenance.note` が列挙している項目
（`mrrOverall`/`hit1Count`/`hit10Count`/`probeCount`/`embeddingSpace`/`haystackKind`）
については成り立っていたが、`label` はその一覧に入っていなかった。**【現物】
⟹ **`label` を比較項目に入れた瞬間、CI は毎回「相違あり」を出し続けることになっていた**
（＝ ADR 0088 §3-3「常に同じ量を出す観測口は読まれない」を、直した側で作り直すところだった）。

**⟹ bench 側を直した**（`cli.ts` の `japanese` 群の `armLabel` に `haystack=sparse` を足す）。
**基準値の値は書き換えていない。**理由: この群の `haystackKind` は JSON でも Job Summary の表でも
`sparse` と名乗っている——**label だけがその条件を落としているのは、
「条件を落とした数字」を label の側で作ることである。**
⟹ 併せて、**各群の label がその群自身の条件（`llm=` / provider / model / 次元 / `haystack=`）を
落としていないことを検査する歯**を置いた。

## 9. 引き受けた負債

1. **⚠ CI が HuggingFace への外向き通信に依存する。**
   ⟹ だから「取得できなかった」を区別する preflight（`warmupLocalEmbedding`）と、
   Job Summary の分岐（`weights_unavailable`）を置いた。
   **⚠ CI 上でモデル重みのキャッシュ（`actions/cache` ＋ `MNEMORA_LOCAL_EMBEDDING_CACHE_DIR`）が
   実際に効くかは、この ADR の時点では実測していない**
   ——キャッシュの効きは2回目以降の run でしか観測できず、
   `transformers.js` の既定キャッシュ位置が環境依存であることは【実測】だが、
   **CI ランナー上でヒットしたことは確かめていない。**
2. **⚠ 標本は 7件 / 12件 / 12件のままである。**閾値の門を置くには足りない（ADR 0033 §3）。
   Issue #109 の項目1「数十件程度」には**まだ届いていない**——開けたのは道であって、到達ではない。
3. **⚠ 新 arm の probe は記録の再生では測れない。**カセットの鍵が入力の SHA-256 だからである。
   ⟹ **この12 probe には「OpenAI 埋め込みでの値」が存在しない**（§5）。
4. **⚠ `identifier-probes` は arm を選ぶ口を持たない**（3群すべてが走る）。
   `retrieval` と同じ形の負債である（ADR 0088 負債2）。
5. **⭐ 要約スクリプトが基準値を読んでいなかったこと自体が、ADR 0088 §3 が名指しした形の
   再発だった**（§8）。**レビューで見つけて直した。**
   ⟹ **仕組みで止まったのではなく、人が読んで気づいた。**
   だから配線の側にも歯を置いた（`ci-yml-identifier-probes-wiring.test.mjs`
   が `--baseline` の指定そのものを固定する）——しかし
   **「次に同じ形を作らない」ことまでは、まだ仕組みになっていない。**
6. **⚠ 文言の二重管理が1つ増えた。**`WEIGHTS_UNAVAILABLE_PREFIX`（TS）と
   `WEIGHTS_UNAVAILABLE_PHRASE`（`.mjs`）——CI の Job Summary の段は `tsx` を通さないため
   import できない。両側の歯が逐語で検査しているので、片方だけ変えれば赤くなる。

---

## 検討して採らなかった案

- ⛔ **カセットを録り直す**（§2 の (い)）。鍵が無く、probe が1件も増えない。
- ⛔ **語彙チャンネルだけで測る**（§2 の (う)）。的が動いている最中である。
- ⛔ **既存 `retrieval` の probe 集合に識別子 probe を足す。**
  カセットの鍵が変わって既存 arm が全部落ちる【現物】。かつ母数の異なる数字が同居する（§3）。
- ⛔ **`identifiersSparse` を `identifiersDense` に差し替える。**
  「疎条件では #106 を表していなかった」という発見が消える（§6）。
- ⛔ **MRR の閾値で落とす門を置く。**§7。標本が足りない。
- ⛔ **基準値との相違で落とす門を置く。**§7・ADR 0088 §2.1。
- ⛔ **基準値を CI が自動更新する。**⭐ 手で更新する手間は目的である
  （ADR 0088 負債3）——更新しないと差分が Job Summary に出続け、
  **意図した変化なら新しい値が PR の diff に必ず現れる。**
- ⛔ **`packages/local-embedding` のコードを変える。**
  `cacheDir` / `createPipeline` は**既にある口**であり、**使うだけにした。**
- ⛔ **`weights_unavailable` のときに前回値・`0`・`null` を埋める。**
  「測ったら0件だった」と区別が付かなくなる（ADR 0008「無いには種類がある」）。

## これが覆るとしたら

- **標本が数十件になり、その母数で偽陽性率に上限を置けると実測できたとき。**
  そのとき「⛔ 門にしない」は覆る——**それが Issue #109 を本当に閉じる一手である**
  （ADR 0088 の「これが覆るとしたら」第1項と同じ）。
- **モデルを差し替えたとき。**`space.model` が変わり**別空間になる**（ADR 0085 の
  「`/sym` を消さないこと」）——このとき `japanese` 群の 0.810 は
  arm B との比較材料としての意味を失い、基準値は測り直しである。
- **CI に実 API の鍵が入ったとき。**§5 の「OpenAI 埋め込みでは測れない」が覆り、
  12 probe を両空間で測れるようになる——**#106 の再現・非再現をはじめて空間間で比べられる。**
- **`recall` の候補生成が語彙チャンネルを既定に含めたとき**（ADR 0092 の先）。
  そのとき識別子 probe の 12/12 は「埋め込みだけで引けた」ことを意味しなくなる
  ——**何が引いたのかを分けて測り直す必要がある。**
