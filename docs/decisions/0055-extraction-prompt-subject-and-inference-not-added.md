## 文脈: ADR 0033 が自分で挙げた「覆る条件」の1つを測った

[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) は `retrieval` ベンチの
`hit@1` が 4/7 である状態を測り、**§7 で「スコアに主語一致の項を足す」「スコアに時制の項を足す」
「`limit` や `scoreThreshold` を調整して3件を通す」を却下した。**

**⚠ ただし §9（これが覆るとしたら）は「抽出プロンプトを変えたとき」を自分で挙げていた。**【現物】
**⟹ 抽出の側は §7 の却下リストの外に在った。**この ADR は、その空白を実 API で測り、
**測った結果として「採らない」と決めた記録である。**

**この ADR は `hit@1` を上げた記録ではない。**数字は動いた（4/7 → 5/7）が、
**決定の理由は数字とは別の場所に在る。**

---

## 決めたこと

**抽出プロンプト（`packages/core/src/extraction.ts` の `buildExtractionPrompt` の `system`）に、
「主語を復元する1文」も「推論を生成する1文」も足さない。**

理由は3つで、どれも `hit@1` の値とは別の場所に在る（詳細は「決定の理由」節）。

1. **`stated` / `inferred` の区別を汚す。**
2. **記憶の件数を膨らませ、北極星の物差しに逆行する。**
3. **`hit@1` の +1件は改善ではなく、run ごとに揺れる運である。**

### ⚠ 決めていないこと

**「`hit@1` を上げない」とは決めていない。「この経路では採らない」だけである。**

**⟹ 空白は開いたままにしてある。**この ADR を「想起の質の改善は却下された」と読まないこと。
次の一手の候補は「travel と時制」節に書いた。

## 測った条件（再現できるだけの手順）

**⚠ この節は、次に読む人が18 run を払い直さずに済むために在る。**

### 器の制約【実測】

**測った器には Postgres も docker も `DATABASE_URL` も無く、公式の
`pnpm --filter @mnemora/example-chat run retrieval` は1回も実行できない**
（`examples/chat/src/cli.ts` の `requireDatabaseUrl()` を全サブコマンドが通る）。【現物】

**⟹ そこで、`runRetrievalQualityArm`（`examples/chat/src/retrieval-quality.ts`）を
そのまま import して呼ぶ計測用スクリプトを使い、`Runtime` の依存だけを
`packages/testkit/src/__fixtures__` のインメモリ実装5つに差し替えた。**

- `hashContent` は `packages/postgres` の `sha256Hex` と同じ形（sha256 hex）。
- provider は `createProviders`（`examples/chat/src/providers.ts`）へ
  `MNEMORA_LLM=openai` / `MNEMORA_EMBEDDING=openai` を渡す。**arm C（本物LLM+本物の埋め込み）だけ**を走らせた。
- `ArmReport.probes[].scoreDetails` は `digest` しか持たないため、gold/distractor が実際に
  どんな `content` になったかは `MemoryStore.createObservationWithOutbox` /
  `createMemoryWithOutbox` を計測スクリプト側で横取りして記録した
  （`usage-meter.ts` が `client.chat.completions.create` を横取りするのと同じ手法。
  `retrieval-quality.ts` と `packages/testkit` の本体は変更していない）。

### 変えなかったもの【実測】

- `runRetrievalQualityArm` のロジック本体（import して呼ぶだけ）。
- `recall()` に渡す引数・`scoreThreshold`・`limit`・スコアの重み。
- probe set（`PROBES`、7件）と haystack（60件）。
- **⟹ 変えたのは抽出プロンプトの `system` 文字列だけである。**

### 4条件（追加した文は逐語）【実測】

`system` 文字列の末尾（「…何も記憶に値しない場合は空配列を返してください。」の直後）へ、
以下を連結した。**それ以外の差分は無い。**

| 条件 | 追加した文（逐語） |
|---|---|
| **baseline** | （追加無し） |
| **主語復元** | 「日本語では主語がしばしば省略されます。その記憶が誰についての事実かを、content に必ず明示してください（話者本人についての事実なら「私は」のように補うこと）。」 |
| **推論生成** | 「明示された事実から自然に導ける事柄があれば、それも provenanceKind: 'inferred' として併せて記録してください。」 |
| **両方** | 上記2文をこの順で連結 |

`@mnemora/core` は `dist` を経由して解決されるため、**条件を当てるたびに
`pnpm --filter @mnemora/core run build` を挟んでいる。**【実測】

### 話題語の機械検査【実測】

**追加した文が probe の話題語を含まないことを、機械的に検査した。**
`PROBE_TOPIC_KEYWORDS`（`examples/chat/src/probe-set.ts`）の**33語**を読み込み、
追加文が部分文字列としてそれを1つも含まないことを条件ごとに確認した——**4条件すべて「重なり無し」。**

**⚠ これは目視ではない。**プロンプトに話題語を入れることは
「数字が良くなる方向へ測る条件を選び直す」ことであり、
[ADR 0022](./0022-fake-provider-compare-does-not-claim-recall-quality.md) が禁じている形に当たる。

### 費用【実測】

**実 API 18 run の合計 $0.094634**（1 run あたり **$0.004455〜$0.006409**）。
1 run の内訳は baseline で `chat.completions.create` 74回 / `embeddings.create` 82回。
1 run の所要は約100秒（3本並列で回した）。

**⚠ この額は `usage-meter` が公開価格表から出した概算であり、OpenAI の請求 API から取得した実額ではない**
（run のログ自身がその注記を出す）。

## 決定の理由

### 1. 🔴 `stated` / `inferred` の区別を汚す【実測】

**主語復元の1文は、原発話が述べていない「話者との関係」を付加し、それを
`provenanceKind: 'stated'` として保存する。**

| 条件 | distractor 7件のうち「私…」で始まる `content` になった件数 |
|---|---|
| baseline | **0件**（6 run すべて） |
| 主語復元 | **1〜3件**（6 run すべてで発生） |
| 両方 | **2〜7件**（3 run すべてで発生） |

実際に保存された `content` の例【実測】: 「**私の**妹の好きな色は緑です。」
「**私の**同僚は Go を推しています。」「**私は**先月大阪へ出張しました。」
——**いずれも `provenanceKind` は `stated` である。**

gold 側も崩れる: 「**私は好きな色は青です。**」「**私は** TypeScript より Rust のほうが好みです。」
（二重主語。主語復元の6 run 中5 run で発生）。【実測】

**⟹ これはこの repo の芯そのものに触る**——**名乗れる以上の精度を主張しない。**
[ADR 0011](./0011-no-window-count-in-ann-stage.md) が
「`hnsw.ef_search` に依存する件数を `countKind: 'exact'` と名乗ることはできない」として
機能そのものを落としたのと、**同じ族の破れである。**
[ADR 0035](./0035-recalled-memory-provenance-kind.md) が `recall()` の返り値に
`provenanceKind` を載せたのも、この区別が呼び出し側から見えることに価値が在るからである。

**⟹ `hit@1` の +1件と引き換えにしてよいものではない。**

### 2. 🔴 推論生成は量を膨らませ、北極星の物差しに逆行する【実測】

記憶件数 **75件 → 129〜138件（+72〜84%）**（推論生成）、**90〜93件（+20%）**（両方）。

北極星の物差しは「使う側が会話ログを全部プロンプトへ積むのをやめられたか」であり、
**積む候補を倍近くに増やす変更は、物差しに逆行する。**
[ADR 0022](./0022-fake-provider-compare-does-not-claim-recall-quality.md) が
「`limit` を上げれば返る `memories` の量が増える——物差しに逆行する変更を、表を ✅ にするためだけに行う」
として却下したのと同じ形である。

**⚠ そして `diet` が1位を取った3 run（推論生成1・両方2）は、3件すべて1位が `inferred` の言い換えだった**【実測】——
「私は牛乳が合わない可能性がある。」「…牛乳を避けるべきです。」「牛乳に対して敏感である。」。
**`gold` の `stated` な記憶は1度も勝っていない。**
質問は「私が避けたほうがいい食べ物はありますか?」であり、
**生成された言い換えが質問の言い回しに寄ったことで1位になっている。**

**⟹ 直したのは想起ではなく、当てやすい文を増やしたことである。**

### 3. ⚠ `hit@1` の +1件は改善ではなく運【実測】

主語復元系の9 run で、`exercise` の `goldRank` は
**LLM が distractor 側にも一人称を付けたかどうかと 9/9 で一致した。**

| distractor に一人称が付いたか | `exercise` の `goldRank` |
|---|---|
| 付いた（3 run） | **2, 2, 2** |
| 付かなかった（6 run） | **1, 1, 1, 1, 1, 1** |

**⟹ 効いているのは「gold に主語が入ったこと」ではなく「gold と distractor のどちらに一人称が付いたか」である。**
**同じプロンプトでも、それは run ごとに揺れる。**
**⟹ 「4/7 → 5/7」を成果として数えられない。**

## 実測で崩れた主張

**⭐ この節が、この ADR のいちばん再利用できる部分である。**
以下は**すべてこの ADR の書き手へ与えられた前提であり、測って崩れたものである。**

### (a) 「原発話の側は7 probe すべてで対称に書かれている」は偽【実測・現物】

`examples/chat/src/probe-set.ts` と `examples/chat/cassettes/retrieval.json`
（**カセットは応答と一緒に `prompt` も保存しているので、入力↔出力を直接突き合わせられる**）を
突き合わせた結果:

| probe | `goldRank`（baseline） | gold **原発話**の一人称主語 | gold **抽出後**の一人称 | distractor 原発話の三人称 |
|---|---|---|---|---|
| color | 1 | **有**（「私の」） | **無**（落ちる） | 有 |
| pet | 1 | **有**（「私は」） | **無**（落ちる） | 有 |
| exercise | 2 | **無** | 無 | 有（「父は」） |
| diet | 6 | **無** | 無 | 有（「妻は」） |
| family | 1 | 無 | 無 | 有（「姉は」） |
| language | 1 | **無** | 無 | 有（「同僚は」） |
| travel | 2 | **無** | 無 | **無** |

**「抽出器は一人称の主語だけを落とし、三人称の主語は残す」は正しい。**
**⚠ ただし落とせる一人称主語が原発話に在ったのは `color` と `pet` の2件だけであり、
それは1位を取っている2件である。**

**⟹ 失敗する3件（exercise / diet / travel）の gold は、原発話の時点で主語を持たない。
⟹ 非対称は抽出の段で作られたのではなく、probe の fixture に最初から書かれている。**

### (b) 主語は十分条件でも必要条件でもない【実測】

- **`language` は `exercise`/`diet` と同じ形**（gold 主語無し・distractor 三人称有）**なのに 18 run 中16 run で1位。⟹ 十分条件ではない。**
- **`travel` は gold も distractor も人称主語を持たない**（「来月、京都へ出張する。」対「先月、大阪へ出張した。」）**のに 18 run 中17 run で2位。⟹ 必要条件でもない。**

**⟹ 「主語の一致／非一致」で失敗3件を説明することはできない。**
ADR 0033 §3 が自分で書いていた警告（「『主語が明示されていれば1位になる』ではない」）と同じ向きである。

### (c) 「一人称の主語を落とさない」という条件は、測る前に答えが出ている【実測】

**失敗3件の gold には、保てる一人称主語が原発話の時点で存在しない**（上の表）。
**⟹ この条件は定義上 `color`/`pet` にしか触れず、その2件は既に1位である。**
**⟹ 実 API の枠を使わずに、(a) の表で答えが出ている。**

## travel と時制 — 「却下」ではなく「前提が足りない」

**`travel` は18 run 中17 run で2位だった**（例外は推論生成の1 run で3位）。**⟹ どの条件でも動かない。**【実測】

gold「来月、京都へ出張する。」対 distractor「先月、大阪へ出張した。」に対し、
質問は「次の遠出の行き先はどこ**でした**か?」である。**⟹ 分けているのは時制である。**

**⚠ ここを読む人が止まらないように書いておく。**
ADR 0033 §7 は「スコアに時制の項を足す」を却下したが、**その理由は
「§4 のとおり、入れる値が無い。`occurredAt` を埋めるほうが先である」であった。**【現物】

**⟹ これは「時制で順位を分けることを禁じた」のではなく、「前提が足りない」と書いたのである。**

前提の現状【現物】:

- [ADR 0037](./0037-callers-pass-occurred-at.md)（採用、2026-09-06）が
  **`ObserveInput.occurredAt` を入口から出口まで実際に通した。**口は在り、`backfill` デモが使っている。
- **⚠ しかし `retrieval` ベンチは `occurredAt` を渡していない**
  （`examples/chat/src/*.ts` を grep すると `occurredAt` は `cli.ts` と `backfill.ts` にしか現れない）。
  **⟹ このベンチの中では、`Memory.occurredAt` は依然として `null` である。**
- [ADR 0036](./0036-clamp-freshness-at-one.md) が `freshness` を 1 で頭打ちにしており、
  「まだ起きていない出来事は、最も古びていない」は既に効く形に在る。

**⟹ 時制の項を検討できるようになる前提は、「`retrieval` の probe set が `occurredAt` を渡すこと」である。**
**⚠ この ADR は、それを足すとは決めていない**（`hit@1` を良くする方向へ probe set を書き換えることは、
測る条件を選び直すことになりうる。そこは別の判断である）。

## 採らなかった案

- **主語復元の1文を、`stated` を汚さない形に書き直して再測する。** 今回は採らない。
  「誰についての事実か」を明示させることと「原発話が述べていない関係を付加しないこと」を
  同時に満たす文面が在るかは分かっていないが、**それを探すのは「プロンプトの文面を回して数字を追う」ことに
  近づく。**まず (a) が示した「fixture の側に主語が無い」という形を、どう扱うかの判断が先である。
- **「一人称の主語を落とさない」条件を実 API で測る。** 採らない。**(c) のとおり、測る前に答えが出ている。**
- **カセット（`retrieval.json` / `compare.json`）を録り直して、変えたプロンプトを門へ載せる。**
  **採らない**——この ADR が「プロンプトを変えない」と決めたので、録り直す必要が消えた。
  **⚠ カセットの鍵はプロンプト全体のハッシュであり、`system` を1文字変えると全件が無効になる**【受】ため、
  もしプロンプトを変えるなら録り直しの道を先に決める必要が在る。**この ADR はその道を決めていない。**
- **probe の文面・`limit`・`scoreThreshold` を回して3件を通す。** ADR 0022 と ADR 0033 §7 が却下済み。ここでも採らない。
- **実 API をこの測定ごと CI へ繋ぐ。** 採らない
  （[ADR 0019](./0019-real-openai-measurement-cost.md) §5c。起こす回数に比例して実費と非決定性が入る）。

## 引き受けた負債

- **この測定は公式の `retrieval`（Postgres 経由）では再現していない。**
  インメモリの store 5つで組んだ `Runtime` に対する実測である。
  `runRetrievalQualityArm` 本体と `recall()` の引数は変えていないが、
  **store の実装差が順位に影響しないことを、この ADR は検査していない。**
- **カセットは録り直していない。⟹ `retrieval.json` は baseline のプロンプトに対応したままであり、
  この ADR の18 run は再生できない。**再現するには実 API を叩き直す必要が在る（約 $0.095）。
- **n は 6 / 6 / 3 / 3 であり、条件間の差に検定を当てていない。**
  「baseline は 6/6 で 4/7」「主語復元は 6 run 中5 run で 5/7」という**分布として書いてあるだけである。**
- **計測に使ったスクリプトは repo に入れていない。**
  `.scratch.ts` として器の中に置いたものであり、器が入れ替われば消える。
  **⟹ だからこの ADR の「測った条件」節に手順を書いた。**そこが唯一の保全である。

## これが覆るとしたら

- **埋め込みモデルを替えたとき。** 数字はすべて `text-embedding-3-small`(256次元) に固有である
  （ADR 0033 §9 と同じ）。
- **抽出の LLM を替えたとき。** 「distractor 側にも一人称を付けるかが run ごとに揺れる」は
  `gpt-4o-mini` の振る舞いであり、mnemora の性質ではない。**理由3はモデルの揺れに依存している。**
- **probe set の gold の書き方が変わったとき。** (a) の「失敗3件の gold に主語が無い」は
  fixture の性質である。**gold を書き換えれば、この ADR の観測はそのまま無効になる。**
- **`retrieval` の probe set が `occurredAt` を渡すようになったとき。**
  時制の項を検討できる前提が満たされる（「travel と時制」節）。
- **`stated` / `inferred` の区別を、いまより弱い契約に変えると決めたとき。**
  理由1はその区別に価値が在ることを前提にしている。
