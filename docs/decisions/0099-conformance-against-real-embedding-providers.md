# ADR 0099: 適合テストを**本物の** `EmbeddingProvider` に当てる — 足場が素直だと、歯は緑のまま嘘をつく

- 状態: 採用

## 問い

ADR 0095 は `describeEmbeddingProviderConformance`（9本の歯）を新設したが、
**当てたのは `packages/testkit` 自身の2実装だけ**で、`@mnemora/openai` と
`@mnemora/local-embedding` には当てていなかった。ADR 0095 自身がこれを負債として、
逐語でこう記録している——**「4つが同じ契約を満たすことはまだ確かめられておらず、
緑になるかも分からない」。**

⟹ **適合テストが在っても、当てた先が擬似物2つだけなら、本物については何も測っていない。**
残る2つに当てるには何が要るのか。当てたら、本物は契約を満たすのか。

---

## 文脈

### 当たっていなかった理由は、設計ではなかった

ADR 0095 が2つに留めた理由は**進行**（片方は別作業の範囲、片方は #122 が走行中）であって、
技術的な障壁ではない。現物を読むと、**どちらの実装にも最初から注入点が在る**:

| 実装                      | 注入点                                          | 要るもの                 |
| ------------------------- | ----------------------------------------------- | ------------------------ |
| `OpenAIEmbeddingProvider` | `client?: Pick<OpenAI, "embeddings">`           | **鍵は要らない**         |
| `LocalEmbeddingProvider`  | `createPipeline?: CreateLocalEmbeddingPipeline` | **重みの取得は要らない** |

どちらのソースにも「テストのための注入点である」と明記してある
（`pipeline.ts` は「ここを差せないと、provider の検査が毎回 36MB のモデルを落とすことになり、
CI では走らせられない」とまで書いている）。⟹ **鍵も、CI の追加費用も、要らなかった。**

### 🔴 芯: 足場が素直だと、歯は緑のまま嘘をつく

注入点が在るということは、**足場が何を返すかを私たちが決められる**ということである。
そして**素直に返すと、実装のロジックを消しても歯は緑のまま通る。**実測で2回踏んだ:

1. 再生 client が `data` を**入力順のまま**返すと、`OpenAIEmbeddingProvider` から
   `index` による並べ直し（`.sort(...)`）を**丸ごと外しても**適合テストは全部緑だった。
2. 再生 pipeline / client が**空入力に空配列を返す**と、`embed()` の
   「空配列でモデル（API）を起こさない」早期 return を**丸ごと外しても**
   「`embed(ctx, [])` は `[]` を返す」の歯は緑だった。

⟹ **「本物のクラスに当てた」は「本物を測った」と同じではない。**
足場は、実装が仕事をしないと通れない形にしなければならない。

### 🔴🔴 そして、歯そのものに穴が見つかった

上の 1. を直そうとして、再生 client に `data` を**逆順**で返させた。それでもなお
`.sort(...)` を外す変異で**適合テストは全部緑のまま**だった（落ちたのは
`packages/openai` 自身のユニットテスト1本だけ）。

原因は足場ではなく、**ADR 0095 の順序の歯そのもの**にあった。当時の歯は
「`embed([a,b])[0]` と `embed([b,a])[1]` が一致するか」を見ていたが、
**入力順をつねに逆にして返す実装は、この等式を恒等的に満たす**
（`[a,b]→[vb,va]` なので0番目は `vb`、`[b,a]→[va,vb]` なので1番目も `vb`）。

⟹ **2件の入れ替えでは「入力順を守る」と「入力順をきっちり逆にする」を区別できない。**
これは順序の契約の要（ずれると memory とベクトルが1つずれて結び付く）を、
測れていなかったということである。

---

## 決定

### 決定1: 本物のクラスに、**本物のベクトル**を流して当てる

4実装すべてに `describeEmbeddingProviderConformance` が当たる状態にする。
追加する2つは、どちらも**注入点を使って本物のクラスを構築**し、そこへ
**本物が実際に返したベクトル**を流す。

- `@mnemora/openai`: `examples/chat/cassettes/retrieval.json`（実 `text-embedding-3-small` /
  256次元 / 152件）から**3件を写して** `packages/openai/src/__tests__/fixtures/` に置き、
  それを再生する client を注入する。
- `@mnemora/local-embedding`: 本物の ruri-v3-30m (ONNX/q8) を実際に走らせて得た3件を写し、
  それを再生する pipeline を注入する。

**なぜ合成のベクトルにしないか**: 「各ベクトル長 = `space.dimensions`」「成分が有限」は、
足場が自分で作った数に対して主張しても**自己成就**する。本物の出力を流せば、
その2本は実物に対して成り立つ。

**なぜカセットを直接読まないか**: `packages/openai` の検査が `examples/chat` のデータファイルの
パスに依存すると、例の側の都合で公開パッケージの歯が壊れる。
`packages/core/src/__tests__/ann-truncation.test.ts` が ADR 0069 §5 の実測値を
provenance 付きで**写して**いるのと同じ作法を採る。⟹ 写しには
**出所・抽出コマンドの逐語・生成条件**を `provenance` として必ず持たせる。

### 決定2: 🔴 足場は「素直に返さない」

- 再生 client は `data` を**逆順**で返す（並べ直しが実行されないと出力が変わる形にする）。
- 再生 client / pipeline は**空入力で例外を投げる**（早期 return を消すと歯が落ちる形にする）。
- どちらも**記録に無い入力で例外を投げる**（黙って作りものへ倒れない。ADR 0051 と同じ規律）。
- 再生 client は `model` / `dimensions` が期待どおり渡ってきたかも検査して、違えば投げる。

### 決定3: 🔴🔴 順序の歯を、2件の入れ替えから**3件の巡回**へ強める

`embed([a,b,c])` と `embed([b,c,a])` を比べ、**同じテキストの位置どうし**が一致することを見る
（`abc[0]=bca[2]` / `abc[1]=bca[0]` / `abc[2]=bca[1]`）。

「つねに逆順」の実装はこれを満たせない（`[a,b,c]→[vc,vb,va]` / `[b,c,a]→[va,vc,vb]` で
`abc[0]=vc` に対し `bca[2]=vb`）。⟹ 実測でも、強めた後に同じ変異を入れ直すと
**順序の歯がちょうど1本落ちる。**

⚠ **バッチ不変性は相変わらず要求していない**——比べる2回はどちらも3件のバッチであり、
「`embed([a,b])` が `embed([a])` と `embed([b])` の連結と一致するか」は依然として問うていない
（ADR 0095 決定5 を維持。**⛔ 測っていないものを契約にしない**）。

⚠⚠ **これは ADR 0095 の決定を動かす変更ではない。**動かしたのは**歯の測り方**だけであり、
**契約の側は1バイトも変えていない**——ADR 0095 決定1 が並べた9本の項目も、
「返る順序が入力順に対応する」という要求そのものも、そのままである。
実測がそれを裏づけている: **4実装すべて（本物の ONNX モデルを含む）が、強めた後も緑。**
契約が動いていたなら、どれかが落ちていたはずである。

⟹ **次に ADR 0095 を読む人へ**: 0095 決定1 の「順序の対応」の歯は、いまは
2件の入れ替えではなく**3件の巡回**で測られている。**0095 と歯が食い違っているのではなく、
0095 の要求を測れるようにしたのがここである。**（この変更はオーナーが承認している。）

### 決定4: `deterministic` は**実測して**宣言する

| 呼び出し口                                         | `deterministic` | 根拠                                                                                                                 |
| -------------------------------------------------- | --------------- | -------------------------------------------------------------------------------------------------------------------- |
| `OpenAIEmbeddingProvider`（再生）                  | `true`          | 決定性を与えているのは再生。**実 API の話ではない**                                                                  |
| `LocalEmbeddingProvider`（再生）                   | `true`          | 同上                                                                                                                 |
| `LocalEmbeddingProvider`（**本物のモデル**、live） | `true`          | ⭐ **実測**: 同じ 3 本を 2 回、**768 成分を要素ごとに比較して不一致 0 件・最大絶対差 0**                             |
| `OpenAIEmbeddingProvider`（**実 API**、live）      | `false`         | **私たちは実 API の再現性の保証を持っていない**（ADR 0095 決定1 の却下理由そのもの）。⟹ 2本は `it.skip` で名前が残る |

⛔ **「たぶん決定的だから」で `true` にしないこと。**上の3行目だけが実測に裏打ちされている。

### 決定5: live 2本にも同じ9本を当てる（opt-in、**CI の費用は増えない**）

`describe.skipIf(!live)` で包む。**中の `it` の名前が `↓` として出力に残ることを実際に走らせて
確かめてある**（ADR 0095 決定3 の要求——「そもそも歯が無い」と「走って通った」を
ログ上で区別できること——を満たす）。

- `MNEMORA_LIVE_LOCAL_EMBEDDING` も `OPENAI_API_KEY` も **CI のどのジョブにも設定されていない**
  ⟹ **CI が落ちる回数は1回も増えない。**
- ⚠ 実 API 側は live 1回あたり `embeddings.create` が **5回**増える（ADR 0019 §5c の規律で明記する）。

### 決定6: suite に `timeout?: number` を足す

本物の実装は vitest の既定5秒に収まらない（モデルのロードだけで約 7.5 秒）。
`createProvider` は `it` ごとに呼ばれる契約なので、その費用は9回掛かる。

⚠ **`deterministic` と違い、こちらは省略できてよい**——`undefined` は「vitest の既定」という
曖昧さの無い意味しか持たない。**ADR 0095 決定2 の理由をここへ持ち込まない。**

## 検討した選択肢

### 5.1 合成のベクトルを注入する（却下）

いちばん簡単だが、「ベクトル長 = `space.dimensions`」「成分が有限」が
**足場の自己申告に対する検査**になる。本物の出力を写す費用は 1 ファイル約 20KB であり、
払う価値がある。

### 5.2 `examples/chat/cassettes/retrieval.json` を検査から直接読む（却下）

写しが要らなくなる代わりに、公開パッケージの歯が例アプリのデータファイルのパスと
再録内容に依存する。決定1 の理由。

### 5.3 CI で本物のモデルを走らせて適合テストを当てる（却下）

`identifier-probes` ジョブは既に重みを落としており（`actions/cache@v6`、
キー `local-embedding-ruri-v3-30m-q8-v1`）、費用は思ったほど大きくない。
それでも却下したのは、**適合テストは「取得できたかどうか」に左右されてはならない**からである。
重みが取れなかった run で適合テストまで赤くなると、**契約が壊れたのか、
ネットワークが落ちていたのかが、赤の色からは区別できない。**
⟹ **CI から測るのは注入版、本物は opt-in の live。**この分担を保つ。

### 5.4 2件の入れ替えの歯を残したまま、3件の巡回を**足す**（却下）

巡回は入れ替えを厳密に含む（入れ替えを通す実装のうち、巡回を落とすものが在る。逆は無い）。
2本置くと、同じ契約を2度主張することになり、片方が壊れたときにどちらが本物の要求かが
読めなくなる。⟹ **置き換える。**

### 5.5 順序の歯の穴を「報告だけ」にして、直さない（却下）

穴を見つけた PR が、**本物に当てたと名乗りながら穴を残す**のはいちばん悪い形である。
⚠ ただしこれは ADR 0095 の決定に手を入れる変更なので、**PR 本文でも名指しで出し、
オーナーの判断を仰ぐ**（実装は用意したうえで、覆されたら1本戻すだけで済むようにしてある）。

## 結果（この決定が招くもの）

- **4実装すべてが、同じ9本の契約に対して緑であることが測れた。**
  ADR 0095 の負債1（「緑になるかも分からない」）は解消した。
- ⭐ **本物の ONNX モデルが9本すべてを満たすことを、実際に走らせて確かめた**
  （決定性・3件の巡回による順序の対応を含む）。これは推測ではない。
- 順序の契約が、初めて**consistent な並べ替えに対しても**測れるようになった。
- `packages/local-embedding` が `@mnemora/testkit` に devDependency で依存する
  （`packages/openai` は既にそうなっている）。**publish 対象の依存は増えない**（dev のみ）。
- 実 API を叩く人にとって、live の費用がわずかに増える。

---

## これが覆るとしたら

- **本物のモデルの決定性が崩れたとき。**別のハードウェア・別の dtype・別の onnxruntime で
  ビット単位の一致が崩れたら、live 側の `deterministic` は `false` へ落ちる。
  ⛔ **そのとき契約を緩めないこと**——落ちるのは宣言であって、契約ではない。
- **実 API が9本のどれかを満たさないと分かったとき。**鍵を持つ人が live を走らせて赤を見たら、
  それは「実装が間違っている」のか「契約が測れないものを要求している」のかを**分けて**
  判断する材料になる。⛔ **赤を消すために契約を書き換えないこと。**
- **バッチ不変性が必要になったとき。**いまは測っていない。要るなら、まず measure してから
  契約にする（ADR 0095 決定5 を維持）。

## 確かめていないこと

- 🔴 **実 API（`OPENAI_API_KEY` を使う経路）には、一度も当てていない。**
  この変更を書いた器に鍵が無く、CI にも鍵が無い。⟹ **「実 API が9本を満たすか」は、
  いまだ誰も測っていない。**置いたのは、鍵を持つ人が1コマンドでそれを測れる口だけである。
- **バッチ不変性**（`embed([a,b])` が `embed([a])` と `embed([b])` の連結と一致するか）。
  意図して測っていない（ADR 0095 決定5）。
- **決定性の実測は「この器・この版で測ったら一致した」である。**仕様の保証ではない。
- 🔴 **適合テストは「どのモデルを実際に読み込んでいるか」を見ていない。**
  変異試験の陰性対照でこれを確認した——`DEFAULT_LOCAL_EMBEDDING_REPO` を
  まったく別の repo 文字列に変えても、適合テスト11本は**全部緑のまま**だった。
  `space.model` は宣言であって、読み込んだ重みの素性ではない。**この穴は塞いでいない。**
- **`LLMProvider` の適合テストは今も無い**（ADR 0072 負債1 の埋め込み側だけを返済した状態が続く）。
