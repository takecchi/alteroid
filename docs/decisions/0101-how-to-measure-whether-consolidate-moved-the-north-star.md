### 2. 🔴【現物】「いまの arm 構成に『統合済み』の arm を足す」は素直に通らない

### 3. 🔴🔴【現物】擬似 LLM の統合は、content を育て、digest を切る

```ts

...

```

⟹ **統合結果の `content` は「プロンプト全文」**（統合の指示文＋対象記憶の全文）であり、

**この非対称が、この ADR のいちばん重い制約である。**

- **digest の側**（41字に切られる）も擬似物の性質であり、**実 LLM の要約の長さについて何も言っていない。**
- ⟹ **recall が実際にプロンプトへ載せるのは `digest` である**（`byTier.digest`）。
  **⟹ いちばん物差しに近い軸（載る量）は、まるごと LLM 依存である。**

## 決定

### 決定1: 🔴 主軸は**トークン数**である。件数は必ず併記するが、成否の判定には使わない

**理由（4つ。上ほど強い）:**

1. **北極星の逐語が「会話ログを全部プロンプトへ積むのをやめられたか」であり、
   問い1 が「毎回渡す量」である。**プロンプトの「量」の単位は**行数ではなくトークンである。**
2. **`docs/north-star.md` の物差しが、件数を名指しで否定している。**逐語:【現物】
   「**記憶の件数でも、機能の数でも、recall の平均スコアでもない。**」
3. 🔴 **統合は N 件を1件にするが、その1件は元のどれよりも長くなりうる**（文脈 §3 / §4）。
   ⟹ **件数だけを見ると `5 → 1` の「勝ち」が出るのに、トークンは増えていることがありうる。**
   **⟹ 件数は北極星と逆へ動きうる。トークンは逆へ動けない。**
4. **計器が既に在る。**`RecallUsage` は `chars` / `estimatedTokens` / `byTier` / `indexChars` を
   返す（`docs/recall.md` §6）。**⟹ 新しい計器を作らずに済む。**

**⛔ それでも件数を落とさない。**トークンが動いた理由（件数が減ったのか、1件が長くなったのか）は、
**件数が無いと読めない。**⟹ **両方出す。判定に使うのはトークンだけ。**

### 決定2: 🔴🔴 主指標は「載った量」ではなく**「gold を載せるのに要った最小のトークン予算」**である

**⚠ 最初に置いた案（「recall が載せた量が何%減ったか」）は、現物に当てると落ちた。**

🔴 **recall は、予算か件数上限のどちらかで一杯まで埋める。**
⟹ **store が縮んでも「載った量」は動かない**——空いた席は別の記憶で埋まる。
⟹ **「積む量」は store の大きさではなく、呼び出し側が渡した `limit` / `budget` が決めている。**

**⟹ 統合が動かすのは「積む量」ではなく「同じ量で積める密度」である。**
統合が効いているなら、**同じ問いの答えを、より少ない予算で載せられる。**

⟹ **主指標:**

```
minBudget(probe, arm) = 予算の階段のうち、その probe の gold が載った最小の maxMemoryTokens
成功 = Σ minBudget が統合後に減り、かつ「どの予算でも載らなかった probe」の件数が増えていない
```

**⭐ これが Issue #136 の芯（「同じ想起の質をより少ない記憶で達成できたか」）に、
分子と分母の両方を持つ形を与えたものである**——質（gold が載ったか）を**保ったまま**、
量（トークン予算）を**動かす**。

**⛔ 「載らなかった probe」を 0 や最大値で埋めない。**別の欄で数える
（`docs/recall.md` の「『無い』の種類を潰さない」の規律を、数に当てたもの）。

### 決定3: 🔴🔴 ⟹ そして、件数とトークンを区別することは、擬似 LLM では原理的にできない

**決定1 でトークンを主軸に選んだが、擬似 LLM の下では、その2軸が同じものに退化する。**

**文脈 §3 の通り、擬似 LLM は `digest` を 40 字で切る。**
⟹ **すべての記憶の digest が一律の長さになる。**
⟹ **「載った量（トークン）」は「載った件数」の定数倍**であり、`minBudget` は
**「gold の順位」の定数倍**でしかない。

**⟹ 擬似 LLM で測れるのは「順位と件数」までであり、
「1件あたりの量が変わったか」——統合がしたと主張する仕事そのもの——は測れない。**

| 軸 | 擬似 LLM で測れるか | なぜ |
|---|---|---|
| `active` の件数 | ✅ **測れる。**LLM に依存しない | 統合は `active` を `N → 1` にする。機構の性質であり、LLM の出力と無関係 |
| gold の順位 / `minBudget` | ✅ **測れる**（`local` 埋め込みは本物） | 順位を決めるのは `similarity` ただ1項（ADR 0081 §1） |
| **1件あたりのトークン量** | ⛔ **測れない** | digest の長さは LLM が決める。擬似物は一律 40 字で切る |

⟹ **「件数とトークンの両方を出す」のは読者の便宜ではない。
片方は測れるが意味が弱く、もう片方は意味が強いが鍵が要る、という非対称の記録である。**

### 決定4: 測る順序を「縮んだか」→「質が落ちていないか」に固定する

Issue #136 のコメント（`takecchi`、2026-09-10T13:01:58Z）の逐語:【現物】

> ⭐ **「想起の質が上がったか」より先に、「そもそも縮んだか」を測るほうが安い。**

**⟹ この ADR は前者（量）だけを測る。**後者（質）はこの ADR で閉じない（下の「⛔ この ADR が閉じないもの」）。

### 決定6: ⛔ 門にしない

**[ADR 0088](./0088-retrieval-quality-measured-in-ci.md) §2.1 の決定をそのまま継ぐ。**
理由も同じで足りる——標本は probe 7件であり（[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §3）、

> | 4 | 「consolidate したら元の Memory を捨てる」 | **落とせた**（統合物は `basis` を解決できなければならない） |

⟹ **`active` の縮みを測るときに、`superseded` を数から落とさない。**
**JSON は `active` と `active + superseded` の両方を出す**——
**⭐ 統合は「store 全体」を必ず**増やす**。それを隠すと、縮み率は嘘になる。**

### 決定8: 退化の検知口を、数の形で出す

**⚠ Issue #136 が名指しした交絡**——「統合すると記憶が減るので、`hit@10` のような k 固定の指標は
自動的に有利になる」——に対して、この ADR は2つで応じる。

1. **予算固定の recall を併せて測る。**`budget: { maxMemoryTokens: N }` を渡し、`limit` は緩める。
   ⟹ **縛るのは件数ではなくトークン予算**にする。**⭐ 北極星の通貨は件数ではなく量なので、
   固定すべきはそちらである。**
2. **`recalledActiveShare`（= 返した件数 / `active` の総件数）を probe ごとに出す。**
   ⟹ **これが 1.0 に近づいた arm は「全部載せる」に退化しており、`hit` が上がっても
   北極星の上では負けている。**⛔ 閾値で落とさない（決定5）。**数として出して、読めるようにする。**

**⚠ そして潰しきれない分を書いておく**——統合は `active` の母数そのものを変えるので、
**arm 間で「探索対象の母数」が違う。**これは交絡ではなく**統合の本質**であり、潰せない。
⟹ **だから `activeCount` を同じオブジェクトに必ず入れる**（ADR 0088 §4「数字を、条件から離さない」）。

## 検討して採らなかった案

### 「縮める擬似統合器」を `packages/testkit` に足す（却下）

**擬似 LLM が縮めないなら、縮める擬似物を作れば鍵なしに CI で測れる。**⛔ 採らない。

🔴 **これは「測定が、測りたいものを仮定に置き換える」形である。**
**この Issue の主題は「入った と 効いた は別」であり、**
⟹ **その主題を測るために「効く前提の擬似物」を作ると、Issue が名指しした穴を
測定装置の中で再生産することになる。**

**2つ目の理由も単独で足りる**——`local` 埋め込みに載せるしかないので、
**既存 arm B/C（`openai` 空間）と比較できない別ベンチになる。**

### 既存の `retrieval` ベンチに4本目の arm を足す（この ADR では却下、順序が理由）

**文脈 §2 の通り、`recorded` 層では走らない。**走らせるには**実 API で一度録り直す**必要があり、
それは**「縮むものが在る」と分かった後の順序**である（決定3）。
⟹ **却下ではなく後置である。**この ADR は前提の測定で止まる。

### `hit@k` の改善を成功の定義にする（却下）

**Issue #136 が逐語で落としている**（「⛔ 『MRR が上がった』だけでは足りない」）。
そして k 固定の指標は、統合が記憶を減らすぶんだけ**自動的に有利になる**（決定8）。

### 件数の減少を成功の定義にする（却下）

**決定1 の理由3。**`5 → 1` は、その1件が元の合計より長ければ**北極星の上では後退**である。
そして擬似 LLM の下では**実際に長くなる**（文脈 §3）。

## ⛔ この ADR が閉じないもの

1. 🔴 **「実 LLM で縮むか」は閉じない。**決定3 の通り、**1件あたりの量が変わったかは鍵が要る。**
   ⟹ 閉じるには、**統合用のカセットを実 API で一度録る**ことが要る（ADR 0051 の経路）。
2. **想起の質は測っていない。**この ADR は量だけである（決定4）。
3. 🔴🔴 **この測り方は「統合の中身が正しいか」を一切見ない。**
   トークンが減って gold が引けても、**統合結果が事実を捻じ曲げている**
   （AI の推論とユーザーが言った事実を混ぜた——北極星の問い4）ことは**検知できない。**
   ⟹ **`basis` / provenance の検査は別の口が要る。**
   ⚠ **これを書いておかないと、次に読む人が「この数字が緑だから統合は安全だ」と読む。**

## 測ったこと

**【実測】**——この ADR の書き手が、**使い捨ての PostgreSQL 17 + pgvector 0.8.6**（`127.0.0.1`、
空の DB を作って `migrate` した）に対して自分の手で走らせた。
provider は **LLM=`deterministic`（擬似）/ Embedding=`local`（`ruri-v3-30m/sym`・256次元）**、
`OPENAI_API_KEY` は明示的に空にしてある。**probe 7件・haystack 60件・`groupSize=5`・
`recallLimit=50`・`budgetLadder=[8,16,24,32,48,64,128,256,512]`。**所要 5.3 秒。

### 1. 🔴【実測】件数は 5分の1 になり、`content` は 3倍以上に育った

| round | `active` | `superseded` | `active` の content 字数 | `active` の digest 字数 | store 全体（active+superseded）の content 字数 |
|---|---|---|---|---|---|
| 0（統合前） | **74** | 0 | **1871** | 1871 | **1871** |
| 1 | 26 | 60 | 4941 | 709 | 6595 |
| 2 | 17 | 72 | 5715 | 340 | 12093 |
| 3 | **15** | 75 | **5908** | 258 | **17784** |

**⟹ [ADR 0090](./0090-embedding-input-token-limit.md) が「⚠ 実際に単調増加することは測っていない」
と書いた筋を、擬似 LLM の下で測った: 単調増加した。**
`active` の content は **1871 → 4941 → 5715 → 5908**（**+216%**）、
store 全体は **1871 → 17784**（**9.5倍**）。
**⚠ これは擬似 LLM の性質である**（文脈 §3）。**実 LLM については何も言っていない。**

⭐ **3周しても埋め込みは1件も失敗していない**（`embeddingStatus: { ok, pending: 0, failed: 0 }`、
`embeddingFailureKinds: []`）。⟹ **ADR 0090 の 8192 トークンの壁には、この規模では届かない。**

### 2. 🔴🔴【実測】recall が載せる**件数**は、store が5分の1になっても 1件も動かない

| round | 載せた件数 | 載せた digest のトークン | `usage.chars` | うち目次帯 | **予算が縛る分（chars − 目次帯）** | `recalledActiveShare` |
|---|---|---|---|---|---|---|
| 0 | **10.00** | 206.0 | 4418.6 | 4187.0 | **231.6** | 0.135 |
| 1 | **10.00** | 186.7 | 1928.1 | 1674.4 | **253.7** | 0.385 |
| 2 | **10.00** | 141.1 | 980.0 | 782.6 | **197.4** | 0.588 |
| 3 | **10.00** | 128.6 | 770.0 | 607.1 | **162.9** | 0.667 |

**⟹ 決定2 の前提が実測で立った。**`active` が 74 から 15 へ減っても、
**recall が載せる件数は 10.00 のまま1件も動かない**——空いた席は別の記憶で埋まる。
**⟹ 「積む量」を決めているのは store の大きさではなく、呼び出し側が渡した `limit` / `budget` である。**

### 3. ⭐⭐【実測】`usage.chars` は 83% 減った。**だが、減ったのはほぼ全部が目次帯である**

`usage.chars` は **4418.6 → 770.0（−83%）**。**しかしその内訳を分けると:**

- **目次帯（`indexChars`）: 4187.0 → 607.1（−85%）**——減り分 3811 のうち **3580（94%）がここ。**
- **予算が縛る memories tier: 231.6 → 162.9（−30%）**。**⚠ round 1 では逆に増えている（231.6 → 253.7）。**

**⟹ 統合がいちばん大きく削ったのは、`docs/recall.md` §6 が「予算の対象外」と定めている帯である。**
**⛔ ここは誰も測っていなかった。**

⚠ **そしてこれを「勝ち」と読んではいけない。**目次帯の存在理由は
「**recall が0件でも、何が在るかは言える**」（[ADR 0008](./0008-absence-taxonomy.md)）であり、
**74件を 15件に畳めば、目次帯が言えることは粗くなる。**
⟹ **目次帯が縮んだのは「無駄が消えた」のか「言えることが減った」のか、この bench は区別していない。**

### 4. 【実測】主指標（`minBudget`）は 42% 下がった。**⚠ 動いたのは 7件中1件だけ**

`budgetLadder` のうち、その probe の gold が載った**最小の `maxMemoryTokens`**:

| round | color | pet | exercise | diet | family | language | travel | **Σ** | どの予算でも載らなかった |
|---|---|---|---|---|---|---|---|---|---|
| 0（統合前） | 24 | 16 | 24 | 16 | 24 | 16 | **128** | **248** | **0件** |
| 1 | 24 | 16 | 24 | 16 | 24 | 16 | **24** | **144** | **0件** |
| 2 | 24 | 16 | 24 | 16 | 24 | 16 | 24 | 144 | 0件 |
| 3 | 24 | 16 | 24 | 16 | 24 | 16 | 24 | 144 | 0件 |

**⟹ 決定2 の成功の定義は満たされた**——Σ が **248 → 144（−42%）**へ下がり、
**どの予算でも載らなかった probe は 0 件のまま**である。
**⟹ 「同じ想起の質を、より少ない予算で」が、この器の上で実際に起きた。**

🔴 **⚠ しかし動いたのは `travel` 1件だけである**（128 → 24）。**他の6件は1段も動いていない。**
**⟹ 標本 7 件のうち、効果が観測されたのは 1 件。**
⛔ **ここから「統合は想起を安くする」と率で言ってはならない**（[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §3）。

⚠ **最初の階段 `[32,64,128,256,512]` では、7件中6件が最下段で既に gold を載せてしまい、
Σ は 320 → 224 としか動かなかった**（床に張り付いて分解能を失っていた）。
**⟹ 階段を 8/16/24/48 まで下ろしたのは、この実測を見た後の変更である。**

### 5. ⭐【実測】退化の検知口が、実際に鳴った

`recalledActiveShare`（= 返した件数 / `active` の総件数）が **1.0 に張り付いた段が実在した:**

```
round 1  budget=512 : 0.962
round 2  budget=256 : 1.000    round 2  budget=512 : 1.000
round 3  budget=256 : 1.000    round 3  budget=512 : 1.000
```

**⟹ この段では、その arm は「全部載せる」に退化している。**
**⛔ 北極星の物差しの上では、これは naive path と同じであり、`hit` が上がっても負けである。**
**⟹ 決定8 の検知口は飾りではなかった。**最初の実測で鳴った。

### 6. 【実測】2回の実行は、`measuredAt` を除いて完全に一致した

同じ DB に対して 2 回走らせ、`measuredAt` を除いた JSON を比較した——**差分なし。**
⚠ **[ADR 0088](./0088-retrieval-quality-measured-in-ci.md) §2.1 の規律をここでも守る——
「2回一致した」は「決定的である」の証明ではない。**⟹ **だから門にしない（決定6）。**

## ⟹ 芯の問いへの答え: 件数か、トークン数か

**【実測】が、決定1 の答えを1段細かくした。**

**トークン数を採る**（決定1 の理由4つは変わらない）。**だが「トークン数」だけでは足りない
——どのトークンかを名指ししなければならない。**実測 §3 の通り、
**同じ round で `usage.chars` は減り、予算が縛る memories tier は増えた。**
**⟹ 「トークンが減った」は、内訳を言わないと嘘になりうる。**

⟹ **この ADR が採る形:**

| 何を | どの数で | 役割 |
|---|---|---|
| **成否の判定** | **`minBudget` の Σ と「載らなかった件数」** | **⭐ 主指標。**質を保ったまま量を動かす、分子と分母の両方を持つ形 |
| 併記（判定に使わない） | `usage.chars` / `indexChars` / その差 | **内訳。**どこが減ったのかを読む |
| 併記（判定に使わない） | `activeCount` / 載せた件数 | **⛔ これ単独では良し悪しを言わない**（下記） |
| 併記（判定に使わない） | `activeContentChars` / `allContentChars` | **統合が store に足した分。**隠すと縮み率が嘘になる |
| 退化の検知 | `recalledActiveShare` | 1.0 へ張り付いたら**その段の比較は成立しない** |

### ⛔ 「減った」は、それ単独では良し悪しを言わない

**この bench の実測が、それを1つの表の中で示している。**同じ3ラウンドで:

- `activeCount` は **74 → 15** に減った
- `activeContentChars` は **1871 → 5908** に増えた
- `allContentChars` は **1871 → 17784** に増えた
- recall が載せた件数は **10.00 のまま動かなかった**

**⟹ 「記憶が5分の1になった」と「保持している文字量が9.5倍になった」は、同じ実行の同じ数字である。**
**⛔ 片方だけを引いて成果と書かないこと。**

## 引き受けた負債

1. 🔴 **擬似 LLM の下でしか測っていない。**文脈 §3 / 決定3 の通り、
   **「1件あたりの量が変わったか」——統合がしたと主張する仕事そのもの——は測れていない。**
2. **効果が観測された probe は 7件中1件である**（実測 §4）。**標本が足りない。**
3. **目次帯が縮んだことを「良い」とも「悪い」とも判定していない**（実測 §3）。
   **区別する器を持っていない。**
4. **`groupSize=5` と「filler だけを統合する」は、この ADR が選んだ1つの当て方でしかない。**
   gold を含む群を統合する形（統合結果から `basis` を辿って gold を数える形）は測っていない。
5. **CI に新しいジョブを1本足す**ので、その分の実行時間が増える（DB サービス + `local` 埋め込みの重み取得）。

## 確かめていないこと

- **実 LLM で統合したときに、`content` と `digest` がどう動くか。**⟹ 段B（鍵が要る）。
- **本番相当の規模**（数千件）でどうなるか。測ったのは `active` 74件からである。
- **`groupSize` を変えたときの感度。**既定の 5 でしか測っていない。
- **CI 上でこのジョブが実際に緑になるか。**手元の使い捨て DB では走ったが、
  **CI の本番経路（`pgvector/pgvector:pg17` サービス・`local` 重みの取得）は走らせていない。**
- **3周より先。**4周目以降で `input_too_long`（ADR 0090）に届くかは測っていない。

## これが覆るとしたら

- **実 LLM が実際に縮めることが測れたら**、実測 §1（「単調増加した」）は
  **「擬似 LLM の下では」という限定つきの記録に後退する。**⟹ **それはこの ADR の想定内である。**
- **目次帯を予算の対象に入れる判断が出たら**（`docs/recall.md` §6 は明確に否定している）、
  実測 §3 の内訳の読み方が変わる。
- **probe が数十件に増えたら**（Issue #109 項目1）、実測 §4 の「7件中1件」が率として語れるようになる。
  **⟹ そのとき初めて、門の話ができる。**
