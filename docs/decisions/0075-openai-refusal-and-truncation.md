# ADR 0075: `@mnemora/openai` も、拒否・打ち切りを「空の成功」にしない — `kind` で区別する

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-09

**この ADR は [ADR 0072](./0072-anthropic-llm-provider.md) の「引き受けた負債」6 を返済する。**
0072 の負債6 はこう書いている——

> **`@mnemora/openai` は `refusal` / `finish_reason` を見ていない**（実測: 0件）。
> **同じ穴が在る可能性が高いが、この PR では直していない。**別の判断である。

⟹ **その「別の判断」がこれである。**

**⚠ 各主張の出所を分ける。**「実測」と書いたものは、断りの無い限り**この作業でこの器から実行して取った**ものである。
**受け取った前提**は、そう明記する。

---

## 問い

`@mnemora/openai` の `OpenAILLMProvider` は、**モデルが答えを拒否したこと**と
**出力が途中で切れたこと**を見ているか。見ていないなら、どう見るべきか。

---

## 文脈

### 実測: 見ていなかった

`packages/openai/src/` 全体（実装4ファイル + `__tests__/` 4ファイル）に対して
`refusal` / `finish_reason` / `content_filter` を grep した結果は **いずれも 0 件**だった。

`completeStructured` は `response.choices[0]?.message?.content` を読み、falsy なら
`new Error("OpenAILLMProvider: structured completion returned no content")` を投げていた。
`complete` は `?? ""` で空文字を返していた。

### ⚠ OpenAI の機構は Anthropic と形が違う

**ADR 0072 決定6 の「`content` を読む前に `stop_reason` を見る」をそのまま持ち込めない。**
`stop_reason` は OpenAI の chat completions に存在しない。

**出所: `openai` 7.10.0 の `.d.ts` を読んで確認した**
（`node_modules/.pnpm/openai@7.10.0_zod@4.5.4/node_modules/openai/resources/chat/completions/completions.d.ts`。
`packages/openai/package.json` はこの版を完全一致でピン留めしている）。
**OpenAI は独立した2つの機構を持つ:**

| 機構 | 型定義 | 型コメント |
|---|---|---|
| `ChatCompletionMessage.refusal` (L1267) | `string \| null` | "The refusal message generated by the model." |
| `ChatCompletion.Choice.finish_reason` (L252) | `'stop' \| 'length' \| 'tool_calls' \| 'content_filter' \| 'function_call'` | `length` = max tokens 到達、`content_filter` = "content was omitted due to a flag from our content filters" |

**⚠ 拒否は HTTP 200 で返る。** `message.refusal` に拒否理由の文字列が入り、
このとき `message.content` は `null` になる。SDK は例外を投げない。

⟹ **`content` を先に読むと、拒否が `no_content` に化ける。**種類が潰れる。

### なぜこれが問題か

このリポジトリの固定点——**「無い」の種類を潰さない**（ADR 0008 / 0013 / 0026 / 0027 / 0044）——に
正面から当たる。`packages/core/src/extraction.ts` の `extractCandidates` はこの例外を
`try/catch` で飲み、`ExtractionOutcome: "llm_failed_whole_observation"` へ倒す
⟹ **種類を潰したまま投げると、「モデルが拒否した」という情報はそこで完全に消える。**

**⚠ その飲み込み側の問題は、この ADR の範囲外である。**別に ADR 0076（別 PR。この PR の時点ではまだ存在しない）で扱う。
**⟹ この ADR だけでは、`kind` は core まで届かない。**2本で1つの穴を塞ぐ形になっている。

---

## 決定

`OpenAILLMProviderError` を足し、**`kind` で3種を区別する。**
`content` を読む**前**に `message.refusal` と `finish_reason` を見る門
（`assertNotRefusedOrTruncated`）を通す。門は `complete()` と `completeStructured()` の両方に置く。

| `kind` | 何が起きたか | 判定 |
|---|---|---|
| `"refusal"` | モデルが拒否した／コンテンツフィルタで出力が省かれた | `message.refusal` が非 null かつ非空、または `finish_reason === "content_filter"` |
| `"truncated"` | 応答が途中で切れた | `finish_reason === "length"` |
| `"no_content"` | 上記のどちらでもないのに `content` が空／欠落 | それ以外 |

エラーは `finishReason`（生の値）と `refusalMessage`（拒否理由の文面）を欄として持つ。

**⚠ `instanceof` ではなく `kind` で分岐させる**——bundler が同じクラスを二重に読み込むと
`instanceof` は落ちるが、`kind` は値なので影響を受けない（ADR 0072 決定6 と同じ）。

**`no_content` のメッセージ文言は1文字も変えていない**
（`"OpenAILLMProvider: structured completion returned no content"`）。
`packages/anthropic/src/__tests__/provider-parity.test.ts` がこの文言に依存しており、
**両 provider を揃えた既存の契約を壊さない。種類は足しただけである。**

**`finish_reason` が未設定／`stop` ／`tool_calls` ／`function_call` なら素通しする。**
**「分からない」を「拒否された」と読まない**（ADR 0072 決定6 と同じ固定点）。
`choices` が空のときもこの門では投げず、既存の `no_content` 経路に任せる。

## 検討した選択肢

- **`content_filter` に固有の `kind` を割り当てる（4種にする）**: 却下。
  ADR 0008 の判定基準は「**その区別があると、呼び出し側の次の一手が変わるか**」である。
  モデル自身の拒否とコンテンツフィルタによる省略は**機構としては別物だが、
  呼び出し側の次の一手は同じ**——同じ入力で再試行しても意味が無い。
  **⟹ 区別できない種類を増やしても「無い」の分類は増えない。**
  **情報は潰していない**——生の `finish_reason` を `finishReason` 欄に残しているので、
  将来 `content_filter` だけを別扱いしたくなったらそこから再分岐できる。
- **`@mnemora/anthropic` の `AnthropicLLMProviderError` をそのまま写す**: 却下。
  `stopReason` / `refusalCategory` という欄は OpenAI には対応物が無い
  （OpenAI は拒否の「分類」を返さず、拒否の「文面」を返す）。
  **API の形が違うものを、揃えるために無理に同じ形にしない。**
  揃えたのは **`kind` の3値と `no_content` のメッセージ文言**だけである。
- **`refusal` を見ず `finish_reason` だけを見る**: 却下。
  **型定義に拒否専用の `finish_reason` 値が無い**（union は `stop` / `length` / `tool_calls` /
  `content_filter` / `function_call` の5値）。⟹ 拒否は `finish_reason` 側に固有の顔を持たず、
  `finish_reason` だけでは検出できない。**⚠ これは型定義からの帰結であって、実 API での実測ではない。**
- **`complete()` の `?? ""` も同時に throw へ変える**: 却下（この PR では）。
  ADR 0072 の負債2 の通り、**両 provider 同時に直す必要があり、公開 API の破壊的変更になる。**
  `docs/autonomy.md` §3 では ⛔（提起までにする）項目である。
  **ただし門を通した後なので意味が変わった**——ここへ来る空文字は「拒否された」でも
  「切り詰められた」でもなく、モデルが本当に何も言わなかった場合だけである。
  **この形を歯で固定し、歯自身に「望ましい姿ではない」と名乗らせてある。**

## 結果（この決定が招くもの）

**良い面**: 拒否・打ち切り・空応答が、呼び出し側から `kind` で区別できるようになった。
**両 provider が同じ3値の `kind` を持つ**ので、差し替えたときに分岐の書き換えが要らない。

**引き受けた負債**:

1. **`kind` は、いまはまだ `packages/core` まで届かない。**`extractCandidates` の
   `catch` が飲むためである。**⟹ この ADR だけでは、実運用の呼び出し側から
   拒否は見えない。**ADR 0076（別 PR。この PR の時点ではまだ存在しない）と対で機能する。
2. **`complete()` は、拒否でない空応答では今も空文字を返す**（負債1 と同じく ADR 0072 負債2 の継承）。
3. **provider の適合テストは今も存在しない**（ADR 0072 負債1）。
   `packages/openai` の歯は自分のパッケージの中に在るだけで、3つ目の provider には効かない。
4. **`logprobs.refusal`（トークン単位のログ確率）は見ていない。**
   拒否の検出には `message.refusal` で足りると判断した。

## これが覆るとしたら

- **OpenAI が拒否を表す機構を変えたとき**（`refusal` 欄の廃止、拒否専用の `finish_reason` 値の追加）。
  歯が赤くなって気づける形にしてある。
- **`content_filter` に対して、呼び出し側が拒否と違う手を打ちたくなったとき。**
  そのときは `finishReason` 欄からの再分岐で足りるか、`kind` を割るべきかを問い直す。
- **`complete()` の空文字が実際に人を騙したとき。**負債2 を、両 provider 同時に直す判断へ。

---

## 確かめていないこと

- **実 API を一度も叩いていない。**この器に `OPENAI_API_KEY` は在るが、意図的に
  `env -u OPENAI_API_KEY` で外して走らせた。
  **⟹ 「実 API が本当に `message.refusal` に文字列を入れて返す」ことは確かめていない。**
  確かめたのは、**SDK 7.10.0 の型定義が定める形に対して、こちらが正しく反応すること**だけである。
- **拒否が実運用でどの頻度で起きるかを測っていない。**
- **`finish_reason === "content_filter"` のときに `message.refusal` も同時に入るのかを、
  実 API では確かめていない。**型の上は両方入りうるので、実装は `refusal` を先に見る。
