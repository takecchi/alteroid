# ADR 0064: 厳密経路の費用倍率を規模で振って測った — 「約2.5倍」の訂正と、`relaxed_order` の recall が規模とともに悪化するという発見

- **状態**: 採用 (2026-09)（**測定と訂正の記録**であり、実装の変更は伴わない。docs のみ）

- **文脈**:

  [ADR 0063](./0063-hnsw-iterative-scan-not-adopted.md) は `hnsw.iterative_scan` を採らないと決めた
  （件数は直るが正しさは直らない）。そのうえで、**[ADR 0059](./0059-period-in-ann-stage.md) が
  申告した負債を塞ぐ手として「厳密（式索引）経路」が在ることを記録し、その費用を
  「`relaxed_order` の**約2.5倍**（24ms → 62ms）」と書いた。**

  **ADR 0063 はこの数字について、次の3つを自分で明記していた**（本 ADR の作業者が現物で確認した）:

  1. 時間は「**同じサーバで別の測定が同時に走っている下での観測**」であり「**根拠の格は低い**」。
  2. 「**⚠ しかし、この『約2.5倍』を本番の既定を変える根拠にしてはならない。**」
  3. 「**⭐ 次に測るべき一点は「2.5倍が規模とともにどう動くか」である。**」

  ⟹ **本 ADR は、その「次に測るべき一点」を測った記録である。**

  **⚠ そして、測った結果として「約2.5倍」そのものを訂正する。**

- **決定**:

  1. **ADR 0063 の「約2.5倍」を訂正する。** これは**同時実行下の観測**であり、
     **静かな条件（他に active なセッションが無い状態）では再現しない**——同じ規模
     （100,000行）・同じ窓（10%）で **1.136倍** だった。⟹ **ADR 0063 の本文には
     この事実を指すポインタを1行だけ足す**（`superseded by` を書くのと同じ形）。
     **⛔ ADR 0063 の結論（`iterative_scan` を採らない）は1文字も変えない**
     ——**本 ADR の測定はその結論を補強している。**
  2. **⛔ 実装は1行も変えない。** 本 ADR は測定と訂正の記録だけである。
  3. **⛔ ADR 0059 の本文も書き換えない。** 分岐点の縮みが ADR 0059 の負債の評価に
     与える影響（下の (d)）は、本 ADR の中に書く。
  4. **根拠の格が低い数字の書き方について、教訓を1つ残す**（下の「🔑 持ち帰る教訓」）。

- **測定台と条件**:

  **⭐ 静かな条件で測った。** 測定の開始前と完了後の両方で `pg_stat_activity` を確認し、
  **`active` なのは測定自身のセッションだけ**で、他は `datname` を持たない常駐プロセス
  （autovacuum / checkpointer / walwriter 等）だけであることを確かめた。**3規模は直列に実行した
  （同時実行なし）。**

  **⚠ ただし「静か」の確認は点検であって、連続監視ではない。** この測定を行った作業環境の
  PostgreSQL インスタンスは**他の作業セッションと共有されている**（実際、本 ADR の門を
  走らせている最中に、別セッションが同じインスタンスの別データベースへ書き込んでいる
  ところを観測した）。⟹ **測定の開始前と完了後には他に `active` なセッションが無かったが、
  測定中ずっと無かったことを保証する仕掛けは無い。**
  ⟹ **時間の値には、この残余リスクが乗っている。**
  **件数と `recall@40` は同時実行の影響を受けないので、そちらは影響を受けない。**

  PostgreSQL 17.11 (Debian 17.11-1.pgdg12+2) + pgvector 0.8.6（CI が使う
  `pgvector/pgvector:pg17` と同版）。**3つの規模はすべて同じ seed レシピで作り、
  行数だけを変えた**——256次元・`setseed(0.20260908)`・`occurred_at` の20%を NULL・
  同じ status 分布・同じクエリベクトル（`setseed(0.777)` 由来の1本）。
  **スキーマは手書きせず `packages/postgres` の移行スクリプト（0001/0002/0003）で作った。**
  埋め込み表の DDL は `packages/postgres/src/vector-space.ts` から書き写した。
  測ったクエリは段1の実物（`packages/postgres/src/vector-store.ts:95-103` の骨格）。
  `LIMIT 40`（`k' = limit 10 × overFetchFactor 4`）。**各セル7回**実行した。

  | 規模 | 10%窓の実在数 | 50%窓の実在数 | seed（HNSW 索引の維持を含む） |
  |---:|---:|---:|---|
  | 30,000 | 2,406 | 11,930 | **1分37秒** |
  | 100,000 | 8,089 | 39,933 | **記録が残っておらず、報告できない** |
  | 300,000 | 24,075 | 119,854 | **31分57秒** |

  **既定のまま変えなかった設定**（`SHOW` した実値）: `hnsw.ef_search = 40` /
  `hnsw.max_scan_tuples = 20000` / `hnsw.scan_mem_multiplier = 1` /
  `random_page_cost = 4` / `effective_cache_size = 4GB` / `work_mem = 4MB` /
  `shared_buffers = 128MB`。

  **測定上の必要で変えたもの（明記する）**: 厳密経路を出すための
  `enable_indexscan = off` / `enable_bitmapscan = off`（ADR 0063 の「正解」と同じ作り方）と、
  seed 投入時の `jit = off`（理由は下の「副産物」）。

- **🔴 (a) 訂正: 「約2.5倍」は同時実行下の値であり、静かな条件では再現しない**:

  同じ 100,000行・同じ10%窓を、静かな条件で測り直した:

  | | ADR 0063（同時実行下） | **本 ADR（静か、中央値）** |
  |---|---:|---:|
  | 厳密経路 | 62ms | **45.20ms**（速くなった） |
  | `relaxed_order` | 24ms | **39.80ms**（遅くなった） |
  | **倍率** | **約2.5倍** | **1.136倍** |

  ⟹ **分子と分母が両方動いて、倍率が半分以下になった。**

  **⭐ 一方、50%窓の値はおおむね保った**（ADR 0063: 55ms / 6ms ≒ 9.2倍 → 本 ADR:
  72.34ms / 6.74ms = **10.731倍**）。⟹ **10%窓が不安定で、50%窓が安定している**、
  という構造が見える。理由は (b) に書く。

  **⟹ ADR 0063 が「格が低い」と添えていたのは正しかったが、添えるだけでは足りなかった。**

- **⭐ (b) 倍率の推移: 50%窓では規則的（∝ N^0.57）、10%窓では規則的でない**:

  倍率 = 厳密 ÷ `relaxed_order`（中央値。各セル7回）:

  | 規模 | **10%窓の倍率** | **50%窓の倍率** |
  |---:|---:|---:|
  | 30,000 | 1.499 | **5.484** |
  | 100,000 | 1.136 | **10.731** |
  | 300,000 | 6.031 | **20.149** |

  隣接する2点から両対数の指数を出した:

  | 区間 | 10%窓 | **50%窓** |
  |---|---:|---:|
  | 30k → 100k | N^**−0.231** | N^**0.558** |
  | 100k → 300k | N^**+1.520** | N^**0.573** |

  ⟹ **50%窓は、隣接する2つの指数が 0.558 と 0.573 で、2.7% で一致する。**
  すなわち **倍率 ∝ N^0.57** という規則が立つ。**10%窓は符号すら反転しており、
  規則が立たない。**

  **⚠ (b-1) confound を隠さない——`exact` は 30k だけプラン形が違う。**

  プランのノード種別を3規模で突き合わせた結果:

  | 腕 | 30k | 100k | 300k |
  |---|---|---|---|
  | `off` / `relaxed_order` | HNSW Index Scan → Nested Loop | **同一** | **同一** |
  | **`exact`** | **`Hash Join` + `Seq Scan`（非並列）** | `Gather Merge` + `Parallel Hash Join` + `Parallel Seq Scan`（`Workers Planned: 2`） | 同左 |

  ⟹ **プランナが並列化を選ぶ閾値を、30k と 100k の間でまたいでいる。**
  ⟹ **厳密にプラン形が揃った隣接ペアは 100k↔300k の1区間だけである。**

  **⛔ 「confound の在る区間の指数（0.558）と、きれいな区間の指数（0.573）がほぼ一致したから
  30k も使える」とは結論しない。** 一致は1点の観察であって、confound が無いことの証明ではない。
  **⟹ 規則 ∝ N^0.57 を支える、プラン形の揃った区間は1つしかない。**

  **(b-2) なぜ10%窓が暴れるのか——`EXPLAIN` から特定した。**

  分母（`relaxed_order`）が HNSW から取り出す候補行数は、**規模ではなく窓の選択率と
  データの巡り合わせで決まり、規模に対してほぼ横ばいかつ非単調である**:

  | 窓 | 30k | 100k | 300k |
  |---|---:|---:|---:|
  | 10% | 457行 | **551行** | 440行 |
  | 50% | 95行 | 110行 | 102行 |

  一方、分子（厳密経路）が読む量は規模にほぼ比例して増える（`EXPLAIN` の Buffers、
  50%窓）: 30k `hit=1316 read=3806` → 100k `hit=4412 read=12806` →
  300k `hit=8826 read=42662`。

  ⟹ **分子は規模に比例、分母は規模に依らずノイズを持つ。**この非対称が、
  10%窓の不規則さ（100k で偶然551行掘る必要があり、分母が膨らんで倍率が潰れた）の
  正体である。**50%窓では分母のノイズが小さい（95 / 110 / 102）ため、
  分子の伸びがそのまま倍率に出て、規則が立つ。**

- **🔴 (c) いちばん重い発見: `relaxed_order` の recall は規模とともに悪化する**:

  **返却数は3規模・両窓のすべてで常に 40件（`LIMIT` 一杯）だった。**
  **その中身が、規模とともに崩れていく:**

  | 規模 | 10%窓の `recall@40` | 50%窓の `recall@40` |
  |---:|---:|---:|
  | 30,000 | 0.750 | 0.625 |
  | 100,000 | 0.500 | 0.350 |
  | 300,000 | **0.325** | **0.200** |

  （`recall@40` の「正解」は、その規模の厳密経路が返した上位40件。）

  参考までに `off`（現状の既定）も規模とともに悪化する:

  | 規模 | 10%窓 返却数 / recall | 50%窓 返却数 / recall |
  |---:|---|---|
  | 30,000 | 7件 / 0.175 | 17件 / 0.425 |
  | 100,000 | 3件 / 0.075 | 16件 / 0.125 |
  | 300,000 | 4件 / 0.100 | 18件 / **0.075** |

  ⟹ **「件数は完璧なまま、中身が規模とともに崩れる」——これが `relaxed_order` の姿である。**

  **⟹ ADR 0063 の結論（`iterative_scan` は件数だけを直し、正しさを直さない）は、
  規模の側から補強された。** ADR 0063 は 100,000行の1点で「正しさを直さない」と結論したが、
  **規模を上げると、直さないどころか悪化する。** 300,000行の50%窓では、
  40件返しているうち **8件しか正しくない**（0.200）。

  **⭐ 速さの倍率より、この軸のほうが重い。** この製品の北極星は「使う側が会話ログを
  全部プロンプトへ積むのをやめられたか」であり、**返ってきた40件のうち32件が
  「窓を埋めるために拾われた別物」であることは、そこを直接壊す。**

- **⭐ (d) プランの分岐点は規模とともに縮む——ADR 0059 の負債は、規模とともに当たる場面が増える**:

  式索引経由から HNSW 経由へ裏返る窓幅を、各規模で特定した:

  | 規模 | 最後に式索引 | 最初に HNSW |
  |---:|---:|---:|
  | 30,000 | 2.2% | **2.3%** |
  | 100,000 | 1.1% | **1.15%** |
  | 300,000 | 0.65% | **0.7%** |

  ⟹ **規模が上がるほど、HNSW 経路へ落ちる窓が広くなる。**
  30,000行では「2.3%より広い窓」だけが HNSW 経路だったが、300,000行では
  **「0.7%より広い窓」がすべて HNSW 経路になる。**

  **⟹ これは ADR 0059 が申告した負債の評価を変える。**
  ADR 0059 の残余（プランナが HNSW 経由を選ぶと `LIMIT` を埋めきれない・真の近傍を
  取り逃す）は、**規模が上がるほど「当たる場面が増える」。**
  ADR 0063 は 100,000行の1点で「残余は分岐点 ≈1.15% より広い側にある」と書いたが、
  **その境界は規模とともに下がり続ける。**

  **⛔ ADR 0059 の本文は書き換えない**（ADR は追記して積む）。この帰結は本 ADR に記録する。

- **⛔ (e) 1,000,000行は測っていない——理由は「時間が無かった」ではない**:

  **理由は、seed が単一トランザクションで、器の入れ替えに対して全損になる形だったためである。**

  実際に起きたこと: 1,000,000行の seed を走らせ、**約50分で42%（約423,000行相当、
  埋め込み表の物理サイズから推定）まで進んだ。**しかし**単一の `INSERT` トランザクション**
  だったため、**中止した時点で1行も残らなかった**（`memories` は 0行のまま）。
  ⟹ **42%は「払い済みの預金」ではなく、卓の上に載ったままの賭け金だった。**

  残り時間の実測見積りは **1.5〜2.5時間**（直近の実測ペース 5,940行/分。
  平均 8,510行/分から落ちており、**HNSW を挿入ごとに維持するため1行あたりが
  規模とともに重くなる**）。⟹ **その時間を全損の形で賭けないと判断した。**

  **⟹ 次にこれを測る人へ: 先に seed をバッチコミット化すること**（下の「副産物」）。

- **⚠ (f) 外挿は外挿として書く（測っていない）**:

  **50%窓の規則（∝ N^0.57）を 1,000,000行へ延ばすと、倍率は約40倍になる。
  分岐点は 0.2〜0.3% 程度になる。⛔ これらは測っていない。外挿である。**

  **外挿の根拠は次の1点だけである**: 「100k↔300k で観測した指数 0.573 が、
  300,000行より上でも成り立つ」と仮定した。**この仮定を支える測定は無い。**
  そして (b-1) の通り、**その指数を支えるプラン形の揃った区間は1つしかない。**
  ⟹ **本 ADR はこの外挿値を、判断の根拠として使わない。**

- **(g) 測れなかったこと・確かめていないこと**:

  - **1,000,000行は測っていない**（上の (e)）。**100万件級は
    `docs/roadmap.md:249` がオーナー決定として前提とする規模であり、
    そこは依然として未測定である。**
  - **100,000行の HNSW 索引構築（seed）にかかった時間は、記録が残っておらず報告できない。**
    既知は 30,000行 = 1分37秒、300,000行 = 31分57秒。**推測で埋めない。**
  - **30,000行の点は、`exact` 腕のプラン形が他の2点と違う**（上の (b-1)）。
    ⟹ **この点を含む区間の指数は、confound を抱えている。**
  - **1,536次元は未測定。** 実運用で使う OpenAI 埋め込みの次元数であり、
    埋め込み表の行幅が違う——プラン選択・費用が変わりうる。**ADR 0059 / 0063 と
    同じ限界がそのまま残っている。**
  - **クエリベクトルは1本のみ**（`setseed(0.777)`）。**単一テナント。**
  - **埋め込みは時間軸と一切相関しない一様乱数**である。現実のデータでは
    「近い時期の記憶は内容も似る」という相関がありうる。**相関を持たせた seed では
    測っていない。**
  - **`random_page_cost` / `effective_cache_size` を本番相当に寄せた場合に、
    分岐点や並列化の閾値が動くかは見ていない。**
  - **並列化の閾値（30k と 100k の間のどこか）そのものは特定していない。**

- **採らなかった案**:

  - **ADR 0063 の本文を書き換えて「約2.5倍」を直す**: 却下。**ADR は上書きせず追記して積む**
    のがこのリポジトリの作法であり（ADR 0059 → 0063 で同じ形を採った）、
    **上書きすると「当時そう判断した」という記録そのものが消える。**
    ⟹ **1行のポインタだけを足し、訂正の中身は本 ADR に置く。**
    **加えて、自分が書いた ADR を自分で書き換えるのは、いちばん歯止めが効かない形である。**
  - **ADR 0063 への追記節にする（新しい番号を立てない）**: 却下。
    **本 ADR の中身は 0063 単独への追記より広い**——とくに (d)（分岐点の縮み）は
    **ADR 0059 が申告した負債の評価を変える**ものであり、**2つの ADR に跨る発見を
    どちらかの付録にすると、もう片方から見えなくなる。**
  - **測定結果を報告に留め、リポジトリに残さない**: 却下。
    **ADR 0063 の「約2.5倍」が再現しないという事実がリポジトリ側に残らなければ、
    次に読む人はその数字を信じる。**⟹ 嘘を残すことになる。
  - **先に 1,000,000行を測ってから書く**: 却下。**バッチコミット化はそれ自体が別の作業**
    であり、**その間ずっと「再現しない数字」が本番のリポジトリに在る状態を放置することになる。**

- **🔑 持ち帰る教訓（書き方について）**:

  **ADR 0063 は「同時実行下の観測であり根拠の格は低い」と、自分で正直に書いていた。
  それでも「約2.5倍」は独り歩きした。**——本 ADR を起こす判断そのものが、
  その数字を前提にして行われた。

  ⟹ **根拠の格が低い数字は、本文で強調しない。強調するなら「再測が要る」を
  同じ行に置く。**「格が低い」という但し書きを別の行や脚注に置くと、
  **数字だけが引用される。**

  ⟹ **本 ADR の (f)（外挿）は、この教訓を自分に適用している**——
  「約40倍」という数字を書いた同じ節の中で、それが外挿であることと、
  根拠が仮定1つだけであることを書いた。

- **これが覆るとしたら**:

  - **1,000,000行を（バッチコミット化した seed で）実測したとき**、
    50%窓の倍率が外挿値（約40倍）と大きく違えば、規則 ∝ N^0.57 は
    300,000行より上では成り立たないことになる。
  - **1,536次元で測り直したとき**、`relaxed_order` の recall の悪化が
    256次元と同じ傾向を示さなければ、(c) の結論を見直す。
  - **時間軸と相関する埋め込みで測ったとき**、recall の絶対値が大きく変われば、
    (c) の「規模とともに悪化する」という傾向そのものは残っても、
    **実害の大きさの見積りは変わる。**
  - **並列化の閾値が本番のコストパラメータで動くと分かったとき**、
    (b-1) の confound の位置が変わり、規則を支える区間の数が変わる。

- **副産物として記録すること（本 ADR の主題ではないが、次の人を救う）**:

  1. **⭐ 大規模な seed はバッチコミットにすること**（例: 100,000行ごとに `COMMIT`）。
     **単一トランザクションだと、器の入れ替え・実行の中断で全損になり、
     途中成果が1行も残らない。**⚠ **本 ADR の測定で `bench_300k`（300,000行）が
     無傷で残っていたのは、それが独立した1回の投入として完了していたからであって、
     設計として守られていたわけではない。**⟹ この区別を落とすと、
     「前は残ったから今度も残るだろう」と読んで同じ全損の賭けをする。
  2. **⭐ 測定用の PostgreSQL を非 root で立てた環境では、`SET jit = off;` が要ることがある。**
     この作業環境の PostgreSQL は LLVM を持たないため、JIT が有効なまま重いクエリを
     投げると `could not load library "...llvmjit.so": libLLVM.so.19.1: cannot open
     shared object file` で落ちる。⚠ **落ち方が「クエリの中身が悪い」ように見えるため、
     原因に辿り着くまでが遠い**——**症状が原因を隠す形である。**
