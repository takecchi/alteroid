## 文脈

**Issue #106**（外部の採用検討者 `the-phage-dev`。社内 Slack AI エージェントへの導入検討中）が
**「`recall` の候補生成が ANN 1チャンネルのみで、固有名詞・識別子を語彙的に引けない」**と報告した。
**mnemora にとって初めての、外部からの実利用フィードバックである。**【受】

**【現物】報告の骨格は現 `main` で成立していた。**

| 報告 | 現物での確認 |
|---|---|
| 候補生成は pgvector の cosine 近傍 1チャンネルのみ | `packages/core/src/recall-runtime.ts` の段1が `vectorStore.search` だけを呼ぶ。同ファイル冒頭の doc が「**ANN 経由の1チャンネルのみ**」と明記 |
| `tsvector` / `to_tsquery` / `bm25` は見当たらない | repo 全体を grep して **0件** |
| タグは候補生成ではなくスコアリングの加点要素 | `docs/recall.md` §「Phase 1 の範囲」が「タグは段2の再スコアにおける加点要素としてのみ参加し、**それ自体で候補を拾い上げる経路にはしない**」と明記 |
| `btree_gin` は既に必須依存に入っている | `packages/postgres/src/migrate.ts` の `REQUIRED_EXTENSIONS = ["vector", "btree_gin", "pgcrypto"]` |

**【現物】そして、この方針を測って否定した ADR は1本も無い。**
`docs/decisions/` 全件を当たり、語彙検索・キーワード検索・全文検索・`RecallQuery` へのチャンネル追加・
追加 PostgreSQL 拡張のいずれについても、**採択済みの ADR が却下した記録は 0件**だった。
関係しそうな15本（0008/0011/0023/0025/0026/0033/0055/0056/0057/0059/0063/0064/0068/0069/0081）は
本文を読んでいるが、**すべて「ANN の*中で*どう絞るか・どう測るか」しか扱っていない。**

**「Phase 1 の範囲外」という線は、オーナーが 2026-09-09 に引き直した。**【受】
⟹ この ADR は、その決定に基づいて**本体を作った**記録である。

### なぜこれが重いか

**[ADR 0081](./0081-similarity-is-the-only-term-that-ranks.md) は、順位を決めているのが
`similarity` ただ1項であることを実測している。**【現物】
`tagMatch` と `strength` は候補集合の上で**1通り**（厳密に 1）、`freshness` は `decay` の
**行ごと厳密な複製**、`decay` の変域は **1e-8 桁**である。
**⟹ スコアの重みを触る道は、好みではなく構造として閉じている**（ADR 0081 §4.2）。

**⟹ チャンネルを足すことは、この閉じた構造の外側から候補集合そのものを変える手である。**
ADR 0081 が並べた3つの案（重み調整・抽出プロンプト・推論記憶）はすべて却下されているが、
**語彙チャンネルは ADR 0081 が検討していない第4の道である。**

## 決めたこと

1. **`RecallQuery.channels` を足す。既定は ANN 1本**（`DEFAULT_RECALL_CHANNELS`）。
   **⟹ `channels` を渡さない既存の呼び出しは、候補も順位も `explain` も1バイト変わらない。**
2. **`LexicalStore` を独立した interface として切る**（`VectorStore` と同じ非対称の契約）。
   postgres 実装は **PostgreSQL 組み込みの `to_tsvector('simple', …)` + GIN 索引**であり、
   **`REQUIRED_EXTENSIONS` を1つも増やさない**（§3）。
3. **`channels` に `"recent"` を入れない**（§4.3）。
4. **`lexicalStore` が配線されていないのに `"lexical"` を明示要求されたら、`recall()` は投げる**（§4.2）。
5. **日本語の文に埋もれた日本語の語（人名を含む）は引けない。**
   **これを隠さない**——測定値ごと §3 に書き、`LexicalStore` を差し替え可能にすることで逃げ道を開ける。

### ⚠ 決めていないこと

- **`hit@1` が上がるとは言っていない。**この ADR は `retrieval` ベンチを回していない（§9）。
- **「タグ一致」「直近取得」のチャンネルを実装していない。**`docs/recall.md` §2 が一般形として
  触れているものは、今も無い。足したのは語彙1本だけである。
- **`pg_bigm` / `pgroonga` を採らないと決めたわけではない**——**いま必須にしない**と決めた（§3.4）。

## 1. 【実測】素の `to_tsvector('simple', …)` では、報告者の主目的が引けない

**日本語の文に埋もれた識別子は、組み込みパーサでは壊れた形になる。**

```
SELECT to_tsvector('simple', 'PROJ-1234の納期が来週まで延びました。');
--> '1234の納期が来週まで延びました':3 'proj':2 'proj-1234の納期が来週まで延びました':1
```

**⟹ 数字が、後続の日本語と地続きの1トークンになっている。**
`PROJ-1234` で引くと、`websearch_to_tsquery` でも `plainto_tsquery` でも **`f`（一致しない）**。

**⟹ 「PostgreSQL 組み込みで足りる」という見立ては、素のままでは成り立たない。**
これは着手前の見立て（「識別子は英数字なので形態素解析なしでも引けるだろう」）を
**実測が否定した点である。**

### 1.1 ASCII の連なりの前後に空白を入れる正規化で解ける

```
regexp_replace(content, '([[:ascii:]]+)', ' \1 ', 'g')
```

```
SELECT to_tsvector('simple', regexp_replace('PROJ-1234の納期が来週まで延びました。','([[:ascii:]]+)',' \1 ','g'));
--> '-1234':2 'proj':1 'の納期が来週まで延びました':3
```

**⟹ 一致する（`t`）。**`regexp_replace`（4引数）も `to_tsvector`（config 明示の2引数）も
**IMMUTABLE なので、式索引に載る。**

## 2. 【実測】正規化した `simple` の再現率と精度

9件の日本語文に対して、`websearch_to_tsquery` で引いた結果（`hits` は行番号）:

| クエリ | 正規化あり | 素のまま |
|---|---|---|
| `PROJ-1234` | **1, 8, 9** | 8, 9（**1 を落とす**） |
| `PROJ-5678` | **2**（誤爆なし） | — |
| `TASK-1234` | **3**（1 を誤爆しない） | — |
| `#ops-alert` | **5**（6 を誤爆しない） | 5 |
| `gurumi-chan-backend` | **7** | 7 |
| `proj-1234`（小文字） | **1, 8, 9** | 8, 9 |
| `PROJ1234`（ハイフン無し） | **0件** | 0件 |
| `田中さん`（日本語の人名） | **0件** | 0件 |
| `納期`（日本語の一般語） | **0件** | 0件 |

行1は `PROJ-1234の納期が…`（識別子が日本語と地続き）、行8は
`昨日の定例で、来期の予算配分について議論しました。PROJ-1234 は据え置きです。`（長文中に空白付き）、
行9は `proj-1234 は小文字表記のゆれです。`。

**⟹ ASCII の識別子については、再現率も精度も満たしている。**
`PROJ-1234` が `PROJ-5678` や `TASK-1234` を拾わないのは、
**`websearch_to_tsquery` がフレーズ（`'proj' <-> '-1234'`）を作るからである。**

**🔴 `plainto_tsquery` を使ってはならない。**同じ入力に対して `'proj' & '-1234'`（AND、隣接なし）を作るので、
**`PROJ-5678 と TASK-1234` のような文を誤って拾う。**実装は `websearch_to_tsquery` 固定である。

**⟹ そして、日本語の語（`田中さん` / `納期`）は引けない。**
**報告者が挙げた5種類のうち、人名だけがこの穴に落ちる。**

## 2.1 🔴 【実測】本文側と同じ正規化をクエリにも通すと、報告者の問いが1件も引けない

**⚠ これは変異試験で見つけた欠陥である。**当初の実装は本文側と同じ
`mnemora_lexical_normalize` をクエリにも通していた。**識別子だけを渡す歯はすべて緑だった。**

```
websearch_to_tsquery('simple', nrm('PROJ-1234について前に何か言ってたっけ？'))
  --> 'proj' <-> '-1234' & 'について前に何か言ってたっけ'
… @@ to_tsvector('simple', nrm('PROJ-1234の納期が来週まで延びました。'))  --> f
```

**⟹ 日本語の残り全体が1つの語彙になり、AND で結ばれる。**その語彙はどの本文にも現れないので、
**識別子が一致していても常に false になる。**

**🔴 Issue #106 の報告者が書いた問いの形が、まさにこれである**【受】——

> 「`PROJ-1234` について前に何か言ってたはず」

**⟹ 直す前の実装は、この Issue が挙げた問いそのもので動かなかった。**

### 2.1.1 ⟹ クエリ側と本文側で、通す関数を分ける

| 側 | 関数 | 何をするか |
|---|---|---|
| 本文（索引式） | `mnemora_lexical_normalize` | ASCII の連なりの**前後に空白を入れる** |
| クエリ | `mnemora_lexical_query_terms` | **非 ASCII の連なりを空白に落とす** |

**非対称は意図である。**根拠は §2 の実測そのもの——**日本語の語は本文側でも文ごと1トークンになるので、
そもそも引けない。⟹ クエリに残しても真陽性を1件も生まず、AND で偽陰性だけを作る。**
**⟹ 落として失うものが無い。**

**⚠ ASCII の語どうしは今も AND で結ばれる。**
⟹ 英語の自然文をそのまま投げると（`what did we say about PROJ-1234`）、
すべての語を含む記憶しか返らない。**これは残る制約である**（§8）。

## 3. 【実測】`pg_trgm` を足したら何が買えるか — そして、なぜ必須にしないか

### 3.1 買えるもの

| クエリ | 正規化 `simple` | `pg_trgm` の `%>`（word_similarity） |
|---|---|---|
| `PROJ-1234` | 1, 8, 9 | 1, 8, 9 |
| `PROJ-5678` | 2 | 2 |
| **`田中さん`** | **0件** | **4**（引ける） |
| `納期` | 0件 | 0件（2文字では `%>` が立たない） |

**⟹ `pg_trgm` が買えるのは「日本語の固有名詞」1点である。**日本語の一般語は買えない。

### 3.2 🔴 そして、ロケール次第で**黙って**0件になる

**【実測】**同一クラスタ内に `LC_COLLATE='C' LC_CTYPE='C'` のデータベースを作って測った:

```
show_trgm('田中さん')  --> {}          （空）
show_trgm('PROJ-1234') --> {"  1","  p"," 12"," pr",123,234,"34 ","oj ",pro,roj}
similarity('田中さんが請求書を…','田中さん') --> 0
'田中さんが請求書を…' %> '田中さん'          --> f
```

**⟹ `C` ロケールのクラスタでは、`pg_trgm` は日本語のトライグラムを1つも作らない。
ASCII は正常に動く。**

**🔴 これは「動かない」ではなく「日本語だけが黙って動かない」である。**
導入者は語彙チャンネルが動いていると信じたまま、日本語の想起だけを永久に落とす。
**⟹ これは mnemora が明文で禁じている形そのものである**——
`AGENTS.md`「**擬似物へ黙ってフォールバックしない**」、
北極星「**『見つからなかった』と『探していない』を、同じ顔で返さない**」。

### 3.2.1 【実測】採用した経路のほうは、`C` ロケールでも壊れない

**⚠ 「`pg_trgm` がロケールに弱い」ことは、採用した経路が強いことを意味しない。別に測った。**
同じ `C` ロケールのデータベースで:

```
to_tsvector('simple', nrm('PROJ-1234の納期が来週まで延びました。'))
  --> '-1234':2 'proj':1 'の納期が来週まで延びました。':3
… @@ websearch_to_tsquery('simple', nrm('PROJ-1234'))   --> t
… @@ websearch_to_tsquery('simple', nrm('#ops-alert'))  --> t   （別の文で）
```

**⟹ 識別子の引き当ては `C` ロケールでも成立する。**

**⚠ ただし差は在る**——日本語側のトークンが `C.utf8` では `'の納期が来週まで延びました'`、
`C` では **`'の納期が来週まで延びました。'`（句点を含む）**になる。
`C` の文字分類が `。` を句読点と見なさないためである。
**⟹ 日本語のトークンの切れ目はロケールで変わる。**この ADR はもともと
「日本語の語は引けない」と言っているので主張は動かないが、
**「ロケールに一切依存しない」と読まないこと。**依存しないと測れたのは**識別子の側だけ**である。

### 3.3 ⟹ 決定: `REQUIRED_EXTENSIONS` を増やさない

**【現物】**`REQUIRED_EXTENSIONS` は `migrations/*.sql` の `CREATE EXTENSION` 行と
**二重管理であり、`schema-namespace.test.ts` が集合の一致を検査している。**
増やすと、すべての導入者の DDL 権限・クラスタ構成に条件が1つ乗る。

**⟹ 買えるものが「日本語の固有名詞」1点で、代償が「全導入者への条件追加」＋
「ロケール次第の沈黙」であるなら、釣り合わない。**

### 3.4 ⚠ ただし「永久に採らない」ではない

**`LexicalStore` を独立 interface にしてあるので、`pg_trgm` / `pg_bigm` / `pgroonga` を使う実装を
導入側が自分で書いて差し替えられる。**これは**報告者自身が挙げた代案**でもある【受】——

> まずは「チャンネルを差し替えられる形」だけあれば、実装は呼び出し側で用意できるかもしれません
> （`VectorStore` のように `LexicalStore` インターフェースが切られている、等）

## 4. 決めた形

### 4.1 索引と正規化（migration 0008）

- **immutable な SQL 関数 `mnemora_lexical_normalize(text)`** を1つ作り、
  **索引式と検索クエリの両方がそれを通る**（正規表現を2箇所に書き写さない）。
- **式索引**であり、列を足さない:
  `CREATE INDEX … USING gin (tenant_id, to_tsvector('simple', mnemora_lexical_normalize(content))) WHERE status IN ('active','contested')`
- **⚠ 生成列（`ALTER TABLE … ADD COLUMN … GENERATED ALWAYS AS … STORED`）を採らなかった。**
  既存の `memories` に打つと**全表書き換え**になり、`runMigrations` は各マイグレーションを
  1トランザクションで包む（`packages/postgres/src/migrate.ts`）ためロックが長い。
  roadmap.md §5 はテナント規模を100万件級と置いている。
- `tenant_id` を同じ GIN に入れられるのは **`btree_gin` が既に必須依存だから**である。
  **⟹ 報告者の見立て（「`btree_gin` が入っているので相性が良さそう」）は、この点では当たっていた。**

### 4.2 🔴 配線されていない語彙チャンネルを要求されたら、投げる

**黙って0件を返さない。**「語彙で探したが1件も無かった」と「語彙で探していない」が
同じ顔になるからである。

**⚠ `embedding_provider_unavailable` と同じ扱いにしなかった。**
あちらは `omitted` の `stage_skipped` に落ちるが、**別の族である**:

| | 埋め込み provider の失敗 | `LexicalStore` の不在 |
|---|---|---|
| 何 | 実行時の失敗 | **配線の誤り** |
| 次に呼んだら | 成功しうる | **何度呼んでも成功しない** |
| degrade したら | 一時的に候補が減る | **「使っているつもりで一度も使えていない」製品が出荷される** |

**⟹ 前者は分類して返す値であり、後者は投げるべき誤りである。**
メッセージの接頭辞は定数（`LEXICAL_STORE_UNAVAILABLE_ERROR_PREFIX`）として出しており、
`UNSUPPORTED_KIND_ERROR_PREFIX`（[ADR 0082](./0082-tick-names-unsupported-job-kinds.md)）と同じ作法である。

### 4.3 ⚠ `"recent"` をユニオンに入れなかった

**【受】**Issue #106 の提案は `Array<"ann" | "lexical" | "recent">` だった。
**【現物】**しかし `RecalledMemory.retrievedVia` には既に **`"tag_match"` / `"recency"` という、
実装が1つも無い値が存在している**——`recall-runtime.ts` はこの2値を一度も書かない。

**⟹ それこそが、報告者が踏んだ罠そのものである**——型に名前が在るので呼び出し側は
「使える」と読むが、実装が無いので黙って何も起きない。
**⟹ 同じ欠陥を新規に1つ増やさない。**リクエスト側のユニオンは、後から広げても呼び出し側を壊さない。

**そして、値の一覧を散文で数え直さない。**唯一の出所は `RECALL_CHANNELS` であり、
zod schema もそこから導く。ADR 0082 の逐語（「**散文で数え直した瞬間に、次に kind が増えたとき
黙って嘘になる。コメントは検査されない**」）をそのまま当てている。

## 5. スコアへの入れ方 — `lexicalMatch` は第6の項ではない

**候補が「クエリにどれだけ近いか」を表す枠を `affinity` と呼び、`similarity` と `lexicalMatch` が
その枠を争う形にした:**

```
affinity = lexicalMatch === undefined ? (similarity ?? 1)
         : similarity   === undefined ? lexicalMatch
         : Math.max(similarity, lexicalMatch)
total    = affinity × decay × tagMatch × freshness × strength
```

**⚠ 第6の項として掛けなかった理由:** 掛ける形にすると、語彙一致が無い ANN 候補の `total` が
0 に落ちるか、中立の 1 を掛けるだけの死んだ項になる。**どちらも「掛ける」を選んだ時点で決まる。**

**🔴 `lexicalMatch` が `undefined` のとき、式は1演算も変わらない。**
`Math.max(similarity, 0)` のような形にしなかったのは意図的で、
**`similarity` は負になりうる**（コサイン距離は最大2まで出るので `1 - distance` は −1 まで下がる。
`VectorHit.distance` の doc、ADR 0036）。max で挟むと**負の類似度の候補の `total` が静かに変わる。**

### 5.1 🔴 `lexicalMatch` は候補集合の上で1通りしか値を取らない — ADR 0081 の教訓を自分に当てる

**語彙チャンネルが返した候補は、すべて `lexicalMatch = 1` である。**
adapter は「クエリの語彙をすべて含む」候補しか返さない契約なので、**語彙一致は二値**だからである。

**⟹ ADR 0081 が測った項（`tagMatch` / `strength`）と同じ族である。**
ただし違いが1つある——**この項はチャンネル間で分かれる**（語彙候補は 1、ANN だけの候補は不在）。
**⟹ チャンネル間では効く。語彙チャンネルの内側では効かない。**

**⟹ 語彙候補どうしの順序を決めているのは `decay` / `freshness` であり、
ADR 0081 の実測ではその変域は 1e-8 桁である。⟹ 事実上ほぼ任意である。**
**これは引き受けた負債である**（§8）。

**⚠ adapter が返す `LexicalHit.rank`（postgres 実装では `ts_rank_cd`）をスコアに流していない。**
尺度が adapter ごとに違い、**コサイン類似度と比較可能な量ではない。**
`rank` は adapter が窓を選ぶのに使い、`explain` に出るだけである。

---

## 6. `explain` — チャンネル1本につき trace を1つ

**`RecallStageName` に新しい段名を足していない。**`candidate_generation` の trace を
**走ったチャンネルの数だけ積む**（各要素の `detail.channel` が出所を名乗る）。

**⟹ 既定（ANN 1本）のとき、`explain.stages` は ADR 0084 以前と1要素も1バイトも変わらない。**
これは「新しい欄を常に足す」案を落とした結果である——足すと**既定の `explain` が変わってしまう。**

**候補ごとの出所は2つの欄が併せて名乗る:**

| | `retrievedVia` | `score.lexicalMatch` |
|---|---|---|
| ANN だけが当てた | `"ann"` | 無い |
| 語彙だけが当てた | `"lexical"` | `1` |
| **両方が当てた** | `"ann"` | `1` |

**⚠ `retrievedVia` 単独を「このチャンネルだけが見つけた」と読まないこと。**
単一の値でチャンネルの**集合**を表そうとしていない。

---

## 7. [ADR 0069](./0069-ann-truncated-says-nothing-about-loss.md) との関係 — 語彙が走ると上界の前提が崩れる

**ADR 0069 の損失可能性の判定は `R = bar / (sim_k' × M_max)` であり、
「ANN の窓の外の候補の similarity は `sim_k'` 以下」を前提にしている。**【現物】

**🔴 語彙チャンネルが走ると、その前提が成り立たない。**
ANN の窓の外に居る候補が、語彙一致によって `affinity = 1` を名乗りうるからである。

**⟹ 語彙チャンネルが走った run では、`ann_truncated` を `certainty: 'undecidable'` に落とす。**
判定を**試みない**——試みて `provably_safe` が返ると、成り立っていない前提の上で沈黙することになり、
**ADR 0069 が塞いだ穴を、こちらから開け直すことになる。**

**⚠ `nonSimilarityUpperBound` の値そのものは変えていない。**
`lexicalMatch` は `affinity`（similarity の枠）の中に居るので、
**非 similarity 4項の積という形も値も変わっていない。**

### 7.1 語彙チャンネルの打ち切りは別の札にする

`lexical_truncated`（`countKind: 'unknown'`、件数を持たない）を足した。
**`ann_truncated` に相乗りさせない**——あちらは損失可能性の判定まで作り込んだ札であり、
**こちらにはその機構が無い。**同じ札に潰すと「証明を試みた結果」と
「証明の機構をそもそも持たない」が同じ顔で返る。
形は [ADR 0026](./0026-ann-unreached-omission.md) の `ann_unreached` に倣っている。

## 8. 引き受けた負債

- **🔴 日本語の文に埋もれた日本語の語（人名を含む）を引けない**（§2）。
  **報告者が挙げた5種類のうち、人名がこれに当たる。**逃げ道は `LexicalStore` の差し替え（§3.4）。
- **🔴 語彙候補どうしの順序が事実上ほぼ任意である**（§5.1）。
  低選択率のクエリ（ありふれた ASCII 語1つ）を投げると、一致した記憶が全件 `affinity = 1` で
  並び、その中の順序は 1e-8 桁の項が決めることになる。
  **緩和は「語彙チャンネルが opt-in であること」だけであり、機構としては塞いでいない。**
- **表記ゆれに弱い**（§2）。`PROJ1234`（ハイフン無し）は引けない。
  **⚠ ここは ANN と壊れ方が違う**——ANN は順位が下がるだけだが、語彙は**崖から落ちる**。
- **`LexicalStore` が書き込み口を持たない。**`memories` の外に索引を持つ実装は、
  この interface だけでは同期できない。**その口が要る実装が現れたら足す。**
- **🔴 ASCII の語どうしは AND で結ばれる**（§2.1.1）。
  **英語の自然文をそのまま `text` に渡す呼び出し側は、語彙チャンネルからほとんど何も得られない。**
  日本語の呼び出しでこれが露見しなかったのは、非 ASCII を落とした結果**残る ASCII 語が
  識別子1つだけになることが多い**からにすぎない。**⟹ 言語によって使い勝手が変わる。**
- **in-memory の実装（`@mnemora/testkit` の `InMemoryLexicalStore`）は、
  §2.1.1 のクエリ側の非対称を持たない。**適合テストは ASCII のクエリしか通さないので、
  **この差は適合テストでは検出されない。⟹ in-memory を「postgres と同じ」と読まないこと。**
- **`retrieval` ベンチを回していない**（§9）。**`hit@1` への影響は測っていない。**
- **`docs/recall.md` §2 の「タグ一致・直近取得」は、今も実装が無い。**
  この ADR はその2本については何も変えていない。

## 9. 【実測・委】報告者の主張を実埋め込みで測った — 単純な形では再現しなかった

**⚠ この節は、報告者の報告を裏取りした結果であり、報告と食い違う。隠さずに書く。**

報告者の主張【受】:

> ベクタ検索だと、同じ形式の別の識別子（`PROJ-5678`）が近傍に来て、欲しいものが埋もれます。

### 9.1 小さいコーパスでは再現しなかった

**コーパス29文（社内 Slack 想定の短文、単文・識別子1個）:**

| クエリ | goldRank | cos(gold) | cos(最上位 distractor) |
|---|---|---|---|
| `PROJ-1234について前に何か言ってたっけ？` | **1** | 0.6824 | 0.5318（`PROJ-2345`） |
| `田中さんについて…` | **1** | 0.5752 | 0.4744 |
| `#ops-alertについて…` | **1** | 0.6185 | 0.5668（`#ops-warn`） |
| `gurumi-chan-backendについて…` | **1** | 0.7112 | 0.7076（`frontend`。**差 0.0036**） |

**⟹ 埋め込みモデルは識別子の文字列トークンそのものを拾っている。**
「同じ文型で ID だけ違う distractor」を置いても逆転しなかった。

### 9.2 大きいコーパスでも、単独の軸では埋もれなかった

**コーパス391文**（識別子を含まない自然な日本語の業務会話375文 + 特殊16文）、
**`kPrime = 40`**（既定 `limit 10 × overFetchFactor 4`）:

- **干し草の量だけでは埋もれない。**29文 → 391文にしても gold は rank 1〜2 を維持した。
  競合するのは常に**同形式の他 ID** であり、無関係な干し草は近傍競争に食い込まなかった。
- **希釈（290字の議事メモに識別子1トークン）だけでも窓は割らない**が、
  cos が 0.62 → 0.37〜0.49 に落ち、goldRank は 1 → 10〜27 に後退した。**マージンは確実に削れる。**
- **distractor を12件に増やしても、逆転（rank 2 に落ちる）は起きるが、窓からは消えなかった。**

### 9.3 ⟹ 埋もれたのは、複合条件のときだけである

| 条件 | goldRank | top-40 |
|---|---|---|
| 希釈 + 表記ゆれ（`Proj-1234`）+ 特定の言い回し | **50** | **❌** |
| 希釈 + 表記ゆれ（`proj1234`。ハイフン無し＋小文字） | **222** | **❌** |
| ID 非言及の言い換えクエリ + 本文が意味的に薄い | **217** | **❌** |

**⟹ 報告者の主張は「そのままの形では」成立しない。**
**⟹ ただし、報告者が懸念した事象そのものは、複合条件で実在する。**

**⚠ そして、3つのうち2つは表記ゆれが効いている。⟹ 語彙チャンネルはそこを救わない**——
`PROJ1234` は語彙でも 0件だからである（§2）。
**救えるのは「希釈」と「言い換え」の側であり、表記ゆれではない。**

### 9.4 ⚠ この節の限界

- **コーパスは作業者が作った合成物**であり、実際の Slack エクスポートではない。
- **複合条件は各1クエリしか試していない**（n=3）。うち1件は**脱落を再現しなかった**。
- **`text-embedding-3-small` / 256次元だけ**で測っている。
- **書き手自身の手では再実行していない**（【実測・委】）。

## 10. 検討した代替案

- **`pg_trgm` を `REQUIRED_EXTENSIONS` に足す。** **採らない**（§3）。買えるのは日本語の固有名詞1点で、
  代償は全導入者への条件追加と、**ロケール次第で日本語だけが黙って0件になること**である。
- **`pg_bigm` / `pgroonga` を足す。** **採らない。**`pg_trgm` より導入負担が重く（contrib ですらない）、
  §3 の議論がそのまま、より強く当たる。**⚠ この2つは実測していない**——
  測定に使った器に control ファイルが無く、`CREATE EXTENSION` が通らなかった。【実測】
- **生成列（`GENERATED ALWAYS AS … STORED`）で tsvector を持つ。** **採らない**（§4.1。全表書き換え）。
- **`plainto_tsquery` を使う。** **採らない**（§2。AND 意味論で `TASK-1234` を誤爆する）。
- **`ts_rank` をそのまま `lexicalMatch` にする。** **採らない**（§5。コサイン類似度と比較可能な量ではない）。
- **`RecallStageName` に `"lexical_candidate_generation"` を足す。** **採らない**（§6。
  既定の `explain` を変えずに済む形が在るのに、型を広げる理由が無い）。
- **`channels` に `"recent"` を入れる。** **採らない**（§4.3）。
- **配線が無いとき黙って0件を返す。** **採らない**（§4.2）。
- **クエリ語彙を OR で結び、`lexicalMatch` を「一致した語彙数 ÷ クエリ語彙数」にする。**
  **この ADR では採らない。**⭐ **ただし、これは筋の良い案であり、次に来る人が再発見しなくて済むように書いておく。**
  §2.1.1 の AND の制約（英語の自然文）と §5.1 の「`lexicalMatch` が1通りしか値を取らない」負債を、
  **1つの変更で両方とも解消する。**採らなかったのは実装の大きさの問題であり、筋の問題ではない——
  被覆率を SQL で行ごとに数える必要があり、`LexicalStore` の契約（AND 意味論）と
  `packages/testkit` の適合テスト・in-memory 実装まで同時に変わる。
  **⟹ 採るなら独立した変更として採るべきである。**
  **⚠ そのとき注意が要る点**: 被覆率は IDF を持たないので、ありふれた語1つだけのクエリでは
  `lexicalMatch = 1` が大量に立つ。**OR にするだけでは §8 の低選択率の問題は消えない。**
- **`retrievedVia` を配列にしてチャンネルの集合を表す。** **この ADR では採らない。**
  既に npm に出ている型の破壊的変更になる。`score.lexicalMatch` の有無で集合は復元できる（§6）。

## 11. これが覆るとしたら

- **日本語の固有名詞を語彙で引けないことが、実運用で効くと分かったとき。**
  §3 の判断は「買えるのは1点」という見立ての上に立っている。
  **⟹ その1点が主目的だったなら、`LexicalStore` の差し替えではなく必須化を再考することになる。**
- **語彙候補の順序の任意さ（§8）が実害を出したとき。**
  低選択率のクエリを投げる呼び出し側が現れると、すぐに出る。
- **`recall()` に `tags` を渡す呼び出し側が現れたとき。**
  ADR 0081 §9 と同じ向きの条件——`tagMatch` が動き出すと、§5 の `affinity` の比重が変わる。
- **PostgreSQL の既定パーサが CJK を分かち書きするようになったとき。**
  §1・§2 のすべてが `simple` パーサの現在の挙動に固有である。
- **導入先のクラスタのロケールが、ここで測った2つ（`C.utf8` / `C`）以外だったとき。**
  §3.2.1 のとおり識別子の引き当てはどちらでも成立したが、**日本語のトークンの切れ目は変わった。**
  ⟹ 「引けないものが引けるようになる」向きの変化なら害は無いが、**測っていない。**
