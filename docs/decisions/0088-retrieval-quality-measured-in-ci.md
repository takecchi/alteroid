# ADR 0088: 想起の質を CI で継続計測する — 記録の再生で鍵なしに測り、⛔ 門にはしない

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-10

**⚠ 各主張の出所を分ける**（[ADR 0081](./0081-similarity-is-the-only-term-that-ranks.md) /
[ADR 0084](./0084-lexical-recall-channel.md) の体裁を踏む）。

- **【実測】** — 本物の PostgreSQL に対して**この ADR の書き手が自分の手で**打った。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【受】** — 報告として受け取り、再導出していない。

## 文脈

**Issue #109**（外部の採用検討者 `the-phage-dev`。[ADR 0084](./0084-lexical-recall-channel.md) の
#106、[ADR 0083](./0083-cjk-aware-heuristic-token-counter.md) の #108 と同じ報告者）が
**「想起の質を実 embedding で継続計測する仕組みが無い」**と報告した。【現物】

**⚠ Issue #109 に「受け入れ基準」の節は無い。**【現物】4節構成
（何が無いか / なぜ要るか / 無い場合の影響 / 提案する形）で、最後の節が3項目である。逐語:

> 1. **固定した小さなゴールデンセット**(数十件程度の記憶と問い、期待される上位)を repo に置き、
>    `hit@1` / `hit@10` / MRR を出す。
> 2. それを**実 embedding で、週次などの頻度**(毎 PR でなくてよい)で走らせ、結果を数字として残す。
>    API キーが必要なので `schedule` + secret のあるジョブに限定する形が現実的だと思います。
> 3. **前回値との差分が閾値を超えたら落とす**、あるいは落とさずともログに出す。
>    閾値の設定自体が難しいので、まずは「値が残る」だけでも十分価値があります。

### 🔴 この issue が立つ前提のうち、1つは既に偽だった

**「API キーが必要」は、この repo では成り立っていない。**【現物】

[ADR 0051](./0051-recorded-provider-cassette.md) が入れたカセット
（`examples/chat/cassettes/retrieval.json`）には、**実 API の埋め込みが 152 件**
（`text-embedding-3-small` / **256 次元**、全件が 256 次元であることを確認した）と
LLM の応答 74 件が既にコミットされている。**`MNEMORA_PROVIDER_SOURCE=recorded` を指定すれば、
`OPENAI_API_KEY` が無くてもこれを再生できる**（[ADR 0068](./0068-the-bench-must-not-lie-about-what-it-measured.md)
が足した明示指定）。**ADR 0081 の測定自体がこの経路で行われている。**【現物】

**⟹ 週次でも `schedule` でも secret でもなく、毎 PR・鍵なしで測れる。**
**issue の提案を下回るのではなく、上回る形で塞げる。**

### ⟹ 本当に塞がっていたのは2つである

1. **【現物】誰も `retrieval` を CI のジョブに配線していなかった。**
   `.github/workflows/` の 2 ファイル（`ci.yml` / `publish.yml`）に `retrieval` の言及は **0 件**だった。
2. **【現物】カセットは入力が固定される。**鍵は入力文字列の SHA-256
   （`packages/testkit/src/__fixtures__/cassette.ts` の `embeddingCassetteKey`）であり、
   記録に無い入力は `RecordedEmbeddingProvider.embed` が例外にする（黙って擬似物へ倒れない）。
   **⟹ probe を1件足すと鍵が変わり、必ず落ちる。**

**この ADR が塞ぐのは 1 だけである。2 は塞がない**（後述「⛔ この ADR が閉じないもの」）。

### ⭐ これは新しい要望ではない — ADR 0022 が名指しした負債である

[ADR 0022](./0022-fake-provider-compare-does-not-claim-recall-quality.md) の
「これが覆るとしたら」の第1項、逐語:【現物】

> - CI に本物の(あるいは安価な)embedding provider を持たせられるようになったとき
>   ——`retrieval` を CI に載せ、想起の質の回帰をそこで検知できるようになれば、
>   `compare` に質の主張を戻す必要も無くなる。

**記録の再生は、追加コスト 0 という意味で文言どおりの「安価な embedding provider」である。**
⟹ **この ADR は ADR 0022 の前提を覆す。**

## 決めたこと

1. **`.github/workflows/ci.yml` に `retrieval` を走らせるジョブを1本足す。**
   条件は `MNEMORA_PROVIDER_SOURCE=recorded`（鍵なし）＋ 本物の Postgres + pgvector の
   service container（既存3ジョブと同じ `pgvector/pgvector:pg17`）。
   **`retrieval` は `DATABASE_URL` を要求し擬似物へフォールバックしない**ので、DB は省けない。【現物】
2. **`retrieval` に機械可読な出力口を足す**（`MNEMORA_RETRIEVAL_JSON=<path>`）。
   **🔴 数字だけを書かない**——arm ごとに**実際に使われた** `llmMode` / `embeddingMode` を
   同じ構造の中に持たせる（後述 §4）。**未設定なら挙動を変えない。**
3. **測った値を、基準値ファイルとの差分として Job Summary に出す。**
   一致していれば1行、**違うときだけ展開する。**
4. **⛔ 門にしない。**基準値と違っても落ちない（`exit 0`）。
   **落ちるのは bench そのものが壊れたときだけ**（カセットに無い入力・DB エラー・出力が壊れている）。

### ⚠ 決めていないこと

- **閾値をどこに置くか。**この ADR は閾値を1つも置かない。
- **ゴールデンセットをどう増やすか。**Issue #109 の項目1（数十件）は**この ADR では塞がらない。**
- **`compare` に質の主張を戻すか**（ADR 0022 の「これが覆るとしたら」の後半）。触らない。

127.0.0.1:5544。**本番ではない**）。commit `0a71a572d57049384d771c2fb6507f5b5046790b`。

実 API を叩いていないことは出力の
`[cassette] provider source: recorded(理由: MNEMORA_PROVIDER_SOURCE=recorded の明示指定…)`
の行で確認した。**所要時間 4.9 秒。**

## 1. 【実測】記録の再生で、鍵なしに ADR 0081 と同じ値が出る

`retrieval` の「arm ごとのまとめ」表（現物のまま）:

| arm | llmMode | embeddingMode | MRR(全体) | MRR(lexicalControl) | MRR(非語彙) | hit@1 | hit@10 |
|---|---|---|---|---|---|---|---|
| A: 擬似LLM+擬似埋め込み | deterministic | deterministic | 0.018 | 0.000 | 0.021 | 0/7 | 1/7 |
| B: 擬似LLM+本物の埋め込み | deterministic | recorded | 0.714 | 1.000 | 0.667 | 4/7 | 6/7 |
| C: 本物LLM+本物の埋め込み | recorded | recorded | **0.738** | 1.000 | 0.694 | **4/7** | **7/7** |

**⟹ ADR 0081 §3 の表と完全に一致した。**【実測】

**⚠ arm を取り違えないこと。**ADR 0081 §3.2 と ADR 0068 冒頭が記録している誤り
（**`MRR 0.714` は arm B の値であり、その arm の `hit@10` は 6/7 である**。
`hit@10 = 7/7` は arm C）は、**3 度起きている。**【受】

**⭐ そして今回は、4 度目が起きなかった。**この ADR の作業を出した委譲文は、
**正しい値（arm C = 0.738 / 4-7 / 7-7）を渡したうえで、誤った合成
「MRR 0.714 / hit@10 7/7」を名指しで警告し、「数字を書くときは、どの条件で測ったか
を必ず一緒に書け」と指示していた。**【受】

**⟹ 対策は効いた。ただし効いたのは、人が毎回それを思い出したからである。**
**⟹ だから §4 の JSON は、数字と条件を同じ行・同じ構造から離さない**
——思い出さなくても離れないようにする。

## 2. 🔴【実測】この bench は「同じ値が出ること」の門にはできない

**まとめ表は 2 回の実行で完全に一致した**（`diff` が空）。
**しかし出力全体は一致しない**——116 行が違った。逐語（同じ probe の同じ候補）:

```
run1:  項ごとの値の幅(返った候補全体): similarity=0.104840 decay=1.000e-7 … freshness=1.000e-7 …
       #1 [top1] total=0.949673 = similarity 0.949673 × decay 1.000000 × … × freshness 1.000000 × …
run2:  項ごとの値の幅(返った候補全体): similarity=0.104840 decay=3.958e-7 … freshness=3.958e-7 …
       #1 [top1] total=0.949672 = similarity 0.949673 × decay 0.999999 × … × freshness 0.999999 × …
```

**⟹ `decay` と `freshness` は実行ごとに揺れる。**`total` の6桁目が動いている。
（tenant id も毎回変わるが、これは `newRunToken()` の意図した挙動である。ADR 0068）

**なぜ見出しの数字は動かないのか。**`similarity` の変域は 0.10〜0.13、
`decay` の変域は 1e-7 台である——**約 10⁶ 倍の開きがある。**
⟹ 順位が入れ替わるには、2件の `similarity` の差が 1e-6 未満である必要がある。

**⟹ これは ADR 0081 §1 の結論が、別の器で再現したということである。**
「順位を決めているのは `similarity` ただ1項」であり、`tagMatch` と `strength` は
候補集合の上で1通りしか値を取らず、`freshness` は `decay` の行ごとの複製である。

### 2.1 ⟹ だから門にしない

**「2 回一致した」は「決定的である」の証明ではない。**
機序として `decay` は時刻に依存し、実際に揺れることを上で観測している。
⟹ **偽陽性率に上限を置けない。**

**⛔ 偽陽性率を上限で抑えられない門は、いずれ無視されるか無効化される。それは門が無いより悪い。**

**⛔ 品質の門（「MRR が閾値を下回ったら落とす」）も置かない。**別の理由による——
[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) §3 の逐語:

> **🔴 ⚠ 標本は probe 7件である。ここから失敗率も成功率も主張しない。**

**n = 7 では、順位が1つ動いただけで `hit@1` が 4/7 から 3/7 になる。**
⟹ 閾値の門は、この標本では偽陽性を出す。

**⟹ 2種類の門を両方とも採らない。**これは Issue #109 の項目3の逐語
（「まずは『値が残る』だけでも十分価値があります」）とも一致する。

## 3. ⚠ 値を「残す」だけでは読まれない — この repo に先例がある

`.github/workflows/ci.yml` の `compare` ステップのコメント、逐語:【現物】

> これまでこの数値は手元で測ったきり CI では実測していなかった
> （ADR 0021 参照）——このステップはそれを埋め、以後の変更で
> 「削れたが答えが落ちた」への回帰を**ログから読めるようにする。**

**⟹ 約束したのは「表を生ログに出すこと」であり、表の中身に対する assertion は1つも無い。**
合否を決めているのは `exit code` だけである。
**⟹ 気づくかどうかは、人間が生ログを開くかどうかに委ねられている。**

**⛔ この ADR は同じ形を繰り返さない。**採る形は3つ:

1. **基準値を repo にコミットする**
   （[`token-count-reference.json`](../../packages/core/src/__tests__/fixtures/token-count-reference.json)
   と `scripts/record-token-count-reference.mjs` が先例。基準値に**出所を添えて**コミットする形）。
   **⟹ 値が動いたら、新しい値が PR の diff に現れる。**git の履歴に残るのはこれだけである。
2. **差分を Job Summary に出す**（生ログではない）。
   **⟹ レビュアが既に居る場所**（PR の Checks）に、ダウンロードなしで描画される。
3. **一致しているときは1行で黙り、違うときだけ展開する。**
   **⭐ 常に同じ量を出す観測口は読まれない。**

## 4. 🔴 数字を、条件から離さない

**この repo では「条件を落とした数字」が実際に3度壊れている**（§1）。
**4 度目を止めたのは、委譲文が毎回それを書いていたからである——仕組みではない。**
⟹ 機械可読出力の構造そのものに、条件を埋める。

- arm ごとに、**宣言値ではなく実際に使われた** `llmMode` / `embeddingMode` を**同じオブジェクトに**持つ
  （`handle.llmMode` / `handle.embeddingMode` が出所）。
- 実行全体で、provider source・カセットの `recordedAt` と `embedding.space`
  （provider / model / dimensions）・probe 件数・haystack 件数・commit を持つ。
- **⚠ 数字をどこにも書き写さない。**出所は `retrieval-quality.ts` の既存の型と `armHeadline()` である。
  写すと、片方を直してもう片方が古いまま緑になる
  （`docs/recall.md` が「走らせられるチャンネルの一覧をここに書き写さないこと」で
  同じ二重管理を禁じているのと同じ理由）。

そして Job Summary には、**数字と一緒に必ず3つの注意書きを出す:**

1. **動いているのは `similarity` ただ1項である**（ADR 0081 §1）。
2. **標本は probe 7件である。ここから失敗率も成功率も主張しない**（ADR 0033 §3）。
3. **⛔ 埋め込みは否定・時制・矛盾を解かない。**
   **⟹ この値が上がっても「精度が上がった」と一言でまとめてはならない。**
   何が上がって何が上がらないかを分けて読むこと。【受】

## ⛔ この ADR が閉じないもの

**⚠ 名乗れるのは「検知できるようにした」までであり、「実際に検知する歯にした」ではない。**

差分の計算は機械がやり、結果はレビュアが既に居る場所に描画される。
**⟹ 生ログより格段に強い。しかし最後は人の注意力に残る。**

**これを閉じるのは、この ADR ではない。**閉じるには閾値の門が要り、閾値の門を置くには
**標本が 7 件では足りない**（ADR 0033 §3）。
**⟹ Issue #109 の項目1（ゴールデンセットを数十件へ）が先に要る。**

**そして項目1は、カセットのままでは構造的に閉じている**（文脈 §2）。
probe を1件足すと鍵が変わり、記録に無い入力は例外になる。
**⟹ 順序は「実 API で録り直せる手段」または「入力が固定されない埋め込み provider」が先である。**

## 検討して採らなかった案

- **⛔ `schedule` + secret のジョブにする**（Issue #109 の項目2そのまま）。
  **鍵が要るという前提が偽だった**ので、採る理由が無い。毎 PR・鍵なしのほうが強い。
- **⛔ 実 API（`MNEMORA_PROVIDER_SOURCE=openai`）を CI で叩く。**
  CI に鍵が無く、**入れる判断はオーナー専権**である（`docs/autonomy.md`）。
  さらに毎 PR の課金が発生する（ADR 0019 §1）。
- **⛔ 基準値との相違で CI を落とす（再現性の門）。**§2.1。
  **一度は採ろうとしたが、`decay` の揺れを実測して取り下げた。**
- **⛔ MRR の閾値で落とす（品質の門）。**§2.1。n = 7 で偽陽性が出る。
- **⛔ 生ログに出すだけにする。**§3 の先例が、それが読まれないことを示している。
- **⛔ stdout をパースして値を取り出す。**表の書式が変わると黙って壊れる。
  機械可読な口を1つ足すほうが素直で、**PR 2 のゴールデンセット拡張でもそのまま使える。**
- **⛔ `verify` を CI に載せる。**`verify` は記録と実 API の乖離を測るもので、
  `OPENAI_API_KEY` が無いと即例外になる。【現物】手動専用である。
- **⛔ 既存4ジョブに `timeout-minutes` を一斉に付ける。**この ADR の範囲外である
  （repo 全体で 0 箇所・既定 360 分だが、**足した1ジョブにだけ**付ける）。

## 引き受けた負債

1. **⚠ 標本は probe 7件のままである。**この ADR は1件も増やしていない。
   CI に常時載ることで、**読み手が標本の小ささを忘れやすくなる危険はむしろ増える。**
   ⟹ だから §4 の注意書き2を、数字と同じ場所に必ず出す。
2. **⚠ 測っているのは arm C だけではない。**A / B / C の3本すべてが走る（`retrieval` に arm を
   選ぶ口が無い。【現物】）。**arm A の MRR 0.018 は実質ランダムであり、
   これを「引けた」と読んではいけない**（ADR 0022 / AGENTS.md）。
3. **⚠ 基準値ファイルは人が更新する。**意図した変更のたびに手で書き換える手間が要る。
   **⭐ ただしその手間は目的である**——書き換えないと差分が Job Summary に出続けるので、
   **新しい値が PR の diff に必ず現れる。**
4. **⚠ カセットは 2026-09-06 に録ったものである。**実 API との乖離は時間とともに開く。
   測っているのは「**記録した時点の** `text-embedding-3-small` で測った質」である。
   乖離は `verify` でしか分からず、それには鍵が要る。
5. **⚠ この ADR は ADR 0022 の状態欄を書き換えない。**
   **この repo に「採用済みの ADR を覆った」と示す書式が無いため**である——
   全 ADR の状態欄を確認したところ、`Superseded` に相当する表記は 0 件で、
   存在するのは「一度も採用されていない」2件（ADR 0025「未決」/ ADR 0074「提案（未採用）」）だけだった。【現物】
   一方、**採用済みの結論を訂正する場面では、状態欄を変えず本文に追記節を足すのが慣行**である
   （ADR 0064 が ADR 0063 の「約2.5倍」を訂正、ADR 0072 の「追記(2026-09-09)」）。
   **⟹ その先例に従い、ADR 0022 の本文に追記節を1つ足した。新しい書式は作っていない。**

## これが覆るとしたら

- **ゴールデンセットが数十件になったとき。**標本が増えれば ADR 0033 §3 の警告が緩み、
  **閾値の門を置けるようになる**——このとき「⛔ 門にしない」は覆る。
  **それが Issue #109 を本当に閉じる一手である。**
- **`decay` が時刻に依存しなくなったとき**（例: 取り込み時刻を固定できる口が bench に入る）。
  揺れが消えれば、再現性の門は偽陽性ゼロで置ける。
- **カセットが実 API と大きく乖離していると分かったとき**（`verify` で測る）。
  そのとき測っているものは「実 embedding の質」とは呼べなくなる。
- **CI に実 API の鍵が入ったとき。**そのとき記録の再生は「鍵が無いから」ではなく
  「毎 PR で課金しないため」の選択に変わる——**理由が変われば、書き直す必要がある。**
