# ADR 0058: 時間項は、既存の probe set を書き換えずに、別 arm で分離して測る — `probe-set.ts` に `occurredAt` を書き込まない

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-08

**⚠ 各主張の出所を分ける。**この文書では次の3つを混ぜない
（[AGENTS.md](../../AGENTS.md)「確かめていないことは『確かめていない』と書く」の適用）。

- **【現物】** — この決定の担当者が、リポジトリのファイルを読んで確かめた。
- **【計算】** — 既に記録されている実測値から、担当者が算術で導いた。**測り直してはいない。**
- **【実測】** — この決定のために、担当者が実際に走らせて得た数字。環境を明記する。

---

## 文脈

[ADR 0033](./0033-what-decided-the-rank-in-the-retrieval-bench.md) は、`retrieval` ベンチの
順位を実際に決めていた項を計装して測り、こう記録した（逐語）:

> **⟹ `total = similarity × decay × tagMatch × freshness × strength` は、
> この測定では実質 `similarity × decay²` であり、`decay²` は全候補でほぼ同一である。**

> **⟹ `decay` / `freshness` / `tagMatch` / `strength` のどれも、この3件のどれ1つ
> 順位を動かせない。**

**⟹ スコアは5項あるが、あのベンチでは4項が定数であり、時間項（`freshness` / `decay`）は
一度も順位を動かしていない。**そして
[ADR 0055](./0055-extraction-prompt-subject-and-inference-not-added.md) は、
ADR 0033 §7 が「スコアに時制の項を足す」に付けた理由を読み直して、こう書いた（逐語）:

> **⟹ これは「時制で順位を分けることを禁じた」のではなく、「前提が足りない」と書いたのである。**

> **⟹ 時制の項を検討できるようになる前提は、「`retrieval` の probe set が `occurredAt` を渡すこと」である。**
> **⚠ この ADR は、それを足すとは決めていない**

**⟹ 宿題が2つに割れて残っていた。**

1. **`probe-set.ts` の gold/distractor に `occurredAt` を書き込むか。**
2. **時間項が順位を動かすかどうかを、そもそもどう測るか。**

**この ADR は 1 を「採らない」と決め、2 に別の道を足す。**

---

## 決定

1. **`examples/chat/src/probe-set.ts` に `occurredAt` を手で書き込まない。**
   既存の gold/distractor 14件は1文字も変えない。
2. **代わりに、「内容は同一・時刻だけ違う」ペアを使う別の arm を足す**
   （`examples/chat/src/time-term-*.ts`）。**既存の probe set には指1本触れない。**

## 1 を採らない理由

**⚠ ここに並べるのは*性質*の理由である**——「いまそうなっている」ではなく
「そう作られている」に根拠を置く。事情の理由（前後比較が切れる等）は §1.6 で別に扱う。

### 1.1 `decay` は `occurredAt` を読まない 【現物】

`packages/core/src/strategies/decay.ts` の起点は `lastReinforcedAt ?? recordedAt` だけである:

```ts
function decayBase(params: DecayParams): Date {
  return params.lastReinforcedAt ?? params.recordedAt;
}
```

`DecayParams` に `occurredAt` の欄は無い。**⟹ `occurredAt` を渡して動くのは
`freshness` の1項だけである。**「時間項2つを動かす」ことにはならない。

### 1.2 `freshness` には上限が在るのに、下限が無い 【現物】

`packages/core/src/strategies/scoring.ts`:

```ts
const freshness = Math.min(
  MAX_FRESHNESS,
  defaultDecayStrategy.strengthAt(input.now, {
    recordedAt: input.occurredAt ?? input.recordedAt,
    ...
```

clamp は `Math.min` の片側だけである（`MAX_FRESHNESS = 1`、
[ADR 0036](./0036-clamp-freshness-at-one.md)）。**⟹ 未来の `occurredAt` は現状と同じ 1 に
なり、過去の `occurredAt` は total を*下げるだけ*である。**

### 1.3 ⟹ probe set に時刻を書き込むと、いま外している1件を専用に押し上げる 【計算】

**⚠ この節は計算である。担当者は測り直していない。**入力は ADR 0033 §1 が記録した
travel probe の実測値（`distractor の total = 0.421283`、`gold の total = 0.388142`）と、
既定の半減期 720時間（`DEFAULT_HALF_LIFE_HOURS`）である。

travel の gold は「来月、京都へ出張します。」（**未来**）、distractor は
「先月は大阪へ出張しました。」（**過去**）である。§1.2 より、gold の `freshness` は
1 に張り付いたまま、distractor の `freshness` だけが下がる。distractor が gold を
下回るのに必要な値は:

```
0.421283 × f < 0.388142  ⟺  f < 0.388142 / 0.421283 = 0.92133
0.5 ** (t / 720h) = 0.92133  ⟺  t = 85.2時間 = 3.55日
```

**⟹ distractor の `occurredAt` が 3.55日より古ければ、値を何にしても逆転する。**
そして distractor の本文は「**先月**」なので、忠実な推定は約30日前であり
`freshness ≒ 0.5` になる。**⟹ 「値を慎重に選んで中立に保つ」逃げ道は存在しない。**
`hit@1` は 4/7 → 5/7 になる。

### 1.4 定数であることは欠陥ではなく、設計された統制である 【現物】

`examples/chat/src/probe-set.ts` の `buildProbeSetConversation` の docstring（逐語）:

> gold の直後に同じ probe の distractor を置く。両者は生成時刻がほぼ同時になるため、
> 順位の差は decay/freshness ではなくスコア(類似度)由来だと言える

**⟹ 時間項が定数であることは、あの probe set が意図して作った統制条件である。**
そこへ時刻を書き込むのは、計装を足すことではなく**統制を外すこと**である。

### 1.5 通っても、通った理由が違う 【現物】

travel が外れる原因は ADR 0033 §2.1 が反実仮想で特定している（逐語）:

> **⟹ 埋め込みは時制を符号化して照合している。**probe の質問が「次の」と言いながら
> **表層は過去形「でしたか」**なので、埋め込みは表層に忠実に過去の記憶を上げている。

**`freshness` は時制の*照合*ではなく、*古び*を測る項である。**
「質問が指す時間の向き」と「記憶がどれだけ古いか」は別の量である。
⟹ `occurredAt` を書き込んで travel が通ったとしても、通した理由は
**原因として特定されているものとは別のもの**になる。

**⟹ [docs/north-star.md](../north-star.md) の問い3（この記憶が選ばれた理由を、後から
説明できるか）に照らして、これは説明の付かない ✅ である。**問い3 は
「説明できない賢さは採らない」と書いてある。

### 1.6 ADR 0037 が、同じ変更を明文で却下している 【現物】

**⚠ ここは担当者が現物で確かめて、受け取った前提を1つ訂正した箇所である。**

[ADR 0037](./0037-callers-pass-occurred-at.md) の「検討して採らなかった案」には、
関係する項目が**2つ**在り、**理由はそれぞれ別の案に付いている**。

**(a) probe set について書かれた項目**（逐語）:

> **`ingestConversation`（`compare` の取り込み段）や `probe-set` の会話に時刻を付ける。**
> **却下。**測定条件そのものを変えることになり、前後が比較できなくなる
> （ADR 0022 の「見栄えの良い数字のために測る条件を選び直さない」に触れる）。
> **サンプルは独立したデモとして足し、主測定には指1本触れない。**

**(b) 隣の別の案について書かれた項目**（逐語）:

> **`occurredAt` を省略したときに `recordedAt` を明示的にコピーする。**却下。
> いまも `effectiveTime` のフォールバックで同じ結果になるうえ、
> **「値が無い」と「値が推定で埋まっている」の区別が消える。**

**🔴 ⟹ 「『値が無い』と『値が推定で埋まっている』の区別が消える」は、
ADR 0037 が probe set について書いた理由では*ない*。**(b) の案に付いた理由である。
**この ADR は、それを 0037 の文言として引かない。**

**⟹ ただし、性質の理由としては延長できる**——`probe-set.ts` の会話は合成であり、
**本当の出来事時刻がそもそも存在しない**。⟹ 書き込む値は必ず誰かの推定になる。
**⚠ これは担当者による延長であり、ADR 0037 の文言ではない。**

**⟹ 0037 が (a) に付けた理由（前後比較が切れる）は、単独では弱い**——測定を改善すれば
前後比較は必ずどこかで切れる。**強いのは §1.1〜1.5 のほうである。**

## 2 で足したもの — 時間項を分離する arm

### 2.1 何を変えれば分離になるか

**時間項だけを動かしたいなら、時間項以外を*構成上*固定すればよい。**

`total = similarity × decay × tagMatch × freshness × strength` のうち、
`tagMatch` は `recall(ctx, {text})` がクエリタグを渡さない限り厳密に 1、
`strength` は作成時に無条件で 1 である（どちらも ADR 0033 §1 が測った通り）。
残るのは `similarity` と時間項2つである。

**⟹ ペアの本文を*まったく同一*にすれば、`similarity` は構成上ぴったり同じになる。**
`DeterministicEmbeddingProvider` は「同じテキストには常に同じベクトルを返す」ことを
契約として持ち【現物】、本物の埋め込みモデルも同じ入力には同じベクトルを返す。

**⟹ 残った差は時間項だけである。**そして arm はそれを仮定せず、
**`similarity` の差が実際に 0 だったことを毎回測って報告する。**

### 2.2 2つの時間項を、別々の口で振る

| 項 | 起点 | 振る口 |
|---|---|---|
| `freshness` | `occurredAt ?? recordedAt` | `observe()` に `occurredAt` を渡す |
| `decay` | `lastReinforcedAt ?? recordedAt` | `Clock` を注入して `recordedAt` を振る |

**⚠ `decay` は `occurredAt` を読まない（§1.1）ので、`occurredAt` では振れない。**
`recordedAt` は `clock.now()` から入るため（`packages/core/src/runtime.ts`・
`extraction.ts`）、`createRuntime` が受け取る `clock` を差し替えれば振れる。
**⟹ `examples/chat` 側に `Clock` を注入する口を足した。`packages/*` は変えていない。**

**⚠ `reinforce`（`observe({kind:'memory_usage'})`）では振らない。**
[ADR 0048](./0048-reinforce-does-not-move-decay-origin-backwards.md) の通り
`reinforce` は起点を*前*へしか動かさないので、「古い側」を作れない。
片方を強化する形にすると、測るものが「時間項の分離」ではなく
**「強化の効果」**に変わる——それは別の問いである。

### 2.3 probe ごとに別テナントを使う

スコープ内に**そのペアの2件だけ**を置く。理由: 既定の `limit`（10）や
`scoreThreshold`（0.1）の外に落ちる可能性と、他 probe との競合を消せる。

**⟹ この arm は「現実らしさ」を捨てて「分離」を採る。**
現実らしさは既存の `probe-set.ts`（7 probe が1つのスコープに同居し、干し草60件が
積まれている）の側が担っており、**両方を1つの probe set に負わせない。**

### 2.4 何を判定材料として出すか

- **ペア内の `similarity` の差**——0 でなければ、この arm は分離できていない。
- **`freshness`（または `decay`）の比**と**`total` の比**。
  **⟹ 順位差の全部が時間項由来だと言えるのは、この2つが一致するときだけである。**
- **順位の分類**（`newer-ranked-higher` / `older-ranked-higher` / `tied` /
  `older-not-returned` / …）。**返らなかったものを 0 に潰さない**
  （[ADR 0008](./0008-absence-taxonomy.md)「無いには種類がある」の適用）。
  ペアが1件に潰れた場合は `collapsed` を返す——**構造上起きないはずだが、
  起きたときに黙って別の分類へ読み替えないため**に持つ。

### 2.5 鳴ってはいけない側を、probe として持つ

- **`same-occurred-at`** — ペアの `occurredAt` を同じにする。
  ⟹ 時間項は順位を決めてはいけない。
- **`absent`** — `occurredAt` を渡さない。
  ⟹ ADR 0033 が測った条件（`freshness` が `decay` と同値）を再現しなければならない。

**この2つが鳴ったら、arm 自身が壊れている。**

### 2.6 provider 層に依らない

ペアの本文が同一なので、`similarity` がどんな値であっても**ペア内では等しい**。
**⟹ この測定はカセットの再録も `OPENAI_API_KEY` も要らない。**

**⚠ ただし「想起の質」は主張しない。**[AGENTS.md](../../AGENTS.md) の線の通り、
擬似 provider で測った順位は性能について何も言っていない。
**この arm が言うのは「時間項が順位を動かすか・どれだけ動かすか」だけである。**

## 測ったこと 【実測】

**出所: この決定の担当者が実行した。**環境は**本物の PostgreSQL 17.11 + pgvector 0.8.6**
（この器に root 権限なしで `.deb` を prefix へ展開して立てたもの。TCP 待受）。
provider は `deterministic` に固定（§2.6 の通り、ペアの本文が同一なので `similarity` は
ペア内で定数になり、この測定は provider 層に依らない）。

### 8 probe の実測

| probe | 振った項 | outcome | newer | older | ペア内 `similarity` の差 | 時間項の比 | `total` の比 |
|---|---|---|---|---|---|---|---|
| `half-life` | `freshness` | `newer-ranked-higher` | `freshness` 1.000000 | 0.500000 | **0.000000** | 0.500000 | **0.500000** |
| `realistic` | `freshness` | `newer-ranked-higher` | 0.977160 | 0.911722 | **0.000000** | 0.933033 | **0.933033** |
| `same-occurred-at` | （振らない） | `tied` | 0.850667 | 0.850667 | 0.000000 | 1.000000 | 1.000000 |
| `absent` | （振らない） | `tied` | 1.000000 | 1.000000 | 0.000000 | 1.000000 | 1.000000 |
| `far-past` | `freshness` | `older-not-returned` | 0.977160 | （返っていない） | — | — | — |
| `decay-half-life` | `decay` | `newer-ranked-higher` | `decay` 1.000000 | 0.500000 | **0.000000** | 0.500000 | **0.500000** |
| `decay-realistic` | `decay` | `newer-ranked-higher` | 0.977160 | 0.911722 | **0.000000** | 0.933033 | **0.933033** |
| `decay-same-recorded-at` | （振らない） | `tied` | 0.977160 | 0.977160 | 0.000000 | 1.000000 | 1.000000 |

**⟹ 言えるようになったこと（3つ）:**

1. **時間項は順位を動かす。**`freshness` でも `decay` でも、**ペア内の
   `similarity` の差が厳密に 0 のまま順位が入れ替わった。**
   ⟹ ADR 0033 が測った「時間項はどれ1つ順位を動かせない（約1050倍の開き）」は、
   **項が弱いことの帰結ではなく、`occurredAt` が全件 null で、かつ全件を1〜2分で
   取り込んでいたことの帰結である。**
2. **順位差の全部が時間項で説明できる。**`total` の比が、振った項の比と
   **小数第6位まで一致した**（0.500000 / 0.933033）。
   ⟹ 「時間項が効いた」ではなく「**時間項だけが効いた**」と言える。
   これが [docs/north-star.md](../north-star.md) の問い3（なぜ選ばれたかを後から説明できるか）に
   対して、この arm が出せる答えである。
3. **時間項は「順位を下げる」だけでなく「候補を落とす」。**`far-past`（`occurredAt` が
   365日前、`freshness` ≒ 2.2×10⁻⁴）では、older 側が `scoreThreshold`（既定 0.1）を
   割って**返ってこなかった**（`omitted` の種別は `below_threshold`）。
   **⚠ 閾値を緩めてこれを返させることはしない**——落ちたこと自体が観測である。

### 現実的に小さい差でも順位は動く

`realistic` / `decay-realistic` は、時間差を **1日 対 4日**しか置いていない
（`freshness`・`decay` の差は 0.0654）。**それでも順位は決まった。**
⟹ 時間項が効くのに桁違いの時間差は要らない。

### ⚠ この測定で消してあるもの

**probe 内で時刻を1点に凍結している**ため、`recordedAt` を明示しない probe では
`decay` の幅が**厳密に 0** になる。**⟹ ADR 0033 が記録した `decay` の幅
（probe ごとに 1.1〜1.8×10⁻⁵）は、ここでは再現していない。**あれは60件超を1〜2分かけて
取り込んだ実時間の産物であり、この arm は「時間項以外を動かさない」ために意図して消してある。
**`absent` probe が再現しているのは、数値の幅ではなく
「`occurredAt` が null なら `freshness` は `decay` と同じ数になる」という構造のほうである。**

### 変異で撃った結果 【実測】

**⭐ 本命は「新しい歯が*固有に*捕まえる変異か」である。**製品コードを一時的に壊して、
**既存の歯が全部緑のまま新しい歯だけが赤くなるか**を見た（撃ったあと必ず元に戻し、
`git diff packages/` が空であることを確認している）。

| 変異 | 結果 | 既存の歯 | 新しい歯 |
|---|---|---|---|
| `recall-runtime.ts` 段2 の `occurredAt: memory.occurredAt` → `null` | **殺した** | `packages/core` 298件・`packages/postgres` 220件・`examples/chat` 既存106件**すべて緑** | `time-term.postgres.test.ts` のみ赤 |
| `recall-runtime.ts` 段2 の `recordedAt: memory.recordedAt` → `now`（`decay` の起点を殺す） | **殺した** | 同上、**すべて緑** | `time-term.postgres.test.ts` のみ赤 |
| `classifyPairOutcome` の順位比較を反転 | 殺した | — | 単体4件が赤 |
| `realistic` probe の新旧を入れ替え | 殺した | — | 単体+統合3件が赤 |
| `observe()` から `occurredAt` を落とす | 殺した | — | 統合が赤（`half-life` が `tied` になる） |
| `Clock` を振らない（`decay` を動かさない） | 殺した | — | 統合が赤（`decay-half-life` が `tied` になる） |
| 対照 `same-occurred-at` を非対称にする | 殺した | — | 3件が赤（**対照が空虚でないことの確認**） |
| `pairCollapsed` の判定を `false` に潰す | **🔴 生き残った** | — | **全部緑のまま** |

**⟹ 上2つが、この arm を足した理由そのものである。**
`observe(occurredAt)` → `recall()` の**順位とスコア内訳**まで一本で見ている歯は、
これまで存在しなかった（`observe-occurred-at.test.ts` は `period` の絞りだけを見て、
`scoring.test.ts` は純関数だけを見ていた）。

**🔴 最後の1つが生き残ったことを、緑の顔で隠さない。**§2.4 の `collapsed` は
**いまのどの歯にも殺せない**——`totalInScope < 2` を公開経路から作り出せないためである。
詳細は「引き受ける負債」に書く。

## 検討して採らなかった案

- **既存 probe set の gold/distractor に `occurredAt` を書き込む。**
  却下。§1.1〜1.6。
- **既存 probe set をそのまま ingest し、あとから `UPDATE memories SET occurred_at = …` で
  時刻を入れる。**却下。**製品コードを迂回して DB を直接書くと、
  `observe()` → `Memory` → `recall()` の配線を測ったことにならない**——
  測りたいものの一部が測定から抜ける。
- **`scoreThreshold` / `limit` を緩めて、落ちた候補も返させる。**
  却下。ADR 0022・ADR 0033 の線（見栄えの良い数字のために測る条件を選び直さない）。
  候補が閾値を割って落ちたなら、**それ自体が時間項の効果の観測である**——
  `omitted` の種別として報告する。
- **`freshness` に下限（`MAX_FRESHNESS` の対）を足す。**
  この ADR では扱わない。**測定が先である。**下限を入れるかどうかは、
  時間項が実際に何をしているかを測ったあとの判断である。
- **スコアに「時制の項」を足す。**
  この ADR では扱わない。ADR 0055 が明文で再開した論点だが、
  **踏み込む前に時間項の測定を置く**という順序をこの ADR が決めている。

## 引き受ける負債・覆えていない範囲

- **🔴 `collapsed` の分岐は、どの歯にも殺せていない** 【実測】。判定
  （`totalInScope < 2`）を `false` に潰す変異を撃っても、8 probe の歯は全部緑のままだった。
  **理由: 公開経路から `totalInScope < 2` を作り出せない**——`observe()` は同一内容でも
  別 `externalId` なら別 Memory を作るので、ペアは必ず2件になる。
  ⟹ **この分岐は「いま効いている検査」ではなく「将来 dedupe が入ったときに、
  `older-not-returned` と読み違えないための名前」である。**
  検出そのものは歯の側の `totalInScope === 2` が担っており、そちらは効いている。
  **⚠ 残すか外すかは判断の分かれるところである**（ADR 0024 の「届かない分岐を残さない」に
  触れる）。**残す側に寄せた理由は、この arm の出力が人が読む測定結果であり、
  潰れたときに「片方が返らなかった」と表示されるより「潰れた」と表示されるほうが
  読み違えにくいからである。**
- **ペアが2件として残ることに依存している。**同一内容の Memory が2件作られるのは、
  抽出の冪等キーに `source_observation_id` が入っているため【現物】であり、
  **dedupe や矛盾検出が入ればこの arm は壊れる。**壊れたときは `collapsed` を返す。
- **現実らしさを捨てている**（§2.3）。この arm の数字から
  「実運用で時間項がどれだけ効くか」は言えない。
- **標本は probe 数件である。**一般的な失敗率も成功率も、ここからは主張できない。
- **`tied` の判定に使う閾値は裁量値である。**強い根拠は無い。
- **既存の `retrieval` ベンチの数字は1つも変わっていない。**
  ⟹ この ADR は `hit@1` を改善していない。**改善していないことが、この ADR の意図である。**

## これが覆るとしたら

- **抽出スキーマに時刻の欄が入り、`occurredAt` が実データから埋まるようになったら。**
  そのとき probe set の `occurredAt` は「誰かの推定」ではなくなり、§1.6 の延長した
  理由は成り立たなくなる。**§1.3〜1.5 は残る。**
- **`freshness` に下限が入ったら。**§1.2・§1.3 の計算は作り直しになる。
- **dedupe / 矛盾検出が入って同一内容が1件に潰れるようになったら。**
  この arm は `collapsed` を報告して自ら壊れたことを示す設計だが、
  **arm の組み方そのものを変える必要がある。**
- **既存 probe set の gold/distractor を、別の理由で作り直すことになったら。**
  そのとき ADR 0033 との前後比較は既に切れているので、§1.6 (a) の理由は消える。
  **§1.1〜1.5 だけで判断し直すこと。**

## 確かめたこと / 確かめていないこと

**確かめた 【現物】**

- `decay` は `occurredAt` を読まない（§1.1）。`freshness` の clamp は片側だけ（§1.2）。
- `probe-set.ts` の docstring が、時間項の定数性を設計された統制として書いている（§1.4）。
- ADR 0037 の却下理由が、2つの別の案に別々に付いている（§1.6）。
- **既存の `probe-set.ts` の gold/distractor 14件は1文字も変わっていない。**
  ⟹ ADR 0033 が記録した `hit@1` 4/7 の系列との前後比較は切れていない。
- `packages/*`（製品コード）の差分は空である。足したのは `examples/chat`（測定の側）と
  `docs/` だけである。

**確かめた 【計算】**

- travel probe の逆転に必要な `freshness` は 0.92133、対応する時間差は 3.55日（§1.3）。
  **⚠ 測り直していない。**入力は ADR 0033 が記録した実測値である。

**確かめた 【実測】**

- 8 probe の順位・スコア内訳（「測ったこと」節）。
- 変異8本のうち7本を殺し、**上2本は既存の歯が全部緑のまま新しい歯だけが赤くなった。**
- **⚠ 取り込み中に `Clock` を取り込み開始より前へ戻すと、embed ジョブが1件も claim されない。**
  `outbox.available_at` は Postgres の SQL `now()` で入るが、`tick()` の claim 条件は
  アプリ側の `Clock` で評価するためである。**最初の実装でこれを踏み、8 probe すべてが
  「この項を持つ候補が無い」になった。**⟹ `recall` の直前に戻す時刻は、
  取り込み開始時点ではなく**取り込み後に取り直した実時刻**でなければならない。

**確かめていない**

- **実運用で時間項がどれだけ効くか。**この arm は分離のために現実らしさを捨てている（§2.3）。
- **本物の埋め込み・本物の LLM でこの arm を走らせた結果。**
  §2.6 の通り構成上 provider に依らないと考えているが、**実際に走らせて確かめてはいない。**
- **`collapsed` の分岐が実際に働くこと**（「引き受ける負債」の1項目め）。
- **時間項に下限を入れるべきか、時制の項を足すべきか。**この ADR は測定を置いただけであり、
  スコアの式について何も決めていない。
