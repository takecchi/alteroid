# ADR 0085: 外部サービスに繋がない埋め込み provider を足す — 契約を変えず、対称 prefix を名前に焼き込む

- **状態**: 採用 (2026-09)
- **日付**: 2026-09-10

**⚠ 各主張の出所を分ける**（[ADR 0081](./0081-similarity-is-the-only-term-that-ranks.md) /
[ADR 0084](./0084-lexical-recall-channel.md) の体裁を踏む）。

- **【現物】** — この repo のコード・文書を**この ADR の書き手が自分の手で**読んで確かめた。
- **【実測・委】** — 実行したのは委譲先の作業者であり、**書き手は数字を受け取っている。**

## 文脈

**【オーナー】2026-09-09、オーナーが「記憶を mnemora で扱うときの『言葉で探す』部分をどう作るか」
という選択に答え、「自前で動かす変換モデルを mnemora に足す（外部サービスに繋がない）」を選んだ。**
同時に、直前に積まれていた「OpenAI の API キーを入れてよいか」という確認を**取り下げている。**
⟹ **この用途で外部の API キーを要求する設計は採れない。**

⚠ **これは「mnemora が今後いっさい OpenAI に触らない」という決定では*ない*。**
`packages/openai` は既に在り、実 API での測定（[ADR 0019](./0019-real-openai-measurement-cost.md)）に
使われている。**本 ADR は足す決定であり、既存の provider を削らない・既定から外さない。**

### なぜ埋め込みなのか

**【現物】[ADR 0081](./0081-similarity-is-the-only-term-that-ranks.md) が測って結論している** ——
`total = similarity × decay × tagMatch × freshness × strength` の順位を決めているのは
**`similarity` ただ1項**である（候補集合の上で `tagMatch` と `strength` は1通り、
`freshness` は `decay` の行ごと厳密な複製、`decay` の変域は 1e-8 桁）。

**【現物】[ADR 0019](./0019-real-openai-measurement-cost.md) §7.4** はさらに直接的で、
arm A → arm B（**変えたのは埋め込みだけ**、LLM は擬似のまま）で MRR が 0.018 → 0.714 に上がり、
arm B → arm C（LLM も記録に）の上積みは 0.714 → 0.738 と小さいことから、
**「この物差しを動かしていたのは埋め込みであり、抽出ではない」**と書いている。

⟹ **埋め込みの質が想起の質をほぼ決めている。**

### そして、CI に埋め込みの質を測る歯が無い

**【現物】[ADR 0022](./0022-fake-provider-compare-does-not-claim-recall-quality.md) が
「引き受けた負債」として名指ししている:**

> 擬似 provider だけを使う CI …では、**想起の質の回帰を検知する歯が無い。**
> `compare` が測るのは量だけであり、`retrieval` は本物の API キーが要るため
> CI には載っていない(手動実行のみ)。…この負債は「実 API キーを CI に持たせる」までは
> 解消しない(費用が発生するため…オーナー判断が要る)。

同 ADR の「これが覆るとしたら」:

> - CI に本物の(あるいは安価な)embedding provider を持たせられるようになったとき

**⟹ 本 ADR はこの条件を満たしにいく。**

### ⚠ ただし「鍵が無いから測れない」は、もう真ではない — 前提を訂正する

**【現物】カセット（[ADR 0051](./0051-recorded-provider-cassette.md)）で、鍵なしに
実 API 由来の埋め込みを再生できる。**`examples/chat/cassettes/retrieval.json` には
実 API の埋め込み **152件**（`text-embedding-3-small` / 256次元）がコミットされており、
`MNEMORA_PROVIDER_SOURCE=recorded` で再生できる。ADR 0081 自身がこの経路で測っている。
CI には Postgres も pgvector も在り、`Recorded*` provider が CI 上で動く実績もある
（`provider-source.postgres.test.ts`）。

**⟹ 本 ADR の論拠は「鍵が無いから測れない」ではない。カセットの構造的な限界のほうである:**

1. **入力が固定される。** 鍵は入力の SHA-256 であり、**probe を1件足す・抽出プロンプトを
   1文字変えると鍵が変わり、記録に無い入力は例外**（ADR 0051）。
   ⟹ **ゴールデンセットを育てる道が、カセットでは閉じている。**
2. **モデル版が凍結される**（ADR 0051 の負債。`verify` は手動・CI 外）。
3. **【現物】ゴールデンセットは probe 7件しかない**（`examples/chat/src/probe-set.ts` を数えた。
   gold 7 / distractor 7 / haystack 60）。ADR 0033 §3 自身が
   「🔴 標本は probe 7件である。ここから失敗率も成功率も主張しない」と書いている。
   **Issue #109 が求めているのは「数十件」である。**

⟹ **自前の埋め込みが在れば、ゴールデンセットを何件足しても API 費用も録り直しもゼロになる。**
本 ADR が買うのはそれである。

### 🔴 本 ADR は #109 を塞がない

**#109 の本体は「ゴールデンセットを育て、CI で回し、値を残す」ことであり、それは本 ADR に
含まれない**（`retrieval` の CI ジョブ化とゴールデンセットの拡張は**別の作業**として分けた）。
**本 ADR が作るのはその前提条件だけである。**

## 2. 🔴 【実測・委】どのモデルも「否定・時制・矛盾」を解けない

**これは採否より重い発見なので、決定より先に置く。**

| ペア | ruri-30m | e5-small | bge-m3 |
|---|---|---|---|
| 「私はコーヒーより紅茶が好きです」/「私は紅茶よりコーヒーが好きです」（**意味が逆**） | **0.996** | **0.998** | 0.983 |
| 「納豆が苦手で食べられない」/「納豆が好きで毎朝食べている」（**否定**） | 0.898 | 0.920 | 0.692 |
| 「去年の夏に沖縄へ旅行した」/「来年の夏に沖縄へ旅行する予定だ」（**時制**） | 0.963 | 0.960 | 0.872 |
| 「山田さんは猫を飼っている」/「山田さんは犬が苦手だ」 | 0.896 | 0.931 | — |

いずれも同義ペアの下位と区別がつかない。**同義の最小 − 紛らわしいの最大は、
測った全モデルで負である。**

**⟹ 埋め込み provider を差し替えても、記憶の矛盾検出も否定の扱いも良くならない。**
そこは reranking か LLM 判定の仕事である
（[docs/roadmap.md](../roadmap.md) §1.3 が reranking を Phase 1 外に置いているのは、
この意味では妥当な線引きだった）。

⛔ **「埋め込みを替えたから精度が上がった」と、外に向けて書かないこと。**
**何が上がって何が上がらないかを分けて書く。**この製品の北極星は
「使う側が会話ログを全部プロンプトへ積むのをやめられたか」であり、
**矛盾検出が良くならないことは、採用を検討する人が最初に知るべきことである。**

### 決定2: `EmbeddingProvider` の契約を変えない。prefix は対称にし、**型で非対称を表現できなくする**

**【現物】`embed()` の本番の呼び出し口は repo 全体でちょうど2つである:**

- `packages/core/src/recall-runtime.ts` — **クエリ側**
- `packages/core/src/runtime.ts` — **文書側**（`memory.content`）

`embed(ctx, texts)` はクエリと文書を区別できない。ruri も E5 も retrieval では本来
**非対称な prefix**（`検索クエリ: ` / `検索文書: `、`query: ` / `passage: `）を付ける。

**【実測・委】対称 prefix にしても、有意には悪くならない:**

| モデル | 条件 | MRR | hit@3 | margin（同義の最小 − 無関係の最大） |
|---|---|---|---|---|
| ruri-v3-30m q8 | 非対称（本来の使い方） | 0.938 | 1.000 | −0.013 |
| **ruri-v3-30m q8** | **対称（空文字）** | **0.906** | **1.000** | **+0.033** |
| intfloat/e5-small | 非対称 | 0.891 | 1.000 | −0.018 |
| **intfloat/e5-small** | **対称（両側 `query: `）** | **0.891** | **1.000** | **+0.008** |

対応ありブートストラップ 20,000 回:
- ruri: **ΔMRR −0.031、95%CI [−0.094, +0.031]** ⟹ **有意差なし**（32本中1本が1位→2位）
- **e5-small: ランキングが32本中0本しか変わらず、ΔMRR ちょうど 0.0000、CI [0, 0]**

**⭐ しかも margin は対称のほうが良い。**非対称 prefix はクエリ側と文書側をわずかに
別の部分空間へ押しやるので、**同じ空間に置いた記憶どうしを比べる用途では対称のほうが素直**である。

**⚠ 言えるのは「対称にしても有意に悪くならない」までである。「対称のほうが優れている」ではない。**

⟹ **`prefix` は単一の文字列として全テキストへ適用する。非対称を表現できる型にしない。**
既定は `""`（ruri の対称 prefix）。**契約で守れないものを、型で守る。**

#### 🔴 【現物】その prefix の分岐が、呼び出し側の配列を漏らしていた（rebase 中に見つけて直した）

当初の実装は `this.#prefix === "" ? texts : texts.map(...)` と分岐しており、
**prefix が空のときは、呼び出し側が渡した配列そのものを `createPipeline` の先へ渡していた。**

書き換える pipeline を注入して実際に測った結果:

| 設定 | 下流が `texts[0]` を書き換えたあと、呼び出し側の配列 |
|---|---|
| **既定（prefix が空）** | **`["MUTATED", ...]` ⟹ 壊れる** |
| prefix を設定 | `["紅茶が好き", ...]` ⟹ 壊れない |

**⟹ 振る舞いが設定に依存して変わり、しかも壊れるほうが既定だった。**
分岐を消して経路を1本にした（`"" + text` は元の文字列そのものなので、増えるのは
配列1本の確保だけで、その費用は推論の前では見えない）。

**⚠ これは [#117](https://github.com/takecchi/mnemora/pull/117) の委譲先が見つけた
「`FakeMemoryStore` が同じ参照を配る」という指摘を、自分のコードに当てて見つけたものである。**
指摘そのもの（偽物が参照を配るせいで歯が測定不能になる）は本パッケージには当たらなかった
——記録側の偽物は `[...texts]` と複製しており、断言も文字列リテラルと比べている。
**当たったのは、本体のほうが呼び出し側の配列を下流へ漏らしていたことだった。**
⟹ **2つの設定の両方で測る歯**を置いた（片方だけだと、また分岐が生えたときに気づけない）。

### 決定3: 🔴 `space.model` に prefix 方式を焼き込む — `"ruri-v3-30m/sym"`

**【オーナー】この点は判断として降りてきた。**

将来 reranking を入れて非対称 prefix へ切り替えたくなったとき、`space.model` が
`"ruri-v3-30m"` のままだと、**既存ベクトルと新ベクトルが同じ埋め込み空間に混ざる。**
[ADR 0002](./0002-embedding-space-tables.md) がテーブルを
`(provider, model, dimensions)` から導出しているので、
**`/sym` を含めておけば、方式を変えた瞬間に別テーブルになり、再インデックスが強制される。**

これは **`docs/vision.md` の「『無い』の種類を潰さない」と同じ族の欠陥**を先回りして塞ぐ
1文字である——**混ざったベクトルは、混ざったことを名乗らない。**

⚠ **この理由をコードのコメントにも書いた。**知らない人が「冗長だ」と言って `/sym` を消す。

### 決定4: 遅延ロードは Promise を握る

`EmbeddingProvider` には `init()` / `close()` が無く、`readonly space` は同期で確定する必要が
あるのに、`pipeline()` は非同期である。**【実測・委】現行契約のまま嵌まることを、実際に
クラスを書いて確かめた:**

```
コンストラクタ直後（await なし）: space 確定済み、pipeline() 呼び出し 0 回
8本同時 embed()（ロード込み）  : 557ms、pipeline() 呼び出し 1 回
2回目 embed()                 : 8ms
cold cache の初回 embed()      : 4,507ms（42MB を4ファイル取得）
```

**🔴 ただし Promise を握らない素朴な実装は8重ロードする**（**557ms / 406MB が
3,138ms / 1,009MB になる**ことを実測した）。⟹ **`#ready` に Promise を代入してから
`await` する形にし、そこに歯を置いた**（並行8本でロードが1回であることを数える）。

失敗したら `#ready = null` に戻し、再試行できるようにする。

### 決定5: 宣言した次元と実物の食い違いを、初回 `embed()` で例外にする

`interfaces/embedding-provider.ts` の
**「次元をモデルに応じて動的に変える実装は許容しない」**を、実行時に守らせる歯である。
`space` はコンストラクタで凍結され、実物と違えば初回 `embed()` が落ちる。

⚠ **これは決定3の保険でもある。**別のモデルを指しても次元が同じなら気付けないので、
**次元の一致は「同じ空間である」ことを意味しない。**だから `model` 名のほうに方式を焼く。

### 決定6: `allowBuilds` は `onnxruntime-node: false`（許可ではなく**拒否を明示**する）

**【実測・委】`onnxruntime-node` はプラットフォーム別バイナリの分割をしていない**
（`optionalDependencies` を使わず、1つの tarball に darwin 35MB + linux 355MB + win32 124MB を
同梱する）。さらに `postinstall` が **npm registry ではなく Nuget フィード**から
CUDA EP を追加ダウンロードする（`libonnxruntime_providers_cuda.so` = 315,724,552 B）。

**【実測・委】しかし postinstall をブロックしたままで推論は正常に動いた** ——
CPU バイナリは tarball に同梱済みで、postinstall は CUDA EP を足すだけである。

| やり方 | 時間 | `node_modules` |
|---|---|---|
| `npm install`（postinstall 実行） | 11.9s | **686MB** |
| `npm install --ignore-scripts` | 3.4s | **384MB** |

⟹ **`false` を明示するほうが軽く、かつ安全である。**⛔ `true` にしないこと。

⚠ **書かないと `pnpm add` が `ERR_PNPM_IGNORED_BUILDS` で落ちる。**「黙って無視される」のでは
なく「エラーで止まる」ので、**この設定は無くても静かには壊れない。**

⚠ **北極星の「やらないこと」に「GPU 基盤の構築」がある。**CUDA EP を入れないことは、
費用の話であると同時に、**その線を踏まないことでもある。**

### 決定7: モデルの重みは npm に載せない。実行時に HuggingFace Hub から取る

**【実測・委】42MB を4ファイル**（`model_quantized.onnx` 37,142,404 B /
`tokenizer.json` 6,724,873 B / `tokenizer_config.json` 3,779 B / `config.json` 1,341 B）。
温まった CDN で 5.80 秒、**冷えているときは同じ repo で 10倍以上ぶれる**
（`ruri-v3-310m` の 1,509MB で 722.7 秒＝2.1MB/s を観測した）。

⟹ **これは [ADR 0084](./0084-lexical-recall-channel.md) が `REQUIRED_EXTENSIONS` を
増やさなかったのと同じ種類の負担である。**ただし性質が違う: 拡張は**DBA の権限**を要求するが、
重みは**ネットワークとディスク**を要求する。`cacheDir` を差せるようにしてあるので、
導入者が置き場所を決められる。

## 4. 採らなかった案

### 4.1 `intfloat/multilingual-e5-small`（第2案として最後まで残った）

**【実測・委】日本語品質はほぼ互角**（MRR 0.891 vs 0.906、差は32本中1本分で有意ではない）。
**ライセンスが `mit` と明示され、上流の著者本人が ONNX を配っている。**
⟹ **素性の確かさでは、こちらのほうが上である。**

**却下の理由: 重みが 465MB（13倍）で、q8 が使えない。**
**【実測・委】`dtype: "q8"` は失敗する** ——
```
Could not locate file: ".../intfloat/multilingual-e5-small/resolve/main/onnx/model_quantized.onnx"
```
intfloat の repo は `model_qint8_avx512_vnni.onnx` という別名で持っており、transformers.js の
`dtype` 命名規約に合わない。`model_file_name` で明示すれば動くが、
**ファイル名が AVX512-VNNI 前提を名乗っている**ので、CPU をまたぐ配布物としては説明が要る。

**【オーナー】この二択はオーナーに上げ、供給リスク（個人の変換 repo であること・
月間DL数百規模であること・消えたら新規に入れる人が使えなくなること）を明記したうえで、
第1案が選ばれた。⟹ 供給リスクは承知のうえの選択である。**
⛔ **「供給リスクがあるので第2案にしましょう」と提案し直さないこと。**

### 4.2 `Xenova/multilingual-e5-*`

**🔴 却下。【実測・委】ライセンスを1文字も表明していない** ——
`cardData.license` / README front-matter / repo 内 LICENSE ファイルの**3点すべてに記載が無い**
（`base_model: intfloat/multilingual-e5-small` を宣言しているだけ）。上流の MIT が及ぶと
解釈するのが自然だが、**repo 自身は何も表明していない。**

そして **【実測・委】埋め込みは intfloat 版と全桁一致した。**
⟹ **選ぶ理由が無い。**q8 が要るなら 4.1 の `model_file_name` 指定で足りる。

⚠ **この候補は、本作業を依頼した側が最初に名前を挙げていたものである。**
実測が依頼者の前提を訂正した。

### 4.3 ONNX が存在しない・使えない候補

**【実測・委】HF API で全件確認した。落とした理由を残す**——同じ候補を次の人が
もう一度調べ直さないため。

| 候補 | 落とした理由 |
|---|---|
| **`cl-nagoya/ruri-*` の公式 repo 全部**（v1/v2/v3） | **ONNX ファイル 0件。**プロセス内で動かす公式の道が存在しない。⟹ コミュニティ変換に頼るほかない |
| `onnx-community/ruri-v3-{30m,130m,310m}-ONNX` | **ロード失敗。**`config.json` と `onnx/*.onnx` しか持たず、tokenizer が1つも無い（`TypeError: this.tokenizer is not a function`）。⚠ **HF 公式変換組織の名前に釣られないこと** |
| **`pfnet/plamo-embedding-1b`** | **ONNX 0件。**HF 全文検索でも変換版のヒット 0 |
| `sbintuitions/sarashina-embedding-v1-1b` | 公式 ONNX 0件。第三者 int8 変換は月間DL 5〜7 で素性が薄い |
| `pkshatech/GLuCoSE-base-ja-v2` / `RoSEtta-base-ja` | ONNX 0件、変換版もヒット 0 |
| `jinaai/jina-embeddings-v3` | ONNX は在るが **`cc-by-nc-4.0`（非商用）**。mnemora は MIT（[ADR 0061](./0061-license-mit.md)）なので採れない |
| `google/embeddinggemma-300m` | **gated**（認証が要る）。変換版は開いているが `license: gemma` で Google の使用条件に従属する。**外部の鍵を要求しない**という本 ADR の前提と噛み合わない |

### 4.4 大きいモデル（`ruri-v3-310m` / `e5-large` / `bge-m3`）

**却下。投資対効果が合わない。**
**【実測・委】`bge-m3` は否定の扱いが全モデル中で最良**（納豆ペア 0.692）で、
cos の分布も広く閾値運用しやすい。しかし重み 2.2GB（q8 で 544MB）、
100万件 5.46h（q8 で 1.40h）、peak RSS 1.75GB、次元1024で pgvector のストレージと索引も重くなる。

**⚠ 【文献】JMTEB の平均では ruri-v3-310m が 77.24 で最も高い**（30m は 74.51）が、
**【実測・委】この評価セットの retrieval では 30m のほうが上だった**（0.906 vs 0.875、
ただし有意差ではない）。⟹ **mnemora の用途（短い抽出物）では、大きさが効いていない。**

「否定・矛盾を埋め込みで扱いたい」という要求が実際に立ったときに、`bge-m3` を再検討する。

### 4.5 別プロセス／別コンテナ（TEI / Ollama / llama.cpp server）

**却下。導入者の負担が OpenAI provider より*増える*。**
`OPENAI_API_KEY` を要求しない代わりに **`EMBEDDING_URL` とコンテナランタイムと常駐サーバと
そのヘルスチェック・再起動・版の固定**を要求することになる。mnemora は
「既存の LLM アプリケーションの下に敷く認知レイヤー」なので、**利用者に docker を要求する型を
既定にはできない。**

**⚠ この案は実測していない**（作業器に docker / podman / ollama がいずれも無かった）。
**原理からの評価である。**

### 4.6 「プロセス内と別プロセスの両方を選べる」抽象を、いま作る

**却下。**`EmbeddingProvider` は既に interface なので、**将来 `packages/tei` のような
別 adapter を足せば済む。**`EmbeddingSpaceId` が `(provider, model, dimensions)` で
テーブルを分けるので、両者が同じ space を名乗らない限り安全に共存する。

**⟹ いま抽象を先に作ると、実在しない型2のために型1の実装が歪む。**
これは [ADR 0024](./0024-remove-exact-counts-option.md)（実装の無い `exactCounts` を
「予約」と書き残さずに削除した）と同じ判断である。

### 4.7 モデルの重みを、この repo に複製して持つ

**【オーナー】選択肢として提示したが、採られなかった。**⛔ **やらない。**

### 4.8 非対称 prefix を使えるように `EmbeddingProvider` の契約を変える

**却下。**決定2 のとおり、対称で有意に悪くならないことを測った。
契約を変えれば `recall-runtime.ts` と `runtime.ts` の両方を触ることになり、
**公開 API の破壊的変更**でもある（`docs/autonomy.md` §3 では ⛔ ＝提起までにする項目）。

**永久に採らない、ではない。**reranking を入れるときに再検討する（→「覆るとしたら」）。

### 4.9 migration を書く

**【現物】不要だった。**当初「モデルの次元が既存の pgvector 列と違えば migration が要る」と
想定していたが、**この repo にはベクトル列を持つ migration が1本も無い。**
`packages/postgres/migrations/0001_init.sql` は `CREATE EXTENSION IF NOT EXISTS vector` と
`memories.embedding_status` を作るだけで、**ベクトル列は `registerEmbeddingSpace()` が
実行時に `vector(${space.dimensions})` として作る**（`packages/postgres/src/vector-space.ts`）。

⟹ **どの次元を選んでも migration は要らず、既存の埋め込みを作り直す必要も無い。**
[ADR 0002](./0002-embedding-space-tables.md) が「次元ごとの列」を退けて
「空間ごとのテーブル」を選んだことの、直接の配当である。

## 6. 引き受けた負債

1. **🔴 供給リスク。**`sirasagi62/ruri-v3-30m-ONNX` は**個人の変換 repo** であり、
   月間DL数百規模である。**消える可能性を否定できない。**
   **【オーナー】これは危険を明記したうえで選ばれた選択である。**
   ⟹ **この判断が成立している条件は「元のモデルは公式（`cl-nagoya/ruri-v3-30m`, apache-2.0）で、
   変換は自分たちでもやり直せる」ことである。**
   🔴 **その「やり直せる」を手順として
   [packages/local-embedding/README.md](../../packages/local-embedding/README.md) に残した。**
   ⚠ **これは歯にできない種類の負債である**（外部の供給の話であり、CI で検査できない）。
2. **`node_modules` が約 383MB 増える。**
   **【実測・委】`onnxruntime-node` がプラットフォーム分割をしていない**ため、
   Linux 機にも darwin / win32 のバイナリが降ってくる。**減らせない。**
3. **重みは実行時に HF Hub から落ちる。**初回 `embed()` が 0.5〜4.5 秒かかる
   （`warmup()` を用意した）。
   ⚠ **完全なオフライン経路は在るが、`repo` オプションだけでは届かない。**
   **【現物】`repo` に絶対パスは渡せない**——transformers.js はモデル id を
   `env.localModelPath` からの**相対**で解決するため、`env`（プロセス全体で共有される大域）を
   触る必要があり、それは `createPipeline` を差す仕事になる。
   **この形が実際に動くこと、およびその経路でも次元の歯が発火することは、書き手が自分の手で
   確かめた**（2026-09-10T00:37Z。手順は README に置いた）。
   ⟹ **オフライン導入は「できない」のではなく「注入点を使う」である。**
   ⛔ このパッケージが `env` を勝手に書き換えることはしない（大域を黙って触らない）。
4. **🔴 `EmbeddingProvider` の適合テストは、今も存在しない。**
   `packages/testkit` の適合テストは Store 系5種だけで、provider 向けは1本も無い
   （[ADR 0072](./0072-anthropic-llm-provider.md) の負債1）。
   **本 ADR で `EmbeddingProvider` の実装が2つ**（`@mnemora/openai` と
   `@mnemora/local-embedding`）**になり、`packages/testkit` の
   `Deterministic*` / `Recorded*` を数えれば実質4つある**が、
   **それらが同じ契約を満たすことを検査する歯はどこにも無い。**
   ADR 0072 の「覆るとしたら」に該当する。
   ⟹ **引き上げは本 PR に混ぜない。住所を付けた: [#116](https://github.com/takecchi/mnemora/issues/116)。**
   ⚠ **「あとでやる」とだけ書かない**——番号の無いものは実行されない。
5. **CI 配線とゴールデンセットの拡張は、本 ADR に含まれない。**
   `retrieval` を CI ジョブに載せることと、probe を 7件から数十件へ育てること
   （**#109 の本体**）は別の作業として分けた。
   ⟹ **本 ADR の時点では、この provider は CI で「skipped」と表示されるだけである。**
6. **評価の標本が小さい。**同義32組・クエリ32本で、95%CI は ±0.06〜0.09。
   **モデル間の差は、対照群（英語モデル）以外は有意ではない。**
   言えているのは「対称にしても有意に悪くならない」「英語モデルは日本語で壊れる」
   「どのモデルも否定・時制を解けない」の3点である。
7. **【実測・委】は書き手が自分の手で再実行していない。**
   §1〜§4 の数字はすべて委譲先の作業者が測ったものであり、
   **この ADR の書き手は受け取っている。**再現に必要な条件は「測った条件」節に書いた。
