# ADR 0098: `recall()` の出力を zod で検証する — 既定では投げず、検証結果を呼び手に返す

- **状態**: 採用 (2026-09)

**⚠ 各主張の出所を分ける**（[ADR 0097](./0097-recall-usage-share-may-exceed-1.md) /
[ADR 0094](./0094-identifier-probes-local-embedding.md) の体裁を踏む）。

- **【実測】** — この ADR の書き手が、この器で自分の手で走らせた。
- **【現物】** — この repo のコード・文書を読んで確かめた。
- **【受】** — 委譲元（マネージャー）から報告として受け取り、自分では再導出していない。

## 文脈

**【現物】`recall()` の戻り値は、実行時に一度も自分自身のスキーマで検証されていなかった。**
`packages/core/src/recall-runtime.ts` が `.parse()` を呼ぶのは入力側の
`RecallQuerySchema`（`runRecall()` 冒頭の1箇所）だけである。出力側の
`RecallResultSchema` / `RecallUsageSchema` を parse している箇所は
`packages/core/src/__tests__/recall.test.ts` の外に**0件**であり、
そこでも `.parse()` ではなく `safeParse` である
（[Issue #131](https://github.com/takecchi/mnemora/issues/131)）。

⟹ **型（TypeScript）はコンパイル時にしか効かないので、実行時に不変条件が破れても
何も起きない（fail-open）。** 呼び出し側が自分で `RecallResultSchema.parse(result)` を
書かない限り、契約を破った値は静かに外へ出る。

**【実測】これは机上の穴ではない。** 呼び出し側が差せる拡張点だけで踏める:
`RuntimeDeps.tokenCounter` に**非整数のトークン数を返す実装**を渡すと、
`usage.estimatedTokens` は `z.number().int()` に違反した値のまま返る
（`TokenCounter.count()` の戻り値が整数であることを実行時に強制する仕組みは無い）。

**【現物】この穴は [ADR 0097](./0097-recall-usage-share-may-exceed-1.md) の
「引き受けた負債」2番目として明文で残されていた**（逐語）:

> **`recall()` の出力は依然として zod で検証されていない（fail-open）。**（…）
> **根本（出力を検証する経路が無いこと）は直していない**

**【現物】ADR 0097 は同時に、この穴を塞ぐときの危険も名指ししている**——
出力検証を足すと `recall()` が**例外を投げるようになる**、すなわち**倒れ方が変わる**。
Issue #131 のコメント（オーナー、2026-09-10）も逐語で
「実装はこの Issue の範囲に含めない——例外を投げる形にすると recall() の倒れ方が変わるため、
別 PR とする」と述べている。⟹ **この ADR が決めるのは「検証するかどうか」ではなく
「どう倒れるか」である。**

### ⚠ `share > 1` は、この検証が弾く対象では**ない**

**【現物】ADR 0097 が `RecallUsageSchema.share` から `.max(1)` を意図的に外した。**
`share` が 1 を超えるのは契約違反ではなく、**実在する正しい値**である
（強制側＝段4の `fits`/`unitTokens` と、計測側＝連結して1回 `count()` する分子とで
数え方が違うため）。

**【実測】この ADR の書き手は、その値を自分の手で見た**——`packages/core` で
`vitest run -t "非CJK20字×2件"`（`EXIT=0`）を走らせ、既存の歯
`✓ 非CJK20字×2件・maxMemoryTokens:10 ⟹ 強制側は両方残すが、連結して測り直すと超えている（share>1 かつ budgetExceeded=true）`
が緑であることを確認した。**⟹ `share > 1` は「超えうる」ではなく「超えている」。**

⟹ **🔴 出力検証を足したことで、ADR 0097 が記録した欠陥が*隠れる*のがいちばん悪い結末である。**
この ADR は次の2つを**両方**禁じる:

1. **値を丸めない・捨てない。** `Math.min(share, 1)` のような正規化はしない。
2. **合法な値を「不正」と誤診断しない。** `share: 1.1` は `ok: true` として通す。

## 決定

1. **`runRecall()` の末尾で、戻り値を `RecallResultSchema.safeParse` に通す。**
   ⛔ `.parse()` は使わない（投げるかどうかはモードが決める）。
   検証は**読むだけ**であり、`draft` の値は一切書き換えない。

2. **倒れ方は「呼び手が受け取る」。既定では投げない。**
   `RecallRuntimeDeps.outputValidation` / `RuntimeDeps.outputValidation` に
   `"off" | "report" | "throw"` を取り、**既定は `"report"`**
   （`DEFAULT_RECALL_OUTPUT_VALIDATION`）。

   | モード | 何が起きるか | 誰が受け取るか |
   | --- | --- | --- |
   | `"off"` | 検証しない | 誰も。欄そのものが無い |
   | `"report"`（既定） | 検証し、結果を戻り値に載せる。**投げない** | **呼び手**（`result.outputValidation` を読んで、捨てるか止まるかを選べる） |
   | `"throw"` | 検証し、落ちていたら `RecallOutputValidationError` | **呼び手**（例外として。`issues` と `recallId` を載せてある） |

   **既定を `"throw"` にしない理由**: `recall()` は使う側の主経路であり、既定で投げる形に
   すると「いままで（誤った値のまま）動いていた呼び出しが、ある日から例外になる」
   ——これは**公開 API の破壊的変更**である。`docs/autonomy.md` §3 は破壊的変更を
   **オーナーだけが行う**ものとして「やらずに提起する」と定めている。
   ⟹ **投げる形は用意するが、選ぶのは呼び手（およびオーナー）である。**

3. **「無い」の3種類を潰さない**（[ADR 0008](./0008-absence-taxonomy.md) の適用）。
   `RecallResult.outputValidation` は:
   - **欄そのものが無い（`undefined`）** ＝ **検証していない**（`"off"`）
   - `{ ok: true, issues: [] }` ＝ 検証して**通った**
   - `{ ok: false, issues: [...] }` ＝ 検証して**落ちた**（`issues` はこのときだけ非空）

   ⛔ **「検証に失敗した」と「そもそも検証していない」を同じ顔にしない。**

4. **`RecallOutputValidationError` は `issues` と `recallId` を載せる。**
   検証は段6（`MemoryStore.createRecall`）の**後**に走る——`"throw"` モードでは
   「`recalls` の行は書かれたのに、呼び手は例外を受け取る」状態になる。
   **その不一致を呼び手が調べられるように、id を例外へ載せてある。**

5. **公開 API への追加は additive のみ。** `RecallResult.outputValidation` は optional で、
   既存欄の意味も値も変えない。`RecallResultSchema` にも optional として足したので、
   **返ってきた結果をそのまま `RecallResultSchema` に通しても通る**（自己参照で落ちない）。

6. **`recall-runtime.ts` に残っていた、ADR 0097 が否定済みの主張を1箇所書き換えた。**
   `share` の分子を計算する直前のコメントが、逐語で
   「段4の切り詰めが memories tier を予算内に収めることを保証しているので、
   分子を memories tier に限れば share は 1 を超えない」と述べていた。
   **これは ADR 0097 が「この理由づけは偽である」と明文で否定した主張そのものであり、
   ADR 0097 が拾い残していた。**出力検証を足すコードのすぐ隣に「1 を超えない」と
   書いてあると、次に読む人が「では検証が弾くのだろう」と誤読する。
   ⟹ **ADR 0097 の結論に揃えた**（超えうる／超えたら `budgetExceeded` が `true`／
   強制側と計測側で数え方が違う）。**これは「ついでの修正」ではなく、この PR が足す
   検証の意味を正しく読ませるために必要な訂正である。**

## 採らなかった案

- **(却下) 既定で `RecallResultSchema.parse()` を呼び、落ちたら投げる。** 静かな失敗を
  うるさい失敗に変える方向自体は正しいが、**既定でそれをやるのは公開 API の破壊的変更**
  であり、`docs/autonomy.md` §3 がオーナーの判断としている領域に入る。
  ⟹ **投げる形は `"throw"` として用意し、既定にはしない。**
- **(却下) ログに出すだけ（`console.warn` / logger を注入）。** **呼び手が回復できない。**
  `packages/core` は実行時依存を zod だけに絞っている（`AGENTS.md`）ので logger を
  足すこと自体が別の判断になるうえ、ログは機械的に読めない——「積むのをやめられたか」を
  測る側が `share` を読むときに、その値が検証を通ったのかどうかを**プログラムから知れない**。
- **⛔ (却下) 検証に落ちた値を丸める・捨てる（`Math.min(share, 1)` など）。**
  **壊れていることを見えなくするだけである。** ADR 0097 が記録した欠陥
  （強制側と計測側で数え方が違う）が、検証を足したことで**消えて見える**——
  後から「なぜ数字が合わないのか」を追えなくなる。**これがいちばん悪い結末である。**
- **(却下) 開発時のみ有効にする（`NODE_ENV !== "production"` で分岐）。**
  **「本番だけ検証されない」を作る。** fail-open が実害を出すのは本番であり、
  検証が最も要る場所で消える。加えて `packages/core` はライブラリであり、
  使う側の `NODE_ENV` を実装が勝手に読むべきではない。
- **(却下) 段6（`createRecall`）より前に検証する。** `recallId` は `createRecall` の
  戻り値なので、検証対象の `RecallResult` はその後にしか組み立てられない。
  `recallId` だけを除いて先に検証する形も考えたが、**検証するスキーマが戻り値の型と
  一致しなくなる**（`RecallResultSchema` そのものを使えない）——「何を検証したのか」が
  読めなくなる代償のほうが大きい。⟹ 段6 の後に置き、**記録が書かれたことは
  `RecallOutputValidationError.recallId` で追えるようにした**（下記「引き受けた負債」1）。
- **(却下) 検証を `recall()` に入れず、`validateRecallOutput()` を export するだけにして
  呼び出し側に任せる。** それは**いまの状態（呼び出し側が自分で書かない限り検証されない）と
  同じ**であり、Issue #131 が「無い」と言っているものを1ミリも足さない。

## 引き受けた負債

1. **検証は段6（記録）の後に走る。** `"throw"` モードでは **`recalls` の行は書かれたのに
   呼び手は例外を受け取る。** `recallId` を例外に載せて相関は取れるようにしたが、
   **「記録は在るが呼び手には届かなかった recall」という状態そのものは残る。**
   これを消すには段6 の位置か `recallId` の生成方法を変える必要があり、別の判断である。
2. **`"report"`（既定）は、呼び手が `outputValidation` を*見る*ことを強制しない。**
   見なければ、いままでと同じく静かに通る。**この ADR が買ったのは「見れば分かる」
   であって「必ず気づく」ではない。**「必ず気づく」を買うには `"throw"` を既定にする
   しかなく、それは上記のとおりオーナーの判断である。
3. **検証しているのは `recall()` の出力だけである。** `observe()` / `tick()` /
   `reflect()` / `forget()` の戻り値は依然として検証されていない。同種の穴が在るかは
   **確かめていない**（Issue #131 の範囲外）。
4. **`RecallResult` を JSON 直列化した姿は変わった**（欄が1つ増えた）。既存欄の意味も値も
   変えていないが、**戻り値全体をリテラルと突き合わせている利用側が在れば、そこは動く。**
   この repo 内では `recall-channels.test.ts` の歯1本が該当し、固定し直した。
5. **`safeParse` の費用はスキーマ単体でしか測っていない**（約18µs/call）。
   `recall()` 全体の前後比較や、`memories` が数百件になったときの振る舞いは
   **測っていない**。逃げ道として `"off"` を用意してある。
6. **`RecallResultSchema` が現物の契約を正しく写しているかどうかは、この ADR の範囲外である。**
   検証は「スキーマに書いてあること」しか見ない——スキーマが緩ければ、緩いまま通る。
   （例: `share > 1` は ADR 0097 の判断により*意図的に*緩い。）

## これが覆るとしたら

- **オーナーが `"throw"` を既定にすると決めたとき。** そのときこの ADR の決定2は
  「破壊的変更をオーナーが承認した」形に置き換わる。実装は `DEFAULT_RECALL_OUTPUT_VALIDATION`
  の1行で切り替わる（そのために定数にしてある）。
- **強制側と計測側の数え方が統一されたとき**（ADR 0097「これが覆るとしたら」の1番目）。
  `share` が構造的に 1 以下になるなら `.max(1)` を戻す設計変更がありえて、そのとき
  **T3 は意味を反転させる必要がある**——⛔ 黙って消さず、なぜ反転させたかを残すこと。
- **`observe()` / `tick()` の出力にも同じ穴が見つかったとき。** そのときは
  「recall だけ検証する」非対称が負債になり、共通の口へ切り出す判断が要る。
