# 設計: 許可を、クローンと人間のやり取りで動的に増やす

**状態: 提案（未承認）。実装は入っていない。**
差し替え対象: PR #182（`packages/core/src/tools.ts` の `CLONE_ALLOWED_TOOLS` へ `Bash(gh pr merge:*)` を直書きする案。人間が破棄）。

> 人間の言葉（#182 のコメント、2026-08-22T10:16:21Z、逐語）:
> 「人間の判断で破棄。許可設定はコードにハードコードするのではなく、クローンと人間のやり取りで動的に増える（DB に格納される）仕組みにする。差し替えの設計を別途起こす。」

この文書はその「別途起こす設計」である。

---

## 0. 結論（先に）

1. **`canUseTool` は繋がない。** 繋いでも効かない — 既定の `permissionMode: 'auto'` では SDK は `canUseTool` を呼ばない（§1.1）。この一点で、いちばん素直に見える設計（確認をその場で人間へ回す）は最初から成立しない。
2. **増やす先は SDK の許可規則そのもの**で、正本は DB に置く。生きているセッションへは `Query.applyFlagSettings({ permissions: { allow: [...] } })` で流し込む（§3.1）。セッションを開き直さずに効き、**外した規則も同じ経路で実際に効く**。
3. **台帳は `allow` しか持たない。`deny` も `ask` も持たせない。** これが正典の地雷（`permissions.yaml` 的なものを作る）を踏まないための不変条件であり、設計上いちばん大事な一線である（§2）。
4. 起点はクローンの提案、承認は人間、書くのはデーモン。**クローンは自分の手ではこの台帳へ書けない**（§3.4）。
5. 既定は締めない。この台帳は**開ける方向にしか動かない**（§5.3）。

## 1. 前提の訂正

依頼の中で示された見立てのうち、**2つは現物と食い違っていた**。設計の中心に効くので先に置く。

### 1.1 訂正: `auto` では `canUseTool` は呼ばれない。だから「繋ぐ」は効かない

依頼にはこうあった:

> 私の理解では、繋いでいないので `ask` になった時点で答える相手が居ず、そのまま拒否で終わります。

**これは `permissionMode: 'default'` の説明としては正しい。** `packages/core/src/claude-provider.ts:93-95` が逐語でそう書いている:

> `default` のまま道具を渡すと「渡したのに使えない」になる — このセッションには `canUseTool` が無く、SDK は確認相手が居ないとき `ask` の判断をそのまま拒否で終わらせる。

**しかし実際に走っている既定は `auto` であり、そこでは仕組みが違う。** `packages/core/src/runner.ts:1410-1416`（逐語）:

> 確認へ上げずにその場で止められた1件（分類器・deny 規則）。
> **`permissionMode: 'auto'` ではここが唯一の生の合図である。** `canUseTool` は呼ばれないので、この合図を捨てるとマネージャーや作業者の手が止まったことは誰にも見えない。SDK 曰くこれは best-effort（取りこぼしうる）で、authoritative なのは `result.permission_denials` — だから**両方**読む。

SDK の型注釈も一致する（`sdk.d.ts:2194`）:

> `'auto'` - Use a model classifier to approve/deny permission prompts.

そしてこれは机上ではなく実測で踏まれている。**PR #50「fix: 分類器に止められた実行がクローンに届かない」**（`009983a`, 2026-08-15）が、まさに「`auto` では SDK が自前で拒否した実行が `canUseTool` を経由しない」ことへの対処として `permission_denied` の取り回しを入れている。

**帰結:** 結果（人間不在のまま黙って落ちる）は依頼の見立てどおりだが、**原因が違うので処方が変わる**。止めているのは「答える相手が居ないこと」ではなく**モデルの分類器**である。`canUseTool` を繋いでも分類器は迂回されないので、依頼にあった案（拒否で終わらせず人間へ確認を出す）は、**この経路では発火しない**。`default` へ落とせば発火するが、それは全ての `Read` や `grep` まで確認へ回す形（PR #35 が実際に人間から2度苦情を受けて直した形）に戻ることを意味する。

### 1.2 訂正: クローンは自分が止められたことを既に見えている

「いま『確認が要る操作』は、クローンにとって*黙って落ちる*ことになります」— **クローンから見れば黙ってはいない。** `packages/core/src/clone.ts:2589` の `#noteDenial` が、生の合図（`system/permission_denied`）と `result.permission_denials` の**両方**を読み、日誌へこう書いている:

> `${tool}` の実行が、確認へ上がらずに止められた（理由）。許可モードは `${permissionMode}` で、**この層に確認を回す相手は居ない**（合図の出所: `${via}`）。

黙って落ちているのは**人間から見たとき**である。日誌を掘らなければ見えず、見えたところで**増やす口がどこにも無い**。これが穴の正確な形であり、既にある `#noteDenial` が提案の起点としてそのまま使える（§3.2）。

### 1.3 訂正: 保存先について、PRD は「記憶」と書いている

依頼では「記憶（`memory`）ではないはずです」とあったが、`docs/PRD.md`「要件: 権限境界」は逐語でこう書いている:

> **判断は記憶に残り、次の判断の材料になる** — 人間が一度「それはやっていい」「それはやらないで」と言えば、同種の判断は以後そうなる。**承認は設定ではなく記憶として持続する**

つまり正典は「承認は記憶へ」と明言している。**そして実装もそうなっている** — 人間が承認に答えたときクローンへ流し込まれる内部プロンプトには「今後同じ判断を自分でできるよう、必要なら記憶へ残すこと」という一文が入っている（`clone.ts:1768-1785`）。

**だが射程は §2 の2層のうち上の層（クローンの判断）までである。** 下の層（SDK の許可エンジン）はこの文の外にあり、**そこには学習の経路が1本も無い**。依頼者の「記憶ではないはず」という直感は結論として正しく、理由は「記憶は判断の根拠を置く場所だから」よりも強い — **上の層は既に学習しており、足りないのは下の層だけだから**である。詳細は §5.1。

## 2. 正典との衝突と、その解き方 — ここが設計の中心

この依頼には、**素直に作ると正典を踏む**構造がある。先に開示する。

`AGENTS.md` の地雷表（逐語）:

| やりがちなこと | なぜ違反か | 代わりに |
|---|---|---|
| 確認が要る行為の一覧（`permissions.yaml` 的なもの）を作る | 権限境界はクローンの判断であって設定ではない | 記憶に根拠があるかで判断させ、判断を日誌に残す |

`docs/north_star.md`「立ち戻るための問い」（逐語）:

> - [ ] 「どこまで人間に確認するか」を設定項目や行為の一覧で表そうとしていないか？　その違いこそクローンが記憶として持っているものである

**「許可設定を DB に一覧として溜める」は、字面ではこの地雷そのものに見える。** ここを曖昧にしたまま実装すると、人間が「ハードコードをやめろ」と言った結果として、正典が名指しで禁じた設定ファイルを DB に作ることになる。

### 2.1 2つの層は別物である

| | 上の層: **権限境界** | 下の層: **実行環境の境界** |
|---|---|---|
| 問い | 「これは人間に確認すべきか」 | 「この実行を器がそもそも通すか」 |
| 決める主体 | クローン（記憶＝価値観から判断） | SDK の許可エンジン（分類器＋規則） |
| 正典 | PRD「権限境界」— **一覧を作るな。記憶として持続させろ** | north_star 禁止2 —「制限は実行環境の境界で表す。**方針は設定で開けられなければならない**」 |
| いまの状態 | 動いている。触らない | クローンの判断を**無視して**先に止める |

**#182 が触ろうとしたのは下の層である。** そして下の層は、いま**上の層を上書きしている** — クローンが記憶に根拠を見つけて「これはやってよい」と判断しても、分類器がその手前で落とす。人間の価値観のコピーが下した判断が、価値観を1つも知らないモデルに覆されている。**これは禁止1（デグレード禁止）に当たる。** 人間が自分の PC で Claude Code を開けば、`gh pr merge` は一度「常に許可」を押せば以後通る。クローンにはその「一度押す」に当たる操作が存在しない。

### 2.2 正典はこの機構を明示的に授権している

north_star 禁止2、逐語:

> 制限が必要なら、能力（ツール一覧）を削るのではなく、**方針**（何をさせないかの宣言）と**実行環境の境界**（サンドボックス・ネットワーク・認証情報の配布範囲）で表す。**方針は設定で開けられなければならない**

最後の一文がこの設計の根拠である。**「開けられなければならない」に対して、いまは開ける口が無い。** #182 は「コードを書き換えてマージする」という形でしか開けられないことを露呈させた。この設計はその口を作る。

### 2.3 だから台帳は allow しか持たない — 不変条件

地雷が禁じているのは「**確認が要る**行為の一覧」＝ *ask / deny* の側である。判断を設定へ移す形。

この台帳が持つのは「**人間が既に許した**行為」＝ *allow* だけで、**判断を設定へ移さない**。クローンは相変わらず記憶から判断する。この台帳が変えるのは「クローンが判断した結果を、器が実行させてくれるかどうか」だけである。

> **不変条件（実装で必ず守る）: この台帳に `deny` と `ask` を持たせない。**
> スキーマに列を作らない。API に口を作らない。「便利だから」で後から足さない。
> 足した瞬間に、これは正典が名指しで禁じた `permissions.yaml` になる。
>
> 何かを止めたくなったら、止める場所はここではない — **方針（記憶・システムプロンプト）と実行環境の境界（配る認証情報の範囲・サンドボックス）**である。

この不変条件は、§5.3（既定を締めるか）の答えにもそのままなる。

## 3. 機構

### 3.1 効かせ方: `applyFlagSettings`（生きたセッションへ、開き直さずに）

クローンは**長寿命の単一セッション**である（`clone.ts:2308` `#ensureQuery` は `if (this.#query) return;`）。`Options` はセッションを開くとき1回しか組まれないので、`allowedTools` を DB から読むだけでは**次にセッションが開くまで効かない**。

SDK にはそのための口がある。`Query.applyFlagSettings`（`sdk.d.ts:2459-2483`、逐語）:

> Merge the provided settings into the flag settings layer, **dynamically updating the active configuration.** Equivalent to the inline `settings` option of `query()`, but **applies mid-session**. Flag settings sit above user/project/local settings and below managed policy settings in the precedence order.
>
> Successive calls shallow-merge top-level keys — **a second call with `{permissions: {...}}` replaces the entire `permissions` object from a prior call.** Pass `null` for a key to clear it from the flag layer...
>
> Only available in streaming input mode.

そして `Settings.permissions.allow?: string[]` が存在する（`sdk.d.ts:5331` の `Settings` インターフェース内）。

この3点がそのまま要求性質に対応する:

- **「動的に増える」** — mid-session に効く。セッションを開き直さない
- **「消せること。そして消したら実際に効くこと」（要求3）** — 後続の呼び出しが `permissions` を**丸ごと置き換える**ので、**常に現在の全量を送る**運用にすれば、外した規則はその場で消える。差分を送る形にしないこと
- **使える** — クローンは `#inputStream()` の AsyncGenerator を渡しており streaming input mode である

**投影は2箇所（両方要る）:**

1. 生きているセッションへ: 台帳が変わるたびに `query.applyFlagSettings({ permissions: { allow: <全量> } })`
2. 次にセッションを開くとき: `buildCloneSessionOptions` へ渡す `allowedTools` に台帳の全量を足す（`#buildOptions` は既に `async` で、`#stores.persona.documents()` を引いている。DB を読む場所として自然）

2 が要るのは、器が落ちて上がり直したときに 1 の効果が消えるからである。**DB が正本、セッションへの投影は2通り**、という形にする。

### 3.2 提案（クローン → 人間）

起点は**既にある** `clone.ts:2589` の `#noteDenial` である。いまは日誌へ1行書いて終わっているので、そこへ「人間へ上げる」を足す。

- 止められた1件から、**規則の候補**を作る（`Bash` なら `tool_name` + `tool_input.command` から `Bash(gh pr merge:*)` のような形）
- **クローンが自分の言葉で人間へ頼む。** 既にある `ask_human` の器（受信箱／`PendingApproval`）に載せる。**新しい確認の経路を作らない** — PRD「人間不在で止まらない」の器がそのまま使える
- **同期的に待たない。** ここが `canUseTool` を繋がない理由（`claude-provider.ts:96-102` の逐語「クローンは長寿命セッション1本で、受信箱のすべてのターンがそこを直列に通る。ここで人間の回答を待って止めれば、止まるのは待っている1件ではなく全部である」）と正面から整合する。**この設計はその制約を壊さない** — 提案を積んで、クローンはそのターンを続ける
- **候補は候補でしかない。** クローンが提案した文字列をそのまま採用しない（§3.4）

### 3.3 承認（人間）— 既にある経路にそのまま載る

**新しい確認の仕組みを作らない。** `ask_human` の経路が端から端まで既にあり、そのまま使える（現物で追跡済み）:

```
ask_human ツール
  → stores.jobs.putApproval(PendingApproval)     一覧・保留として保存
  → stores.journal.append({type:'escalation'})   監査
  → context.emit({type:'ask_human', ...})        SSE で CLI / Web へ即時通知

人間が答える（CLI / HTTP / Web のどこからでも）
  → POST /approvals/:id/answer  または  POST /approvals/answer（まとめて）
  → clone.answerApproval(id, answer)             （clone.ts:855-877）
      → putApproval(...answeredAt, answer)       行は消さず追記で更新
      → journal.append({type:'escalation', answeredAt, answer})
      → post({type:'human_answer', ...})         受信箱へ
  → クローンの内部ターンとして回答が流し込まれる（clone.ts:1768-1785）
```

**この設計が足すのは、この経路の終点に「台帳へ1行書く」を1つ増やすことだけである。** 保留の器も、3入口からの回答も、監査も、既にある。

**広さを見せる（要求5）。** `Bash(gh pr merge:*)` と `Bash(gh *)` と `Bash(*)` は別物である。**狭めない。ただし広さは必ず見える形にする:**

- 規則を**広さの段階**（例: 特定コマンド / コマンド族 / ツール全体）に分類し、一覧と承認の両方に出す
- **クローンが要求した規則と、人間が承認する規則が違ってよい。** 人間は `Bash(gh *)` を求められて `Bash(gh pr merge:*)` を承認できる。**承認は編集を伴う操作である**（`PendingApproval.answer` は自由文字列なので、器としてはこれを載せられる）
- 一番広い段階（`Bash(*)` のようにツール全体を丸ごと開ける形）は、承認時に広さを明示的に確認する。**禁じるのではなく、気づかずに通らないようにする**

### 3.4 書き手はデーモン（要求1: クローンが自分だけで増やせないこと）

- クローンの MCP 道具に、**台帳へ書く口を作らない**。作れるのは「提案する」ところまで
- 台帳へ書くのは、**人間の承認が入った経路のデーモン側のハンドラだけ**。`memory` が `PUT`/`DELETE /memory/:slug` の2箇所でだけ `cause: 'human'` を名乗るのと同じ形（`tools.ts:97-99` にその作法がある）
- クローンは台帳を**読める**（自分に何が許されているかを知らないと判断できない）。読みと書きを分ける

**攻撃面の確認:** クローンは `Bash` で `gh` を叩ける（許可されれば）。デーモンの HTTP API を `curl` で叩いて自分に許可を書き込む、という迂回が成立しないこと。承認を入れる口には人間の資格が要る形にし、**クローンが持つ資格情報でそこへ到達できないこと**を実装時に確かめる（§6-E5）。

### 3.5 記録（要求2）

**いつ・何を・誰の承認で・どの提案から**を残す。要求2の「記録に残らない許可は、許可として成立していません」をそのまま満たす。

- 提案 / 承認 / 却下 / 削除の4つとも日誌へ（追記専用。`journal` は既にそういう器である）
- 台帳の行そのものにも由来を持たせる（作成時刻・承認者・元になった拒否の `tool_use_id`）
- **削除しても記録は消えない。** 台帳から行が消えても、日誌には「いつ誰が消したか」が残る

## 4. 「必ず要る」5つの性質への対応

| # | 性質 | どこで満たすか |
|---|---|---|
| 1 | クローンが自分だけで増やせない | §3.4。クローンの道具は「提案」まで。書き口はデーモン側の人間経路のみ |
| 2 | 増えたことが必ず記録に残る | §3.5。提案／承認／却下／削除の4つを日誌へ。行にも由来を持たせる |
| 3 | 消せる。消したら実際に効く | §3.1。`applyFlagSettings` が `permissions` を丸ごと置換するので、**全量送信**にすれば削除がその場で効く |
| 4 | 人間が一覧を見られる。CLI / HTTP / Web が等価 | §4.1。`commitments` の5点セットをそのまま写す |
| 5 | 広い許可が広いと分かる | §3.3。段階分類を一覧と承認の両方に出す。狭めない |

### 4.1 3入口の等価性 — 触る場所は5つ（`commitments` の実例から特定済み）

PRD「入口の等価性」（逐語）:

> **入口の等価性** — ある入口でできることが別の入口でできない状態を作らない。
> - **Web UI は API の特権的な消費者ではない。** 画面のためだけの経路をデーモンへ足さない

CLI は `hono/client`、Web は `@alteroid/api-client`（`openapi.json` から生成）で、**どちらも同じ `apps/daemon/src/app.ts` のルートを叩く**。だから HTTP に1本足せば3入口すべてに届く。写経元 `commitments` から、触る場所は次の5つ:

| # | 場所 | 何を足すか |
|---|---|---|
| a | `packages/core/src/schema.ts` / `store.ts` | 型（zod）と新ストアのインターフェース |
| b | `packages/storage-pg/src/{migrate,schema}.ts` / `storage-fs/src/` | DDL は `STATEMENTS` 配列の**末尾**へ。fs 版も同時に |
| c | `apps/daemon/src/{app,openapi}.ts` | GET 一覧 / POST 承認 / DELETE 取り消し ＋ zod スキーマ |
| d | `apps/cli/src/chat.ts` | スラッシュコマンド |
| e | `apps/web/app/hooks/{queries,mutations}.ts` ＋ `app/routes/` | 画面 |

そしてクローン自身も台帳を**読める**必要がある（自分に何が許されているか知らないと判断できない）ので、`packages/core/src/tools.ts` に**読み取り専用**の道具を1つ。**書き口は作らない**（§3.4）。

**注意（既知の穴を踏襲しないこと）:** `apps/daemon/src/app.ts` には「宣言済みの zod スキーマで応答を `.parse()` していないルート」が多数あり、通しているのは `/managers` と `/managers/:id` の2本だけだとコード中に明記されている。新しいルートは**通す側**で書く。

## 5. 決めきれていなかった3点への答え

### 5.1 保存先 — 記憶でも profile でもなく、第三の置き場

**答え: 第三の置き場（`commitments` と同型の一覧ストア）を新設する。** 依頼者の見立て（記憶ではない／profile は一覧になっていない）は**両方とも現物で裏が取れた**。ただし理由は依頼者が挙げたものより強い。

**記憶ではない理由。** PRD が「承認は設定ではなく記憶として持続する」と書いているのは §2.1 の**上の層**についてである。そして**上の層は既に学習している** — 人間が承認に答えると、クローンへ流し込まれる内部プロンプトにこの一文が入っている（`clone.ts:1768-1785`、逐語）:

> 今後同じ判断を自分でできるよう、必要なら記憶へ残すこと。

**つまり「人間の承認から学ぶ」機構は、上の層には既にある。無いのは下の層だけである。** ここへ SDK の規則文字列（`Bash(gh pr merge:*)`）を混ぜると2つの層が1つに潰れ、「記憶を編集すると器の許可が変わる」ことになる。記憶は判断の根拠を置く場所であって、器の設定値を置く場所ではない。`storage-fs/src/profile.ts` が同じ線を逐語で引いている:

> `memory/` には置かない。記憶は人格であり、こちらは鍵と `PATH` の話である。混ぜるとクローンのシステムプロンプトへ鍵が載る。

**profile でない理由（現物で確定）。** `EnvProfile` は `{ script: string; updatedAt: string }` の単一オブジェクトで、`ProfileStore` に `list()` は無い。pg 実装は `PROFILE_ID = 'default'` の固定鍵1行、fs 実装は単一ファイル。依頼者の「全文置換の1本」は**正しい**。

**そして `migrate.ts` の DDL コメントが、この設計を名指しで先回りして警告している（逐語）:**

> 実行環境プロファイル（`.zprofile` 相当）。**高々1行**である。
> 用途ごとに行を増やす形にしないのは、増やせる形にした瞬間に「どの行が
> どの層に効くか」の対応表が生まれ、**それが権限の一覧に化けるからである。**

`packages/core/src/profile.ts` も同じことを言っている:「ここでは、**環境変数の一覧を持たない**」。

**これは「profile を使うな」以上のことを言っている。** この repo は既に一度、「層ごとに効く設定の行を持つ表」が権限の一覧へ化ける道筋を見つけて、それを塞いでいる。**いま作ろうとしている表は、まさにその形になりうる。** だから不変条件をもう1つ置く:

> **不変条件2: 台帳の行を「どの層に効くか」で鍵付けしない。**
> 層の列を作らない。まずクローン層だけを対象にした1種類の台帳として作る。
> マネージャー層へ広げるのは別の判断であり、広げるなら**そのとき**、上の DDL
> コメントを読み直したうえで人間が決める（§5.2）。

**形は `commitments` を写す**（`id` 主キー ＋ `jsonb` 本体 ＋ 索引用の列を別出し ＋ 部分索引）。`schedule` も同型だが、`commitments` のほうが CRUD 全種・人間とクローンの両方の書き込み経路・CLI・Web 画面まで揃っていて写経元として網羅的である。

### 5.2 マネージャー層 — **今回は対象にしない**（保留ではなく、意図して外す）

依頼では「同じ仕組みにするか、別にするか」を問われた。**答え: 今回はクローン層だけを作る。**

まず事実の訂正。マネージャー層にも**同じ穴がある** — `auto` では `canUseTool` が呼ばれないので、分類器に止められた1件はクローンにも確認として上がらない（`runner.ts:1410-1416`）。依頼にあった「マネージャーには `canUseTool` が繋がっていて、確認はクローンへ上がってきます」は、**クローンやマネージャーが `ask_human` を経由して上げた確認**については成り立つが、**分類器が落とした1件については成り立たない**。この穴は実在する。

それでも今回外すのは3つの理由による:

1. **§5.1 の不変条件2。** 層ごとに効く行を持った瞬間、`migrate.ts` が警告している「どの行がどの層に効くかの対応表」そのものになる
2. **`runner.ts:63-65` の明示の線**（逐語）:
   > この層は**判断をしない**。「これは人間に聞くべきか」「この道具は許してよいか」は一切持たず、確認をそのままデーモン（＝クローン）へ上げる。**ここに行為の一覧を置いた瞬間、権限境界が設定に化けて人による違いが潰れる**（AGENTS.md 地雷3）。
3. **粒度が決まっていない。** マネージャーは複数同時に走り、寿命も cwd も違う。「全マネージャー共通か／リポジトリ単位か／1体ごとか」を決める材料がいま無い。クローン層を1本動かせばその材料が増える

**#182 の発端（クローンの `gh pr merge`）はクローン層の話なので、これで人間の要望は満たせる。** マネージャー層は、穴があることを記録したうえで次の段へ送る。

### 5.3 既定 — 締めない。この台帳は開ける方向にしか動かない

**依頼者と同じ側に倒す。締めない。** 理由を3つ:

1. **締めると禁止1（デグレード禁止）に当たる。** いま通っているものが止まるのは、人間が自分の PC で Claude Code を開いたときにできることが減ることを意味する
2. **`dontAsk`（"deny if not pre-approved"）へ倒せば台帳の設計は楽になるが、それは能力の削除を前提にした楽さである。** 台帳が空の初日にクローンが `Read` すらできなくなる。PR #35 が実際に人間の苦情で直した形へ戻る
3. **§2.3 の不変条件の帰結。** この台帳は `allow` しか持たない。締める手段を持たない以上、既定を締める話とそもそも接続しない

**したがって `permissionMode` は `auto` のまま、環境変数での差し替えもそのまま。** この設計が変えるのは「分類器が落としたものを、人間が後から通せるようにする」ことだけである。分類器は引き続き第一の関門として働き、台帳はその上に**開ける**規則を積む。

## 7. 秘密について

- 台帳が持つのは**規則の文字列だけ**。鍵・トークン・資格情報は1つも持たない
- **規則から資格情報を読み出す経路を作らない。** 特に `Bash(cat *)` のような形は、承認されれば器の中の任意のファイルを読める。§3.3 の「広さを見せる」はこのためでもある（狭めはしないが、人間が広さに気づかないまま通ることは避ける）
- 台帳の内容は秘密ではないので、3つの入口すべてで**読み書きできる**。ただし「読み書きできること」の等価であって、**生の値が画面に出ることの等価ではない**（依頼者の但し書きのとおり）
- **この repo には既に伏せ方の作法がある。** `fingerprintOf()`（`credentials.ts:120` / `profile.ts:121-124`、sha256 の先頭12桁）で同一性だけを見せ、本文は返さない。`evaluateProfile` は環境変数の**名前だけ**を外へ出して値を返さない（逐語:「**値は返さない。** 何が増えたかは人間の確認に要るが、値は指紋と同じでここに晒すものではない」）。**許可規則そのものは秘密ではないので伏せる必要は無いが、規則の中に値が書けてしまう形（例: 具体的なトークン文字列を含むコマンドを規則にする）を作らないこと**
