## 危険や行為を数え上げて渡す限り、抜けが出る

危険や行為を数え上げて渡す限り、依頼者が思いつかなかったものは必ず抜ける。実際に漏れと過剰の両方が出た — 「`@claude` を投稿するな」と書いた依頼では、squash マージが PR 本文をコミットメッセージへ写す経路が抜けていた。「管理者バイパスがあれば止めろ」と書いた依頼では、既存の広さを継承しているだけの PR まで止まった。

## 実例（#247 の 4 / PR #304）

実例(2026-08-23、#247 の 4 / PR #304): Issue は「**横向きの左右 inset（`--safe-left` / `--safe-right`）は Drawer にしか当てていない**」と書いていた。**これはアプリ全体についての主張である** — 当てるべきなのに当たっていない場所は、全部この Issue の中身になる。作業者は6箇所へ当てたうえで、7つ目（`Nav`。`MOBILE_BREAKPOINT = 768` 以上では `MobileTopBar` が描かれず `Nav` が左端に出る）を「この PR が作った穴ではない」として範囲外に上げ、マネージャーが**範囲内**と判定して差し戻した。**問い2 の適用としては完璧で、それでも答えが違った。**

- **6/7 を直して「#247 の 4 を直した」と書く PR は、履歴に嘘を焼く**（squash 本文は消せない）。しかも**残る1つが、Issue の言う症状にいちばん近い場所だった**

## 実例（#285）: 作った穴と既存の穴

実例(2026-08-23、#285): 画面の分岐を `else` で受けていて、**将来 enum に足された値が黙って網の外へ出る**形になっていた。これは**その PR が作った穴なので同じ PR で塞いだ**（`switch` ＋ 型の網羅性）。同じ画面の別の箇所も未知の値でラベルが空になるが、**そちらは以前から在る挙動なので Issue（#288）にした。** **そしてこの2つは`種類の違う欠陥`である** — 上の #304 が「同じ欠陥が1つ多いだけ」だったのと対になる。
