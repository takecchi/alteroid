# PR を squash マージする直前に確かめること

**squash の本文は `main` のコミットメッセージに焼かれ、二度と消せない。** CI の門は PR の本文を見るが、**マージの口で足されたもの・本文と差分のずれは、どの門も見ていない。** ⟹ マージする人がここで見る。

## 1. 本文は明示して渡す（既定の本文で squash しない）

`gh pr merge <N> --squash --match-head-commit <確かめた head の sha> --subject "<件名>" --body "<本文>"`（本文が長いときは、本文を書いたファイルを `--body-file <file>` で渡す。`--body` の代わりに使う）（MCP の `merge_pull_request` なら `commit_title` / `commit_message`。MCP 側の sha の引数の有無は確かめていない）で渡す。既定の本文のままにすると:

- PR 本文の末尾のフッタ（`_Generated by …_`）がそのまま写る
- squash するコミットの author がマージする人と別人なら、GitHub が共著者の行を足す。SDK 更新の枝（`automation/claude-agent-sdk`）はコミットが bot の名義なので、既定の本文だと必ず付き、`main` のコミットにトレーラが焼かれる（#1350。実例: `045968c`）。main 側でこれを見る門はもう無いので、ここで外すしかない

件名は PR のタイトル（`<type>: <description>`）に ` (#<PR番号>)` を付けた形にする。

## 2. 本文が名乗った変更と、実際の差分を突き合わせる（#1130）

`gh pr diff <N> --name-only`（MCP なら `pull_request_read` の `get_files`）で変更したファイルを取り、本文が「追記した / 変更した / 新設した / 消した」と**動詞で名乗っているファイル**が、その一覧に在るかを見る。

- **本文がファイルを名指しするだけなら突き合わせない。** 名指しの大半は参照であって変更の主張ではない（#1130 の実測: 直近30本で名指しの 34.7% が差分に無く、機械の門にすると27本が赤くなる）。見るのは動詞で変更を名乗った箇所だけである
- **範囲が途中で縮んだ PR ほど危ない。** 「このファイルは外して」と指示して差分から消えても、本文は誰かが直すまで古いまま残る（実例: `888724a2`。本文は `AGENTS.md` へ追記したと名乗るが、差分に `AGENTS.md` は無い）
- ずれていたら、本文を直してからマージする（渡す本文を直すだけでよい。PR 本文を編集すると本文を見る門がもう一度走る）

## 3. 本文から外すもの

- `Co-Authored-By:` などの帰属トレーラ、`🤖 Generated with …` のフッタ、`_Generated by …_` のフッタ（リポジトリの約束。門は `no-attribution-trailers`）
- 閉じるキーワード（`close` / `fix` / `resolve` の活用形 ＋ `#番号`）。閉じたいなら次の行を使う

## 4. Issue を閉じる行

閉じる Issue があるなら、本文に独立した行で `Alteroid-Issue-Done: <番号>` を残す（無ければ `Alteroid-Issue-Done: none`）。マージの後に workflow が閉じる。**閉じたかは、マージの1〜2分後に Issue を引き直して確かめる**（`closed_by` が `github-actions[bot]`）。

**`Alteroid-Issue-Done` は PR 本文に書く。squash の本文だけに書いても効かない**（`scripts/issue-done-trailer.mjs` は `gh pr view --json body` で PR 本文を読む）。実例: PR #1909 は squash の本文にだけ `Alteroid-Issue-Done: 1882` を書き、PR 本文は `none` のままだったので #1882 は閉じず、手で閉じた。

## 5. マージの口には `--match-head-commit <sha>` を付ける（#1192 N7）

**緑を見た head と、マージされる head がずれうる。** PR の CI は `refs/pull/N/merge` を見ていて `strict: false` なので、見た後に push された head は機械では突き合わされていない。`gh pr merge` に `--match-head-commit <sha>`（緑を確かめた head の sha。`gh pr view <N> --json headRefOid` で取る）を付けると、head が動いていれば gh が拒む。`--auto` にも付ける。

- alteroid の manager / worker の `Bash` では、付いていない `gh pr merge` は `bash-wait-guard.ts` が弾く（形は `gh-pr-merge-no-match-head-commit`）。`--disable-auto` と `--help` は弾かない
- 弾かれたら sha を確かめ直して付ける。sha は緑を確かめたときの値を使う（マージの直前に取り直すと、ずれを機械が拒む意味が消える）

## 6. squash には本文（`--body` / `-b` / `--body-file` / `-F`）を付ける（#1350、#2280）

§1 の決定を、Bash のガードでも見る。`gh pr merge` で `--squash`（または `-s`）を使い、本文のフラグが1つも無いものは `bash-wait-guard.ts` が弾く（形は `gh-pr-merge-squash-no-body`）。`--merge` / `--rebase` と、`--disable-auto` / `--help` は弾かない。

- 直し方の例: `gh pr merge <N> --squash --match-head-commit <sha> --body-file <file>`
- `--match-head-commit` も欠けていれば、形は `gh-pr-merge-no-match-head-commit` のまま、理由に両方が書かれる
- 効く範囲は manager / worker の `Bash` だけ。クローンと人間の操作、MCP の `merge_pull_request`、`gh api` には効かない
- 根拠の実測（2026-09-30）: #1465 の後に main へ入った実トレーラ3件（`87eec2bb`、`39721665`、`2a275f8d`）は、どれもマージの本文が PR 本文の写し（既定の本文）だった。本文を書き直して渡した squash では、author が別の身元の PR でも行は付いていない（#1468〜#1488 の 10 本）
