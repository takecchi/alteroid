# 実行環境プロファイル（`.zprofile` 相当）

<!-- AGENTS.md から移設。パスはリポジトリの根からの相対である。移設時は本文を1文字も変えていなかったが、その後 `BASH_ENV` が読まれる条件の記述を実測に合わせて直した。 -->

**環境変数を器に増やす代わりの口である。** 道具の鍵や `PATH` を `compose.yaml` へ足していくと、1つ増えるたびに器を焼き直すことになる ＝「環境を直す」と「走行中の仕事を失う」が同じ操作になる。人間が `~/.zshenv` に1行足せば済ませていることが実装作業になっている時点でデグレードである（north_star 禁止1）。設計の全体像は [docs/architecture.md](./docs/architecture.md)「実行環境プロファイル」。

- **道具（パッケージ）を足す口ではない。** apt のパッケージや rustup のような「器に入っている道具」は、ビルド時の追加層（runner の Service 変数 `ALTEROID_EXTRA_APT_PACKAGES` / `ALTEROID_EXTRA_SETUP`。#2534。置き方は `railway/README.md`「使う人ごとの道具を足す」）で入れる。追加層は root でビルド時にだけ走り、実行時の uid 1001 の境界は変えない。**分担は「道具は追加層、`PATH` や `RUSTUP_HOME` のような環境はプロファイル」である** — 追加層で `/opt` に入れた道具を uid 1001 から呼べるようにするのは、こちらの1行（`export PATH=…:$PATH`）の仕事。逆に、プロファイルの中で `apt-get` や `curl | sh` を走らせて道具を入れようとしないこと（uid 1001 には root が無く、評価は仕事を起こすたびに走る）
- 実体は**シェルスクリプト1本**。器は中身を解釈しない（`export` でも `eval $(...)` でも `PATH` 追加でもよい）。**環境変数の一覧を持たないこと**が要点で、名前の表を足したくなったらそれは `credentials` の口の仕事である
  - **その `credentials` の口には正本が在る**（`alteroid credential set <名前>` / `PUT /credentials`。記憶ストアの `credentials.json` / `manager_credentials`）。名前は任意で、`hello` のたびに降り直す。**秘密はそちらへ置くこと** —— こちらは `GET /profile` が本文ごと返すのに対し、あちらは指紋しか返さない。そして**走行中の `gh` / `git` に届くのもあちらだけ**である
  - **⚠️ プロファイルに `GH_TOKEN` のような名前を書くと、`credentials` の口を影にする**（`#childEnv()` はプロファイルを鍵より後に重ねるので勝つ）。撒いた側は「撒いた」と報告し、子プロセスは古い値を受け取る。検出はある（`credentialNamesShadowedByProfile`）が、止めはしない
- 置き場は記憶ストア（fs なら `~/.alteroid/profile.sh`、pg なら `env_profile` の1行）。**記憶ではない**ので `memory/` には置かない（クローンのシステムプロンプトに鍵が載る）
- 操作は `alteroid profile show|status|edit|set|clear`、API は `GET /profile` / `PUT /profile`、**クローンの道具は `profile_read` / `profile_write`**
- **撒く先 `scope`（`all` / `app` / `runner`。既定 `all`。2026-10-03）。** 環境変数（`alteroid credential set --scope`）と同じ3値で、`app` = クローン（デーモン）だけ、`runner` = マネージャー・作業者だけ、`all` = 両方。オーナーの指示（逐語:「env-profileを環境変数と同じように指定できるようにして欲しい」「デフォルトは両方です」）で、きっかけは runner にだけ要る Rust の `PATH` / `RUSTUP_HOME` がクローンにも届いたこと。**`credentials.scope`（2026-09-14）と同じ理由で AGENTS.md 地雷3 を上書きしている** — scope は確認・許可ではなくプロセストポロジーの表現（`packages/core/src/store.ts` の `EnvProfile.scope` の doc）
  - 口: `alteroid profile set|edit --scope <all|app|runner>`（**省略は今の撒く先を保つ**。無ければ `all`）・`PUT /profile` の `scope`（不正値は 400）・`profile_write` の `scope`・Web の「撒く先」。`profile status` が撒く先を出す。**`profile show` の標準出力は本文だけのまま**（パイプで `set` へ戻す使い方があるので変えない）
  - **判定は1か所**（`profile-service.ts` の `profileScopeAppliesTo` / `scriptFor`）。`apply`・`restore`・`syncRunner`・runner への配布すべてが通る。**届かない側へは「触らない」ではなく空を降ろす** — all → runner へ狭めたとき、本文が同じでもクローンから外れなければ、鍵を含みうる本文が残り続ける
  - **runner 宛て（`runner`）の本文は、デーモンでは評価されない。** クローンへ効かせない本文を、デーモンのプロセスで評価すると、runner にしか無い道具（`eval "$(some-tool env)"` など）で誤って落ちる。評価は runner が `setProfile` で行い、読めなければ `ok: false` で返る（**正本の保存は済んでいる** — `all` / `app` のように「読めなければ保存もしない」は `runner` では保証できない）
  - 置き場: fs は `profile.sh` を素のスクリプトのまま保ち、隣の `profile.sh.scope`（1語。無ければ `all`、3語のどれでもない中身も `all` として読み、次の write が直す）。pg は `env_profile.scope` 列（`default 'all'`）。外すと scope も消える。`revert` は本文・更新日時・scope を組で戻す
  - runner の指紋との突き合わせ（`profile status`）は、`app` のとき「載っていないのが正しい」として出す（食い違い扱いにしない）
- **クローンにも人間と同じ手を持たせてある。** 人間は自分の `~/.zshenv` を開いて直せるのだから、その写像であるクローンにできないのは能力の削除である（north_star 禁止2 は層を問わず効く）。人間が chat で「このトークン使って」と言ったものを、クローンが実行環境へ移せる形にしてあること自体が要件である
  - **鍵が文脈に載ることは方針で扱い、道具を取り上げて表現しない。** システムプロンプトで「本文を記憶にも日誌にも書き写さない」と言っている（記憶は人間が開く場所であり、クローンのシステムプロンプトにも載る）。ここを「読ませない」で解こうとしないこと
  - 人間の口とクローンの道具は**同じ経路を通す**（`profile-service.ts` の `apply`）。別々に書くと、片方だけに検査が入って「人間が置くと弾かれるのにクローンが置くと通る」が生まれる
- **触れるのは実行環境の持ち主だけ**（`requireOwner`。持ち主と、持ち主として宣言されたアカウントだけ。2026-09-24 に `requireOperator` から移した（#1122）。`requireOperator` でしか叩けない経路の一覧は `scripts/require-operator-routes.test.ts` の `EXPECTED_OPERATOR_ROUTES` が持つ）。`access grant` を通しただけのアカウントには開けない — `PUT` の本文はデーモンの `process.env` を土台にその場で評価される＝**記憶ストアの鍵を持つプロセスでの任意コマンド実行**であり、評価中の出力は応答にも返る。`GET` も同じ扱いにする（本文に鍵が丸ごと入りうるので、読み側が緩ければ書き側を締めても意味が無い）。**「使ってよい」の2値に、実行環境を差し替える資格を含めないこと**
- **runner に「読みに行かせない」。** 読みに行けるということは runner に記憶ストアの鍵があるということで、M4 受け入れ基準3 が消える。降ろすのはデーモンで、runner が名乗る（`hello`）たびに降ろし直す（器を作り直しても環境が痩せないため）
- **どこまで届くかを取り違えないこと。** 本命は **SDK 子プロセス起動時の評価**で、これを継承した先でマネージャーも作業者も MCP サーバも走る（＝**これから起こす仕事には即座に効く**）。**走行中の仕事へ確実に届くのは `gh` シムがファイルを読み直す経路だけ**である（`credentials.ts` と同じ形）。`BASH_ENV` も置いてある。**bash がこれを読むのは非対話のときで、`bash -c` も `bash -lc` も読む — 読まないのは対話シェル（`bash -ic`）だけである**（歯: `packages/core/src/profile.test.ts` の `describe('BASH_ENV が読まれる条件')`）。ここには長く逆が書いてあった（「`bash -c`（stdin が端末でない）では読まない」）が、bash の実際の挙動とは**逆向き**である。**それでも「1コマンドごとに全員へ読み直される」と書かないこと。理由が入れ替わっただけで、結論は変わらない** — 実測（2026-09-06）では、マネージャーが Bash ツールで打つそのシェル自体はプロファイルを読んでおらず、そこから起きた入れ子の bash は読む。**届く相手と届かない相手が混在し、その機序は特定できていない**（対話モード・ログインシェル・`SHELLOPTS`・`POSIXLY_CORRECT`・ハーネスの shell snapshot はいずれも否定済み）
- **上（記憶）へ到達する鍵は、本文が何を `export` しても配らない。** シェルが何を export するかは静的に読めない（`eval` がある）ので、「書かせない」ではなく「最後に `unset` する」で守る。器が書く行・評価側の削除・合成順序の三重で塞いである。**どれか1つに寄せて他を消さないこと**
- **⚠️ 秘密を意図的に「配らない」で走らせたいときは、`BASH_ENV` も一緒に外すこと。** `env -u <名前> …` だけでは外れない — `BASH_ENV` が残っていると、起きた bash がプロファイルを読み直して**同じ名前を入れ直す。** そして**外れなかったことはエラーにならない**（値が在るので動いてしまう）ので、対照実験のつもりが本物を叩く。実際にこれで意図しない課金が出た（2026-09-05）。正しい形は `env -u <名前> -u BASH_ENV …` である。**なお「この実行ではこの秘密を配らない」を選ぶ口は、いまの alteroid には無い**（`alteroid profile` の `scope` は撒く先をクローン／runner で分けるだけで、仕事ごとには選べない）
- **壊れたものは保存も配布もしない。** `BASH_ENV` に載せると以後すべてのコマンドが壊れた環境で走り、原因はどこにも出ない。置く前に1度評価し、通らなければ 400 で理由を返す（前のものが残る）
- **更新は1本の列（`profile-service.ts`）を通す。** 人間の口・クローンの道具・runner の再接続時の降ろし直しは同じものを書き換えるので、**インスタンスは1つだけ作って全経路へ渡すこと**。順序は評価 → 正本へ保存 → クローンへ反映 → runner へ配布で、**どの段で落ちても旧版で揃える**（反映に落ちたら正本を書き戻す）。「失敗を返したのに1層だけ新版」を残すと、次の名乗りでそれが配られて分裂が黙って広がる
- **`credentials` を消さないこと。** あちらは「1つの鍵を、名前を検査したうえで回す」細い口である。効く順序は credentials → profile（人間が明示的に書いたほうが勝つ）
- 動作確認: `alteroid profile status`（各層へ届いているか。本文は出ない）、`docker compose exec -u 1001 runner env | grep SOME_KEY`
