# 一覧→詳細（オンデマンド）の設計

**エージェントへ返すものが件数に比例して伸びる形を作らないこと。** 一覧は「何があるか」を答えるものであって、「中身が何か」を答えるものではない。中身は別の呼び出しで取りに行く。

この文書は**設計の約束**である。手順の一部（変異で歯を確かめる）は `.claude/skills/mutation-testing/` が持つ。

## なぜこれが規律として要るのか

**この repo は同じバグを3回踏んでいる。**

| 回  | 何が起きたか                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| #39 | `manager_list` が件数で溢れた（**実測 52,997 文字**）。MCP の出力上限を超えた応答はクローンに1文字も届かないので、一覧が丸ごと使えなくなる |
| #51 | `journal_read` が出力上限で丸ごと落ちた                                                                                                    |
| #95 | `digest` の6節が黙って切れていた                                                                                                           |

3回とも「溢れた1本を後追いで塞ぐ」形で終わっている。原因は `packages/core/src/digest.ts` の冒頭が逐語で記録している:

> 後から足した6節が黙って切れていたのは、**この行が各節の実装の側にあって書き忘れても何も落ちなかったから**

**道具の側も同じ形だった。** `manager_list` にだけ「件数が増えても壊れない」歯が立っていて、`approvals_list` / `schedule_list` / `runner_list` は無上限のまま残っていた（#192 で塞いだ）。**歯が1本ずつだと、次に足す一覧も無上限で入る。**

## 統一する3つの性質

新しい一覧を足すとき、または既存の一覧を直すとき、**3つ全部**を満たすこと。

1. **一覧は本文を全文で載せない** — 識別子 + タイトル/要旨を1行にして、`excerptLine` で切る
2. **一覧は文字数の予算を持ち、切ったら件数と続きの取り方を必ず出す**
3. **詳細は `page()` で `offset` 継続できる**

### 1. 一覧に載せるもの

- **識別子は必ず載せる。** 詳細を取りに行く鍵がなければ、抜粋にした瞬間に到達できないものが生まれる
- 本文は `excerptLine(text, LIMIT)` を通す。`excerptLine` は改行を潰すので1行に収まる
- **上流のキャップを自分の根拠にしないこと。** `manager_list` の返事待ちは runner 側の `brief(input, 200)` が実質のキャップになっていたが、`AskUserQuestion` の経路（`describeQuestions`）は質問文を `join(' / ')` で連ねてそのキャップを通らなかった。**出す側で締める**

### 2. 予算は件数ではなく文字数で持つ

**⚠️ 件数の上限だけでは足りない。**

実例: #170 は記憶の目次に `MEMORY_TOC_ENTRY_LIMIT = 300`（件数）と `MEMORY_TOC_LINE_LIMIT = 200`（1行の長さ）を入れた。**300 × 200 = 60,000 文字**で、実測で溢れた 52,997 文字を超える。件数から出力量を決めると、**何件で壊れるかが運任せになる**。

積む形は `packages/core/src/excerpt.ts` の `renderListing()` が持つ。**一覧ごとに予算のループを手で書かないこと**（それが3回踏んだ原因である）。

```ts
return text(
  [
    renderListing(items, {
      budget: MY_LIST_BUDGET,
      omitted: ({ rest, shown, total }) =>
        `…ほか ${rest} 件は省略（全 ${total} 件のうち ${shown} 件だけ出した）。`,
    }),
    '（本文は抜粋。全文は my_tool id=<id> で取れる）',
  ].join('\n'),
);
```

- `omitted` には**続きの取り方**を書く。「N 件省略」だけでは、受け取った側は落ちたものへ行けない
- **1件だけで予算を超えるときは `renderListing` がその1件を切って出す。** 落とすと「何も出ない一覧」になり、丸ごと出すと予算が意味を失う——どちらも「上限がある」と言えなくなる
- 予算の定数は**用途ごとに別に置き、doc に由来を書く。** 値が同じでも使い回さないこと（片方だけ直したくなったときに一緒に動いてしまう）。既存の分け方は `tools.ts` の `REPORT_PAGE` / `TRANSCRIPT_PAGE` が手本

### 3. 詳細の口

**一覧を抜粋にしたなら、同じ PR で全文の口を用意すること。** 人間は Web UI で全部読める。クローンだけが抜粋しか読めないなら、それは**能力の削除**である（north_star 禁止1）。

```ts
const part = page(body, offset, MY_PAGE);
const tail = part.more
  ? `\n\n…（ここで切れている。続きは my_tool id=${id} offset=${part.to}）`
  : '';
return text(`${head}（${describePage(part)}）\n\n${part.body}${tail}`);
```

- **切って捨てるのではなく、分けて渡す。** `offset` があれば全部届く
- **切れていないときに注記を出さない側へ倒せる。** 毎回付けると、本当に切れているときの目印が効かなくなる（`memory_read` がその形）
- **全文置換の口と対になっている詳細は、切れたことの帰結まで書く。** `profile_read` は `profile_write` が全文置換なので、切れた本文をそのまま書き戻すと行が黙って消える（しかも切れた shell も妥当に見えるので検証を通る）。だから「ここで切れている」だけでなく「書き戻すつもりなら先に最後まで取ること」まで出力に書いてある

### 一覧と詳細を、1つの道具にするか2つにするか

**どちらも既にこの repo に在る。** 揃えるのは上の3性質であって、道具の数ではない。

| 形                              | 例                                                                                                                         | 選ぶとき                                                                            |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **1つの道具＋引数でモード切替** | `journal_read`（引数なし＝一覧 / `id`＝全文）、`usage_read`（`axis`）、`approvals_list`（`id`）、`schedule_list`（`kind`） | 既定。`CLONE_TOOL_NAMES` を増やさずに済む                                           |
| **一覧の道具＋詳細の道具**      | `memory_list` → `memory_read`、`manager_list` → `manager_report` → `manager_transcript`                                    | 詳細が**段になる**とき（報告 → 生ログのように大きさの桁と `null` の意味が違うもの） |

## 歯（テスト）

歯は `packages/core/src/tools.test.ts` の **「一覧は例外なく件数で壊れない（`*_list` の総当たり）」** に在る。

- `CLONE_TOOL_NAMES` から **`_list` で終わる名前を機械的に集める。** `_list` で終わる一覧を足した人は、この試験に何も書き足さなくても捕まる
- 1つの器（`flooded()`）に全ストアを積んで、そこから全部の一覧を撃つ。**一覧ごとに別の器を作らないこと** — 積み忘れたストアの一覧が「0件だから短い」で通ってしまう（実際にこれで `usage_read` の穴を作り、歯が拾った）
- 測るのは2つで、**別々の `it()` にしてある**（片方が通るともう片方も通ったように見えるため）
  - 出力が `OUTPUT_CAP` 未満に収まる
  - 切ったなら合図が出る（`TRUNCATION_MARK`）

### ⚠️ この網が拾えない範囲

**網が全部を覆っていると読まれるほうが、覆っていないと分かっているより悪い。**

- **名前が `_list` で終わらない一覧は拾わない。** `journal_read` / `usage_read` / `conversation_read` はテスト側で名指ししてある。**別の名前で新しい一覧を足す人は、自分で足す必要がある**
  - **1つの道具が複数の一覧モードを持つなら、モードごとに名指しすること。** `conversation_read` は引数なし＝会話の一覧 / `conversationId`＝中身 / `q`＝語で探す の3つを持ち、**積む向きが違う**（中身だけが `renderListingFromEnd` を通る）。1つ測っても他は何も測れていないので、4件に分けてある（一覧は既定と `limit` 最大の2件）
- **`TRUNCATION_MARK` の語彙を増やすほど、この試験は「何か書いてある」しか測らなくなる。** 新しい一覧はまず既存の言い方（`…ほか N 件は省略`）に寄せること。ここへ1語足すのは「その言い方も契約に入れる」という判断であって、通し方の調整ではない
- **既定の引数では予算に届かない一覧がある。** `journal_read` は既定 20 件 × 抜粋 120 字 ≒ 3,000 字で、`JOURNAL_BUDGET`（8,000）は一度も拘束条件にならない。**「呼び手が広げられる上限まで広げた呼び」も測ること**（`limit: 200`）
- **足場が薄いと歯は生き残る。** `runner_list` は 12 台の足場では内訳の件数上限だけで収まってしまい、ブロックの予算を落とす変異が生き残った（＝その一覧については何も測れていなかった）。120 台へ増やして殺せるようになった

**歯を足したら、必ず変異を当てて確かめること。** 手順は `.claude/skills/mutation-testing/`。**生存＝テストが通ったなので、証拠が要るときにだけ消える。**

## いま揃っていないもの（範囲外として残した）

**「無い」と読まないための記録である。** 直すときはここを更新すること。

- **`conversation_read` の会話一覧だけは、要旨が `excerptLine` を通っていない**（#181 の時点）。通しているのは `conversation.ts` の `preview()` で、80字で切って `…` を付けるが**省いた分量を言わない** — 上の性質1と食い違う。**わざとそうしてある**: この値は `GET /conversations` の `preview` として人間の Web UI と CLI にそのまま出ているもので、`app.ts` から1文字も変えずに移設した。**寄せると人間側の表示が変わる**ので、直すなら人間側の表示の変更として別に諮ること（他の2モードは `excerptLine` を通っている）
- **プロンプトへ焼く記憶の目次（`renderMemoryToc`）は件数の上限だけを持つ。** 300件 × 200字 = 60,000 字になりうる。ここを文字数へ寄せるかは #170 の設計判断（`premise` は切らない・`fact` は落としてよい、という区分の話）に触るので、道具側の統一とは分けた
- **`commitment_list` に詳細の口が無い。** 本文は 240 字の抜粋で止まり、全文へ行く道具が無い（`journal_read` から辿れることはあるが、台帳の id から直接開く口ではない）
- **HTTP の口（`GET /commitments` / `GET /usage` / `GET /reports/:date` / `GET /archive`）は上限を持たない。** これは**意図である** — 人間はブラウザで扱えるので、ここを締めると人間側の能力が落ちる。**エージェントへ返す口と混ぜて数えないこと**
- **データそのものの保持期間・掃除の機構は無い**（`prune` / `retention` / `cleanup` の実装は0件）。文脈へは出ないが、日報を組むための読みが運用日数に比例して増える（`digest.ts` が `jobs.listJobs()` と closed commitments を全期間読む）。`CLOSED_HISTORY_LIMIT = 500` は fs 実装にだけ在り、pg には無い
