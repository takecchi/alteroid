# 観測用テスト（いまの挙動を記録しただけのテスト）

## 何が「観測用テスト」か

いまの挙動を記録しただけで、受け入れ基準ではないテストである。ふつうのテストとわざわざ分けるのは、状況が動けば測っているものは古くなるのに、**アサーションは緑のまま残るので、CI では絶対に見つからない**からである。

## 名乗ること

歯C（`scripts/test-guard-core.mjs`）は、観測用テストと**名乗った**ファイルにしか反応しない。名乗りは次の2形だけである（散文で「観測」「書き捨て」等と書いても判定されない——この repo の137ファイルが「観測」を別の意味で使っており、誤検出になることが実測されている）。

```
1. パス名に `.observed.` / `.scratch.` / `-scratch.` を含む
2. 冒頭コメント領域に「@観測」という語が在る
```

**名乗らなければ、歯Cは中身を見ない。**

## 名乗ったら書く2項目

名乗ったファイルの**冒頭コメント領域**（コメントでも空行でもない最初の行の直前まで）に、次の2項目を書く。

```
終了条件: <空でない文字列>
見直し期限: YYYY-MM-DD
```

`YYYY-MM-DD` はゼロ埋め必須である。冒頭コメント領域より後ろに書いても拾われない。

## 到達を見るのは `pnpm test` である

見直し期限を過ぎると、歯Cが `pnpm test` を赤くする。**人間がこれを覚えている必要は無い。** これが「観測用テストが書いた終了条件への到達を、誰が・いつ見るのか」という運用ルールの答えである。

⭐ **見る人は「書いた本人」ではなく「そのとき `pnpm test` を打った人」である。** 期限が来て赤くなったとき、それに気づくのは元の担当者とは限らない。だから次の手のうち「延ばす」を選ぶなら、**なぜ延ばすかを一緒に書くこと**——次に当たる人はその観測がなぜ始まったかの経緯を知らない。

## 赤くなったときの次の手（3択）

- 終了条件に到達しているなら、「基準」に書き換える（普通のテストに昇格させる）
- 到達していて、もう要らないなら捨てる
- まだ到達していないなら見直し期限を延ばす（延ばす理由を一緒に書く）

## 3状態を混ぜない

歯Cは次の3つを別の状態として扱う（それぞれ別の exit code。値そのものはここには書かない——正本は下の「検出の詳細の正本」）。

- **走査対象0ファイル**——「判定できない」。見て0件だったのではなく、見ていない
- **申告不備**——名乗ったのに2項目が無い、または見直し期限の書式が壊れている
- **見直し期限超過**——到達を見る番が来た

## 見直し期限の決め方の目安

「その観測が支えている調査が終わりそうな時期」を置くとよい。分からなければ、短く置いて後で延ばすほうがよい——**延ばす操作は経緯とともに残るが、忘れる操作は何も残さない。**

## 限界（隠さず書く）

- **「名乗れ」は強制できない。** 歯Cが強制できるのは「名乗ったら書け」までである。散文の「観測」で判定すると誤検出になるため、歯Cは散文を見ない——つまり名乗らずに観測用テストを書くこと自体は防げない。
- **期限で赤くするのは時限式である。** 期限の日が来ると、**その日以降の関係の無い PR も止まる。** これは「誰かが必ず気づく」を保証する性質そのものだが、代償でもある。警告だけ出す／CI の別ジョブに切る、という設計もあり得たが、PR #542 はこの時限式を採った。
- **期限当日はまだ赤くならない**（比較は `>` であって `>=` ではない）。

## 検出の詳細の正本

名乗りの形・拾う領域・書式の検証・exit code の値——これらの正本は `scripts/test-guard-core.mjs` の歯Cの節（`isObservationFile` / `readObservationDeclaration` / `findObservationDebts` / `judgeObservationScan` / `formatObservationGuardMessage`）である。**ここへ値を書き写さないこと**——書き写せば二重管理になり、実装が変わったときに必ずずれる。上の記述は、読む人がこの運用ルールを守るために要る最小限に留めてある。
