# 認証トークンのプール（枠に当たったら回す候補）

**⚠️ この文書は「回るようになった」時点のものである。** 枠に当たると、回し手（デーモンの中の1本）が次の候補を選んで runner とクローンへ撒き、日誌へ残し、クローンのセッションを作り直す。

**⚠️ 2026-09-07 に契機が増えた。**「枠に当たったら」だけでは足りなかった —— **その6つの検知点はどれもセッションが回っているあいだにしか鳴らない**ので、**全層が止まると観測を上げる主体が1つも居なくなり、通る鍵がプールに残っていても何も起きなかった**（下の「回す契機は観測だけではない」）。いまは記録の状態と、セッションを1本も使わない枠の probe も契機である。

**⚠️ ただし「回った」は「復帰した」ではない。** 撒いた先が新しいトークンで走るのは**次にセッションを起こすとき**からで、走行中のマネージャーには届かない（下の「走行中には届かない」）。**回ったことの権威ある証拠は、次のターンが成功することだけである。**

**Issue #393 の残りは無い**（人間の決定 2026-08-25）。受信箱への通知は**入れないと決めた** —— 回した事実は日誌に出るので、クローンのターンを1本焼く価値が無い。**⚠️ この決定は 2026-09-07 に一部だけ覆っている** —— 「通る鍵に戻った」ときは受信箱へ合図を入れる（下の「通る鍵に戻ったら、止まっていた層を起こす」）。**覆ったのは _再開の契機_ の側だけで、_知らせ_ を入れない判断はそのままである。**クローンの道具は**読み取りだけ入った**（`token_list`。書き込みは渡さない —— 回すのは実装であって、クローンの判断を待たない。PRD「provider」）。

**Web UI の画面は入った**（Issue #464 は CLOSED。`apps/web/app/routes/tokens.tsx`）。**この節はかつて「Web UI にプールの画面が1つも無い」と書いていたが、それは腐っていた** —— 画面が在ることは `ls apps/web/app/routes/tokens.tsx` で当たる。

**台帳との紐付けは入った**（下の「どのトークンでいくら使ったか」）。

## 何のためにあるか

いま `CLAUDE_CODE_OAUTH_TOKEN` は器の環境変数1本きりで、枠（利用上限）に当たったら人間が器を焼き直すまで全層（クローン・マネージャー・作業者）が止まる。ここは、人間が登録した複数のトークンを1つのプールとして持つための器である。プールは全層で1本（同じアカウントの枠を共有する前提）。

## 登録する（CLI）

```
alteroid token add --label <名前> --file <path>
# または
echo -n "<あなたのトークン>" | alteroid token add --label <名前>
```

- `--label` は人間が読む名前で、**秘密ではない**（`alteroid token list` にそのまま出る）
- 値は**ファイルか標準入力からだけ**渡す。**コマンドライン引数（`--value` のような形）は無い** — `argv` は同じ器の他のプロセスから見える（`ps` 等）ので、秘密をそこへ置かない設計である

他の操作:

```
alteroid token list                 # 一覧（値は出ない）
alteroid token remove <id>
alteroid token disable <id>         # 人間の判断で外す（戻らない側）
alteroid token enable <id>          # 戻す
alteroid token policy               # いまの契機・冷却を見る（引数無し）
alteroid token policy free_exhausted --cooldown-ms 18000000
```

## 登録する（HTTP）

```
curl -X PUT http://127.0.0.1:4517/tokens \
  -H "authorization: Bearer $(cat ~/.alteroid/state/daemon.json | jq -r .token)" \
  -H 'content-type: application/json' \
  -d '{"tokens":[{"label":"<名前>","value":"<あなたのトークン>"}]}'
```

- `/tokens` は **alteroid を使う許可があれば通る**（`authenticate` だけ。`requireOperator` は付いていない）。**2026-09-06 のオーナー決定**で、`access grant` を通したアカウントを実行環境の持ち主と同格にした（それ以前は `requireOperator` で「課金の主体を決める操作だから」と閉じていた）。**`/profile` だけが同格の外に在る** — あちらは `GET` が本文ごと鍵を返すので、外へ配られる bearer token の側には開けない
- `PUT /tokens` は**全文置換**。並べ替え・改名・`disabled` の切り替えだけなら `value` を省略してよい（省略すると既存の値を引き継ぐ——他の行の秘密を貼り直す必要が無い）
- **⚠️ curl の例をそのまま打つときも、シェルの履歴にトークンの値が残る。** ヒアドキュメントや `-d @file.json`（ファイルは使い終わったら消す）を使うほうが安全である

## 回す契機（`rotateOn`）— 3値。それぞれ誰のための値か

| 値                           | 意味                     | 誰のための値か                    |
| ---------------------------- | ------------------------ | --------------------------------- |
| **`free_exhausted`（既定）** | 無料枠が尽きたら回す     | 課金枠（overage）を焼きたくない人 |
| `overage_exhausted`          | 課金枠まで閉じてから回す | 課金枠を使い切ってから回したい人  |
| `off`                        | 回さない（記録だけする） | 自動切替そのものを切りたい人      |

冷却（`cooldownMs`）は「`resetsAt` が取れなかったときだけ使うフォールバック」であって、枠の単位そのものの主張ではない（既定はいちばん短い枠の単位である5時間に寄せてある——早く起きすぎるほうが安全側という判断）。権威ある期限は `resetsAt` のほうである。

## 回す契機は「観測」だけではない — 状態の側にも在る（2026-09-07）

**⚠️ ここは 2026-09-07 に変わった。それまで契機は6つの検知点だけで、6つとも「セッションが回っているあいだ」に鳴るものだった。**

⟹ **全層が枠で止まった状態は、観測を上げる主体が1つも居ない状態でもある。** 抜けるには誰かがもう一度本番で失敗して観測を上げるしかなく、**プールに通る鍵が残っていても何も起きない**時間ができた（人間の報告: 「枠塞がってないトークンがあるのに何故何もしてないことがある」）。人間が新しい鍵を足しても同じで、`PUT /tokens` は記憶ストアを書くだけだった。

**⟹ いま契機は2系統ある。**

| 系統                                                       | 入口                                                                 | 鳴る条件                                                                     |
| ---------------------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **観測**（`signal` が枠の6値）                             | `TokenRotator.observe`                                               | セッションが回っているあいだに枠の文言 / `rate_limit_event` が届いた         |
| **状態**（`signal` が `stranded`。日誌の `reason` が付く） | `TokenRotator.reconsider`（`apps/daemon/src/token-watch.ts` が呼ぶ） | **記録の上でいまの現役が通らないのに、通る候補が在る**。セッションは要らない |

**状態の側が見るのは1つだけである** —— 「現役が `ready` でないか」。`ready` なら**回さない**（健全な鍵から勝手に移らない歯止めがここである）。

**契機（日誌の `reason`。数え上げの持ち主は `packages/core/src/schema.ts` の `token_rotation.reason` の `z.enum`）:**

| `reason`           | 何で鳴るか                                                                            |
| ------------------ | ------------------------------------------------------------------------------------- |
| `tick`             | 見張りの目盛り（60秒）。**冷却明けもここで拾う**                                      |
| `startup`          | デーモンが起きた直後の1回（引き取り＝`restore()` の**後**）                           |
| `pool_changed`     | `PUT /tokens`（＝ `alteroid token add` / `remove` / `disable` / `enable` / 並べ替え） |
| `settings_changed` | `PUT /tokens/policy`（＝ `alteroid token policy`）                                    |
| `runner_connected` | runner が載った / 器が入れ替わった                                                    |
| `account_probe`    | **枠の probe が現役を測った**（5分ごと。`apps/daemon/src/usage-poller.ts`）。下の節   |

**⚠️ 「冷却が明けた」専用の値は持たせていない。** 見張りは記憶ストアを読まないので、目盛りが鳴った回が冷却明けだったのかどうかを**言えない** —— 言えないことを名前で主張する値を作ると、`AGENTS.md` の地雷「取れない軸に 0 の行を作る」と同じ形になる（**誰も出さない enum の値は、schema がついた嘘である**）。

**⚠️ 目盛りは安い。** `reconsider` はふつうの状態では記憶ストアを3回読むだけで終わり、**候補が全部冷却中でも probe を1本も焼かない**（候補選びは記録だけを見る純粋関数で、`ready` な行が無ければ probe の前に打ち切る）。焼くのは「現役が通らないのに `ready` な候補が在る」＝まさに回したい瞬間だけである。

**⚠️ `off` はどちらの系統でも回さない。** 状態の側でも設定を読む（判定は回し手1箇所に閉じてある）。ただし**記録は残る** —— `signal: 'stranded'` / `event: 'not_rotated'` で「止まっていることは分かっていた」が日誌に出る。

## セッションを1本も使わない観測（`account_probe`）

**枠の probe（`usage-poller.ts`、5分ごと）はプロンプトを1つも送らないので、全層が止まっていても現役の枠を読める。** それを候補と同じ目（`judgeTokenCandidate`）に通して回し手へ渡す。

| probe の判定  | 何が起きるか                                                                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `unusable`    | **記録が `ready` でも冷却へ入れて回す。** 「観測がどこからも上がらないまま止まり続ける」を塞ぐ本体                                              |
| `usable`      | **止まった記録を消す**（`markTokenUsable`）。冷却が既定の5時間で入っていて実際はもっと早く開いていた回がここで戻る。日誌は `event: 'recovered'` |
| `undecidable` | **記録だけで判定する。** probe の失敗・通信断・締め切りはここへ落ちるので、**器が混んでいる回に現役を冷却へ入れることはない**                   |

**⚠️ この probe は 2026-09-07 まで「器の環境変数のトークン」を測っていた**（`Options.env` を渡していなかったので子プロセスが `process.env` を継承した）。⟹ **回した後は降りた鍵のアカウントの枠を報告し続けていた**（`GET /usage` の `account` とクローンが見る `accountUsage` の両方）。いまは現役の値を渡す。

### ⚠️ 復帰の下限は目盛りの60秒ではなく、probe の5分である（実運用のレビューで判明。2026-09-07）

**「記録の上で現役が `ready`」の状態からは、目盛りは何回鳴っても動かない**（それが「健全な鍵から勝手に移らない」の歯止めそのもの）。記録を `ready` から動かせるのは2つだけである:

| 誰が                              | 何を書くか                                    | 周期             |
| --------------------------------- | --------------------------------------------- | ---------------- |
| `observe`（セッション由来の観測） | 降りる鍵の冷却                                | 観測が届いたとき |
| **`account_probe`**               | `currentVerdict: 'unusable'` で**現役**の冷却 | **5分**          |

**`currentVerdict` を渡す口は1つだけである**（`token-watch.ts` の `run('account_probe', verdict)`）⟹ `tick` / `pool_changed` / `runner_connected` / `startup` は**記録しか見ない。**

**そして観測が飲まれる形は実在した。2つあり、#668 で1つ塞いだ**（`#667` / `#668`）:

| 飲まれる形                                                           | いま                                                     |
| -------------------------------------------------------------------- | -------------------------------------------------------- |
| `manager.ts` / `clone.ts` の `case 'rate_limit'` の**遷移の門**      | **塞いだ**（#668。遷移が取れなかった回も回し手へ渡す）   |
| `observe` の `freshness === 'stale'` が**冷却を書く手前で `return`** | **残す**（#667。**これは正しい** —— 下の「なぜ残すか」） |

**塞いだ側（#668）** —— 遷移の判定材料（`#rateLimits`）は**そのインスタンスの寿命ぶん**残るので、同じ `kind` の `rejected` が**別のトークンで**再発しても `usageTransitionOf` は `undefined` を返し、回し手へ一度も届かなかった。⟹ 記録は `ready` のまま、実際は 429。**実運用で20分以上の停止として観測された**（2026-09-07）。

いまは**状態でも回る。ただし観測がいまの世代を名乗ったときだけ**である（`decideTokenRotation` の `freshness`）。**「毎ターン回さない」を保証する歯が、遷移から世代へ移った:**

| 何が「1回の当たりで1回だけ」を保証するか    | 効く範囲                                      |
| ------------------------------------------- | --------------------------------------------- |
| 遷移（**〜#668**）                          | そのインスタンスの寿命（＝2度目が落ちる）     |
| 世代（`freshness === 'current'`。**いま**） | いまの現役1本ぶん（回せば世代が上がって黙る） |

**⚠️ 身元を運ばない観測（`freshness === 'unknown'`）では状態で回さない。** 回し手は `unknown` を `current` として扱うが（飲み込むほうが悪い）、その規則は状態の側へ広げていない —— 世代を照合できない器では「回した後は自動で黙る」が成立せず、`rejected` が続くあいだ毎ターン回してプールを食い潰す。**その器では下限はいまも probe の5分である。**

**なぜ `stale` の `return` を残すか（#667 の候補1・2 を両方採らない）:**

- **候補1「`stale` でも冷却は書く」→ 冷却が縮む。** `resetsAt` を運んでいない観測が書く期限は `min(記録, now + 既定)` なので、遅れて届いた観測は**本物の期限が未来に在る鍵を早く `ready` に見せる**。**⚠️ 2026-09-07 に入れた `min` はこの判断を動かさない** —— 塞いだのは逆向き（推測が記録を**後ろ**へ動かす側）だけで、前へ動かす側は意図して残してある
- **候補2「世代は古いが `tokenId` は現役と同じ観測を `current` にする」→** `observationFreshness` が `generation` を見る理由（同じ鍵が冷却明けにもう一度選ばれた後の、前の在任期間ぶんの遅れた通知）をそのまま取り込む
- **そもそも `stale` な観測は、いまの現役が通るかどうかについて1文字も言っていない**（名乗っているのは前の世代の鍵で、それは既に冷却済みである）

⟹ **「記録は `ready`、実際は 429」を作っていたのは遷移の門のほうだった。** 身元を運ぶ観測が届く器では、**復帰の下限は観測が届いた時点へ戻る**（5分刻みではない）。

### ⚠️ probe はセッション上限を見られない —— `usable` は「セッションが起きる」の証明ではない

probe が読むのは**アカウントの枠**（`five_hour` / `seven_day` / … と課金枠）で、**セッション単位の上限に対応する枠が無い**（`usage-snapshot.ts` の窓の一覧）。⟹ `You've hit your session limit` で止まっている鍵に対して `usable` が返りうる:

1. **その形は `unusable` として検出できない** —— 上の「塞ぐ本体」が効くのはアカウントの枠を使い切った形だけである
2. **`usable` で止まった記録を消すと、通らない鍵を `ready` に戻しうる。** そこから先は自己修復する（起こされた層が失敗し、**その失敗が新鮮な観測になって** `observe` が冷却を書き、次の候補へ回る）が、**1ターンぶんの空振りを払う**

**⟹ 起こすことは「仕事を再開させる」だけではない。「飲まれていた観測を新鮮にし直す」でもある** —— 引き取られたセッションは `#rememberTokenIdentity` を通るので、いまの世代を名乗る（`manager.ts` の3箇所: 新規の `start` / 引き取り / `resume`）。**`stale` で全部飲まれていた状態は、起こした時点で解ける。**

## 通る鍵に戻ったら、止まっていた層を起こす（2026-09-07）

**⚠️ これは 2026-08-25 の決定（受信箱への通知は入れない）を、この場合について覆したものである。**

**撒くだけでは、止まったものは止まったままである。** 枠に当たったクローンは解除の契機を**新しい合図の到着**にしか持たない（`clone.ts` の `#usageBlocked`: タイマーを持たない）。マネージャーも同じで、枠で落ちたセッションは引き取り（`ManagerPool#restore`）が走るまで再開しない。⟹ **鍵が通るようになった瞬間に、誰も動かなかった。**

人間の逐語（2026-09-07）:

> limitが来て止まってトークン回して復活したら復活させたことをcloneやmanagerに通知する必要があるのでは？なぜならlimit来て止まっているのでセッションを再開する必要があるでしょ

**2026-08-25 の決定と矛盾しないのは、種類が違うからである** —— あのとき「価値が無い」と判断されたのは**知らせ**（回した事実を伝えること。それは日誌に出る）で、ここで入れているのは**再開の契機**である。**止まっている層は、合図が来ないかぎり自分では動けない。**

| 何が起きたか   | 起こすか       | なぜ                                                                                                    |
| -------------- | -------------- | ------------------------------------------------------------------------------------------------------- |
| `rotated`      | **起こす**     | いま通る鍵に移った                                                                                      |
| `recovered`    | **起こす**     | 止まっていた現役が、また通ることを観測できた                                                            |
| `parked`       | **起こさない** | 撒いた鍵は `earliestAt` まで通らない。起こしても同じところで止まり、**保持していた合図を1件無駄に焼く** |
| `exhausted` 他 | **起こさない** | 何も変わっていない                                                                                      |

**`parked` の側は放置ではない** —— 冷却が明ければ枠の probe（5分ごと）が `usable` を観測し、`recovered` としてここへ戻ってくる。

**起こし方は層で違う**（判定は `apps/daemon/src/index.ts` の `reopenedTokenOf`。**測れる形に切り出してある** —— 起こすべき回に起こさない側の壊れ方は「何も起きない」なので**出力から見えない**）:

| 層           | どう起こすか                                                                                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| クローン     | 受信箱へ合図を1つ（`source: 'token-pool'`）。これが `#releaseRequested` を立て、保持していた合図が FIFO のまま配り直される                                                                                                            |
| マネージャー | **2本を順に通す。** `ManagerPool#restore()`（台帳に `running` / `waiting_human` で残っている委譲を、runner に居なければ resume する）→ `ManagerPool#resumeStoppedByUsage()`（**枠で止まった委譲へ、続きを促す一言を投げる**。下の節） |

**`restore()` だけでは1本も起きない（2026-09-07 に足した）。** あれは**プロセス内の像に無い**委譲だけを拾う（`#restoreJobs` の先頭が `if (this.#records.has(job.id)) continue;`）うえに、resume するのは台帳が `running` / `waiting_human` の分だけである。⟹ **枠で終わったターンはどちらの条件からも外れる** —— デーモンは走り続けているので像は在り、台帳は `done`（報告として終わった）か `failed` / `lost`（セッションごと落ちた）になる。だから `resumeStoppedByUsage()` が要る。

## 枠で止まった委譲を起こす（`resumeStoppedByUsage`）

**撒いた鍵で開き直したセッションは、誰かが話しかけるまで何もしない。** `runner.ts` の `#reopenForTokenRotation` が保つのは**会話**であって仕事ではない。ここが投げる一言がその「話しかける」である。

- **`send()` に相乗りする**（新しい経路を作らない）。生きたセッションが在れば push、無ければ**同じ `sessionId` で resume** ⟹ どちらの道でも会話は続く（最初からやり直しにならない）
- **起こすのは `done` / `failed` / `lost` だけ**（ホワイトリスト）。`running` は走っている、`waiting_human` は人間の回答待ちであって枠待ちではない、`stopped` は甦らせない
- **印は `usage_notice` の `kind === 'reached'` で立つ**（`usageLimitKindSchema` の doc が言う「もう通らない。仕事は止まっている」）。自力でターンを終えた回（`failure` 無しの `report`）で下ろす
- **⚠️ 印は `await` の手前で立てる。** `#onEvent` は `void` で起こされるので同じターンの `usage_notice` と `report` は並行に走り、後ろに置くと**下ろしが先に走って**「自力で終えた委譲に印が残る」

### ⚠️ 鍵が戻った瞬間には、まだ走っていることがある（借り）

**鍵を回す契機は、たいていその委譲自身の `usage_notice` である。** ⟹ 回し手が `resumeStoppedByUsage()` を呼ぶ瞬間には `report` がまだ届いていないことがある。**そこで印を捨てると、回転は済んでいるので次の契機が来ず、その委譲は永久に止まる**（同じ鍵で回すことは #668 の門が止める）。

同じ形がもう1つ —— **別の層が枠に当たって鍵が回った直後**、まだ古い鍵で走っていた委譲がそのターンで枠に落ちる場合。こちらも鍵の側からの契機は二度と来ない。

⟹ 鍵が戻った時点で走っていた委譲を**借り**（`#usageWakeOwed`）として控え、**そのターンが終わった地点**（`case 'report'` / `case 'closed'`）で返す。**枠で終わった回だけ**が実際に起こされ、自力で終えた回は借りだけが下りる（1ターン焼かない）。

**⚠️ 印はプロセス内である。** 枠に当たってから鍵が戻るまでにデーモンが入れ替わると消える ⟹ その回は起動時の `restore()`（台帳が `running` / `waiting_human` の分）と、受信箱に残る報告を読んだクローンの判断に落ちる。

## 止まった事実の記録と、回復の見込み

**枠に追い返された1回は、そのトークンの行に残る。**

| 列                                     | 何が入るか                                                                                                                                                                                                                             |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lastRejectedAt`                       | 止まった時刻                                                                                                                                                                                                                           |
| `lastRejectedReason`                   | **SDK が出した文言そのまま**（言い換えない）                                                                                                                                                                                           |
| `cooldownUntil`                        | 戻る見込みの時刻。`resetsAt`（権威ある値）、取れなければ設定の `cooldownMs`。**取れなかった回は、記録されている未来の期限より後ろへは置かない**（逐語は `grep -Fn -- '推測が記録を後ろへ動かさない' packages/core/src/token-pool.ts`） |
| `createdAt` / `updatedAt`              | 行を置いた時刻 / 最後に変わった時刻                                                                                                                                                                                                    |
| `recovery`（**保存されない。導出値**） | その文言が時間で戻るか（`time` / `action` / `unknown`）。読むたびに文言から導く                                                                                                                                                        |

- **使えることを確認できたら、上の記録は消える**（`markTokenUsable`）。消えるのは記録だけで、値も `disabledAt`（人間が外した印）も残る
- **`updatedAt` は「実際に変わった行」にだけ立つ。** `PUT /tokens` は全文置換だが、全行に判を押すと「最後に誰かが `PUT` を打った時刻」に化けて、どの行がいつ変わったかが取れなくなる
- **`createdAt` が無い行がある。** PR1 の版で置かれた行がそれで、**`now()` で埋め直していない**（埋めると「いま作られた」という嘘になる）。CLI はその行を出さない

### 回復の見込みは3値。**`kind` とは別の軸である**

`classifyUsageNotice` の `reached` は「いま通らない」しか言わない。**その中に、待てば戻るものと人間が動かないと戻らないものが混ざっている。**

| 値        | 意味                                              |
| --------- | ------------------------------------------------- |
| `time`    | リセット（5時間 / 週 / 請求期間）を待てば戻る     |
| `action`  | 入金・管理者の設定・座席種別の変更が要る          |
| `unknown` | どちらとも言えない。**`action` の同義語ではない** |

- **`unknown` を「捨てる」側へ倒さないこと。** `action` と読むことは候補を1本永久に降ろす判断になりうる。読み違えの代償が非対称である（`time` を `action` と読むと**まだ戻るトークンを捨てる**が、逆は「冷却が明けてもう一度試す」だけで済む）
- **扱いは当面一律である**（人間の決定 2026-08-25）。`action` と判定される文言でも**冷却へ倒し、`invalidatedAt` は立てない**。⟹ **分類は記録されるが、いまも何も分岐させていない** —— 回し手は `action` の行も冷却へ倒す。**分類を扱いへ効かせるなら、そのときが人間の決定の出番である**
- **分類の表（`LIMIT_RECOVERY_BY_PREFIX`）は SDK の文字列を鍵として書き写している。** 接頭辞ごとに違う注記を付けるには他に方法が無いためで、**腐ったら赤くなる形にしてある** — `usage-limits.test.ts` が表の鍵の集合と SDK の配列を**両方向で**突き合わせるので、SDK が1つ足しても1つ改名しても落ちる。実行時の倒れ先は `unknown`
- **表の判定は書き手の判定であって Anthropic 側の仕様の主張ではない。** 例外は `"You've hit your"` の1行だけで、そこは人間の実測である（`You've hit your org's monthly spend limit` は無料枠を使い切って従量課金へ切り替わったときに組織の課金上限へ達して出るもので、請求期間が変われば戻る）

## 置いたら何が変わるか

`GET /tokens` / `alteroid token list` に登録した行が現れる。並べ替え・外す（`disable`）・戻す（`enable`）ができる。回す契機（`rotateOn`）と冷却の既定（`cooldownMs`）を変えられる。

## 走行中には届かない（⚠️ ここがいちばん詰まりやすい）

**回っても、いま走っている「ターン」のトークンは変わらない。** SDK 子プロセスの env は**起動時に凍る**ので、撒いた鍵が効くのは次に起こす分と、次のターンの境界からである。

| 相手                               | いつ新しいトークンで走るか                                                                                            |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| これから起こすマネージャー・作業者 | **即座**（`#childEnv()` は spawn のたびに呼ばれる）                                                                   |
| **走っているマネージャー**         | **次のターンの境界から。** セッションを畳んで `resume` で開き直す（会話は続く）。**いま走っているターンには届かない** |
| **クローン**                       | 次のターンの境界でセッションが畳まれ、`resume` で作り直される（会話は続く）                                           |

**⚠️ 「走っているマネージャーは（枠に当たって終わるまで）ならない。引き取りで起き直るときに新しい env になる」は誤りだった（2026-09-06 実測で否定された）。** 回転後も走行中だったマネージャーは、引き取り（デーモンの再接続）を一度も経ずに、古い鍵のまま枠へ2回当たり続けた——回した事実そのものは正しく撒かれていた（3台の runner とも現役の指名の指紋と一致していた）。**直したのは runner 側**（`packages/core/src/runner.ts` の `Host#setCredentials` / `#reopenForTokenRotation`。fix/recycle-manager-session-on-token-rotation）——**ターンの境界**（入力待ち・確認待ちが無い・背景処理が無い・resume できる状態）でセッションを畳んで `resume` で開き直す形にした。上の表の行はその直し後の事実である。

⟹ **日誌の「撒いた」を「回った」として読まないこと。** 撒いた先ごとの成否は日誌に出るが、それは「置いた」までである。

**⚠️ そして runner が1台も繋がっていなければ、撒く先が無い。** そのことも日誌に出る（成功に畳んでいない）。**ただしそれで永久に届かないのではない** —— 後から上がってきた runner には次の節の導線で届く。

## 再接続の瞬間に、現役が降りる（撒く先が無かった回も追いつく）

**runner は繋がるたびに `hello` を送り**（`apps/runner/src/app.ts`。SSE のストリームが張られた最初のフレーム）、デーモンはそれを全部 `#reattach` へ通す（`packages/core/src/manager.ts`）。⟹ **降ろす契機は3つあり、どれも「その瞬間」である:**

| 契機                                  | 経路                                                   |
| ------------------------------------- | ------------------------------------------------------ |
| 名簿に新しく載った                    | `runners.subscribe` → `#connectTo` → `#pushAgentToken` |
| **ストリームが繋がった / 繋ぎ直した** | runner の `hello` → `#reattach` → `#pushAgentToken`    |
| 器が入れ替わった（`onSwap`）          | `reattachRunner` → `#reattach` → `#pushAgentToken`     |

**降ろすのは `createRunnerTokenSync`（`apps/daemon/src/token-spread.ts`）で、`spread()` と同じ表現を使う** —— `source: 'env'` の行が現役なら**空文字**を降ろす（runner の鍵ファイルを消して器の環境変数へ落とす）。**「値が無い」を「何もしない」と読まないこと**（あちらの doc に、混ぜたときに何が起きるかが逐語で在る）。

**箱（`AgentTokenHolder`）が一度も撒いていなければ何もしない** —— 器の環境変数だけの既定の構成で1文字も変えないためである（受け入れ基準7）。

**そして 2026-09-07 から、runner が載ったことは「見直し」の契機でもある**（`reason: 'runner_connected'`）。降ろすのは上の3経路が既にやるので、見直しが足すのは別の1つ —— **指名そのものが古いときは降ろしても直らない**（器の入れ替えは分単位、枠は5時間単位なので、入れ替えのあいだに冷却が明けていることが普通に起こる）。

## 何は変わらないか

**プールが空の器では、何も起きない。** 器の環境変数だけの既定の構成は1文字も変わらない（受け入れ基準7）。

**⚠️ その状態では、環境変数のトークンが止まっても記録が残らない。** 器の環境変数を指す行は**予備を1本でも登録したときに生える**ので、1本も登録していない器には行が無く、冷却の入れ先も無い。`alteroid token list` がこのことを言う。

## 置いたことを人間が確かめる手段

`GET /tokens`（または `alteroid token list`）が返すのは:

```json
{
  "tokens": [
    { "id": "…", "label": "…", "order": 0, "sha256": "…", "createdAt": "…", "updatedAt": "…" }
  ],
  "settings": { "rotateOn": "free_exhausted", "cooldownMs": 18000000 }
}
```

止まった記録が付いている行では、ここに `lastRejectedAt` / `lastRejectedReason` / `cooldownUntil` / `recovery` が加わる（上の「止まった事実の記録」）。

**⚠️ 値（`value`）は絶対に返らない。** これは欠陥ではなく設計である——API・CLI・Web・日誌・ログのどこにも出さない（`packages/core/src/token-pool.ts` の `AgentTokenView` の doc）。「置いた値と同じか」を確かめたいときは、`sha256`（指紋、先頭12桁）を自分で計算して突き合わせる。

## どのトークンでいくら使ったか（台帳の軸）

台帳に `tokenId` の軸が在る（#393 受け入れ基準6）。**4つの口すべてから同じものが引ける:**

| 口                      | 絞り込み        | 内訳                       |
| ----------------------- | --------------- | -------------------------- |
| `GET /usage`            | `?tokenId=<id>` | `breakdown.byToken`        |
| `alteroid usage`        | `--token <id>`  | 「認証トークン別」         |
| Web `/usage`            | `token` の入力  | 「認証トークン別」のカード |
| クローンの `usage_read` | `tokenId`       | `axis="token"`             |

`<id>` は `alteroid token list` が `id=` で出すもの（**ラベルではない**。台帳が持っているのは id だけで、ラベルを引くのはプールの側である）。

**⚠️ ここがいちばん誤読しやすい — `tokensSince` が null なのは2つの意味を持つ。**

| 状態                                           | 読み方                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------ |
| `since` も null                                | 台帳へまだ1件も積んでいない                                        |
| **`since` は非 null で `tokensSince` が null** | **プールを使っていないので帰属が取れない。これが既定の構成である** |

後者では `byToken` が **`tokenId: null` の1件だけ**を返す。**これを「1本のトークンで全部使った」と読まないこと** — 0 でも既定値でもなく、**取れていない**である。だから4つの口はどれも `tokensSince` の但し書きを数字の隣に必ず出す。

- **`byToken` の `null` の要素は落としていない。** 落とすとこの軸だけ合計に足し合わなくなり、しかも他の軸は「出てこない値を 0 で補わない」約束なので、**読み手には足りないことに気づく手がかりが無い**
- **帰属は「そのセッションが起きた瞬間の身元」である。** 消費が届くたびに現役を読み直さない——読み直すと、回した直後に届いた**前のセッションぶんの消費**が新しいトークンに付く（`manager.ts` の `#tokenIdentities` の doc）。**その誤りは合計を変えないので、この軸を引いたときにだけ嘘になる**
- **軸を足す前の行は帰属を持たない。** `layer` / `site` のように「既定が古い行にとって真」ではない——**どのトークンで走ったかは、どこにも記録されていない**

## 失効しても回らない（非対称）

**回す契機は枠の2つだけである**（人間の決定 2026-08-24。`auth_failed` のような契機は一旦足さない——恒久の否定ではない）。

- **現役のトークンが失効した**（アカウント停止・組織による不許可など）**ときは回らない。** 枠に当たったとき（`cooldownUntil`。いずれ復帰する）と違い、**全層が止まったままになる。** 人間が `alteroid token disable <id>` で手で外すまで復旧しない
- **候補の側とは非対称である。** まだ現役でない候補が失効していれば（`invalidatedAt` / `invalidatedReason`）、回す側はそれを飛ばす。**⚠️ ただし、いまこの2列へ値を入れる経路はまだ無い** —— 回し手は枠の当たりを `cooldownUntil` へ倒すだけで、「恒常的に通らない」と確定する側を誰も書いていない。⟹ **失効した候補も、冷却が明ければもう一度 probe される**（probe が `unusable` を返して冷やし直すので、無限には試さない）
- `invalidatedReason` は解釈しない文字列（SDK やプローブが返した語をそのまま持つ）である。分岐に使ってよい enum ではない

## 最初に置いたときに見るもの

**⚠️ ここから先は、あなたが最初に置いたときが初回の実測になります。** 本物のトークンを扱わない枷があるので、実装側からは原理的に測れません。

**⟹ 置いたら、この3つを見てください:**

1. **登録された事実が出るか** — `alteroid token list` / `GET /tokens`（値は出ません。出ないのが正しい）
2. **指紋が、あなたが置いたものと合っているか** — 貼り間違い・改行の混入をここで捕まえる
3. **⚠️ 出てこなかったときにいちばん疑うべき場所——CLI（または叩いた API）が話しに行ったデーモンと、いま動いているデーモンが同じか。** `add` と `list` は独立した2回の呼び出しで、それぞれが `resolveTarget()`（`apps/cli/src/target.ts`）で接続先を決め直す。手元のデーモンが `add` と `list` の間で再起動していた・`ALTEROID_URL` が途中で変わっていた、のどちらかがあると、書いた先と読んだ先が別のプロセス（別の記憶ストア）になり、「登録したのに一覧に出ない」がそのまま起きる。**この版はまだ何も回さないので、回る側の失敗（probe に渡す env・`PATH` が消える、等）はここでは起こらない——起きるとしたら「登録できていない」の形だけである**

**⚠️ 回るようになったので、疑う場所が2つ増えた（下の 4 と 5）。**

4. **置いたのに回らない / 回ったのに効かない** —— まず**日誌**を見る。**種別で絞れる**（`token_rotation`）:

   ```
   journal_read types=token_rotation      # クローンの道具
   GET /journal?type=token_rotation       # HTTP
   ```

   **⚠️ 文言で探さないこと。** かつてここは `exchange` に入っていて、`認証トークン:` で始まる行を探す案内をしていた —— **`exchange` は53箇所が書く雑多入れ**なので、漁ることになるうえ、整形の言い方が変わると当たらなくなる。

   **`event` を潰さずに読むこと。数え上げの持ち主は `packages/core/src/schema.ts` の `token_rotation.event` の `z.enum` である**（ここに数を書くと、増えたときに数のほうが先に腐る。実際に 5 → 6 → 8 と増えている）:

   | `event`          | 読み方                                                                                                                                        |
   | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
   | `rotated`        | 正本は書き換わった。**撒いた先ごとの成否も `text` に出る**（「撒いた」であって「回った」ではない）                                            |
   | `parked`         | **いま通る鍵は1本も無い。いちばん早く戻る鍵を撒いて待っている**（2026-09-07）。`earliestAt` **まで全層が止まる**が、開いた瞬間にそのまま通る  |
   | `exhausted`      | **撒くものが無いまま返った。** `earliestAt` が付くのは「いちばん早く戻るのが現役自身だった」回だけ（無いなら戻る見込みの立つ候補が1本も無い） |
   | `sweep_stopped`  | 候補を試し切る前に持ち時間で打ち切った。**まだ試していない候補が残っている**（`exhausted` と同じ顔にしない）                                  |
   | `recovered`      | **止まっていた現役が、また通ることを観測できた**（2026-09-07）。**回してはいない** —— 消したのは止まった記録だけである                        |
   | `not_rotated`    | 契機に当たらなかった（設定が `off` / `org_policy` / まだ課金枠が生きている）。**これは正常である**                                            |
   | `restored`       | 起動時に現役を撒き直した（世代は増えていない）                                                                                                |
   | `restore_failed` | 起動時に撒き直せなかった（指名が消えている / 人間が外している / 撒く先が無い）                                                                |

   **`exhausted` と `not_rotated` を同じ顔にしないこと。** 前者は全層が止まっていて、後者は何も起きていない。

   **そして `parked` を `rotated` の側に読まないこと。** 撒けてはいるが**その鍵はまだ通らない** —— `earliestAt` より前に重い委譲を起こす判断をしないための時刻がそれである。3つの違いは「全コンテナが持っている鍵」で切れる: `rotated` はいま通る鍵、`parked` はいちばん早く戻る鍵、`exhausted` は**降りた鍵のまま**。

   **`signal` に `stranded` が在る回は、観測ではなく記録から決めた回である**（上の「回す契機は観測だけではない」）。そのときだけ `reason` が付き、どの契機で見直したかが読める。**セッションが1本も走っていないあいだにも出る。**

   当たった文言は `noticeText` に**言い換えずそのまま**入っている（`text` の中にも出るが、整形が変わっても原文は `noticeText` の側に残る）。**`stranded` の回には `noticeText` が無い** —— 文言を見ていないので、無いのが正しい（無いことを「文言が落ちた」と読まないこと）。

   **1件も出ないなら、回し手まで届いていない。** そのときは (3) と同じく「話しに行った先」を疑う。

5. **候補が残っているのか、全部冷却中なのか** —— `token_list`（クローン）/ `alteroid token list` / `GET /tokens` / Web の `/tokens`（`apps/web/app/routes/tokens.tsx`）。**値は出ない**（id・ラベル・指紋・状態だけ）。

## 回復の見込みの表を直すとき

**分類（`time` / `action` / `unknown`）を1行変えるのは、`packages/core/src/usage-limits.ts` の `LIMIT_RECOVERY_BY_PREFIX` の1行を変えるだけである。**

- **扱いが一律のうちは、変えても挙動は変わらない**（記録と表示だけが変わる）。回し手が読み始めてから初めて挙動になる
- **`action` へ倒すときはとくに慎重に。** 回し手が入った後は「候補を1本永久に降ろす」判断になりうる（上の非対称）
- 表の鍵を消したり、SDK に無い文字列を足したりすると `usage-limits.test.ts` が落ちる。**それは正しい落ち方である** — 鍵は SDK の配列と1対1でなければならない
