# 変異試験（テストが本当に守っているかを測る）

<!-- AGENTS.md から移設（#132）。移設の時点で本文は1文字も変えていない。その後この場所で足したものは git の差分で追える。パスはリポジトリの根からの相対である。 -->

**手順そのものは単純である。テスト対象のコードを意図的に壊し、テストが落ちるかを見る。落ちなければ、そこに歯は無い。**

**問題は、この道具自身が壊れうることである。** だから7つの歯を全部入れる。1つ欠けると「壊したまま気づかない」か「当て忘れたのに測れたことにする」のどちらかが起きる。

1. **md5 を記録する**（変異前・変異後・復元後）
2. **空パターンで落ちる** — 空の検索文字列は「0件」ではなく「全箇所」へ振り切れる（80,045か所へ挿入した実例がある）
3. **期待件数と一致しなければ落ちる** — 少なすぎる側だけ見るのは片側の歯である
4. **復元後に md5 が一致しなければ落ちる**
5. **変異前後の md5 が同一なら落ちる** — 当て忘れの検出。4 とは比べる向きが逆である
6. **書く前にパターンの一意性を検査する** — 書いてから数えるのでは、落ちたときにファイルが変異したまま残る
7. **計測フラグをベースラインで1回通し、期待どおりの値が出ることを確かめる** — 歯は「落ちる」ことで自分の故障を知らせるが、**結果を読む計測フラグは黙って嘘の値を出す。** そして守ろうとしているのが「テストが1本も走らなかった」＝まさに黙って通る失敗なので、疑っても倒す先が無い（信じれば全結果を捨て、無視すれば守りが消える）。**併せて `Tests N passed (N)` のような加工前の証跡もログへ残す** — フラグが壊れても事後に derive し直せる（実際に2回救った）

そのほか:

- **変異前にベースラインが `exit 0` であることを確かめる** — 「落ちた」と「テストが1本も走らなかった」はどちらも exit 1 である
- **`pnpm --filter <パッケージ> test` は1本も走らせない。** テストは root の `vitest.config.ts` 1本が集めており、`packages/*` / `apps/*` の `package.json` に `test` スクリプトは1つも無い。**pnpm は無い script を黙って飛ばして exit 0 を返す**（実測（2026-08-20 観測）で出力0行・exit 0）。**変異試験でこれを使うと、変異が当たっていても落ちない＝偽の「歯が無い」が出る。** 絞るなら root から `pnpm test <パスの一部>`（引数は vitest へそのまま渡る）
- **変異が生存したとき（テストが通ったとき）、テストの中に仕込んだ `console.log` は出力に出ない。** vitest の既定の reporter は console を横取りしており、**通ったテストのぶんは捨てる**（落ちたテストのぶんは `stdout | <ファイル> > <テスト名>` の形で出る）。実測（2026-08-22T04:28Z 観測、`vitest@4.1.10`。この repo の `vitest.config.ts` は `reporters` / `silent` / `onConsoleLog` / `disableConsoleIntercept` のどれも指定していないので既定のままである）。**`console.error` も同じで、`process.stdout.write` だけは横取りを通らず、通っても落ちても出る**
  - **重いのは、消えるのが「通ったとき」＝生存したときだけだからである。** 変異が生存したあと、次に知りたいのは「そのコードパスをテストが踏んでいるのか」である（踏んだうえで assertion が無いのか、そもそも到達していないのか。**どちらも「歯が無い」だが、次にやることが違う**）。それを見るために出力を仕込む — **その出力が、生存したときにだけ捨てられる。** 結果として**出力の不在が2つの意味を持つ**（何も起きなかった / 出力が捨てられた）。`AGENTS.md`「静かに失敗する道具」の `grep -c` が返す 0 と同じ形である
  - **仕込みが効いているかを「1回落として確かめる」と、必ず誤った結論に至る。** 落ちたぶんは出るので「出た＝ちゃんと出る」と読めてしまい、生存した変異でだけ黙って消える。**確かめるなら通るテストで確かめること**
  - **出す方法は2つとも実測で確認した。** `pnpm test --reporter=verbose`（通ったぶんも `stdout | …` として出る）か、`console.log` ではなく `process.stdout.write` を使う。**歯7が守るのは「計測フラグが嘘の値を出す」ことで、これは「証拠そのものが無い」ことなので別の歯である**
- **テストを付けなかった箇所にも変異を1本かける。** 何も落ちなければ「歯が無い」が測定として確定する。**「テストを書かなかった」と「守られていないことを確かめた」は別**である
- **復元に `git checkout` / `git restore` / `git stash` を使わない。逆変異＋md5 照合で戻す** — 「壊したものを戻す」手段が「変更を捨てる」手段と同じだと必ず事故る（未コミットの修正を4ファイル消した）。変異試験はコミット前に歯を確かめることが多い＝**最も危険な状態でこの道具を使う**
  - **ただし「逆変異」を文字列置換で書かないこと。復元は、変異前に読んだ原文をそのまま書き戻す形にする。** 歯2（空パターンで落ちる）は**変異を当てる側にしか掛かっていない**。変異が「消す」形（`to` が空文字）のとき、その逆は `replace('', from)` になり、**空文字は先頭に一致するので消したはずのものがファイルの先頭へ挿入される**。実測（2026-08-20T15:47Z 観測、`packages/core/src/inbox.ts`）: `while (...) { ... }` の5行を削る変異の復元で、その5行が `import` 文より前の1行目へ挿入された。**変異は当たり、テストも期待どおり落ちたので、壊れたのは復元だけである** — 「歯はあった」という結論は正しいまま、ファイルが壊れて残る。拾えたのは歯4（復元後の md5 照合）で、**逆変異の側には歯が無かった**。原文の書き戻しは `git` を1つも使わないので、上の禁止と競合しない
- **復元の最終確認は md5 照合と `git status` の両方で行う** — md5 は「数えたファイル」しか守らず、`git status` は「数え忘れたもの」を拾う
- **置換パターンは前後の一意な文脈まで含める**（`  return true;` がインデントの違う別箇所の部分文字列に当たった）
- **1つの変異で複数の保証を確かめない**（assertion は最初の1つで止まる）
- **複数落ちたら、別の箇所を変異させて落ちる集合が分かれるかを見る**（分かれるなら別々の保証である）。**説明は書き手の理解に依存するが、実験は依存しない**
- **回しているあいだ、同じ作業ツリーで他の誰か（作業者を含む）にテストを走らせない。** 別 worktree を使うか順番に回す。ファイルを一時的に壊す作業なので、並行実行は必ず汚染する（実際に汚染した）。**ただし別 worktree で分かれるのはファイルだけで、プロセス空間は共有されている**（`AGENTS.md`「自分が走っている器」参照）— 走らせているプロセス自体は他の作業者から見えるし、撃たれうる
  - **止まってもらう対象はテストだけではない。回しているあいだ、そのツリーは「現物」ではない** — ファイルは意図的に壊れた状態にある。**同じツリーで `grep` / `cat` / `git diff` / build を走らせないこと。読むだけの操作も、変異した中身を現物として読む形になる。** 歯4（復元後の md5 照合）が守るのは復元の正しさであって、**途中で読んだ者の結論は守らない**

## 自己修復する設計は、書き込み側の変異を隠す

**一般則: 「壊れていたら直す」経路を持つコードは、その経路が読み出しで走る限り、書き込み側を壊しても結果が正しく見える。**

**診断**: そのコードのテストが**「新しいものを作る → すぐ読む」形しか無いなら、修復経路を通っている疑いがある。** この形では、書き込み側が何も記録していなくても、直後の読み出しが「まだ無い」を検出して**現在の状態から正しい値を導出してしまう。**

**打ち手: 修復が働かない状態から測る。** 一度読んで値を確定させてから、2回目の書き込みで壊す。**「まだ無い」ではなく「在るが食い違う」を作れば、修復では埋まらない。**

**実例**（2026-08-22、`packages/storage-{fs,pg}/src/persona.ts` の本文ハッシュ）。記憶の保護は「デーモン経由で最後に書いた本文のハッシュ」を持ち、**無ければ現在の本文から作り直す**（索引を失っても凍らないため）。当時のテストは全部「新しい文書へ最初の1回書く → すぐ読む」形だった。

- `write()`/`append()` の**ハッシュ更新を丸ごと削除**しても、fs 79件・pg 84件が**全通過**した（＝生存）。修復が毎回埋めていた
- **同じ変異が、pg の `append()` だけに当てると検出できた。** `write()` が先に非 null を確定させているので、`append` だけ壊すと「無いから修復」ではなく**「在るが食い違う」**という本物の不一致になる
- **fs では同じことができなかった。** `write`/`append` が `#writeNow` 1本を共有しているので、**片方だけ壊せない**（両方まとめて死ぬ＝両方まとめて修復に隠れる）

**この非対称は、テストの本数でもカバレッジでも出ない。変異試験でしか見えない。**

**「片方だけ壊せない」ときは、それを設計の性質として書き、測定結果として残す。** 「歯が無い」と結論しないこと — **測れなかったのであって、守られていないと分かったのではない。** 上の「テストを書かなかった」と「守られていないことを確かめた」は別、と同じ線である。

**そして生存した変異は、必ず4つのどれかに分類する。**

1. **当てすぎ** — 仕様の範囲内で、落ちなくて正しい
2. **歯が無い** — その性質を測るテストが本当に無い
3. **テストの構造が観測不能にしている** — 上の自己修復がこれ。テストは在るが、その経路を通っていない
4. **変異が届いていない** — `packages/core/src` を壊したのに `pnpm --filter @alteroid/core build` を挟まず、`dist/` 経由で import する側（`apps/daemon` など）へ届いていない

**4 は、測っていないのに 1 や 2 と同じ見た目になる。** だから**変異を当てた後に「実行対象へ届いたこと」を先に示す** — その変異を必ず踏むはずのテストが1本落ちることを確かめてから本番の測定に入る（検出器が非0を出せることの、変異試験版の対照）。**届いていることを示せない変異は「不明」として出す。「生存した」と書かない。**

**そして 2 と判断しても、歯を無理に生やさないこと。** 要求を満たすために書かれただけのテストは、次に読む人へ「この性質は守られている」と嘘をつく。**足さない判断も、理由が書いてあれば正しい報告である。**

## 同じツリーで HEAD を動かすのも「汚染」に見える

上の「回しているあいだ、同じ作業ツリーで他の誰かに走らせない」は、**ファイルを触らない操作にも及ぶ。**

**実例**（2026-08-22）: マネージャーが、作業者の変異試験の最中に**別のファイルを `git add` してコミットした。** 作業ディレクトリのファイルは1バイトも変えていないが、**作業者は `git rev-parse HEAD` が動いたのを見て「他プロセスがこのツリーを汚染している」と誤認し、変異を復元して調査した。**

**実害は無かったが、往復を1つ作った。** そして**「実害が無かった」と「仕組みで塞げている」は別である** — 作業者が HEAD を突き合わせていたから気づけただけで、突き合わせていなければ**変異の結果を汚染された測定として捨てた**か、**汚染に気づかずに読んだ**かのどちらかになる。

**回している側の打ち手**: `md5sum` に加えて **`git rev-parse HEAD` も変異の前後で突き合わせる**（この実例の作業者は途中からそうした）。
**外から触る側の打ち手**: **回しているあいだは commit もしない。** 未 push を守る必要があるなら、**別の clone か worktree から押す。**
