## 手順を手で回さない。ハーネスが在る

<!-- ハーネス追加時に足した節（PR #257）。ハーネス追加の時点で、以下の本文（「手順そのものは
     単純である」以降）は1文字も変えていない。その後この場所で足したものは git の差分で追える。

下に書いてある手順（7つの歯・生存の4分類・復元の作法）は、そのまま手で叩ける形で
`.claude/skills/mutation-testing/mutate.mjs` に落としてある。**依存なし・ビルド不要**
（node の組み込みモジュールだけで動く。壊れた `pnpm build` の下でも使える必要があるため）。
実体は3ファイルに分かれている — `mutate-core.mjs`（手順を組み立てる層）・`mutate.mjs`（薄い CLI 層）・
`mutate-selftest.mjs`（自己検証。ハーネス本体には無い迂回路を使ってよい層）。同じディレクトリの
素の `import` で足しているだけで、`node_modules` には一切依存しない。

```
node .claude/skills/mutation-testing/mutate.mjs status                     # 印の有無を報告する。誰でも引数なしで打てる
node .claude/skills/mutation-testing/mutate.mjs baseline                   # ベースラインが緑であることを確かめる
node .claude/skills/mutation-testing/mutate.mjs apply --spec <spec.json>   # 段階実行: 1つの変異を当てて印を置くところまで
node .claude/skills/mutation-testing/mutate.mjs restore [--restore-from-marker]  # 段階実行: 印を読んで復元する
node .claude/skills/mutation-testing/mutate.mjs run --plan <plan.json>     # 本番: 複数の変異を順に回す
# baseline / run は `--max-workers <n>` と `--max-workers=<n>` の両方を受ける（#331）。
# 器が混んでいて並列度を下げるよう指示されている場面向け。省略時は既定の 4 のまま
# （`mutate-core.mjs` の DEFAULT_MAX_WORKERS）。
# selftest --scenario <name>: 自己検証（受け入れ条件とレビューで見つかった欠陥の回帰確認）。
# 本数と内訳は数えない — 省略した出力が名乗る一覧（mutate-selftest.mjs の SELFTEST_SCENARIOS）が本籍である。
node .claude/skills/mutation-testing/mutate.mjs selftest --scenario <name>
```

**全コマンド共通で `--root <path>` を受ける。** 省略時は既定（このスクリプト自身の
位置から3階層上）のまま——`ROOT` はスクリプト自身の位置から決まり、上書きする
引数が無かった。別の repo に立ってこの clone の `mutate.mjs status` を呼ぶと、
エラーにならず「このツリーに変異が当たったままの状態は無い」と答える——その
「このツリー」が呼び出し元ではなくこの clone であることが、出力からは分からな
かった。**`--root` を渡したかどうかに関わらず、実効の ROOT を毎回出力の先頭へ
出す**（`ROOT: <path>（既定 / --root で上書き）`）ことで、対象の取り違えを
「そうと分かる形」にしてある。不正な `--root`（存在しない・ディレクトリでない）
は fail-closed で拒否する。

`baseline` / `run` は、印（`MUTATION-IN-PROGRESS.json`）が残っている状態では測定を始めずに落ちる
（既定）。中断されたツリーで新しい測定を始めると、生存も検出も意味を失うため。逃げ道は
`--allow-existing-marker` の1つに限ってある。

### ⛔ 手で仕込まないこと —— 「緑」には3通りあり、summary 行では2つが区別できない

| 緑の意味                    | 何が起きているか                                                                  |
| --------------------------- | --------------------------------------------------------------------------------- |
| **生存**                    | 変異は着地したが歯が噛まなかった ⟹ **正しい観測**（歯が足りない）                 |
| ⛔ **変異が着地しなかった** | 仕込みそのものが失敗した ⟹ **無意味な緑。「歯が噛まない」と読むと逆の結論になる** |

**実例（2026-09-16、別の担当の報告。逐語）**: 変異を `python3` のヒアドキュメントで手で仕込んだところ、**この器に `python3` は無い**ので書き込みが静かに失敗し、テストは緑で返った。「その緑は『変異が一度も着地しなかった』であって『歯が噛まない』ではなかった —— 気づけたのは summary 行ではなく**変異した行そのものを印字した**からである」。

**ハーネスを通せば、この3つ目はハーネスが名乗る**（手で仕込むと名乗る者が居なくなる）:

- `validateSpec`（`[0]`）—— `spec` の形が崩れていれば **「何も書き込んでいない（控え・印・変異のいずれも0バイト）」** と言って落ちる
- **歯3/6**（`[5]`）—— `from` の一致件数が `expect` と違えば **「書き込みは行わない」** と言って落ちる。**#1096 で `weak-tooth` を止めたのはこの歯である**（止まり方は安全側だった）
- **歯5**（`[7]`）—— 変異前後の md5 が同一なら **「当て忘れの疑いがある」** と言って落ちる

**⟹ 手で仕込むなら、最低限この2つを自分でやること:** (1) **変異した行を印字して目で確かめる**（summary 行を読まない） (2) **対照を1本置く** —— 同じ変異で**別の既存の歯**が赤くなることを見せる。対照が赤ければ「変異は確かに着地した」と言えるので、そのうえで測りたい歯が緑なら**それは本物の「生存」である。対照なしの緑からは、どちらとも言えない。**

**`weak-tooth` シナリオは、この形をそのまま実演している** —— 同じ1つの変異（両ケースで `md5Post` が同一）を当てて、**弱い歯は緑（生存）・強い歯は赤（検出）**になる。強い歯が対照である。

**集計行は ANSI を剥がしてから読む**（#372。`mutate-core.mjs` の `stripAnsi` /
`parseAggregateLines`）。色が付くと `^\s*Test Files` の `^\s*` がエスケープシーケンスを
空白として読まず、**テストが緑でも集計行が `null` になって「判定できない」へ倒れる**。
**色が付く経路は実在する** —— #374 自身の CI（`Run pnpm test`）の raw log archive で、
集計行2本に ESC(0x1B) が16個入っていることを実測した。**その生バイトは ANSI 除去なしの形へ
通すと両方 `null` になる。⚠️ ただし「ハーネスが踏んだ」ではない** —— ハーネスは器の中で
`spawnSync` から起こすので、GitHub Actions の中では走らない。**`raw` は加工前のまま残す**
——剥がすのは判定に使う側だけである（歯7の「加工前の証跡」）。同じ形が `scripts/` 側にも
在るが、**共有の出所は作っていない**（ハーネスの「依存なし・ビルド不要」を壊さないため）。
食い違いは `scripts/mutate-core-strip-ansi.test.ts` が両方へ同じ入力を通して見張る。

**集計「ブロック」が複数出たら判定を拒む。** `parseAggregateLines` の元の実装は
`.match()`（`/g` 無し）だったため、**必ず最初の集計ブロックを返していた。** 測定対象の
repo の `test` スクリプトが `vitest run && pnpm -r --if-present run test && …` のような
複合スクリプトだと、vitest の集計ブロックが複数出ることがある——このとき「最初の1件」を
返す実装は、変異と無関係な最初のブロックを判定材料にしていた（実測・別 repo・mnemora:
8アサーションが赤なのに「生存」と判定された。同じ機構から逆向き＝偽の「検出」も起こりうる。
そちらは未実測だが機構からの帰結）。alteroid 自身の `test` スクリプト（`scripts/test.mjs`
の `spawn('vitest', ['run', ...])`）は vitest を1回しか起こさないので単一ブロックしか
出ないが、**この機構が黙って嘘をつくのを止めるため**、`parseAggregateLines` は「最後」の
ブロックを返す形に直し、さらに `assertAggregateBlocksUnambiguous` が「複数ブロックが在れば
判定そのものを拒む」（`HarnessError`）を、判定の入口3箇所全部
（`decideJudgementCategory` / `mutate.mjs` の `cmdBaseline` / `cmdRun`）へ足した。
**`/g` を足して最後を採るだけでは終わらせていない** — 複数在ったという事実そのものを
`countAggregateBlocks` が件数として持ち回り、複数なら判定せずに理由と次にやること
（生ログを `Test Files` で検索して目で確かめる／`test` スクリプトが vitest を1回だけ
起こす形か確認する）を含むメッセージで拒む。歯は `scripts/mutate-aggregate-blocks.test.ts`。
**この修正は `mutate-core.mjs` だけに入っている** — 同じ形の実装を持つ
`scripts/test-guard-core.mjs` / `scripts/verify-core.mjs` は範囲外（触っていない）ので、
複数ブロック入力に対する3箇所のふるまいは今後食い違う（`scripts/mutate-core-strip-ansi.test.ts`
の該当 `describe` にも同じ注記がある）。

**ソース（git 管理下）を書き戻しただけでは復元は完了と見なさない。** 対象パッケージに `target` が設定されていたら、**手順13（印を消す）より前**に `dist` を再 build し、実際に読み直して変異が消えたことを確認する（手順9「`build` の終了コードでは判定しない」を、逆向きに後始末にも適用する）。**確認が取れなければ印を消さない** — ソースの復元は成功しているのに印が残る形になるが、「静かに壊れた `dist` を伴ったまま印だけ消える」よりましだ、という判断である。

**この確認は最初、抜けていた。** `dist` の再 build を入れた直後の版は、build の終了コード・確認結果のどちらも誰も読まずに印を消していた——実測（マネージャーが PATH に exit 1 する擬似 `pnpm` を置いて確認）で、後始末の build が落ちても `restore` が exit 0 で終わり、印が消え、`git status` が clean になり、`status` が「変異は無い」と言い切る形が再現された。**歯9（入り）と同じ基準を後始末（出）にも適用していなかった**、という欠陥だった。

`pnpm build` が資源枯渇で落ちる事例が記録されている（#254）。**⚠️ ただし「落ちるのは `-r`（並列）のときで、`--filter` を1つずつなら完走する」とは言えない。** 以前ここにはそう読める書き方（別のマネージャーの報告の伝聞）が在ったが、2026-08-23 に測り直して範囲が狭まった。**言える範囲は4つで、どれも「`-r` が落ちる」を一般則にしない:**

- **共有ツリーの器で落ちたという観測は実在する**（#254 / PR #137 / #140 / #264 / #304 に生ログが在る）
- **CI（1ジョブ1コンテナ）では全期間 1,016 run で真陽性0件**（`EAGAIN` / `ThreadPoolBuildError` に当たった22 run は全件が、`docker/build-push-action` の provenance JSON に埋まった PR 本文の引用文字列だった。数え上げは 2026-08-23 の調査による）
- **専用ツリーの隔離された実測でも再現しなかった**（2026-08-23。試行の内訳は `AGENTS.md`「自分が走っている器」の build の項に在る）

- **⚠️ 後方互換の注意——この修正より前に、`contains` を escape 済みの形（`\uXXXX`）で書いていた spec があれば、この修正でそちらが当たらなくなる**（`dist/*.js` が生の UTF-8 に変わるため）。**実測で確認済み**（escape 済み形の文字列は charset 修正後の `dist/index.js` に見つからず、生の日本語は見つかる）。書き直す先は生の日本語である。**現時点で追跡ファイル中の `contains` に非 ASCII の値は無い**（#378 の調査で確認済み）ので実害は無いはずだが、新しく spec を書くときは生の日本語で書くこと。
- **（経緯・もう使わない案）** escape 済みの形で書く案も検討されたが、下位仕様が2つ抜けていた——esbuild の既定は**大文字 hex**（`\u82F1` であって `\u82f1` ではない）、JSON の spec ファイルに書くには**バックスラッシュを二重に**する必要がある（`"\\u82F1"`。`"\u82F1"` と書くと `JSON.parse` がその場で漢字へ戻し、生の日本語を書いたのと同じ結果になる）。**この案は上の charset 修正で不要になった**——書き残すのは、同じ罠を踏んだ人が「昔はこう書けと言われた」という記録に迷わされないようにするためである。

**⚠️ `spec` のキー名は、以前は誰も検査していなかった（#301。修正済み）。** 変異を名乗る鍵は **`id`** である——`label` や `name` と書いても**ハーネスは何も言わずに受け取り**、控えが `undefined.bak` になり、見出しが `── apply: undefined ──` になり、判定行も `undefined` を名乗っていた（実測 2026-08-23、PR #292 の作業中）。**測定そのものは正しく動くので、出力の名前を読むまで気づかない。** しかも `mutate-selftest.mjs` に在る「判定行が `spec.id` を正しく名乗っているか」の歯は、**両側が文字列 `"undefined"` に揃うので素通りしていた。**

**いまは `applyMutation`（`mutate-core.mjs`）の入り口で `validateSpec` が `id`（非空文字列・パス区切りや `..` を含まない）・`file`・`from`（非空文字列）・`to`（文字列。空文字は許す）・`expect`（1以上の整数）・`mustFail`（1本以上の非空文字列の配列＝狙いの歯。#993）を検査し、不正なら控え・印・変異のどれも書かずに落とす。** `mutate-selftest.mjs` の `spec-validation` シナリオがこの検査自体の回帰を見る。**「`apply` の見出しを1度見て確かめる」という人間（AI）の目視の手当ては、もう要らない** — 機械に確かめさせられるものを人間の目視に残さないこと、という上の原則をここでも適用した。

**この一件が一般化して言えるのはここである: 比較の両側が同じ経路で同じ値へ強制されると、比較そのものが恒真になる。** `judgement.text` 側は `formatJudgement` がテンプレートリテラル（`` `${mutationId}` ``）で `spec.id` を文字列へ強制し、比べる側の `.includes(spec.id)` も同じ強制を受ける。**`spec.id` が `undefined` のときにだけ両側が `"undefined"` という同じ文字列に揃うので、この歯は「いちばん名前が壊れている場合にだけ」鳴らなかった** — 型が違うほど検出しやすくなるのではなく、**型の欠落がいちばん深い箇所でだけ検出が消える**という形である。`mutate-selftest.mjs` の `scenarioJudgementIdIntegrity`（逐語は `grep -Fn -- 'この比較を書くときの一般形の注意（#301 で見つかった）' .claude/skills/mutation-testing/mutate-selftest.mjs`）にある同種の比較にも、この形への注意を直接書いてある。次に似た比較（`formatJudgement` のような差し込み系と、`includes`/`===` のような突き合わせ系を両側に持つ形）を書くときは、**型を確かめてから比較する**か、**強制されない値（オブジェクトの参照や `Symbol` など）で突き合わせる**かのどちらかを検討すること。

**変異試験でこれが効く理由は、変異が `dist/` に焼かれたかどうかが、この試験の成否そのものだからである。** 生存の4分類の4「変異が届いていない」は、まさにこれを見落とした形で生まれる——`#220`（記憶の `created_at` バックフィルの絶対条件1に対する変異試験）の本文に実例が在る。`apps/daemon` は `@alteroid/storage-fs` を `dist/index.js` 経由で import するため、`packages/storage-fs/src` を変異させただけでは daemon 側へ届かず、`pnpm build` を挟まずに測ると daemon 統合の歯が緑のまま通った（fs 単体の歯は赤のまま）。**実運用（2026-08-23、同じ `packages/storage-fs` を対象にした変異試験）でも `artifact` を指定せずに走らせ、そのつど自分（AI）で `grep` して `dist/index.js` の中身を目視で確認するという手当てをした。それは手当てであって仕組みではない。** 機械に確かめさせられるものを人間（AI）の目視に残さないこと——`spec` を書くときは `target` と揃えて `artifact: { file: '<パッケージ>/dist/....', contains: '<変異後にのみ現れる文字列>' }` を必ず添える。

**そして `contains` に置く文字列は、変異を当てる前に、その成果物へ 0 件であることを確かめること。** `grep -c "<contains>" <artifact.file>` が `0` を返すのを見てから `apply` / `run` へ入る。**この一手で、判定に推測が要らなくなる。**

**⚠️ ただし事前の 0 件は、「`contains` がそもそも当たる形か」までは保証しない（実測 2026-09-11、issue #844 の変異試験）。** `packages/core/src/tools.ts` の定数を変える変異2本で、`contains` に**変異後のソースの字面をそのまま**置いた（`3600000` と `current.length > 100000`）。どちらも変異前の `packages/core/dist/index.js` に 0 件であることは確かめてあり、変異自体はソースへ載っていた。それでも照合は外れ、判定は #444 の例外（build が exit 0・狙ったファイルは実在・`contains` だけが外れた）へ倒れて、「テスト結果に委ねた」警告付きの判定になった。**原因は届いていないことではなく、成果物の字面がソースと違うことだった** —— 同じツリーの `const COMMITMENT_LIST_BUDGET = 8_000;`（`packages/core/src/tools.ts`）は `dist/index.js` では `8e3` として出ている（実測21箇所）。`36e5` / `current.length > 1e5` へ直して撃ち直すと、10本とも警告なしで判定が出た。

**⟹ 確かめる回数を1つ足す: `contains` は「変異前に 0 件」だけでなく、「変異後に 1 件以上」も確かめる。** 前者は「変異が届いていない」と「歯が無い」を分ける準備であり、後者は「`contains` が当たる形か」を分ける準備である —— **2つは別のことを見ている。** 段階実行（`apply`）なら、`grep -c "<contains>" <artifact.file>` を `apply` の前後で1回ずつ打てばよい。

**⚠️ 書き換えうるものを数え上げないこと。** ここで実測したのは数値リテラル1種類だけである。**他にも在りうる**（どの字面が、どの設定で、どう出るかは測っていない）。⟹ **網羅した一覧を作ると、そこに無いものは書き換わらないと読まれる。** 上の手当て（変異後に 1 件以上）は、何が書き換わるかを知らなくても効く。

- 0 件を先に確かめてあれば、build の後に **在れば届いた／無ければ届いていない**が決まる。手順9の「見つかった（届いている）」が、**変異とは無関係に元から在った文字列を拾ったのではない**と言い切れる
- **これが効くのは、生存の4分類の 2「歯が無い」と 4「変異が届いていない」が、事後には見分けにくいからである。** どちらも「緑だった」という同じ観測として出てくる。**事前に 0 件を確かめておけば、緑を読むときに残る可能性が「歯が無い」だけになる**——事後の切り分けを、事前の準備に移し替えている
- **`contains` は「変異後にのみ現れる」だけでは足りない。「変異前には無い」を実際に測ること。** 前者は書き手の意図で、後者は観測である

**#220 がこの取り違えの実例である。** PR #220 の本文には測定が2つ並んでいる（逐語）:

| 測定 | 条件                          | fs 単体の歯 | daemon 統合の歯 |
| ---- | ----------------------------- | ----------- | --------------- |
| A    | `pnpm build` を挟まない       | **赤**      | 緑              |
| B    | 変異を当てたまま `pnpm build` | **赤**      | **赤**          |

そして同じ本文が「**測定Aの『緑』は『歯が無い』ではなく『変異が届いていない』である**」と明記している。**にもかかわらず、下流へは測定Aだけが「daemon 側に歯が無い」として運ばれた**（この伝播そのものは alteroid 自身の記録の側に在り、**git からは確かめられない**）。**両方書いてあっても、読み手が片方だけを取る形は起きる。** 0 件確認は、そもそも A と B が別の答えを出す状態に入らないための準備である。

**`target` の選び方は「何を変異させるか」ではなく「どの歯で測るか」で決まる。** 変異させるパッケージと、赤くなってほしい歯が在るパッケージが違うなら、その境界は `dist` である。

- 例（2026-08-23 実測、`updatedAt` の導出2本）: 変異先は `packages/core/src/schema.ts`、測る歯は `packages/core`（ヘルパ単体）・`packages/core`（MCP）・`apps/daemon`（HTTP）・`apps/cli`（CLI）の4面に散っている。`apps/daemon` と `apps/cli` は `@alteroid/core` を `dist/index.js` 経由で読むので、`target: '@alteroid/core'` を指定して build を挟まなければ届かない
- **⚠️ 同じパッケージの中の歯は、build を挟まなくても赤くなる。** vitest は `packages/core/src/schema.test.ts` の `./schema.js` をソースへ解決するので、`dist` を作り直さなくても変異が効く。**だから「core 単体の歯が赤い」を見て「届いた」と読むと誤る**——#220 の測定Aで fs 単体の歯が赤かったのと同じ形である。届いたかどうかを答えるのは歯の色ではなく、手順9の成果物検査だけである

**手順そのものは単純である。テスト対象のコードを意図的に壊し、テストが落ちるかを見る。落ちなければ、そこに歯は無い。**

**問題は、この道具自身が壊れうることである。** だから7つの歯を全部入れる。1つ欠けると「壊したまま気づかない」か「当て忘れたのに測れたことにする」のどちらかが起きる。

1. **md5 を記録する**（変異前・変異後・復元後）
2. **空パターンで落ちる** — 空の検索文字列は「0件」ではなく「全箇所」へ振り切れる（80,045か所へ挿入した実例がある）
3. **期待件数と一致しなければ落ちる** — 少なすぎる側だけ見るのは片側の歯である
4. **復元後に md5 が一致しなければ落ちる**
5. **変異前後の md5 が同一なら落ちる** — 当て忘れの検出。4 とは比べる向きが逆である
6. **書く前にパターンの一意性を検査する** — 書いてから数えるのでは、落ちたときにファイルが変異したまま残る
7. **計測フラグをベースラインで1回通し、期待どおりの値が出ることを確かめる** — 歯は「落ちる」ことで自分の故障を知らせるが、**結果を読む計測フラグは黙って嘘の値を出す。** そして守ろうとしているのが「テストが1本も走らなかった」＝まさに黙って通る失敗なので、疑っても倒す先が無い（信じれば全結果を捨て、無視すれば守りが消える）。**併せて `Tests N passed (N)` のような加工前の証跡もログへ残す** — フラグが壊れても事後に derive し直せる（実際に2回救った）

    - 対処は**不足しているパッケージを build すること**。`pnpm --filter <パッケージ> build` を1つずつ、**依存する側のパッケージまで含めて**打つ形でよい。**⚠️ ただしこれを「`pnpm -r build` は EAGAIN で落ちるから `--filter` にする」と読まないこと。** `-r` が落ちたという観測は実在するが、それは器の条件に依存する — **範囲は上の「`pnpm build` が資源枯渇で落ちる事例が記録されている（#254）」の段落に在る。** ここで `--filter` を使うのは、**足りないパッケージだけを名指しで build するため**である
    - **変異試験では特に致命的である。** ベースラインが緑だと誤認したまま変異を当てると、生存4分類の判定が丸ごと狂う——「検出」「歯が無い」「観測不能」「届いていない」のどれだと結論しても、その手前にある「ベースラインは変異の影響を受けていない」という土台そのものが崩れている
- **`pnpm --filter <パッケージ> test` は、その test script が無ければ1本も走らせない。** テストは root の `vitest.config.ts` 1本が集めているが、**#246** で `packages/*` / `apps/*` の8ワークスペース全部の `package.json` に `test` script を足した（以前はどれも `test` script が無く、`pnpm --filter <パッケージ> test` は出力0行・exit 0 だった。実測（2026-08-20 観測）はその状態でのものである）。**同じ PR で `pnpm-workspace.yaml` に `failIfNoMatch: true` も足した** ので、存在しないパッケージ名・打ち間違いは exit 1 になる。**それでも塞がっていない穴が残る** — `failIfNoMatch` が見るのは「フィルタに一致するプロジェクトが在るか」であって「その `test` script を持つか」ではないため、**実在するパッケージでも `test` script が未整備なら、いまも出力0行・exit 0 のまま**である（実測 2026-08-23: `packages/api-client/package.json` から `scripts.test` を一時的に外して `pnpm --filter @alteroid/api-client test` を打つと `failIfNoMatch: true` の下でも exit 0・出力0行だった）。**新しく足したパッケージや、`test` を書き終える前のパッケージを変異試験で filter するとこの穴を踏む。** 機械的な歯（`scripts/workspace-test-scripts.test.ts`。root の `pnpm test` に含まれる）はこれを検出するが、**`pnpm --filter <パッケージ> test` という個別コマンドそのものは自分では落ちない** — 対象パッケージの `package.json` を自分の目で確認するか、絞るなら root から `pnpm test <パスの一部>`（引数は vitest へそのまま渡る）を使うほうが安全である。**設定そのものの話（`failIfNoMatch` が何を塞ぎ何を塞がないか）は `pnpm-workspace.yaml` の `failIfNoMatch: true` の傍に在る。片方だけ直して終わらせないこと** — pnpm の挙動が変わったら、こちらの実測も古くなる
- **変異が生存したとき（テストが通ったとき）、テストの中に仕込んだ `console.log` は出力に出ない。** vitest の既定の reporter は console を横取りしており、**通ったテストのぶんは捨てる**（落ちたテストのぶんは `stdout | <ファイル> > <テスト名>` の形で出る）。実測（2026-08-22T04:28Z 観測、`vitest@4.1.10`。この repo の `vitest.config.ts` は `reporters` / `silent` / `onConsoleLog` / `disableConsoleIntercept` のどれも指定していないので既定のままである）。**`console.error` も同じで、`process.stdout.write` だけは横取りを通らず、通っても落ちても出る**
  - **重いのは、消えるのが「通ったとき」＝生存したときだけだからである。** 変異が生存したあと、次に知りたいのは「そのコードパスをテストが踏んでいるのか」である（踏んだうえで assertion が無いのか、そもそも到達していないのか。**どちらも「歯が無い」だが、次にやることが違う**）。それを見るために出力を仕込む — **その出力が、生存したときにだけ捨てられる。** 結果として**出力の不在が2つの意味を持つ**（何も起きなかった / 出力が捨てられた）。`AGENTS.md`「静かに失敗する道具」の `grep -c` が返す 0 と同じ形である
  - **仕込みが効いているかを「1回落として確かめる」と、必ず誤った結論に至る。** 落ちたぶんは出るので「出た＝ちゃんと出る」と読めてしまい、生存した変異でだけ黙って消える。**確かめるなら通るテストで確かめること**
  - **出す方法は実測で確認した（#314 で歯が入った後に取り直した。観測 2026-08-23T10:03Z、`vitest.setup.ts` が在る状態）。** `pnpm test --reporter=verbose` なら **`console.log` が通ったテストでも `stdout | …` として出る**。既定の reporter のままなら `process.stderr.write` が出る（`console.error` は横取りされるので出ない）。**⚠️ `process.stdout.write` はもう観測に使えない** — 出はするが、そのテストが赤くなる（下の「落ちなかったとき、理由を推測しない」を見ること）。**歯7が守るのは「計測フラグが嘘の値を出す」ことで、これは「証拠そのものが無い」ことなので別の歯である**
- **テストを付けなかった箇所にも変異を1本かける。** 何も落ちなければ「歯が無い」が測定として確定する。**「テストを書かなかった」と「守られていないことを確かめた」は別**である
- **復元に `git checkout` / `git restore` / `git stash` を使わない。逆変異＋md5 照合で戻す** — 「壊したものを戻す」手段が「変更を捨てる」手段と同じだと必ず事故る（未コミットの修正を4ファイル消した）。変異試験はコミット前に歯を確かめることが多い＝**最も危険な状態でこの道具を使う**
  - **ただし「逆変異」を文字列置換で書かないこと。復元は、変異前に読んだ原文をそのまま書き戻す形にする。** 歯2（空パターンで落ちる）は**変異を当てる側にしか掛かっていない**。変異が「消す」形（`to` が空文字）のとき、その逆は `replace('', from)` になり、**空文字は先頭に一致するので消したはずのものがファイルの先頭へ挿入される**。実測（2026-08-20T15:47Z 観測、`packages/core/src/inbox.ts`）: `while (...) { ... }` の5行を削る変異の復元で、その5行が `import` 文より前の1行目へ挿入された。**変異は当たり、テストも期待どおり落ちたので、壊れたのは復元だけである** — 「歯はあった」という結論は正しいまま、ファイルが壊れて残る。拾えたのは歯4（復元後の md5 照合）で、**逆変異の側には歯が無かった**。原文の書き戻しは `git` を1つも使わないので、上の禁止と競合しない
- **復元の最終確認は md5 照合と `git status` の両方で行う** — md5 は「数えたファイル」しか守らず、`git status` は「数え忘れたもの」を拾う
- **`git show HEAD:<path> > <path>` でも戻せるが、これは HEAD に正解が在る状況でのみ当たる。未コミットの修正を持っているときは当たらない。**（ハーネス追加時の注記。印の manualRestore にはこの前提つきの代替を逐語で添えてある — 復元の主経路は控え/印からの書き戻しであって、この `git show` はそれが両方失われたときの最後の手段でしかない）
- **置換パターンは前後の一意な文脈まで含める**（`  return true;` がインデントの違う別箇所の部分文字列に当たった）
- **1つの変異で複数の保証を確かめない**（assertion は最初の1つで止まる）
- **複数落ちたら、別の箇所を変異させて落ちる集合が分かれるかを見る**（分かれるなら別々の保証である）。**説明は書き手の理解に依存するが、実験は依存しない**
- **回しているあいだ、同じ作業ツリーで他の誰か（作業者を含む）にテストを走らせない。** 別 worktree を使うか順番に回す。ファイルを一時的に壊す作業なので、並行実行は必ず汚染する（実際に汚染した）。**ただし別 worktree で分かれるのはファイルだけで、プロセス空間は共有されている**（`AGENTS.md`「自分が走っている器」参照）— 走らせているプロセス自体は他の作業者から見えるし、撃たれうる
  - **止まってもらう対象はテストだけではない。回しているあいだ、そのツリーは「現物」ではない** — ファイルは意図的に壊れた状態にある。**同じツリーで `grep` / `cat` / `git diff` / build を走らせないこと。読むだけの操作も、変異した中身を現物として読む形になる。** 歯4（復元後の md5 照合）が守るのは復元の正しさであって、**途中で読んだ者の結論は守らない**

## 落ちなかったとき、理由を推測しない

**手順を先に置く。** この下にある分類（生存の4分類、下の「足場が触る対象と重なる4形」）は**閉じていない** — 今日1日で新しい形が4つ出た。**読む人が自分の場合を一覧へ当てはめる形にすると、一覧に無い形はそのまま見落としになる。手順は、まだ見つかっていない形にも効く。**

**歯が落ちなかったら、変異を当てたまま、中を出す。**

- **戻してから調べない。** 復元してしまうと、生存の理由は再現できない状態でしか推測できなくなる
- **出すのは「なぜ落ちなかったか」の見当ではなく、突き合わせている値そのものである。** 実例（2026-08-22）: `DUMP[i] idxA=112 idxB=123` を出したところ、**目印が本文ではなく別の場所 — 台帳の断り書きに並んだ id の一覧 — に一致していた**ことが見えた。**その日の3例とも、この一手で見えている**
- **⚠️ 生存しているときは `console.log` が出ない。** 上の「変異が生存したとき…」の項目そのものである — 生存＝テストが通ったなので、vitest の既定の reporter が捨てる。**中を出すのに `console.log` を使うと、いちばん要るときにだけ消える。** `--reporter=verbose` で回すこと（通ったテストの `console.log` もそのまま出る）。既定の reporter のままで出したいなら `process.stderr.write` を使う
  - **⚠️⚠️ 観測に `process.stdout.write` を使わないこと。変異試験では、観測する行為そのものが測定値を反転させる。** #314 で `vitest.setup.ts` に「テストが spy を張らずに本物の stdout へ書いたら `afterEach` で落とす」歯が入った。**生存した変異の中を見ようとして `process.stdout.write` を1行足すと、そのテストが赤くなる。** そして変異試験で赤は `検出` になりうる（**この記述は #993 で半分だけ古くなった。** 当時の `decideJudgementCategory` は `allPassed ? '生存' : '検出'` の1行で、引用もそのままここに残っていた。いまは門1〜5 を通り、最後は `surviving` と `spec.mustFail` の交差で決める。**ただし指摘そのものは生きている** —— 観測のために足した1行で赤くなる歯が、たまたま `mustFail` に宣言した歯であれば、やはり `検出` になる。**いまは宣言した歯でなければ `身代わり` へ倒れるので、赤くなった歯の名前が判定に出る分だけ気づきやすい**）。**＝ 生存を「検出」と読み違える。強めるべき歯を、守られている場所として通してしまう。** しかも観測を外せば緑に戻るので、**手元では再現しない。**
  - **実測（2026-08-23T10:03Z 観測、歯が在るブランチで取得）。** `renderConversationsList` の空表示を1語だけ見る弱いテストに、その語を残したまま文言を変える変異を当てた（＝本当は生存する）。**テストの論理も変異も動かさず、観測の1行だけを足し引きしている:**

    | 観測に使ったもの                          | 集計行                | ハーネスの判定     | 中は見えたか |
    | ----------------------------------------- | --------------------- | ------------------ | ------------ |
    | 何も足さない                              | `Tests  1 passed (1)` | **生存**（正しい） | —            |
    | `process.stdout.write`                    | `Tests  1 failed (1)` | **検出**（誤り）   | 見えた       |
    | `console.log` ＋ `--reporter=verbose`     | `Tests  1 passed (1)` | **生存**（正しい） | 見えた       |
    | `process.stderr.write`（既定の reporter） | `Tests  1 passed (1)` | **生存**（正しい） | 見えた       |

  - **`process.stdout.write` の中身が見えなくなったわけではない。** 歯は握り潰さず本物の stdout へ通すので出力自体は出るし、失敗の差分にも書いた内容が載る。**見えるのに測定が壊れる、というのがこの形の質の悪さである** — 「出た」を確認して安心すると、判定のほうが反転していることに気づかない。
  - **ハーネス自身（`mutate.mjs` / `mutate-core.mjs` / `mutate-selftest.mjs`）はこの歯を通らない。** `setupFiles` は vitest が読むもので、ハーネスは素の node プロセスだからである。だから `mutate-core.mjs` の `log()` が `process.stdout.write` を使っているのは**そのままでよい**（実測: この節を書いた PR #319 の時点、当時の全シナリオ8件で `selftest --scenario all` が全部通って exit 0。**シナリオは #353 で10件に増えており、この「8」はいまの本数ではなく当時の記録である**。`mutate-selftest.mjs` が書き出す一時テストも純粋関数しか呼ばないので鳴らない）。**歯が掛かるのは vitest が走らせるテストの中だけである。**

**そして直した後、落ちることを確かめる。そのとき「アサーションの不一致で落ちた」のか「タイムアウトで落ちた」のかを見分ける。**

**タイムアウトは、測っているものと無関係な待ちで落ちている疑いである。** 落ちた事実だけを見ると歯が生えたように読めるが、**歯が測っているのは待ち時間であって、変異させた性質ではないかもしれない。** どちらだったかを報告に書くこと。

## 落ちた歯を「組」で読む

**落ちた本数を数えても、何本の保証が在るかは分からない。** 見るのは組み合わせである。

- **単独で殺せる歯と、群でしか落ちない歯を分けて書く。** 単独で殺せる歯は、その1本だけで保証を持っている。**群でしか落ちない歯は、どれか1本を消すと保証が消える。** 表の価値は本数ではなく、この分かれ方が書いてあることにある
  - **⚠️ 数えるときは「変異の本数」と「歯の本数」を混ぜないこと。** この2つは別の軸で、混ぜると内訳が合わなくなる（実際に混ざった報告が上がっている）。実例（2026-08-22、`#183`）は**変異6本 × 歯5本**である:

    | 変異             | 落ちた歯          |
    | ---------------- | ----------------- |
    | M1               | T1 + T4 + T5      |
    | M2               | T2 + T5           |
    | M3               | T2 + T5           |
    | **M4**           | **T4 のみ**       |
    | M5               | T1 + T2 + T4 + T5 |
    | **M6（逆向き）** | **T3 のみ**       |

    **単独で殺せるのは T3 と T4 の2本。残る T1 / T2 / T5 の3本は群でしか落ちない**（2 + 3 = 5 は歯の数であって、変異の数の 6 ではない）。**この表は他の2項目の実例にもなっている** — M2 と M3 は落ちる集合が同一（だから撃たれたアサーションを見る必要がある）、M1 の集合は M5 の真部分集合（包含関係）である
- **「同じテストが落ちた」を「同じ歯」と数えない。どのアサーションが撃たれたかを見る。** 実例（2026-08-22）: **同じ2本のテストを落とす2つの変異が、片方は `toMatchObject` で、片方は `expected '(不明)' to be undefined` で落ちた。** 落ちたテストの集合は同一でも、撃たれた場所が違うので**別の保証**である。**別のときは包含関係だった**（片方の落ちる集合が、もう片方の真部分集合）。集合が一致するか・包含か・交差かで意味が変わる
- **予想は測る前に固定し、外れたら外れたまま残す。** 「この変異はこのテストで落ちるはず」を先に書き、**外れたら書き直さない。** 後から予想のほうを直すと食い違いが消え、次に読む人は「予想どおりだった」としか読めなくなる。**食い違いこそが検出器である** — 実例（2026-08-22）では、その日に見つかった欠陥3件が**すべて予想と実測の食い違いから出ている**
- **鳴らなかった歯も観測である。** 落ちた集合が予想より小さいとき、それは「歯が足りない」とは限らない——**その経路がそもそも到達しないことの確認**でありうる。実例（2026-08-23、`updatedAt` の導出）: `approvalUpdatedAt` が `answeredAt` を無視する変異は、ヘルパ単体・HTTP・CLI の3本を落としたが、**MCP（`tools.ts` の `approvals_list`）の歯は鳴らなかった。** これは `approvals_list` が `listApprovals({ pendingOnly: true })` をハードコードで呼び、左枝（`answeredAt` 有り）へ到達しないという `schema.ts` の doc の主張そのものであり、**1回の変異で「doc が書いている到達不能」と「新しく足した経路が実際に到達すること」（`GET /approvals?pending=false` の歯が鳴った）が同時に取れている。**
  - **⚠️ だからこの読み方は、到達不能が先に書いてあるときにしか使えない。** 測った後で「鳴らなかったのは到達しないからだ」と説明を作れば、それは生存の4分類の 2「歯が無い」を言い換えただけになる。**予想を測る前に固定する**（直上の項目）が、ここでも効いている

## 自己修復する設計は、書き込み側の変異を隠す

**一般則: 「壊れていたら直す」経路を持つコードは、その経路が読み出しで走る限り、書き込み側を壊しても結果が正しく見える。**

**診断**: そのコードのテストが**「新しいものを作る → すぐ読む」形しか無いなら、修復経路を通っている疑いがある。** この形では、書き込み側が何も記録していなくても、直後の読み出しが「まだ無い」を検出して**現在の状態から正しい値を導出してしまう。**

**打ち手: 修復が働かない状態から測る。** 一度読んで値を確定させてから、2回目の書き込みで壊す。**「まだ無い」ではなく「在るが食い違う」を作れば、修復では埋まらない。**

**実例**（2026-08-22、`packages/storage-{fs,pg}/src/persona.ts` の本文ハッシュ）。記憶の保護は「デーモン経由で最後に書いた本文のハッシュ」を持ち、**無ければ現在の本文から作り直す**（索引を失っても凍らないため）。当時のテストは全部「新しい文書へ最初の1回書く → すぐ読む」形だった。

- `write()`/`append()` の**ハッシュ更新を丸ごと削除**しても、fs 79件・pg 84件が**全通過**した（＝生存）。修復が毎回埋めていた
- **同じ変異が、pg の `append()` だけに当てると検出できた。** `write()` が先に非 null を確定させているので、`append` だけ壊すと「無いから修復」ではなく**「在るが食い違う」**という本物の不一致になる
- **fs では同じことができなかった。** `write`/`append` が `#writeNow` 1本を共有しているので、**片方だけ壊せない**（両方まとめて死ぬ＝両方まとめて修復に隠れる）

**この非対称は、テストの本数でもカバレッジでも出ない。変異試験でしか見えない。**

**「片方だけ壊せない」ときは、それを設計の性質として書き、測定結果として残す。** 「歯が無い」と結論しないこと — **測れなかったのであって、守られていないと分かったのではない。** 上の「テストを書かなかった」と「守られていないことを確かめた」は別、と同じ線である。

**そして生存した変異は、必ず4つのどれかに分類する。**

1. **当てすぎ** — 仕様の範囲内で、落ちなくて正しい
2. **歯が無い** — その性質を測るテストが本当に無い
3. **テストの構造が観測不能にしている** — 上の自己修復がこれ。テストは在るが、その経路を通っていない
4. **変異が届いていない** — `packages/core/src` を壊したのに `pnpm --filter @alteroid/core build` を挟まず、`dist/` 経由で import する側（`apps/daemon` など）へ届いていない

**4 は、測っていないのに 1 や 2 と同じ見た目になる。** だから**変異を当てた後に「実行対象へ届いたこと」を先に示す** — その変異を必ず踏むはずのテストが1本落ちることを確かめてから本番の測定に入る（検出器が非0を出せることの、変異試験版の対照）。**届いていることを示せない変異は、下の3条件を全部満たすときを除いて「不明」として出す。「生存した」と書かない。**

**⚠️ 唯一の例外（#444）**: **build が exit 0 で終わり、かつ狙った成果物ファイルが実在し、かつ `contains` の照合だけが外れている**——この3条件を全部満たすときに限り、「不明」で止めずにテスト結果（本当に赤くなったか）へ判定を委ねてよい。build 自体が失敗した場合や、狙ったファイルがそもそも存在しない場合はこの例外に当たらない——その場合は「変異がその成果物へ本当に届いたか」自体が確認できていないので、これまでと同じく「不明」のままにする。**この例外でテスト結果に委ねた判定（検出/生存）は、成果物への到達を実際に確認したわけではない**——`contains` の誤字・死コード除去等で、狭い条件を通ってしまっている可能性が残る。だから**この例外を通った判定には、判定行の末尾に警告が付く**（逐語: `⚠️ build は exit 0 で終わり、対象ファイルの存在も確認できたが、spec.artifact.contains の照合だけが外れたため、この判定はテスト結果に委ねている（#444）。変異がこの成果物へ本当に届いたことまでは確認できていない。spec.artifact.contains の誤字・死コード除去等、spec 側の誤りの可能性がある。`）。**⚠️ ただしこの警告が出るのは判定行だけで、`run` のまとめ行（`変異 <id>: <判定>`）には出ない。** まとめ行だけを読む使い方では、この例外より前なら `不明` として目に入っていた `contains` の誤字が、`検出`/`生存` と区別できない形で通る。**まとめ行で `検出`/`生存` を見たら、`spec.artifact` を書いた変異については判定行まで戻ること。**

**この3条件の分かれ方と、警告の注記が実際に生成されることの回帰は、`mutate-selftest.mjs` の `judgement-undelivered-gate` シナリオが見る。** `judge()` は `artifactResult` / `testResult` を受け取るだけの純関数なので、**build を1度も回さずに**合成した入力で全分岐を表で測れる。分類（検出/生存/不明）だけでなく**注記の中身**（テスト結果に委ねたこと・spec 側の誤りの可能性）も受け入れ条件に含めてある — 分類だけを見る歯は、注記が空文字や `null` に化けても緑のままになるためである。

**そして 2 と判断しても、歯を無理に生やさないこと。** 要求を満たすために書かれただけのテストは、次に読む人へ「この性質は守られている」と嘘をつく。**足さない判断も、理由が書いてあれば正しい報告である。**

## 足場が触る対象と、歯が測る対象が重なる

**変異試験の足場（同期の待ち、目印、歩調取り）が、その歯の測ろうとしている当のものを使っていると、測定が壊れる。** 実測で出た形を4つ置く。**ただし一覧は閉じていない** — 上の「落ちなかったとき、理由を推測しない」が本体で、これは例である。

| #   | 重なったもの                                                                       | 出る誤り                         |
| --- | ---------------------------------------------------------------------------------- | -------------------------------- |
| 1   | **同期条件**が、その歯の測る当のものを使っている                                   | **偽陽性**（測る前に落ちる）     |
| 2   | **歩調取り**が、測定対象を肩代わりしている                                         | **偽陰性**                       |
| 3   | **目印**が、別の*安定した順*の場所にも現れる                                       | **偽陰性**                       |
| 4   | **待ち方**が「何も起きない」を扱えていない／**待ち方が変異点そのものを使っている** | **足場が落ちる**（実装ではない） |

- **1 と 2 は、歯を読めば見つかる可能性がある。** 足場と assertion が同じものを見ていないかを目で追える
- **3 は歯を読んでも見つからない。** 目印が別の場所にも現れるかどうかは、**本番のコードが何を出力するかを知らないと分からない** — つまり**テストの外側から入ってくる。** 上の `DUMP[i] idxA=… idxB=…` が見えたのはこの形である
- **4 は「当てすぎ」の一種であって、「歯が無い」を意味しない。** 落ちているのは足場で、実装ではない。生存の4分類でいう 1 の側に入る。**足場を直してから測り直すこと。この状態で「歯が無い」と報告しない**

## 同じツリーで HEAD を動かすのも「汚染」に見える

上の「回しているあいだ、同じ作業ツリーで他の誰かに走らせない」は、**ファイルを触らない操作にも及ぶ。**

**実例**（2026-08-22）: マネージャーが、作業者の変異試験の最中に**別のファイルを `git add` してコミットした。** 作業ディレクトリのファイルは1バイトも変えていないが、**作業者は `git rev-parse HEAD` が動いたのを見て「他プロセスがこのツリーを汚染している」と誤認し、変異を復元して調査した。**

**実害は無かったが、往復を1つ作った。** そして**「実害が無かった」と「仕組みで塞げている」は別である** — 作業者が HEAD を突き合わせていたから気づけただけで、突き合わせていなければ**変異の結果を汚染された測定として捨てた**か、**汚染に気づかずに読んだ**かのどちらかになる。

**回している側の打ち手**: `md5sum` に加えて **`git rev-parse HEAD` も変異の前後で突き合わせる**（この実例の作業者は途中からそうした）。
**外から触る側の打ち手**: **回しているあいだは commit もしない。** 未 push を守る必要があるなら、**別の clone か worktree から押す。**

## 12c（`git status`）が見ているのは HEAD ではない（#321）

**復元の手順12c は「対象ファイルに正当な未コミット変更が在るかどうか」を見る検査ではない。** 以前の実装は `git status --porcelain -- <file>` が空文字であること（＝ HEAD と一致していること）を要求していたが、**変異試験は「いま手元で書いているコードに歯が効くか」を測る道具なので、対象ファイル自身に未コミットの変更が在るのは異常ではなく通常である。** ファイルを直す → そのファイルの歯を変異で確かめる、が最も自然な順序なので、通常の使い方で必ず踏む形だった。

**いまの12c は「変異を当てる前の `git status --porcelain -- <file>`」と「復元後の同じ出力」を比較する** — HEAD との一致ではなく、**前後で変わっていないこと**を見る。印には `statusBefore`（`applyMutation` の手順1の直後、まだ何も書き込んでいない時点で記録する）を持たせてある。**旧い印（`statusBefore` を持たない）は比較せず、ログに「変異前の git status を印が持っていない（旧い印）ので比較しない」と出す** — 空文字と比べる形に倒すと直した欠陥が戻るため、判定できないという3つ目の状態を明示する。

**いちばん危なかったのは検査の中身ではなく、落ちる位置だった。** 12c のすぐ下（旧実装）には、復元後の後始末（`dist` の再 build と検証）が失敗しても「ソースが変異したまま」ではなく「ソースは復元済みで `dist` の確認が取れていない」と次に来た人へ伝えるための印の書き換え（`stage: 'dist-unverified'`）が置いてあった。**12c はその書き換えの1行手前で throw していた。** 対象ファイルに未コミット変更が在ると、ソースの復元（12b・md5 照合）が完全に成功していても12cが必ず落ち、**印は `stage: 'source-mutated'`（「ソースが変異したまま」）に固定されたまま残った。** 次に来た人はそれを信じて印の `manualRestore`（`cp <backup> <file>`）を実行しかねず、その人自身の正当な未コミット変更が消える経路になっていた。

**直したのは比較対象（上）と、印を進める位置の両方である。** `stage: 'dist-unverified'` への書き換えを、**12b（ソースの復元が md5 で確認できた地点）の直後・12c の前**へ移した。12b/12c/12d が落ちる条件は1つも変えていない — 落ちたときに印がどの段階を名乗るかだけを直した。これで12c・12d・後始末のどれが失敗しても、印は「ソースは復元済みで dist（または git status）の確認が取れていない」を正しく名乗る。

**確かめた経緯**: `git log -S'git status に対象ファイルが残っている' --format='%h %cI %s' -- .claude/skills/mutation-testing/` はハーネス追加コミット（`d5cca68`）の1件だけを返す。**それ以降で12cの意図が変わった、あるいは別の意図で足された、という証拠は見つかっていない。**

## judge() の禁止語検査は、id を部分文字列では見ない（#348）

**判定行の禁止語検査（合格/OK/ok/pass/passed/成功/問題なし/緑/✓）は本物の目的を持つ** — 変異試験は「生存＝テストが通った」なので、通ったことを肯定的な語で書くと、いちばん重い失敗（歯が無い）が成功に見える。**この検査自体は外していない。**

**外したのは「判定テンプレートに `spec.id` を差し込んだ後の完成文を、丸ごと部分文字列で検査する」というやり方のほうである。** これだと `bypass`（`pass` を含む）・`broken`（`ok` を含む）・`lookup`（`ok` を含む）のような、変異の名前として自然に出てくる語を含む id が誤って拒否されていた。とくに `bypass` はこの repo でいちばん測りたいもの（歯を迂回する変異）を指す語である。

**いまは2段に分けて検査する**（`formatJudgement`。`mutate-core.mjs`）:

1. **id そのもの**は、部分文字列ではなく**語の境界**で見る。ASCII の禁止語（`OK` / `ok` / `pass` / `passed`）は英数字に挟まれていたら当てない（`lookup-drop` の `ok` は `lo` と `up` に挟まれているので当てない）。`-` や文字列の端で区切られていれば当てる（`token-ok` / `m1-ok`）。**非 ASCII の禁止語（合格/成功/問題なし/緑/✓）は部分一致のままにしてある** — `validateSpec` は id にパス区切りと `..` しか禁じておらず、非 ASCII 文字自体は形式上禁止していないので、この判断（紛れ込みようが無い、という前提）は確認していない推測である
2. **テンプレート由来の語彙**は、id を差し込む**前**の状態（プレースホルダで埋めたもの）で検査する

**id が原因で拒否されたときは、その旨がメッセージに出る**（`変異 id "<id>" そのものが禁止語 "<word>" に単独の語として一致した（判定テンプレートの語彙が汚れているのではなく、id 由来）`）。以前は「テンプレートが汚れている場合」と同じ文言だったため、実装を読まないと区別できなかった。

**回帰は `mutate-selftest.mjs` の `judgement-forbidden-word-boundary` シナリオが見る。** `bypass` を含む自然な id が通ることに加えて、`token-ok` / `m1-ok` のように語として単独で禁止語に一致する id が**依然として拒否される**ことも確認する — 前者だけでは「検査を丸ごと外した」実装でも緑になるため。

### どう塞いだか

**この repo に既に在る形 —— 「判定を出さない」門 —— を当てた。** `decideJudgementCategory` には既に2つ在り、3つ目を同じ形で足した（この節を書いた時点の話。その後、別の PR が門その2「`Errors` 行」を間へ足したので、この節が言う「3つ目」はいまの門番号では門4である——下の「vitest が『緑のまま exit 1』になる（偽の「生存」。判定を拒む門その2）」）:

| 門  | 拒む条件                                                                     | 出所                                       |
| --- | ---------------------------------------------------------------------------- | ------------------------------------------ |
| 1   | 集計ブロックが複数在って選べない                                             | `assertAggregateBlocksUnambiguous`（#742） |
| 2   | ⭐ `Errors` 行が出ている（未処理の例外/rejection。集計行が緑でも赤でも拒む） | `assertNoUnhandledErrorsLine`              |
| 3   | 集計行そのものが無い（落ちたのか走らなかったのか区別できない）               | `HarnessError`                             |
| 4   | ⭐ **落ちた歯が在るのに、その名前を判定に使えない**                          | この節                                     |

**この節が言う「門3」は、いまのコード上の門番号では門4である（下の門2「Errors 行」を後から挟んだため）。中身は3段である:**

1. **ハーネス自身が、撃つ前に「印だけ・無変異」の対照を1回取る**（`measureScaffoldControl`）。走行範囲（`spec.testFilter`）は測る側と揃える
2. **落ちた歯の名前を捕まえ**（`parseFailedTestNames`）、**見出しが宣言する件数と照合**して（`parseDeclaredFailureCount` / `extractFailedTeeth`）、対照で落ちた名前を差し引いた集合が空かどうかで判定する
3. **名前が取れなかったら「検出」とも「生存」とも言わず、判定を出さない**（`HarnessError`）

**差し引きは安全機構を弱めない。**

- **差し引く集合の出所は `measureScaffoldControl` だけである。** CLI のフラグも、plan / spec の項目も作っていない ⟹ **人が「これは既知の失敗です」と宣言できる形が無い**（そこが弱くなる境目である）
  - **⚠️ #993 が `spec.mustFail`（狙いの歯の宣言）を足したが、この約束は1文字も変わっていない。** `mustFail` は**赤を1本も差し引かない** —— `surviving` が確定した後に交差を1度取るだけで、`検出` を名乗れる条件を**狭める**（`検出` → `身代わり`）。**区別は「差し引く集合に触るかどうか」であって、矢印の向きではない**（#1087。上の「「判定が甘い」の向き」）: 禁じられているのは宣言が**差し引く集合そのものになる**形（対照の実測を宣言で置き換える）で、そこが**判定を甘くできる口**である —— 狭く宣言した分だけ印に起因する赤が残り、**偽の「検出」**になる。`mustFail` は差し引く集合に一切触らないので**厳しくする側にしか動かない**。歯が固定している（「何を宣言しても `生存` が `検出` へ変わらない」「`[残った]` から名前が消えない」）
- **`--allow-existing-marker` の逃げ道は増やしていない。** 印を置かない経路も足していない（印は安全機構なので触らない）
- **`cmdRun` の「印なし・無変異のベースラインが緑でなければ中止する」を1文字も緩めていない**
- **差し引いた名前は必ず出力へ列挙する**（`formatScaffoldSubtractionReport`）。黙って引かない

### ⚠️ この門が測っていないこと

- **差し引いた歯の中に本物の検出が隠れている可能性**は残る（同じ歯が、印にも変異にも反応する場合）。この門（いまの門番号では門4）はそれを分離しない ⟹ だから名前を列挙する
- **対照に無かった揺れがこの走行で出れば `検出` に化ける。** 変わったのは「その赤に名前が付く」ところまでで、揺れかどうかの判断は読む人に残る
- **絞り込んだ走行（`spec.testFilter`）の判定は、走らなかった歯について何も言っていない。** 判定行が走行範囲（`全件` / `絞り込み`）を名乗るのはこのためである
- **対照は1回しか取らない。** 「印だけ」の対照の中で出た揺れを、印に起因する赤と分離することはできない（実測: ctlB1 / ctlB2 の4本のうち1本が揺れだった）。N 回取っても完全な集合は示せず、全件は1回で数分かかる ⟹ 代わりに `notReproduced`（対照で赤かったのにこの走行では赤くならなかった歯 ＝ 揺れの署名）を、追加の走行を1回も足さずに毎回出す
- **「印を置くと赤くなる歯が在る」ことそのものを、実 ROOT で測る歯は置いていない。** 実 ROOT へ印を置く歯は、それ自体が他の歯を汚染する（並行実行するとその印が本物の測定に見える）。⟹ 代わりに `scripts/mutate-scaffold-control.test.ts` が、**印の有無で赤/緑が変わる歯を模した使い捨てツリー**で機構を端から端まで測る（印が在るときだけ落ちる偽の `pnpm` を `PATH` に置き、`--root` で使い捨ての git ツリーへ向ける）

## 落ちた歯が、測っていた歯とは限らない（偽の「検出」。判定を拒む門その5。#993）

**判定は「何本落ちたか」ではなく「どの歯が落ちたか」で決める。**

かつて最後の1行は `return diff.surviving.length === 0 ? '生存' : '検出';` だった。`surviving` は**落ちた歯の名前の配列**で、証跡（`[残った]`）には名前が出ていたのに、**判定はそれを件数へ潰していた。** ⟹ **測っていた歯が緑のままでも、無関係な歯が1本赤くなれば「検出」と名乗った。**

**実測（2026-09-16、#993）。** `packages/core/src/excerpt.ts` の3行ブロック2行目の末尾へ**半角スペースを1つ**足すだけの変異で:

```
  [残った] … > approvals_list — どの1件も id + 名前 / 作成 + 更新 / 概要 を決まった順で出す（P2）
  [残った] … > manager_list — …（P2）        ほか5本（すべて P2 系）
変異 m2-timestamp-line-trailing-space: 検出 — この歯はこの変異を捕まえた
```

P1（`fiveFieldViolations`）の作成/更新の検査は**非アンカー**の正規表現なので末尾スペースに反応せず、**緑のままだった。** ⟹ **P1 を測るつもりでこれを撃った人は「P1 は効く」と読む。P1 は1度も反応していない。**

### どう塞いだか

**変異 spec に `mustFail`（狙いの歯の名前の配列）を必須で宣言させ、`surviving` との交差で判定する。**

| `surviving`（変異に起因する赤） | `mustFail` との交差 | 判定           |
| ------------------------------- | ------------------- | -------------- |
| 空                              | —（宣言を見ない）   | `生存`         |
| 非空                            | 在る                | `検出`         |
| 非空                            | 無い                | **`身代わり`** |

- **宣言が無ければ判定を出さない**（`HarnessError`）。`validateSpec` が**走らせる前に**拒む（テストを1回走らせた後で気づく形にしない）
- 名前は vitest の `FAIL` 行と同じ「`<ファイル> > <describe> > <it>`」を1本の文字列で書く。**拾い方は、一度走らせて証跡の `[残った]` を写すこと**
- `検出` の文言から「**この歯**」という定冠詞を外した（`宣言した歯がこの変異を捕まえた`）。ハーネスは、宣言が入るまでその主語を1度も持っていなかった

### ⚠️ これは「既知の失敗の宣言」ではない（禁じられている形との区別）

**区別は「差し引く集合に触るかどうか」である**（#1087。**矢印の向きではない** —— 下の2行は**どちらも `検出` から遠ざかる**ので、矢印だけでは可否を決められない。向きの正典は上の「「判定が甘い」の向き」）。

| 宣言が触るもの                                            | 何が起きるか                                                                         | 可否                                                  |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| **差し引く集合そのもの**（対照の実測を宣言で置き換える）  | 集合の広さを人が握る。**狭く宣言した分だけ印に起因する赤が残り、偽の「検出」になる** | **⛔ 禁止**（門4 と `measureScaffoldControl` の doc） |
| **何も触らない**（`mustFail`。確定後に交差を1度取るだけ） | `検出` を名乗れる条件が狭まる（`検出` → `身代わり`）                                 | **可**                                                |

**一方向性は構造で保つ** — 宣言した集合は `surviving` が確定した**後**に交差を1度取るためだけに使い、`scaffoldSet` にも `diffScaffoldFailures` にも渡さない。歯が固定している: 「何を宣言しても `生存` が `検出` へ変わらない」「`[残った]` から名前が1本も消えない」。

### ⚠️ この門が測っていないこと

- **（#993 段2 で塞いだ）宣言した名前の打ち間違いと、本物の `身代わり` を区別できない、という欠陥が在った。** ハーネスは `FAIL` 行しか解析しておらず、**緑の歯の名前を1つも持っていなかった** ⟹ 実在しない名前を宣言すると、恒久的に `身代わり` が出続けていた。倒れる向きは厳しい側だったが、**理由を取り違えていた**（打ち間違いなのか、本物の身代わりなのかが出力から分からなかった）。**塞ぎ方は下の「census を副回線として足す（#993 段2）」**——JSON レポータを副回線として足し、緑の歯も含む全歯の名前と結果（census）を取れるようにしたことで、`mustFail` の実在検査（門6）と「身代わり」の実測化ができるようになった。
- **宣言した歯が「変異した挙動を測っている」ことまでは測れない。** 宣言は人が書くので、狙いそのものを取り違えていれば、その取り違えごと `検出` になる。**変わったのは、取り違えが spec に**書かれて残る**ことである**（以前は判定のどこにも現れなかった）

## census を副回線として足す（#993 段2。打ち間違いと本物の「身代わり」を区別する）

**テキスト解析は1行も外していない。** 門1〜4 と `extractFailedTeeth` / `parseDeclaredFailureCount` はそのまま残っている。足したのは、そこからは絶対に取れないもの——**その走行の全歯の名前と結果**（緑の歯も含む）——を読む副回線（`runTests` が `pnpm test` へ `--reporter=default --reporter=json --outputFile=<一時ファイル>` を足す）だけである。

### なぜ「JSON へ全面移行」ではないか（実装前の実測で崩れた前提）

`vitest 4.1.11` で、未処理の rejection を撒くが歯そのものは緑という走行を作り、両方のレポータを同時に取った（issue #993 のコメント。実測は上の「vitest が『緑のまま exit 1』になる」の節と同じ現象）:

```
テキスト:  Test Files  1 passed (1) / Tests  1 passed (1) / Errors  1 error
JSON:      success: true / numFailedTests: 0（Errors に相当する欄が無い）
```

**JSON のトップレベルの鍵をすべて出しても、`Errors` 行に相当する欄は無い**（`numTotalTestSuites` 等9個の `num*` 系と `success` / `snapshot` / `startTime` / `testResults` だけ）。⟹ JSON へ全面移行すると、門2（`assertNoUnhandledErrorsLine`）が捕まえていた「集計行は緑のまま壊れている走行」を無条件に緑と読む。**だから門1〜4 は残し、JSON は census としてだけ使う。**

もう1つの理由: `scripts/test-guard-core.mjs` が同じ `pnpm test` の生テキストを、変異試験ハーネスとは無関係な別の消費者として解析している（歯A/B/C）。既定レポータ（`--reporter=default`）を落とすと、この消費者が壊れる。だから `--reporter=default --reporter=json --outputFile=<path>` を**併用**する——実測で確認済み（stdout は今までどおりの人間向け出力のままで、JSON は指定した path にだけ書かれ、stdout には混ざらない）。

### 名前の形式が違う。`fullName` をそのまま使ってはいけない

同じ1本の赤い歯について、テキストと JSON は別の形で名前を持つ（実測、`vitest 4.1.11`）:

```
テキスト:  FAIL  packages/core/src/__scratch993.test.ts > 外 > 内 > 赤の歯
JSON:     {"file":"<絶対パス>","ancestorTitles":["外","内"],"title":"赤の歯","fullName":"外 内 赤の歯"}
```

`fullName` は**空白区切り・ファイル名なし**で、`mustFail` が使う「`<ファイル> > <describe> > <it>`」（テキストの `FAIL` 行と同じ形）とは別物である。**`path.relative(ROOT, testResults[].name)` と `[...assertionResults[].ancestorTitles, .title]` を `>` で繋ぎ直すと `FAIL` 行と一致する**（実測で確認済み。`censusEntriesForFile`、`mutate-core.mjs`）。

### スイート自体の読み込み失敗を、個々のテストの失敗と取り違えない

素朴に `assertionResults` の `status === 'failed'` だけを集めて、テキスト由来の落ちた歯の集合と突き合わせると、**大量の偽の食い違いが出る**（実測、2026-09-17、`packages/core/src` を未 build のツリー——`generated/canon.ts` が無い状態——で走らせた）: 80本の `FAIL` 行のうち77本が「テキストにしか無い」という食い違いになった。原因は、**スイートの読み込みそのものが失敗したファイルは JSON では `assertionResults: []` かつ `status: 'failed'`、`message` にロードエラーが入るという*ファイル単位*の形**で表れ、`assertionResults` の集計だけでは1本も拾えないことだった。テキストの `FAIL` 行はこのとき `<file> [ <file> ]` という形（vitest 既定 reporter の形）を取るので、**census 側もこの形（`<rel> [ <rel> ]`）で名前を作る**ことで、両者は一致する（同じ実測、および別の実測——実 ROOT で足場対照の印を置いて起きる S1〜S3 の再現——の両方で、食い違いは0件だった）。

### 使い道は3つ

|                         | 何をするか                                                                                                        | 倒れる向き                                                                   | 出所                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **門6（新）**           | `mustFail` の各名前が census に**実在しない**なら判定を出さない                                                   | `HarnessError`（打ち間違いが恒久的な `身代わり` に化けなくなる＝段2 の本体） | `requireDeclaredNamesExistInCensus`                                 |
| **`身代わり` の実測化** | census で狙いの歯が実際に `passed` だったことを見てから言う。証跡（判定行の外）に宣言した歯の名前そのものを載せる | 段1 の積み残しがここで片づく                                                 | `requireDeclaredTeethActuallyPassed` / `formatDeclaredTargetReport` |
| **交差検算（新）**      | テキスト由来の落ちた歯の集合と census 由来の `failed` 集合が食い違ったら判定を出さない                            | `HarnessError`（2つの独立した解析が互いを検算する）                          | `requireCensusAgreesWithTextFailures`                               |

**census が取れなかったとき（ファイルが無い / JSON として parse できない / 形が想定と違う）も `HarnessError`。**「判定できない」を緑にしない。`loadCensus` は `available: false` と理由を返すだけで自分では投げない——投げるのは `mustFail` を使う判定（門6・身代わりの実測化・交差検算）に実際に census が要る箇所だけである。**すべて緑の判定・落ちた歯が全部足場対照由来だった判定は、これまでどおり census 無しで済む**（1文字も変えていない。「すべて緑のときは対照を要求しない」と同じ向き）。

### ⚠️ 宣言した歯が census に在り、`passed` でも `failed` でもない状態（`pending` / `todo` / skip）が在りうる

**黙って `passed` 扱いにしない。** 倒れる向きは厳しい側に決めた: `passed` 以外は「身代わり」を出さず `HarnessError` にする（`requireDeclaredTeethActuallyPassed`）。理由はコード（同関数の doc）に書いてある——実行されなかった歯を「身代わり」の証拠にすると、実際には「宣言した歯が走っていない」だけかもしれない状態を隠すため。

### ⚠️ 検討して採らなかった道（逃げ道）

- **「census が取れなければ、今までどおりテキストだけで判定すればよい」は採らない。** 取れなかった理由の大半は走行そのものが壊れた側にあり、そこで従来経路へ落ちると壊れた走行ほど検査の緩い経路を通る（段1 が `mustFail` を必須にしたときに退けた形と同じ）
- **「`mustFail` の実在検査を `validateSpec`（走行前）でやる」は採らない。** 実在はその走行の産物なので、走らせる前には分からない。門として判定の手前に置く

### 偽の `pnpm`（CLI 統合テスト）も census を吐く

`scripts/mutate-scaffold-control.test.ts` の CLI 統合テスト群は、本物の vitest ではなく `PATH` の先頭に置いた偽の `pnpm`（`FAKE_PNPM_BODY`）が生テキストを手書きで模造している。census を必須にしたので、この偽 `pnpm` も `--outputFile=<path>` を見て JSON を書くように直した。**歯のロジック（`markerHere` / `target.includes('HELLO')` の2行）は1文字も変えていない**——census が使う真偽もこの同じ2行から作る。フィクスチャは3本目の歯（`OTHER_TOOTH`。変異にもマーカーにも反応せず常に `passed`）も持つ——「身代わり」を測るには、宣言できる**実在の**狙いの歯が要るためである（実在しない名前を宣言すると、それは「身代わり」ではなく門6 が拒む「打ち間違い」になる。それこそが段2 の本体）。

## vitest が「緑のまま exit 1」になる（偽の「生存」。判定を拒む門その2）

**`decideJudgementCategory` は `testResult.exitCode` を1文字も見ない設計である**（`grep -Fn -- '変異試験ハーネスとの関係' scripts/test-guard-core.mjs` の doc に明記——この非対称性は意図的で、`scripts/test-guard-core.mjs` の歯A/B/Cが付ける専用の終了コードを「検出」に化けさせないためである）。**判定は集計行（`Test Files` / `Tests`）の文字列だけで決まる。**

**しかし vitest には、集計行が完全に緑のまま exit 1 で終わる場面が実在する。** テストが全部通った*後*に、`queueMicrotask` の中で投げられた例外や、拾われなかった Promise の reject（`Uncaught Exception` / `Unhandled Rejection`）が起きた場合である。このとき vitest は `⎯⎯⎯ Unhandled Errors ⎯⎯⎯` の節を出し、集計ブロックへ3本目の行 `Errors  N error(s)` を足すが、**`Test Files` / `Tests` の2行は `passed` のまま変わらない**。実測（別の作業者が本物の vitest 5.0.0 で採取）:

```
 Test Files  1 passed (1)
      Tests  1 passed (1)
     Errors  1 error
```

⟹ **`exitCode` を見ない設計のまま `Errors` 行も見ないと、この壊れた走行は集計行の緑だけで「生存」に判定される。** `cmdBaseline` に至っては「ベースライン成立。」と exit 0 で*名乗ってしまう*——「`exitCode` を見ないことの害は安全側（偽の生存）に倒れるはず」という前提そのものが、ここでは成り立たない。

**⚠️ 実装は「集計行が緑のとき」に条件を絞っていない。** `assertNoUnhandledErrorsLine` は `Errors` 行が在れば、集計行が緑でも赤でも無条件に拒む——上の実測（緑のケース）は「この門が要る理由」であって「この門が発火する条件」ではない。**なぜ赤のときも拒むか**: 変異が本物のテスト失敗と未処理エラーを同時に起こした場合、その赤が「変異を検出した」のか「未処理エラーに巻き込まれたノイズ」なのかを、このハーネスは判別できない。判別できたことにせず、集計行の緑/赤を見るより前に無条件で拒むのは、門1・門3・門4（当時「門3」と呼んでいた節）と同じ考え方——「判定できない」を「たぶんこちら」に倒さない。

### なぜ `exitCode` を見る形にしなかったか（独立した2本の根拠）

1. **害の非対称性が意味を失う。** 上に書いたとおり、`cmdBaseline` が成立を名乗ってしまうので、安全側に倒れているはずの非対称性がここでは意味を持たない——これだけでも直す理由になるが、これは「見ないことの害が大きい」という理由であって「見る形にすべき理由」ではない
2. **形の独立性。** `exitCode` を判定に使う形にすると、ハーネスが `scripts/test-guard-core.mjs` の終了コード割り当て（歯A/B/Cの専用コード）に結合し、他 repo へ持ち出すたびに除外リストを持つ必要が出る。`Errors` 行は vitest 自身の出力なので、`exitCode` を1文字も見ないという既存の性質（歯の専用終了コードを巻き込まない）を壊さずに済む

**⟹ 代わりに、`assertAggregateBlocksUnambiguous`（門1）と同じ作法で、`Errors` 行の存在そのものを理由に拒む純関数（`assertNoUnhandledErrorsLine`）を足した。** 門1 の直後・門3（`testsRanCleanly`。当時「門2」と呼んでいた）より前に置く——集計行が「緑に読める」かどうかを見るより先に、その集計ブロックが信用できるかを見るという、門1 と同じ考え方の延長である。`assertAggregateBlocksUnambiguous` と同じ4つの呼び出し元（`decideJudgementCategory` / `足場対照` / `mutate.mjs` の `cmdBaseline` / `cmdRun` の baseline 確認）から呼ぶ。

### 意図的な赤を巻き込まないことの対照

`scripts/test-guard-core.mjs` の歯A/B/Cは vitest の外側（`test.mjs`）が追加のメッセージと専用 exit を出す形であって、vitest 自身の集計ブロックへは1行も足さない。実測（歯Bが無条件の `it.skip` を検出、exit 4）:

```
 Test Files  1 passed (1)
      Tests  6 passed | 1 skipped (7)
```

`Errors` 行が無い——だからこの門は歯A/B/Cの意図的な赤を誤って拒まない。`scripts/mutate-unhandled-errors.test.ts` がこの対照を固定入力として持つ。

### 偽陽性の検査

- **紛らわしい行（`Errors: none` / typecheck の `Type Errors` 行 / 散文中の小文字 `errors`）で発火しないことを歯で固定した。** `Errors\s+\d+\s+errors?` まで絞っている——`Errors\s+.+$` のように緩めると `Errors: none` のような行まで拾う（手で当てて確認済み。下の「変異試験について」）
- **alteroid 自身の正常な `pnpm test` の出力に `Errors N error` 行が出ないことを、実際に走らせて確認した**（この PR の検証門で2回走らせたログのどちらにも一致しない）
